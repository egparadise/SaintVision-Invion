# 사용자 결정 대기 — 한자리 (2026-09-22)

> **⚑ S01-DB는 2026-09-22 닫힘.** 계약 검증·설계 검토·인벤토리 보고와 실제 PostgreSQL 34건(0 skip)이 기록되었고 migration head도 0045로 갱신됐다. ## 1. CI 개방 — ✅ 결정 내려짐 (2026-09-22 사용자 승인, 결제 복구)
> **결정: 연다(A).** 이 항목이 막던 검증 표면이 풀린다.
> **딸려 오는 것(이제 풀림)**: Go 첫 컴파일·PG 통합(오늘 밤 1008 skip이던 것)·브라우저 레인·계약/서빙앵커 게이트가 매 push 자동 실행 · Codex의 이중 anti-skip PG 가드가 **실제 발화** · 임시 교차레인 절차([[CI개방전_임시_교차레인_검증절차]])는 종료 조건 4항 충족 시 **삭제 경로 진입**(다섯 workflow가 같은 SHA에서 실제 green 확인되면).
> **첫 실행 주의(중요)**: 이 CI는 한 번도 안 돌았고 PG/Go/브라우저가 처음 깨어나므로 **첫 실행에서 red가 대량**일 수 있다(미검증→검증의 순간, 나쁜 신호 아님). 대량 red의 조율 규율은 미리 세워둠 → [[CI_첫실행_분류귀속조율_규율]]. 실행 결과 읽기는 gh 인증 후. Codex=워크플로 machinery, Claude=triage/조율.
> **아래는 결정 근거(기록)**. 결정은 났으므로 참고만.

- **무엇을 정하나**: 호스티드 CI(결제 포함)를 열 것인가.
- **왜 지금 — 오늘 밤 실제로 일어난 일이 답이다**: 세 agent가 오늘 30여 코드를 착지시켰고, 각자 **자기 조각만** 검증했다(나=내 파일 게이트, Codex=자기 시험, Gemini=프런트 vitest). 그 사이에 **조각 사이 깨짐이 실제로 integration에 들어앉았고 아무도 몰랐다**:
  - 무슨 일: `EvidenceViewer.tsx`(화면)가 무결성 PASS를 실검증(`verified===true`) 대신 해시 존재로 판정하도록 회귀했다 — **예전에 고쳐서 가드까지 만든 결함이 되돌아왔다.**
  - 어떻게 안 잡혔나: 그 가드는 **파이썬 시험**(`test_route_coverage`)인데 **화면 레인은 파이썬을 안 돌린다.** 그래서 Gemini는 vitest **646 통과**를 **정직하게** 적었는데, 바로 그 순간 integration엔 빨간 것이 앉아 있었다. **가드는 있었는데 그 가드를 돌리는 사람이 없었다.**
  - 무엇이 잡았나: **마지막 상태에서 전부 돌리는 것**뿐이었다. 그리고 그건 새벽에 사용자가 시켜서 **사람이 손으로** 했다.
  - **CI가 하는 일이 정확히 그것이다 — 매 push마다 전부 돌린다.** 즉 CI 개방은 "검증 자동화"라는 막연한 이득이 아니라, **오늘 밤 이 일을 다음엔 사람 없이(새벽 수작업 없이) 잡는다**는 뜻이다.
- **선택지**: (A) 연다 → Go 컴파일·PG 통합·브라우저 인수·계약/서빙앵커 게이트가 매 push 자동 실행. Codex PG 시험(일회용 컨테이너로만 돈 것)도 자동 강제. (B) 안 연다 → 조각 검증만 계속 → 오늘 같은 조각-사이 깨짐이 사람이 우연히 전수를 돌릴 때까지 숨는다.
- **열면 처음부터 빨갛다 — 그게 막을 이유가 아니라 일한다는 증거**: 지금 CI를 열면 위 EvidenceViewer 회귀 때문에 backend 게이트가 **처음부터 red**다. 이는 CI 개방을 미룰 이유가 아니다 — CI가 켜지자마자 **오늘 밤 숨어 있던 바로 그것을 즉시 잡는다**는 실증이다. (Gemini 수정 후 green이 된다.)
- **안 두면**: 큰 작업(Go, PG, #2)이 계속 막히고, "배선됐으나 휴면"인 보호(예: Codex의 이중 anti-skip PG 가드)가 발화 못 하며, **조각-사이 회귀가 다음에도 사람이 새벽에 전수를 돌릴 때까지 숨는다.**

## 2. 노드 자원 사용량 읽기 계약 — [작업차단]
- **무엇을 정하나**: 노드 자원 **사용량**을 화면에 내려주는 HTTP 읽기 계약을 신설할지, 그리고 그 모델을 **capability별**로 할지 **평면(flat) metrics**로 할지.
- **왜 지금**: 사용량은 수집·저장되고 placement가 내부에서 읽지만 **화면용 읽기 라우트가 0**이다. 계약 모양(capability별 vs 평면)이 안 정해져 이 백엔드 카드가 착수 못 한다.
- **선택지**: (A) capability별 → cpu/gpu/ram/disk 각각의 used/total을 구조적으로; 화면이 항목별로 그림. (B) 평면 metrics → 단일 평면 키값; 단순하나 항목 구분 약함. (C) 신설 안 함 → 화면은 사용량 미제공 유지.
- **안 두면**: 노드 화면이 용량은 보여도 **사용률을 못 보여준다**(현재 정직 상태). 관측성 공백이 지속되나 오작동은 아니다.

## 3. 노드 상태 어휘 — [작업차단; 조용한 거짓은 해소, 어휘 정합만 남음]
- **무엇을 정하나**: 노드 **liveness 표시**를 어떻게 낼지 — (A) 백엔드가 heartbeat 신선도로 online/degraded/offline을 **새 필드**로 계산·노출, (B) 프런트가 계약 어휘(active/lost/…)로 표시를 맞춤.
- **왜 지금**: 계약 status는 `{enrolling,active,draining,lost,retired}`(백엔드 진실)인데 화면은 `{online,degraded,offline,…}`를 기대한다. **진행분**: 백엔드 절반(계약 좁힘) 착지 `9b6e9a4a`; Gemini가 **조용한 거짓을 고침**(`827f1756`) — active를 몰래 'enrolling'으로 꾸미던 것을 이제 **'unknown'으로 정직 표시**. 남은 건 **어휘 정합 결정**뿐이다.
- **선택지**: (A) 백엔드 liveness 필드 신설 → 화면의 online/degraded가 실데이터로 살아남; 백엔드 작업 발생. (B) 프런트가 active를 healthy로 매핑 → 프런트만 수정(Gemini), 더 가벼움. (C) 두면 → 아래.
- **안 두면**: 이제 거짓은 아니지만(정직한 'unknown'), **정상(active) 노드가 healthy로 안 보이고 'unknown'·텔레메트리없음으로 남는다**. 데이터 손상 없음, 표시 정확도 미결. 조용한 오작동은 이미 해소돼 급도는 낮아졌다.

## 5. 다운로드 정본 선택 — [조건부]
- **무엇을 정하나**: 산출물 다운로드의 **정본 응답 계약**을 확정하고(현 control-plane의 `X-Content-SHA256` 경로), 레거시 경로(`X-Checksum-SHA256`, `sha256:` 형식)를 **폐기/정합**할지.
- **왜 지금**: 저장소 안엔 정본 다운로드 경로가 하나뿐이고 무결성 헤더가 붙는다. 그러나 레거시 fixture 모양(`tests/fixtures/legacy_control.py`)이 다른 헤더를 낸다. **저장소 밖 배포가 아직 레거시 경로를 돌리는지는 사용자만 안다.** Gemini의 엄격한 다운로드 클라이언트는 정본 헤더가 없으면 다운로드를 **거부**한다.
- **선택지**: (A) 정본=현 경로 확정 + 레거시 배포 없음 확인 → 그대로 안전. (B) 레거시 배포 있음 → 그 배포를 정본 계약으로 올리거나 폐기해야 함(그전까진 그쪽 다운로드가 거부됨).
- **안 두면**: 레거시 배포가 **있다면** 그쪽 사용자는 다운로드가 조용히 실패한다. **없다면** 무해. 즉 피해는 배포 현실에 조건부 — 사용자의 확인이 필요.

### 6a. 실패 Run 재시도 — 가장 놀랄 공백
- **무엇을 정하나**: 일반 **실패한 Run을 다시 실행하는 제품 경로**를 노출할지(그리고 owner/권한).
- **왜 지금(왜 다른가)**: 복구는 "있는지 모를 수 있는" 기능이지만 **실패한 것을 다시 해보는 것은 당연히 된다고 여긴다.** 그런데 **없다** — 재시도처럼 보이는 것들은 실행 재실행이 아니다: DeliveryQueue=전달 재관찰, OutputIngestion=결과 재수집, WorkspaceResume=`recovering` 상태의 다음 step(상태기계상 **failed→recovering 전이 없음**=failed는 종단), Run목록 "다시 시도"=목록 재조회. `ModelRetryStore`는 child Run·placement·lineage를 만들지만 **제품에서 호출 안 됨**(시험만). **독립검토 확인**: 상태기계(migration)가 failed=종단으로 구조 강제, ModelRetry·ShardRecovery 미배선, 갈래들 실제로 distinct.
- **선택지**: (A) ModelRetry에 제품 endpoint/권한 연결 → 실패 Run 재실행 가능; 문서가 남긴 후속 작업. (B) 미룬다 → 실패 Run은 failed로 남고 새 Run 수동 생성만 가능.
- **안 두면**: 사용자가 실패 후 "다시 시도"를 찾다 없다는 걸 알면 **놀랄** 공백(기대와 어긋남). 데이터 손상은 없다.
- 근거: [[2026-09-22_Run_retry_path_and_low_risk_write_contracts_Codex]] · [[2026-09-22_ControlPlane_제품경로_도달성_감사_Codex]] · 내 독립검토 [[2026-09-22_Codex_재시도부재_및_저위험7결속_독립검토_Claude]](상태기계 failed=종단·미배선·갈래 distinct 확인).

### 6b. 복구 경로 연결
- **무엇을 정하나**: 온디맨드 **복구 실행 API**(WorkspaceRecovery restore/checkout·복제본/샤드 수복)를 제품에 연결할지.
- **왜 지금**: 복구 **관측**은 있으나 **실행** 엔드포인트가 제품 조립에 없다(WorkspaceRecovery는 시험에서만 호출). 프런트는 "모의 / 복구 불가·미수행"으로 정직 고지. resume/prepare가 요구하는 checkout row의 writer도 이 미연결 클래스다.
- **선택지**: (A) 연결한다 → 실제 온디맨드 수복; 상당한 백엔드/커널 작업. (B) 미룬다 → 관측만·정직 고지 유지.
- **안 두면**: 복구 수동/불가 유지. 데이터 손상 없음, 능력 공백.

### 6c. 배치(placement)
- **무엇을 정하나**: 별도 결정이라기보다 6a의 downstream — `PlacementStore.reserve`(노드 배치 예약)의 **유일한 제품 caller가 미연결 ModelRetry**라 함께 미도달이다. 재시도를 연결하면 배치도 함께 살아난다.
- **안 두면**: retry와 운명 공유. 독립 항목으로 억지 분리하지 않는다.
- 근거(6a/6b/6c 공통): [[2026-09-22_ControlPlane_제품경로_도달성_감사_Codex]]. (도달성 감사의 NodeTransfer·CredentialRegistry·Outbox broker는 Node 통합 전제/선택 경계로 **제품 결함 아님**으로 분류 — 이 부류에 안 넣음.)

## 7. 노드 시각 스큐 알람 활성화 — [보류 가능]
- **무엇을 정하나**: 노드 시계 어긋남(clock skew) **알람**을 활성화할지. 활성화하려면 규격 개정(ERR-DESIGN-007 채택)이 먼저다.
- **왜 지금**: 커널은 이미 `clock_skew_seconds > 5` 적격성 필터를 쓰지만, 이를 **운영자 알람**으로 라우팅하는 건 규격·장비 보정·채널·담당이 미결이라 governance-gated 상태다.
- **선택지**: (A) 규격 개정 후 활성화 → 스큐 시 운영자 알람. (B) 보류 → 커널 필터는 계속 동작(부적격 노드는 이미 걸러짐), 다만 능동 알람은 없음.
- **안 두면**: **당장은 괜찮다.** 커널 필터가 이미 스큐 노드를 배제하므로 안전성엔 문제 없고, 다만 운영자가 능동 통지를 못 받는다. 규격 선행 조건 때문에 지금 바로 못 정함.
- 근거: [[2026-09-21_알람평가_GOV-ALERT-001_복구_Claude]] · §4 ④.

## 8. fixture 실제-발생-가능 검증 장치 — [검증 장치 투자; Codex 제안]
- **무엇을 정하나**: **schema는 통과하나 실제 producer가 결코 낼 수 없는 fixture 상태**(값 또는 필드 조합)를 잡는 장치를 만들지. Codex가 명명한 부류 = "schema-valid but producer-unreachable fixture state". schema round-trip 초록은 **모양 호환**만 증명하지 그 fixture가 **도달 가능한 상태**임을 증명하지 않는다.
- **왜 지금**: 오늘 이 병이 **두 번, 서로 다른 이유로** 기존 검사를 통과했다. (1) 내 node fixture `status:"online"` — producer가 안 내는 **도메인 밖 값**. schema가 도메인을 안 담아(loose str) 통과 → NodeResponse.status를 좁히니 그제야 잡힘. (2) node enrollment fixture `heartbeatSequence:12`+non-null `lastHeartbeatAt` — 갓 등록은 seq 0·timestamp null인데 **불가능 조합**. 각 필드는 개별 schema-valid라 model 검증이 조합을 못 봄 → Codex가 소스 대조로 발견·수정. 현 `check_contract_bindings`는 fixture 참조·serving anchor만 보지 **값/조합을 producer·DB 제약과 대조하지 않는다**.
- **선택지**: (A) 장치 신설 → fixture 값·조합을 producer 상태 도메인/reachability(및 DB CHECK 등 원천)와 대조. (B) 안 만듦 → 사람 대조에 의존(오늘처럼 좁힘·감사 때 우연히 발견).
- **안 두면**: schema 초록이 유지돼도 fixture가 **도달 불가 상태를 그린다** — "초록 = 도달 가능"으로 오독하고, 다음에도 누군가 좁히거나 감사할 때만 우연히 드러난다(데이터 손상 아님, 그러나 거짓 확신).
- **관련**: 내 [[2026-09-22_되돌아오는결함_구조가막나_주의에기대나_Claude]] 권고 2(응답필드 타입↔원천도메인 검사)와 **같은 부류**(fixture/타입을 원천 도메인에 묶기) — 함께 설계 검토 권고. 근거: [[2026-09-22_response_model_shape_self_audit_Codex]].
