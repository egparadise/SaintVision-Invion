# 최종 개발 계획 - 모든 개발의 지침


이 문서는 Saint Vision INV를 개발하는 **Codex·Claude·Gemini(Antigravity)**의 최종 공통 지침이다. 기존 24개 파일의 기준과 Claude 보완안 5개를 통합했다. 기능이 구현됐다는 선언이 아니라 구현·검증·기록의 기준선이다.

## 저장 위치와 권위

- 구현·문서 정본: `C:\Project\SaintVision-Invion`
- Git origin: **https://github.com/egparadise/SaintVision-Invion.git**
- Obsidian: `C:\Users\egpar\OneDrive - Inviz\15.Vibe Cording\Obsidian\SaintVision-Invion`
- Git의 `docs/vault`가 배포할 문서 정본이다. Obsidian은 동일 문서 ID·버전의 조회·편집 제안 공간이다.
- 사용자의 현재 지시와 승인 범위를 우선한다. 프로젝트 문서 사이의 충돌은 이 지침 → 승인 ADR → 공통 계약 → 상세 계획 → 원문 순으로 해결한다.
- Gemini 작성 보충 문서는 이번 원문 집합에서 확인되지 않았다. Gemini 의견을 대신 작성하거나 검토 완료로 표시하지 않는다.

## 완성 프로그램

5대 Windows/Linux PC가 허용한 CPU·GPU·RAM·폴더를 연결한다. 사용자는 내부망 웹에서 Project와 Workspace를 만들고, 편집·Git·Build·GPU 실행·모델 평가·승인된 배포·복구까지 수행하며 모든 결과를 증거로 추적한다.

기존 OS·사용자 파일·업무를 보존한다. Workspace와 물리 Node를 분리하고, 물리 RAM/VRAM을 하나의 메모리로 사용할 수 있다고 표시하지 않는다. 자원 배치·Lease·권한·상태 전이는 결정론적 코드가 소유한다. 개발 Agent와 제품 내부 Agent의 역할은 별도 프로필로 관리한다.

## 책임

| Agent | 최종 책임 | 구현 범위 |
|---|---|---|
| Codex | 최고 난도·기술 통합 | Scheduler, Lease/Fencing, RunGraph 복구, DB 동시성, 보안 경계, Storage 무결성, Reverse-Ontology |
| Claude | 중간 난도 서비스·운영 | 업무 API, CRUD, 일반 Migration, Context, Adapter 연결, 테스트, 운영 문서 |
| Gemini / Antigravity | 디자인·Frontend·웹 배포 | 디자인 토큰, 전체 화면, UI 연결, 접근성, 시각 검증, 내부망 HTTPS 배포와 웹 롤백 |
| 사용자 | 제품·운영 책임 | 범위·환경·필요한 운영 권한 결정 |

작업당 owner는 하나다. Frontend의 고난도 인증·프로토콜 코어는 Codex가 계약을 제공하고 Gemini가 통합한다. 작성자의 자기 검증만으로 통합하지 않으며 교차 검토자를 지정한다. 상세 규칙은 [[Agent 역할과 인계 계약]].

## 필수 설계 방식

[[Reverse-Ontology 최종 설계]]에 따라 **완성 목표 → 합격 조건 → 필요한 증거 → 기능 → 계약·데이터 → 작업 → 담당자** 순으로 역산한다. 예상 결과와 실제 증거는 별개다. 모든 작업은 목표 ID, 증거 요구, 계약, owner, reviewer, 선행 작업을 가진다.

Prompt·Context·Harness·Skill·ROOF·Graph·Agent를 버전 관리하고 실행 기록에 사용 버전을 고정한다. `Promt`, `cotext`, `foof`는 Prompt, Context, ROOF의 별칭으로 정리한다. ROOF와 Reverse-Ontology는 프로젝트 내부 정의이며 공인 표준이라고 주장하지 않는다.

## 모든 작업의 절차

매 작업의 진입점은 [[전체 개발 진행 현황]]과 자기 Agent 작업판이다. 작업 전 현재 카드/선행/증거를 확인하고, 작업 후 작업한 것·확인한 증거·이어 할 첫 행동과 담당을 기록한다. [[Agent 지속 개발 운영 규칙]]에 따른다.

**init → 구현·로컬 검증 → commit → push → CI build → Obsidian report → 검토·인계**

최초 init만 Git 초기화다. 이후 init은 최신 문서·원격 상태·작업 ID·브랜치·변경 범위 확인이다. build 실패·push 실패·report 미동기화는 완료가 아니다. 구체적인 명령과 인계는 [[Git Build Obsidian 운영 절차]]를 따른다.

미래 계획은 `planned`, 실제 수행 결과만 개발 과정 페이지에 기록한다. 모든 실행 기록은 KST 시각·작업 ID·Agent·커밋·검증 결과를 가진다. 오류와 해결은 각각 [[오류 및 해결 인덱스]]에서 별도 페이지로 연결한다.

## 합격 기준

| 지표 | 목표 |
|---|---|
| 등록·관측 | 5 Node, 이탈 감지 ≤60초 |
| Scheduler / 취소 | P95 ≤2초 / ≤10초 |
| Workspace 생성 | ≥95% |
| Evidence 기록 / trace 완전성 | ≥99.99% / ≥99% |
| Prompt 구조화 / 코딩 과제 | ≥99% / ≥70% |
| Node 장애 복구 성공 | ≥95% |
| 정책 우회·중복 부수 효과·원문 비밀 노출 | 0건 |
| 백업 | RPO ≤15분, RTO ≤1시간 복원 실측 |

실측되지 않은 수치는 목표다. 99.5% 월 가용성은 단일 Control Plane에서도 측정할 SLO이며 HA를 제공한다는 뜻이 아니다. 24주 파일럿의 최종 보고에는 실제 측정 기간과 표본 수를 함께 기록한다.

## 범위와 진행 상태

초기 시험 데이터는 합성 데이터다. 완전한 분산 파일시스템·공용 멀티테넌트 서비스·자동 임의 모델 분할·무인 관리자 실행은 후속 범위다. 장비 값, 내부 DNS·TLS, IdP, 저장 용량은 S01의 확인 항목이며 임의 값으로 채우지 않는다.

최초 문서 기준선의 제품 시작 전 상태는 역사 기록이다. 현재 구현·검증·운영 인수는 [[전체 개발 진행 현황]]의 고정 SHA 증거를 따른다. 문서 검증과 제품 성공을 혼동하지 않는다. 원문 근거는 [[원문 분석 및 반영 목록]]을 본다.
