# 보완 설계 종합 요약

## 목적

이 문서는 `SaintVision-Invion` 설계 볼트의 기존 19개 문서를 전수 정독한 뒤, **구현 착수 전에 반드시 메워야 할 공백**을 Frontend, Backend, DB, Storage 네 영역으로 정리한 것이다.

기존 문서는 수정하지 않는다. 이 폴더의 문서들은 기존 설계를 **대체하지 않고 보완**한다.

## 1. 전제: 지금 어디에 있는가

| 항목 | 현재 상태 |
|---|---|
| 설계 문서 | 19개, 약 200KB. 개념·정책·계약 층은 baseline 수준 |
| 구현 저장소 `C:\Project\SaintVision-Invion` | **빈 폴더** |
| 착수 체크리스트 (인덱스 문서) | 6개 항목 전부 미완료 |
| 문서 상태 | `시스템 아키텍처와 기술 스택` = proposed, `시스템 스키마` = draft, `24주 구현 로드맵과 백로그` = proposed, `Ontology 설계` = draft |

즉 **설계는 있으나 확정되지 않았고, 코드는 0단계**다.

## 2. 이미 충분한 영역 (건드리지 않는다)

아래는 다른 어떤 항목보다 구체성이 높고, 그대로 구현에 넘길 수 있다. 보완 문서에서 재설계하지 않고 **그대로 인용해 사용**한다.

- 자원 3층 모델 (Capacity / Offer / Lease)과 예약 가능량 계산식
- Fencing Token 기반 이중 실행 차단
- 명령 위험 등급 L0~L3와 승인 매트릭스
- `EvidenceEnvelope` 구조와 "민감 원문은 Evidence에 넣지 않는다" 원칙
- 오류 코드군 10종 (`VAL-*`, `AUTH-*`, `CTX-*`, `TOOL-*`, `RES-*`, `NET-*`, `GRAPH-*`, `VERIFY-*`, `SEC-*`, `BUDGET-*`)
- AI CLI Adapter 8 오퍼레이션 (probe / install / authenticate / run / cancel / collect / redact / attest)
- 불변 조건 7개 (`시스템 스키마` §10)
- 신뢰 경계 7개, Prompt Injection 방어 8원칙, 비밀 관리 6항목
- MLOps Lineage와 ModelVersion 승인 전제조건

## 4. 문서 간 모순 해소 — 정본표

같은 개념이 문서마다 다르게 적혀 있는 지점이다. 각각에 대해 **정본 하나를 고르고 나머지를 폐기**한다. 폐기 대상을 계속 두면 구현자가 어느 쪽을 따를지 매번 판단해야 한다.

| # | 충돌 | 정본 | 폐기 | 근거 |
|---|---|---|---|---|
| 1 | 실행 상태기계 2종 | **`공통 계약 요구사항과 완료 기준`의 11개 상태** (`draft, validated, planned, awaiting_approval, scheduled, running, verifying, recovering, succeeded, failed, cancelled`) | `단계별 개발 계획` G3의 `Specified…Completed` | 정본 문서만이 "임의 문자열을 추가하지 않는다"고 명시. `ContextReady`/`PolicyChecked`는 `validated`의 내부 단계로 흡수 |
| 2 | 게이트 체계 2종 (같은 "G3"가 다른 의미) | **품질 게이트 = G0~G6 (성숙도)**, **일정 = R0~R4 릴리스 열차** | `개발 플랜`의 G0~G10 주차 게이트 번호 | 두 축을 분리해야 충돌이 사라짐. 주차 정보는 릴리스 열차로 이미 표현됨 |
| 3 | API 경로 규약 | **서브리소스 스타일** (`POST /v1/runs/{id}/cancel`) | 커스텀 메서드 스타일 (`POST /v1/jobs/{id}:cancel`) | OpenAPI 생태계 표준. 콜론 방식은 gRPC 트랜스코딩을 전제하는데 이 프로젝트는 REST + WebSocket이 진입점 |
| 4 | 리소스 명칭 `Job` vs `Run` | **`Run`으로 통일** | `Job`, 식별자 접두사 `job_` | 온톨로지 TTL에 `Job` 클래스가 없고, RunGraph가 전 문서의 축. 용어 사전은 Job을 "Workload에서 생성된 실행 단위"로 정의하나 이 역할은 `Run`이 이미 수행 |
| 5 | `/v1/resources/snapshot` vs `/v1/resource-graph` | **둘 다 유지, 역할 분리** | — | 서로 다른 질문에 답한다. snapshot = 특정 시점 측정값, resource-graph = 토폴로지와 관계 포함 조회 |
| 6 | `runs/{id}/evidence` vs `runs/{id}/explain` | **둘 다 유지** | — | evidence = 감사 원본 조회, explain = 배치·정책 사유. `inv explain` CLI가 후자에 대응 |
| 7 | `ContextPack` vs `ContextBundle` | **`ContextBundle`** | `ContextPack` | 계약 정본 문서(`공통 계약 요구사항과 완료 기준`)의 명칭 |
| 8 | `WorkloadSpec` vs `IntentSpec` vs `AgentRunSpec` | **세 개 모두 유지, 변환 단계로 정의** | — | 혼용이 아니라 파이프라인이다. `IntentSpec`(자연어 구조화) → `WorkloadSpec`(자원·런타임 중립 계약) → `AgentRunSpec`(Agent 실행 제약). 이 관계를 명시하는 문서가 없던 것이 문제 |
| 9 | Redis "필요 시" vs 배포 토폴로지 기본 포함 | **MVP 필수로 승격** | "초기에는 불필요한 중복 도입 금지" | Terminal 세션 상태, rate limit 토큰 버킷, 멱등성 키 캐시에 필요. 이미 배포 토폴로지와 저장소 매핑표에는 기본 포함되어 있음 |
| 10 | Storage 단계 3단계 vs 5단계 | **5단계로 통합** | 3단계 표현 | 세분화된 쪽이 실행 가능. 매핑: 1→1, 2→2·3, 3→4·5 |
| 11 | 위험도 표기 `0/1/2` vs `L0~L3` | **`L0~L3`** | API 표의 숫자 표기 | 거버넌스 문서의 정의가 가장 상세하고, L3(기본 차단)이 숫자 표기에는 아예 없음 |
| 12 | 상관관계 ID 체인 2종 | **`traceId → runId → stepId → toolCallId → evidenceId`를 체인으로, `workspaceId`/`nodeId`는 span attribute로** | 두 목록을 각각 유지하는 것 | 거버넌스 문서는 `toolCallId` 포함, 공통 계약은 `workspaceId`/`nodeId` 포함. 계층 관계가 있는 것과 부가 속성을 구분하면 둘 다 살릴 수 있음 |

## 5. 온톨로지 트랙 — 별도 처리 권고

온톨로지는 Frontend/Backend/DB/Storage 어디에도 직접 속하지 않지만, 방치하면 DB 설계와 충돌한다.

발견된 문제:

1. **설계 문서가 열거한 클래스 20개 이상이 TTL에 미구현.** 특히 `RunGraph`, `RunAttempt`, `Checkpoint`, `AgentProfile`, `Tenant`, `ProvenanceRecord`는 6단계 통합 모델과 Competency Question이 명시적으로 요구하는 개념이다.
2. **`Ontology 설계` §11의 예제 SPARQL이 현재 TTL에서 빈 결과를 낸다.** `inv:hasLocation`, `inv:registersModel`, `inv:consumesDataset`으로 쓰였으나 TTL의 실제 정의는 각각 `ml:hasLocation`, `ml:registersModel`, `ml:consumesDataset`이다. 온톨로지가 한 번도 로드·질의 테스트되지 않았음을 시사한다.
3. **SHACL shapes 파일이 없다.** §7의 12개 제약과 §13의 "SHACL Example Validation" CI 요구를 실행할 산출물이 존재하지 않는다.
4. **T-Box와 A-Box가 한 파일에 혼재.** `saintvision-inv.ttl` 하나에 스키마와 예제 인스턴스가 같이 있어 프로덕션 로딩 시 예제 데이터가 함께 들어간다.
5. **TTL 예제와 JSON-LD 예제가 다르다.** JSON-LD에만 `res:tool-claude-code`와 `res:adapter-claude-code`가 있다. 단일 소스에서 생성되지 않았다는 뜻이다.
6. **온톨로지 채택 자체의 근거가 없다.** `최신 기술 출처와 설계 근거` 문서 전체에 RDF/OWL/SPARQL 출처가 0건이다. 6단계 모델은 1차 출처로 무장되어 있으나 온톨로지 트랙만 근거 등급 체계 밖에 있다.

**권고**: MVP는 `단계별 개발 계획`이 이미 정한 대로 **PostgreSQL을 source of truth로, RDF는 교환 포맷으로만** 유지한다. TTL 수정(위 1~5)은 DB 구현과 분리된 별도 작업으로 처리하고, 착수 차단 항목으로 취급하지 않는다. 다만 `Ontology 설계` §12의 테이블↔클래스 매핑표 15행은 DB 물리 스키마 설계의 출발점으로 그대로 사용한다.

5. **실시간 전송 방식** (Terminal / Run 이벤트) → [[10_Frontend 보완 설계]]

### 파일럿 차단 — 합격 지표를 만족하려면 필요

## 7. 재사용 가능한 사내 자산

같은 조직의 `C:\Project\SaintviewPACSai`가 이미 가동 중이며, INV 설계가 미결로 남긴 항목 상당수의 답이 여기에 있다.

| 자산 | 경로 | 재사용 대상 |
|---|---|---|
| FastAPI + SQLAlchemy 2.0 + Alembic 계층 구조 | `backend/app/` (`api/`, `models/`, `repositories/`, `services/`) | Backend 서비스 골격 |

파일럿 도메인이 의료영상(PACS)이라는 점에서도 이 저장소는 참조 가치가 높다.

## 8. 미해결로 남기는 항목

아래는 이 보완 문서 세트가 **의도적으로 결정하지 않는다**. 기술 판단이 아니라 사업·법무 판단이기 때문이다.

- **Web IDE 라이선스**: Microsoft 공식 문서가 VS Code Server의 서비스 호스팅을 허용하지 않는다고 명시한다. code-server와 OpenVSCode Server는 코드 라이선스뿐 아니라 extension marketplace 이용 조건도 별도 검토가 필요하다.
- **의료기기 소프트웨어 규제 범위**: 파일럿 도메인이 PACS·DICOM인데 기존 설계 전체에 HIPAA/GDPR/개인정보보호법 언급이 없다. [[40_Storage 보완 설계]]에서 기술적 처리 경로는 제시하지만, 규제 적용 여부 판단은 하지 않는다.
- **상용 AI CLI의 자동화 허용 범위**: Provider별 이용약관 검토가 선행되어야 한다.
