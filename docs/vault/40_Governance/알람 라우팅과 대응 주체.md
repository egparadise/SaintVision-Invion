# 알람 라우팅과 대응 주체

**draft.** CR-10에 대한 Claude 영역(운영 문서) 산출물이다. 채널·수신자의 실제 값은 사용자 결정 사항이며 현재 `unknown`이다. 이 문서는 **구조와 규칙**을 확정하고 값이 정해지면 채운다.

배경: [[Backend 최종 개발 계획]]은 측정 대상과 임계를, [[DB 최종 개발 계획]]은 실패·용량 알람을 정했다. 그러나 알람이 **누구에게 어떻게 가는지**가 없어 [[보안 평가 운영 가이드]]의 사고 대응 1단계(탐지)가 성립하지 않는다.

## 1. 심각도 정의

파일럿은 소수 인원이므로 3단계로만 나눈다. 단계를 늘리면 아무도 구분하지 않는다.

| 심각도 | 의미 | 응답 기대 |
|---|---|---|
| **P1** | 안전·무결성이 깨졌거나 제품이 정지했다 | 즉시 |
| **P2** | SLO를 위반했거나 곧 위반한다 | 근무 시간 내 |
| **P3** | 추세가 나쁘다. 지금 조치하지 않아도 된다 | 주간 검토 |

## 2. 알람 목록과 심각도

[[Backend 최종 개발 계획]]·[[DB 최종 개발 계획]]·[[Storage 최종 개발 계획]]의 지표에서 역산했다.

| 알람 | 조건 | 심각도 | 1차 대응 역할 |
|---|---|---|---|
| 비밀 원문 노출 탐지 | >0건 | **P1** | 보안 |
| 정책 우회 또는 승인 없는 L2/L3 실행 | >0건 | **P1** | 보안 |
| Evidence 기록 실패 | >0건 (5분) | **P1** | DB 운영 |
| Evidence partition 잔여 <1개월 | 상시 검사 | **P1** | DB 운영 |
| OPA 응답 실패·타임아웃 | >0건 | **P1** | Backend 운영 |
| 체크섬 불일치 | >0건 | **P1** | Storage 운영 |
| 중복 부수 효과 탐지 | >0건 | **P1** | Backend 운영 |
| Control Plane 오류율 | >5% (5분) | **P1** | Backend 운영 |
| Node 시각 스큐 한도 초과 | 한도 초과 | **P2** | 인프라 |
| Control Plane 오류율 | >1% (5분) | **P2** | Backend 운영 |
| 스케줄 결정 P95 | >2초 (10분) | **P2** | Backend 운영 |
| 정책 결정 P95 | >200ms (10분) | **P2** | Backend 운영 |
| Run 이벤트 전달 P95 | >5초 (10분) | **P2** | Backend 운영 |
| Node 이탈 감지 지연 | >60초 | **P2** | 인프라 |
| Evidence partition 잔여 <2개월 | 상시 검사 | **P2** | DB 운영 |
| 백업 실패 또는 복원 스모크 실패 | >0건 | **P2** | DB 운영 |
| 아티팩트 검증 대기 적체 | 임계 초과 | **P2** | Storage 운영 |
| 캐시 적중률 하락 | 추세 | **P3** | Storage 운영 |
| 버킷 용량 추세 | 추세 | **P3** | Storage 운영 |
| lock wait 증가 | 추세 | **P3** | DB 운영 |

`node_clock_skew_seconds`의 **라우팅 알람은 2026-09-22 활성화됐다**(결정 #7 선택지 A, [[ERR-DESIGN-007 시각 동기화 요구 부재]] v2.0.0 제4조). `tools/alarm_check.py`가 `status='online'` 노드 중 미측정·비유한·`abs(clock_skew_seconds) > 5`인 노드가 있으면 `Node 시각 스큐 한도 초과`를 P2·1차 대응 인프라로 발화하고, 후속 heartbeat가 한도 안이면 다음 평가에서 해제한다(래치 없음). 커널의 런타임 적격성 필터(같은 술어)는 그대로이며 알람은 그 필터를 **보이게** 만드는 것이다. 자동 조치는 없다. 통지 채널·수신자의 실제 값은 여전히 이 문서 §3의 `unknown`을 따른다(기록 채널).

## 3. 라우팅 규칙

| 심각도 | 채널 | 재알림 | 자동 조치 |
|---|---|---|---|
| P1 | 즉시 알림 채널 + 기록 채널 | 30분마다 미확인 시 | 해당 범위 kill switch 검토(자동 실행 아님) |
| P2 | 기록 채널 | 없음 | 없음 |
| P3 | 주간 요약 | 없음 | 없음 |

**자동 조치는 두지 않는다.** [[보안 평가 운영 가이드]]가 kill switch를 사람의 판단으로 두고 있고, 파일럿 규모에서 자동 차단은 오탐 피해가 더 크다.

### 대응 역할과 실제 사람

파일럿 인력은 4명 + 겸임 1명이다([[24주 통합 실행 계획]] 가정). 역할은 사람이 아니라 **책임 영역**이며 한 사람이 여러 역할을 겸할 수 있다.

| 역할 | 1차 담당 | 백업 |
|---|---|---|
| 보안 | `unknown` | `unknown` |
| Backend 운영 | `unknown` | `unknown` |
| DB 운영 | `unknown` | `unknown` |
| Storage 운영 | `unknown` | `unknown` |
| 인프라 | `unknown` | `unknown` |

**미확인 값이며 임의로 채우지 않는다.** 사용자가 인력 배정을 결정하면 갱신한다.

### 채널

| 용도 | 값 |
|---|---|
| 즉시 알림 채널 | `unknown` |
| 기록 채널 | `unknown` |
| 주간 요약 | `unknown` |

**미확인 값이며 임의로 채우지 않는다.** 파일럿 초기에는 Grafana 알림 규칙만 정의하고 채널을 비워둘 수 있다. 다만 **P1 채널이 비어 있는 동안에는 릴리스 게이트의 "사고 연락망 검증"을 통과했다고 표시하지 않는다.**

## 4. 온콜을 두지 않는다

파일럿은 내부망·단일 팀·업무 시간 사용을 전제한다. 24시간 온콜 조직은 과하다. 대신:

- P1은 **근무 시간에만** 즉시 대응을 기대한다.
- 근무 시간 밖의 P1은 다음 근무 시작 시 최우선으로 처리한다.
- 이 한계를 [[전체 개발 진행 현황]]과 파일럿 보고서의 **알려진 제한**에 명시한다.

가용성 99.5%(월 3.6시간)를 온콜 없이 달성한다고 주장하지 않는다. 야간 장애 1건이 예산을 크게 쓴다. ADR-018대로 99.5%는 **측정 대상**이며 보장이 아니다.

## 5. 검증

알람 설정 자체를 시험한다. 규칙만 있고 도달하지 않는 알람은 없는 것과 같다.

- 각 P1 알람에 대해 **인위적으로 조건을 만들어** 실제 채널 도달을 1회 확인한다.
- 도달 확인 결과를 S11의 릴리스 게이트 증거로 남긴다.
- 채널이 `unknown`인 동안에는 이 시험을 `not_run`으로 기록한다.

## 6. 미확인 값 요약

AC-01의 "미확인 값 명시" 요구에 따라 모아 둔다.

- 대응 역할별 1차 담당·백업 5쌍
- 즉시 알림 채널, 기록 채널, 주간 요약 채널
- 월간 partition 잡의 실행 주체([[Claude 영역 구현 준비]] §1)
- 근무 시간 정의
