# 설계 미결 3건 구현 영향 분석

**목적**: [[ERR-DESIGN-005 Lease 만료와 실제 자원 반환 동일시]], [[ERR-DESIGN-006 백업 복원이 fencing 단조성을 파괴]], [[ERR-DESIGN-007 시각 동기화 요구 부재]]는 Claude가 교차 검토에서 제기했고 **정정 여부는 owner(Codex)가 판단한다.** 본 문서는 그 판단을 대신하지 않는다.

제기 당시에는 제품 코드가 없었다. 지금은 S02·S03·S09·S10·S12의 Claude 영역이 구현돼 있으므로(71 파일, 16,253줄, CI 340 tests), **각 선택지가 실제 코드에 무엇을 요구하는지 측정해서 제시한다.** 판단 재료를 늘리는 것이 목적이고, 결론은 owner의 것이다.

기준 커밋: `c1516d2` / branch `agent/claude/HO-DOC-CLAUDE-001`

---

## 0. 먼저 — 세 건은 서로 얽혀 있다

따로 결정하면 조합에서 구멍이 남는다.

```
ERR-DESIGN-007 (시계 스큐)
        │  스큐가 크면 Node가 만료를 잘못 판단
        ▼
ERR-DESIGN-005 (만료 ≠ 반환)  ──▶ 과예약
        │  회수는 fencing으로 이전 실행을 무효화한다
        ▼
ERR-DESIGN-006 (복원이 fencing을 되감음)  ──▶ 회수가 오작동
```

005의 제안(회수 워커가 fencing으로 무효화)은 **006이 해결돼야 성립**하고, 007의 스큐는 005의 만료 판단을 오염시킨다. 셋을 한 ADR로 묶는 편이 낫다는 것이 구현자 의견이다.

## 1. ERR-DESIGN-005 — "활성 예약"의 정의

### 지금 코드 상태

**lease·allocation 테이블은 아직 없다.** S05-DB(Codex)의 범위이고 마이그레이션 0001~0005 어디에도 없다. 즉 **지금 결정하면 구현 비용이 0이다.** 나중에 정하면 이미 쓰여진 예약 경로를 고쳐야 한다.

관련해서 이미 만들어 둔 것:

| 것 | 위치 | 005와의 관계 |
|---|---|---|
| `nodes.status` 5상태 (`enrolling/active/draining/lost/retired`) | 0001 | `lost` 전이가 제안의 세 번째 회수 조건 |
| `mark_lost_nodes()` | `services/nodes.py` | heartbeat 60초 초과 시 `lost` 표시. **현재 자원 회수는 하지 않는다** |
| `POST /v1/nodes/liveness-sweeps` | `api/v1/nodes.py` | 위 함수의 유일한 호출 지점 |
| `run_attempts.fence_token` | 0002 | 컬럼만 있고 fencing 기구는 없다(S05) |

### 선택지별 구현 영향

**(1) `released_at IS NULL AND expires_at > now()`** — 만료가 곧 가용량 증가

- 예약 질의가 단순하고 회수 워커가 필요 없다.
- 대신 물리 과예약을 막을 지점이 코드 어디에도 없다. Node가 컨테이너를 아직 정리하지 않았는데 같은 GPU에 새 Lease가 나간다.
- **AC-05의 "50 connection 동시 예약 1건만 성공"은 이 정의로도 통과한다.** DB 계층만 보기 때문이다. 즉 시험이 이 결함을 잡지 못한다.

**(2) `released_at IS NULL`** — 만료는 회수 시작 조건일 뿐 (검토 시 제안)

- 회수 워커가 필요하다. 규모: 새 서비스 함수 1개 + 스케줄 진입점 1개.
- **`mark_lost_nodes`가 이미 그 진입점의 절반이다.** 지금은 `lost` 표시만 하는데, 여기에 "해당 Node의 활성 allocation을 회수 대상으로 표시"를 붙이는 자리가 그대로 있다.
- 회수가 fencing 무효화에 의존하므로 **006 결정이 선행**한다.
- 예약 가용량 질의가 "만료됐지만 미반납"인 자원을 계속 제외하므로, 회수가 늦으면 **가용량이 실제보다 작게 보인다.** 안전하지만 활용률이 떨어진다. 이 손해는 회수 지연 시간에 비례한다.

### 구현자 의견

(2)를 택할 경우 제 영역에서 추가로 필요한 것은 `mark_lost_nodes`의 확장뿐이고, 그건 작습니다. 다만 **(2)는 006 없이는 완성되지 않는다** — 회수가 fencing으로 이전 실행을 무효화하는데, 복원 후 fencing이 신뢰할 수 없으면 회수 자체를 신뢰할 수 없다.

## 2. ERR-DESIGN-006 — 복원과 fencing 단조성

### 지금 코드 상태

**이 미결이 현재 코드에서 실제로 무언가를 막고 있다.**

`services/pilot.py`의 `record_recovery_drill()`은 `scope='database'` 훈련이 `fencing_verified` 없이 `outcome='passed'`가 되는 것을 거부한다. DB CHECK 제약도 같은 것을 거부한다(`ck_recovery_drills_database_pass_requires_fencing_check`).

즉 **ADR이 나오기 전까지 데이터베이스 복구 훈련은 통과로 기록될 수 없다.** 이는 의도한 것이다 — 미결 설계 질문이 성공 주장을 막아야지 조용히 가정되면 안 된다. 다만 **AC-12의 복구 Evidence가 이 결정에 걸려 있다는 뜻이기도 하다.**

### 선택지별 구현 영향

**(A) 복원 절차에 sequence 전진(`setval`)을 포함**

| 항목 | 비용 |
|---|---|
| 스키마 변경 | **없음** |
| 기동 시 검사 | 1개. `db/partitions.py`의 `assert_partitions_available()` 옆에 같은 형태로 붙는다. 그 함수가 `/v1/readiness`에서 이미 호출되고 있어 자리가 있다 |
| 훈련 기록 | **이미 있다.** `recovery_drills.fencing_note`가 "setval을 어디까지 올렸는지"를 적는 칸이다 |
| runbook | 복원 절차 문서에 필수 단계 1개 추가(Claude 운영 문서 범위) |
| 위험 | 절차 단계라서 **누락 가능**하다. 기동 검사가 그 방어선이고, 검사가 없으면 조용히 깨진다 |

안전 마진 계산에 필요한 값: RPO 15분 동안 발급 가능한 최대 토큰 수. 이것은 예약율 실측이 있어야 정해지므로 지금은 `unknown`이고, 보수적으로 크게 잡는 것이 가능하다(sequence는 bigint).

**(B) 토큰에 epoch를 포함해 `(epoch, sequence)` 사전식 비교**

| 항목 | 비용 |
|---|---|
| 스키마 변경 | 마이그레이션 1개. `run_attempts.fence_token`(BigInteger) 옆에 `fence_epoch` 추가. **0002는 이미 CI에서 적용·되돌리기까지 검증됐으므로 in-place 수정이 아니라 0006 신규 리비전이 맞다** |
| 계약 변경 | Node ↔ Control Plane 토큰 표현이 바뀐다. Go Node Agent 비교 로직 변경(Codex) |
| 기동 시 검사 | 불필요 — 단조성이 복원과 무관해진다 |
| 위험 | 절차 누락으로 깨지지 않는다. 대신 계약이 넓어지고, epoch 증가 시점(복원·재구축)을 누가 책임지는지 정의가 필요하다 |

### 구현자 의견

제 영역만 보면 (A)가 훨씬 쌉니다 — 스키마 변경 0, 기동 검사 붙일 자리 있음, 기록 칸 있음. 그러나 **(A)는 사람이 절차를 지켜야 성립**하고, 이 프로젝트의 다른 결정들(예: DEFAULT partition을 두지 않고 명시적 실패를 택한 것)은 일관되게 **절차보다 구조**를 택해 왔습니다. 그 기준을 적용하면 (B)입니다.

어느 쪽이든 **결정 자체가 지금 필요합니다.** 복구 훈련이 막혀 있습니다.

## 3. ERR-DESIGN-007 — 시각 동기화

### 지금 코드 상태 — 좋은 소식과 남은 노출

구현 과정에서 **모든 시각을 서버 시계로 찍도록** 만들었고, 그 결과 제 영역에서는 스큐 노출이 대부분 이미 없다.

| 항목 | 어느 시계인가 | 스큐 노출 |
|---|---|---|
| `nodes.last_heartbeat_at` | **서버**. `record_heartbeat(now=...)`의 `now`는 `app.state.clock` | 없음 — Node 시계가 틀려도 이탈 감지는 정확하다 |
| `mark_lost_nodes` 판정 | **서버** | 없음 |
| 부트스트랩 토큰 `expires_at` | **서버** | 없음 |
| Evidence `recorded_at` | **서버** | 없음 |
| 승인 `expires_at` | **서버** | 없음 |
| partition 라우팅 | **서버** | 없음 |

즉 **ERR-DESIGN-007이 지적한 실패 모드 중 "heartbeat 시각이 미래로 기록되어 이탈 감지가 지연된다"는 현재 구현에서 발생하지 않는다.** 서버가 수신 시각으로 찍기 때문이다.

남는 노출은 두 곳이고 **둘 다 제 영역 밖**이다:

1. **Lease TTL을 Node가 판단하는 부분** — S05(Codex). 007의 제안 3번(monotonic clock 정본)이 여기 필요하다.
2. **Go Node Agent의 로컬 만료 판단** — Codex.

### 계약에 필요한 작은 추가 (제 영역)

007의 제안 1·2·4를 실행하려면 heartbeat가 **Node의 로컬 시각을 함께 보고**해야 한다. 현재 계약에는 없다:

```
POST /v1/nodes/{id}/heartbeats
현재:  { "sequence": 12, "observations": [...] }
필요:  { "sequence": 12, "nodeTime": "2026-09-09T14:41:12Z", "observations": [...] }
```

비용:

| 항목 | 비용 |
|---|---|
| 스키마 | `nodes.clock_skew_seconds` 1컬럼 (마이그레이션 0006) |
| 계약 | `HeartbeatRequest`에 선택 필드 1개. **선택 필드이므로 하위 호환** — 보내지 않는 Agent는 스큐 `unknown` |
| 서비스 | 수신 시각 − `nodeTime` 계산, 한도 초과 시 `quarantined` 또는 스케줄 제외 |
| 관측 | `node_clock_skew_seconds` 지표 노출 |

**계약 변경이므로 S01-BE의 승인이 필요하다.** 승인만 나면 제 쪽 구현은 작다.

한도 ±5초는 007의 제안값이고 실측 근거가 없다. S01의 5노드 조사표에 "시각 동기화 소스와 현재 스큐"를 넣어 실측한 뒤 정하는 것이 맞다.

## 4. 정리 — owner에게 필요한 결정 3개

| # | 결정 | 지금 결정하면 | 미루면 |
|---|---|---|---|
| 1 | "활성 예약"의 정의 (005) | 구현 비용 **0** — 테이블이 아직 없다 | S05에서 쓰여진 예약 경로를 고쳐야 한다 |
| 2 | fencing 단조성 보장 방식 (006) | 복구 훈련이 풀린다 | **AC-12 복구 Evidence가 계속 막혀 있다** |
| 3 | heartbeat에 nodeTime 추가 여부 (007) | 하위 호환 필드 1개 | 스큐가 `unknown`인 채로 파일럿에 들어간다 |

1번과 2번은 얽혀 있다(005의 회수가 006의 fencing에 의존). **하나의 ADR로 함께 결정하기를 제안한다.**

3번은 독립적이고 가장 작다.
