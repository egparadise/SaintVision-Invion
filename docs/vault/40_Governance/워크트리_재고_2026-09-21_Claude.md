# 워크트리 재고 — 2026-09-21

## 왜 (오늘 세 번 뿌리가 됐다)
1. **저장소 전체 grep 오염**: 낡은 워크트리(`.worktrees/*`, 제거 이전 SHA 고정)가 recursive grep에 섞여 이미 사라진 코드가 살아 있는 것처럼 보임(오늘 LegacyProjectCatalog 히트가 전부 낡은 워크트리였음).
2. **뒤처진 트리에서 측정**: 어느 트리가 무엇인지 한눈에 안 보여 뒤처진 나무에서 잼 → 틀린 상태를 봄.
3. **공유 index 사고 3건**: 여러 워크트리가 한 `.git`을 공유하는 구조가 뿌리.

**삭제하지 않는다.** 남의 작업이 있을 수 있고 삭제는 되돌릴 수 없다. **재고만** 만든다. 각각을 소유자가 판단하도록 목록으로 남긴다.

## 스캔 기준 (측정 순간 못 박기)
- 스캔 시각 origin/integration tip = **`f7bc087`**("docs(contracts): clarify node telemetry exposure boundary"). ahead(`a`)/behind(`b`)는 이 tip 기준. tip은 세션 중 계속 이동하므로 이 SHA로 고정.
- `dirty` = `git -C <path> status --porcelain` 줄 수(미커밋 변경). **미커밋이 핵심** — 그것이 있으면 살아 있는 작업이고 워크트리를 지우면 잃는다.
- 소유자는 **디렉터리/브랜치 이름에서 추정**(표시: [추정]). 실제 소유는 이름과 다를 수 있다.

## ★ 핵심 발견 (분류의 근거)
- **미커밋 변경은 주 워크트리 1곳뿐(dirty=3), 나머지 45개 형제 워크트리는 전부 dirty=0.** → **어떤 형제 워크트리를 지워도 미커밋 작업 손실이 없다.**
- **워크트리 제거 ≠ 브랜치·커밋 삭제**: `git worktree remove`는 체크아웃과 미커밋 변경만 버린다. 브랜치 ref와 그 커밋은 `.git`에 남는다. 그래서 `ahead>0`(미병합 커밋 보유) 워크트리도 **워크트리 자체는 제거해도 커밋을 안 잃는다** — 단 **브랜치는 지우지 말 것**(미병합 작업이 거기 있음).
- 결론: 정리 안전성은 미커밋(dirty)으로 갈리고 전부 0이므로 형제 워크트리 정리는 일률적으로 안전하나, **지시대로 삭제하지 않고 목록만** 남긴다. `ahead>0`은 브랜치 보존 필요로 별도 표시.

## 주 워크트리 상태와 원인 (사용자가 27c853b·미커밋 3 본 건)
- **현재**: HEAD `ddb16ac`, branch `integration/all-agents-unified`, **tip보다 11 behind**, dirty=3.
- **dirty=3의 정체**: `이어가기…Claude.md`(M), `CI-PREFLIGHT-CONFIG-CLAUDE-001.md`(M), `Codex착지…독립검토_Claude.md`(??) — **전부 내 세션 문서**. **작업-트리 사본이 push된 커밋본(`9ed6df9`/`a25b0e2`, 둘 다 tip 조상)과 diff 0줄** = 이미 커밋·push됨, 손실 아님. dirty로 보이는 이유: 내 **개인 index 커밋**(GIT_INDEX_FILE)이 공유 index·HEAD를 안 건드리므로, 뒤처진 주 HEAD(ddb16ac) 기준으론 그 파일들이 수정/미추적으로 남는다.
- **`27c853b`의 정체**: 사용자가 본 그 SHA는 **고아 커밋**(어떤 브랜치도 안 가리킴 — `git branch --contains` 공집합). Gemini 접근성 커밋(`화면 접근성 상태 역할 분리…`)의 **대체된 쌍둥이**로, integration 라인의 판본은 `ddb16ac`(공통 부모 `1f8415d`). 사용자 측정 이후 주 HEAD가 27c853b→ddb16ac로 이동함.
- **왜 뒤처지나**: 아무도 공유 주 HEAD를 origin tip으로 전진시키지 않는다. 에이전트들은 각자 워크트리/개인-index push로 일하고, 주 HEAD는 명시적 checkout/reset 때만 움직여 ddb16ac에 방치됨. **결과: 주 워크트리에서 도구를 돌리는 사람은 11-behind 트리 + 내 3개 유사-dirty 파일을 본다** — 오늘 사용자가 틀린 것을 본 원인.

## 권고 — 이 구조에서 안전한 측정·커밋
커밋 쪽은 [[공유워크트리_개인index_커밋규칙]] R1~R5가 덮는다. **측정 쪽 규칙이 없었다.** 오늘 clean 고정-tip 워크트리(`C:/vw`)에서 잰 방식이 통했으므로 규칙화한다(그 문서에 R6로 추가 제안):
- **R6-a 주 워크트리에서 측정·검증하지 마라**: 공유 주 트리는 origin tip보다 뒤처지고, 남의 파일 + 개인-index 유사-dirty 파일을 이고 있어 **틀린 상태**를 보인다. `provenance.working_tree_clean=YES`가 아니면 결과를 신뢰하지 마라.
- **R6-b 전용 detached 워크트리를 origin tip 정확 SHA에 고정해 측정**: `git fetch` → `git -C <측정트리> checkout --detach <tip-SHA>` → `git -C <측정트리> status --porcelain`이 **빈 출력(dirty=0)** 확인 후 측정. 잰 **SHA를 결과에 명시**(tip은 세션 중 이동).
- **R6-c 짧은 경로·full checkout**: 실 파일이 필요한 시험(LAN 등)은 longpaths 짧은 경로(`C:/vw`)에서 full checkout. sparse는 collection 에러 유발.
- **R6-d 측정 워크트리 재사용**: `C:/vw` 하나를 재사용해 매번 `fetch`+`checkout --detach <tip>`로 갱신. 측정 트리를 늘리면 grep 오염·혼동만 커진다.
- **R6-e 정리 원칙**: 형제 워크트리 삭제 전 반드시 `dirty=0` 확인(이 재고 기준). `ahead>0` 브랜치는 워크트리만 제거하고 **브랜치 ref 보존**. 삭제는 소유자만.
