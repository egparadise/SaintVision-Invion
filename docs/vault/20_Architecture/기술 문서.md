# Saint Vision INV 기술 문서

## 1. 기술적 정의

INV는 이기종 Node가 자발적으로 제공한 자원을 논리 Resource Fabric으로 표현하고, Workload의 요구사항과 정책에 따라 실행 위치와 실행 방식을 결정하는 분산 Control Plane이다. Saint Vision은 이 Control Plane 위에 Web Portal, Dev Workspace, AI Operator와 MLOps 경험을 제공한다.

INV는 하드웨어 수준의 단일 시스템 이미지를 구현하지 않는다. 일반 프로세스가 다른 PC의 RAM을 로컬 메모리처럼 접근하게 하지 않으며, 여러 GPU의 VRAM을 자동으로 하나의 연속 메모리로 만들지 않는다. 대신 Framework가 지원하는 분산 계산과 모델 병렬 기능을 선택적으로 사용한다.

## 2. 전체 계층

| 계층 | 책임 | 대표 구현 후보 |
|---|---|---|
| Experience | Portal, Web IDE, Terminal, AI Operator | Web App, xterm.js, code-server 또는 OpenVSCode 검토 |
| API and Identity | 인증, 권한, API, WebSocket | OIDC, API Gateway, RBAC |
| Control Plane | Project, Workspace, ResourceGraph, Scheduler, RunGraph | 자체 서비스, PostgreSQL, Redis |
| Trust Plane | Policy, Approval, Secret, Audit, Evaluation | OPA 후보, Vault 계열, OpenTelemetry |
| Runtime | Container, Process, Ray, PyTorch, vLLM | Docker 또는 containerd, Runtime Adapter |
| Node | Capability, Heartbeat, 실행, 로그와 자원 제한 | INV Node Agent |
| Data | Dataset, Model, Artifact, Build Cache | S3 호환 저장소, Local Cache, 단계적 분산 Storage |
| Infrastructure | 기존 Windows와 Linux PC, GPU, NAS, LAN 또는 VPN | 5 Node 파일럿 |

## 3. Plane 분리

### Experience Plane

사용자가 Project와 Workspace를 만들고, Terminal과 IDE를 열며, Run 상태와 MLOps 결과를 확인하는 영역이다. Experience Plane은 Node의 관리자 Interface를 직접 노출하지 않는다.

### Control Plane

원하는 상태와 실제 상태를 조정한다. Node Registration, Resource Snapshot, Workload Validation, Lease, Placement Plan, RunGraph와 Metadata를 소유한다.

### Data Plane

Node에서 실제 Container, Process, Model Server와 Training Worker를 실행한다. 대용량 Dataset과 Artifact 전송도 Data Plane에서 수행한다. Control Plane Database를 통해 대용량 데이터가 흐르지 않게 한다.

### Trust Plane

Identity, Policy, Approval, Secret, Audit, Risk와 Evaluation을 횡단 관심사로 제공한다. 모든 실행 경로는 Trust Plane을 우회할 수 없어야 한다.

## 4. Node Agent

Node Agent는 기존 PC에 설치되는 작은 서비스다.

### 책임

- Node Bootstrap, 인증서 등록과 주기적 갱신
- OS, CPU, GPU, RAM, Disk, Network와 Runtime Capability 탐지
- Host 소유자가 허용한 자원 상한과 시간대 적용
- Heartbeat와 Resource Snapshot 전송
- Lease와 Fencing Token 검증
- Process 또는 Container 실행, 취소와 정리
- stdout, stderr, Metrics와 Artifact 수집
- Host 사용자 활동, 온도와 전력 Guard
- 비정상 Run과 잔여 자원 Reconciliation

### 비책임

- 최종 Placement 결정
- 사용자 Credential 장기 저장
- 정책의 임의 변경
- 다른 Node에 대한 직접 명령
- Control Plane 없이 새로운 Run 생성

## 5. Resource Model

자원은 세 층으로 구분한다.

1. **Capacity**: Node의 물리 총량
2. **Offer**: Host가 INV에 제공하기로 한 한도
3. **Lease**: 특정 Run이 제한된 시간 동안 예약한 자원

현재 실제 사용량은 Usage로 별도 측정한다. Capacity에서 Usage를 뺀 값만 보고 예약하면 동시 요청이 이중 할당될 수 있으므로, Scheduler는 Offer에서 활성 Lease를 뺀 값으로 예약 가능량을 계산한다.

GPU는 Device ID, Vendor, Model, VRAM, Compute Capability, Driver, Runtime Compatibility, MIG 또는 Partition 지원과 Topology를 보존한다. 논리 화면에서 합계를 제공하더라도 실제 Placement는 Device 단위다.

## 6. 실행 모드

| Mode | 설명 | 적합한 작업 |
|---|---|---|
| Single Node | 한 Node의 자원으로 실행 | Build, Test, 단일 GPU Inference |
| Task Parallel | 독립 작업을 여러 Node에 분산 | Batch 전처리, Hyperparameter Sweep |
| Request Routing | 완전한 Model Instance에 요청 분배 | 여러 소형 LLM Replica |
| Data Parallel | 같은 Model을 여러 Worker가 학습 | PyTorch Distributed Training |
| Tensor Parallel | Tensor 연산을 GPU 사이에 분할 | 고속 연결을 가진 다중 GPU |
| Pipeline Parallel | Model Layer를 Stage로 분할 | 단일 GPU에 들어가지 않는 Model |
| Hybrid | 위 방식을 조합 | 대형 Model 학습과 서빙 |

서로 다른 PC 사이의 Tensor Parallel은 Network Latency와 Bandwidth에 민감하다. 파일럿은 먼저 Benchmark를 수행하고, 성능이 불충분하면 Request Routing, Task Parallel 또는 Pipeline Parallel을 선택한다.

## 7. Scheduler

Scheduler는 Hard Constraint를 먼저 적용한 뒤 후보에 점수를 준다.

### Hard Constraint

- Node online, draining 또는 quarantined 여부
- OS와 CPU Architecture
- GPU Vendor, 최소 VRAM과 Runtime Compatibility
- CPU, RAM, Storage와 Network 최소량
- Dataset 접근 권한과 Mount 가능 여부
- Workspace Image와 Driver 호환성
- 사용자와 Project Policy
- Host 제공 시간과 현재 사용자 부하 한계
- Gang Scheduling에서 필요한 전체 Resource 동시 확보

### Score

개념적 Score는 다음 요소를 포함한다.

~~~text
score =
  data_locality_weight   * data_locality
+ resource_fit_weight    * resource_fit
+ network_weight         * network_quality
+ reliability_weight     * node_reliability
+ cache_weight           * image_and_data_cache_hit
- transfer_weight        * estimated_transfer_time
- host_load_weight       * host_interference
- thermal_weight         * thermal_risk
- cost_weight            * execution_cost
~~~

가중치는 Policy Version과 함께 기록한다. 동일 Snapshot과 Policy에서 같은 결과가 나오는 것이 Scheduler V1의 원칙이다.

### Explainability

Placement Plan은 선택 Node만 저장하지 않는다. 후보별 Hard Filter 결과, 점수 구성, 데이터 전송 예상량, 대안과 Policy Decision을 저장한다. 사용자는 inv explain으로 이를 확인한다.

## 8. RunGraph

기본 상태 흐름은 다음과 같다.

~~~text
requested
  -> validating
  -> awaiting_approval
  -> scheduled
  -> starting
  -> running
  -> verifying
  -> succeeded
~~~

어느 단계에서든 정책에 따라 failed, cancelled, timed_out 또는 lost로 이동할 수 있다. 재시도는 새로운 Attempt를 만들고 이전 Evidence를 보존한다. 외부 부수 효과가 있는 Task는 Idempotency Key와 Fencing Token이 없으면 자동 재시도하지 않는다.

## 9. Workspace와 Terminal

Workspace는 Project의 지속적인 파일, Toolchain, 설정과 Credential Reference를 가진다. 실제 실행 Node는 Scheduler가 바꿀 수 있다.

- Workspace Terminal: 격리된 Container 또는 VM 안에서 Bash, Zsh, PowerShell 7을 제공
- Node Terminal: 승인된 관리자만 특정 Node에 제한적으로 접근
- Terminal Transport: Browser xterm UI, 인증된 WebSocket, 서버 PTY
- File: Workspace Volume과 inv URI를 Mount
- Lifecycle: create, start, suspend, resume, archive와 delete

Windows 전용 Tool이 필요하면 Windows Workspace Profile을 제공하되, 동일한 Policy, Audit와 Secret 규칙을 적용한다.

## 10. Docker와 Container

Docker는 1급 기능이지만 Workspace에 Host Docker Socket을 그대로 Mount하지 않는다. 다음 중 하나를 선택한다.

- Rootless Docker 또는 BuildKit
- 별도 Build Service
- 격리된 Node의 Container Runtime API
- 제한된 Docker Command를 Tool Gateway가 대행

Image는 Tag뿐 아니라 Digest를 기록하며, Build Provenance, Source Commit, Dependency Lock과 Vulnerability Scan 결과를 Artifact로 연결한다.

## 11. Git

Repository는 Workspace의 기본 Source of Truth다. 각 Run은 가능한 경우 Commit SHA와 Working Tree 상태를 기록한다.

- 사용자별 SSH Key 또는 OAuth Credential은 Vault에 저장
- Project에 Remote, Default Branch와 보호 규칙 설정
- AI Agent의 Commit과 Push는 별도 Policy 적용
- Merge와 Release는 Review와 Test Evidence 연결
- 대형 Dataset과 Model은 Git에 직접 저장하지 않고 inv URI와 Version Metadata 사용

## 12. AI CLI Hub

AI CLI Hub는 특정 업체의 CLI를 재구현하지 않는다. 설치, 인증, 실행, 권한과 추적을 공통 Adapter로 감싼다.

Adapter 계약은 다음 기능을 가진다.

- Provider와 CLI Version 탐지
- 사용자 Credential Reference 연결
- Workspace별 설치와 Update Policy
- 허용 Tool, Network Destination과 File Scope
- Prompt와 Output의 민감정보 처리
- Token, 시간과 비용 Budget
- Process 종료, Timeout과 Audit
- Provider별 결과를 공통 Run과 Evidence에 연결

상용 CLI의 사용 조건, 배포 권한과 자동화 허용 범위는 Provider별로 검토해야 한다.

## 13. Storage

초기에는 모든 Disk를 즉시 하나의 분산 Filesystem으로 만들지 않는다.

### 1단계

S3 호환 중앙 Object Storage와 Node Local Cache를 사용한다. Dataset, Model, Artifact에는 inv URI를 부여하고 실제 DataLocation을 Metadata로 관리한다.

### 2단계

복제, Checksum, Cache Eviction, Bandwidth 제한과 장애 복구를 추가한다.

### 3단계

필요성이 검증되면 Ceph, SeaweedFS 또는 다른 분산 Storage Adapter를 평가한다. 기존 사용자 Folder는 명시적 제공 없이 자동 포함하지 않는다.

## 14. Network

- 같은 LAN의 1GbE는 일반 Build와 독립 Task에 사용할 수 있다.
- 대형 Dataset과 다중 Node GPU에는 10GbE 이상을 우선 검토한다.
- 원격 Node는 WireGuard 또는 Tailscale 계열 Overlay를 사용할 수 있지만 Latency를 ResourceGraph에 반영한다.
- Control Traffic과 Data Transfer를 논리적으로 분리하고 mTLS를 사용한다.
- Bandwidth 예약, 전송 Checksum과 재개 가능한 Copy를 지원한다.

## 15. 신뢰성과 복구

- Heartbeat와 Lease TTL로 Node 손실 탐지
- Fencing Token으로 이전 실행의 늦은 명령 차단
- 상태 변경 Event의 중복 제거
- RunGraph Checkpoint와 Attempt 기록
- Immutable Artifact와 Checksum
- Control Plane Database Backup과 Restore Drill
- Quarantine 상태로 이상 Node의 새 작업 배치 차단
- Kill Switch로 Project, Workspace, Provider 또는 Cluster 범위 중지

## 16. 보안

- OIDC와 MFA, Project와 Node 범위 RBAC
- Node Agent와 Control Plane 사이 mTLS
- Workspace별 Filesystem, Network, Process와 Resource 격리
- L0 관찰, L1 제한 변경, L2 중요 변경, L3 파괴적 또는 민감 명령 등급
- Secret Vault와 실행 시 단기 주입
- AI Agent의 Tool Gateway 강제
- Prompt Injection을 외부 데이터의 지시 권한으로 해석하지 않음
- 모든 Policy Decision, Approval과 ToolInvocation의 감사 기록

상세 기준은 [[보안 평가 운영 가이드]]를 따른다.

## 17. 관찰성

모든 요청에 Correlation ID, Workload ID, Run ID, Attempt ID, Workspace ID와 Node ID를 전파한다.

필수 Metrics는 Node 가용성, Lease 충돌, Queue 시간, Schedule 시간, Startup 시간, Run 성공률, 취소 지연, GPU와 VRAM 사용량, 데이터 전송량, Cache Hit, Policy Deny와 Secret Redaction 수다.

OpenTelemetry Collector에서 민감정보를 마스킹하고 Metrics, Logs와 Traces를 Backend별로 분리한다.

## 18. 기술 선택 원칙

- Ray는 AI Task Runtime 후보이며 전체 INV Scheduler와 Policy를 대체하지 않는다.
- vLLM은 Model Serving 후보이며 범용 Workload Runtime이 아니다.
- PyTorch Distributed와 NCCL은 지원되는 GPU와 Network에서만 사용한다.
- Kubernetes와 Slurm은 후속 Cluster Adapter이며 MVP의 전제 조건이 아니다.
- Web IDE는 Source License와 Extension Marketplace 조건을 함께 검토한다.
- 외부 표준의 실험 상태 필드는 내부 안정 Schema 뒤에 둔다.

## 19. 배포 Topology

파일럿은 다음 구성을 권장한다.

- Control Node: API, Scheduler, RunGraph, Policy, PostgreSQL, Redis와 Telemetry
- Storage Node 또는 NAS: Object Storage와 Backup
- Worker Node 5대: INV Agent, Container Runtime, GPU Runtime와 Local Cache
- 사용자 Browser: Portal, IDE와 Terminal

Control Node가 Worker 중 하나와 겸용일 수 있지만, 장애 시험과 Resource Offer에서 Control Plane에 필요한 최소 자원을 예약한다.
