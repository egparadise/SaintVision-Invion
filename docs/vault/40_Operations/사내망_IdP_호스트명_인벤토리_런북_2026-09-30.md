# 사내망 IdP·호스트명·인벤토리 런북 (카드 152, 2026-09-30)

## 0. 결론

세 가지를 세웠고, 세 가지 모두 **주장이 아니라 실행으로 확인**했다.

| | 상태 | 근거 |
|---|---|---|
| 사내 IdP | **https로 동작** — `https://idp.sv.lan` (P-256 leaf), realm `saintvision`, public client(PKCE S256), API audience, 사용자 2명 | 운영 IdP가 발급한 실제 토큰이 `services/control-plane/src/inv/identity.py`의 `AccessTokens.verify`를 **통과**했다 — `providerRole=production` 증거(§4-4). 평문 listener는 **공개하지 않는다**(§3-2) |
| 호스트명 | **확정** — `cp` · `portal` · `idp` · `node1`~`node5` (모두 `.sv.lan`) | §1. 카드 150에 전달했다. **이름이 정해진 것과 인증서가 있는 것은 다르다** — 지금 발급된 leaf는 두 개뿐이다(§1 표) |
| 인벤토리 | **BLOCKED (invalid 0)** — 실측 3대 + 자리표시 2대 | `tools/s01_readiness_preflight.py` 실행 결과 `inventory-values-missing`, `nodeCount=5 missingFieldCount=74 invalidFieldCount=0` (§7-3) |

**issuer scheme 불일치는 해소됐다.** v1.1 시점에 남아 있던 단 하나의 미충족 — `AccessTokens.__init__`이 `https://`가 아닌 issuer를 bundle을 읽기도 전에 거부하는 것 — 은 카드 150이 ECDSA P-256 leaf를 재발급한 뒤 §6의 여섯 단계를 실제로 실행해 닫았다. v1.0이 이것을 "한 줄"이라고 적은 것은 틀렸고, 실제로는 여섯 단계였다. **이제 CP identity 5값이 전부 확정값이고, 기동을 막는 것은 CP 자체의 미배포뿐이다.**

남은 사용자 작업은 **hosts 적용과 신뢰 root 반입**이다(§2·§5-3). 그것 없이는 이 PC와 브라우저가 `idp.sv.lan`을 해석하거나 신뢰하지 못한다 — 서버는 이미 올바르다.

## 1. 호스트명 결정

| 이름 | 무엇 | 왜 이 이름인가 |
|---|---|---|
| `cp.sv.lan` | control plane | 역할 이름. 호스트가 바뀌어도 이름은 남는다 |
| `portal.sv.lan` | 웹 portal | 사용자가 주소창에 치는 유일한 이름 |
| `idp.sv.lan` | Keycloak | 토큰의 `iss`에 박히므로 **가장 바꾸기 어려운 이름**이다. 장비 이름이 아니라 서비스 이름이어야 하는 이유가 여기에 있다 |
| `node1.sv.lan` ~ `node5.sv.lan` | 물리 노드 5대 | 번호는 **사설 IPv4 오름차순**으로 고정한다. 규칙을 적어야 나중에 누구든 같은 배정을 다시 만들 수 있다 |

**`.sv.lan`을 쓰는 이유**: `.local`은 mDNS가 가로채고, 실재하는 공개 TLD를 사내에 쓰면 어느 날 공개 DNS와 충돌한다. `.lan`은 그 두 사고를 모두 피한다.

**번호 배정** — IPv4 오름차순. 지금 등록된 Ubuntu 3대가 `node1`·`node2`·`node3`을 가져가고 `node4`(미등록 Ubuntu worker)와 `node5`(CP 겸임 Node)가 예약으로 남는다. 이름과 실제 IP의 대응은 저장소 문서에 적지 않는다(§2).

**카드 150 PKI의 실제 상태** — v1.0은 "8개 이름 전부가 SAN 대상"이라고 적었다. 그것은 요청이지 사실이 아니었다. 실제로 발급된 것은 다음뿐이다.

| leaf | SAN | 상태 |
|---|---|---|
| `cp.sv.lan` | `cp.sv.lan` + CP 호스트 주소 하나 | 발급됨. **`portal`·`node1`~`node5`는 이 leaf에 없다** |
| `idp.sv.lan` | `idp.sv.lan` + IdP 노드의 주소 | **ECDSA P-256으로 재발급돼 적용 완료**. 만료 2026-12-28. 처음 발급된 Ed25519 leaf는 브라우저가 거부하므로 쓰지 않았다 |
| `portal.sv.lan`, `node1`~`node5` | — | **미발급.** 필요해지는 시점에 카드 150에 요청해야 한다 |

즉 이름을 정한 것과 인증서가 있는 것은 다르고, 이 문서는 둘을 구분해 적는다. `portal`이 필요해지는 시점(카드 153)에 그 leaf를 카드 150에 요청해야 한다.

## 2. hosts 적용 (사용자 실행)

이 PC의 hosts 수정은 관리자 권한, 노드 `/etc/hosts`는 sudo가 필요하다. **노드 sudo 비밀번호가 없으므로 명령만 만들고 실행하지 않았다.** 정확한 명령은 코디네이터에게 따로 전달했다. 형태만 적는다 — 실제 IP는 저장소 문서에 남기지 않는다(5-node inventory의 IP를 문서에서 제거한 기존 결정을 따른다).

- **Windows(관리자 PowerShell)**: 시스템 hosts 파일에 8줄을 **중복 없이** 덧붙이고 DNS 캐시를 비운다.
- **각 노드(sudo)**: `/etc/hosts`에 같은 8줄을 덧붙인다. 덧붙이기 전에 같은 이름이 있는지 검사하는 형태로 만들었으므로 **두 번 실행해도 줄이 늘지 않는다**.
- **노드 하나에 한 줄 더**: 세 노드 중 하나는 로그인 사용자가 `docker` 그룹에 없어 컨테이너를 다룰 수 없다. `usermod -aG docker`와 재로그인이 필요하다. 그 노드에 서비스를 올릴 계획이 없다면 하지 않아도 된다.

DNS 서버를 따로 세우지 않고 hosts로 가는 이유: 이름이 8개뿐이고, 바뀌는 일이 드물며, 사내 DNS를 세우면 그 자체가 또 하나의 가용성 의존이 된다. 노드가 늘면 그때 다시 본다.

## 3. IdP 구축

### 3-1. 무엇이 떠 있는가

| | 값 |
|---|---|
| 스크립트 | `deploy/intranet/idp-up.sh` (기동) · `deploy/intranet/idp-realm.sh` (realm 설정) |
| Keycloak | `quay.io/keycloak/keycloak@sha256:4ee8200b…` = 26.4.7, `start --hostname=https://idp.sv.lan --hostname-strict=true --https-port=8443` + leaf·key 경로 |
| 노출 | **443(https)만 LAN에 공개.** 평문 listener는 container 안에만 있고 어디에도 publish하지 않는다(§3-2) |
| 인증서 | 노드 `~/.sv-idp/certs/` — chain `0444`, **private key `0400`**. 사본은 노드와 operator 워크스페이스 **두 곳**이고 각각의 폐기·교체 절차는 §5-3에 있다 |
| DB | `postgres@sha256:ab838056…` = 16.10, **별 container**, 포트 미공개, 전용 volume |
| 네트워크 | 전용 bridge. DB는 Keycloak에게만 보인다 |
| 재시작 | 둘 다 `unless-stopped` |

**digest로 고정한 이유**: tag는 움직인다. IdP는 움직이는 이미지를 받아들일 마지막 자리다. digest 옆에 해당 tag를 주석으로 적어 사람이 무엇을 보고 있는지 알 수 있게 했다.

**비밀**: 노드의 `0600` 파일에서만 생성·소비한다. 저장소·PR·화면에 값이 나온 적 없다. 기동 스크립트는 **이미 있는 비밀을 다시 만들지 않는다** — 다시 만들면 Keycloak이 자기 DB에서 잠긴다.

### 3-2. 노출 경계

v1.0의 기동 스크립트는 8080을 **모든 인터페이스에** 공개했다. TLS 종단이 없는 상태에서 그것은 **평문 로그인 폼과 평문 토큰 endpoint를 LAN에 올려 둔다**는 뜻이었다. 지금의 경계는 이렇다.

| | 값 | 왜 |
|---|---|---|
| LAN에 열린 것 | **443(https)뿐** | 브라우저와 CP가 쓰는 유일한 경로다 |
| 평문 listener | container 안에만, **publish 안 함** | `kcadm`이 `docker exec`로 `localhost:8080`을 쓰기 위해 살려 둔다. LAN의 어떤 클라이언트도 도달할 수 없으므로 realm `sslRequired`는 `external`로 충분하다 — `all`은 이 관리 경로를 막으면서 아무것도 더 얻지 못한다 |
| `hostname-strict` | `true` | `false`면 다른 이름으로 들어온 요청의 Host가 Keycloak이 발행하는 URL에 그대로 반영된다 |
| portal redirect·origin | `https://portal.sv.lan` + **loopback만** | `http://portal.sv.lan`은 authorization code를 LAN 평문으로 흘린다. loopback은 네트워크를 나가지 않으므로 native-app flow에서 허용되는 그 경계다 |

TLS 없이 기동하면(인증서 경로를 주지 않으면) 스크립트는 평문을 **loopback에만** bind한다. 확인: 이 PC에서 노드 8080으로 HTTP 요청이 `http=000`으로 닫힌다(§8).

### 3-3. realm 설정과 그 이유

`deploy/intranet/idp-realm.sh`는 **빈 Keycloak에서 realm 전체를 만들어 낼 수 있는** 설정기다(§8에서 실제로 그렇게 했다). 각 설정은 취향이 아니라 `AccessTokens.verify`가 없으면 거부하는 것들이다.

| 설정 | 없으면 |
|---|---|
| client `sv-api` (audience 전용, 로그인 불가) | `aud`에 넣을 이름이 없다 |
| client `sv-portal` = public + PKCE `S256` | public client에서 PKCE가 없으면 authorization code 가로채기가 성립한다 |
| direct access grant **끄기**(매 실행 강제) | public client의 password grant는 자격증명 깔때기다 |
| RFC 9068 token type | header `typ`가 `JWT`로 나오고 verifier는 `at+jwt`만 받는다 |
| audience mapper → `aud: "sv-api"` | audience 검사가 실패한다 |
| 기본 client scope `roles` **제거** | `aud`가 `["sv-api","account"]` 배열이 되고, verifier가 쓰는 `strict_aud`는 **배열을 금지한다** |
| hardcoded claim `client_id` | verifier의 필수 claim 목록에 `client_id`가 있는데 Keycloak은 `azp`만 낸다 |
| client scope `inv.api` | verifier는 scope에 `inv.api`가 없는 토큰을 거부한다 |
| 사용자 profile을 채우고 required action 비우기 | `VERIFY_PROFILE`이 걸려 모든 grant가 *"Account is not fully set up"* 으로 실패한다 — realm 고장처럼 읽히지만 원인은 빠진 성(姓)이다 |

마지막 두 줄은 **빈 Keycloak에 스크립트를 돌려 보고서야 나왔다.** 기존 realm만 고쳤다면 둘 다 놓쳤을 것이다.

### 3-4. drift — 설정한 것과 아직 그렇다는 것은 다르다

v1.0의 설정기는 **없으면 만들기**만 했다. 그러면 누가 관리 콘솔에서 TTL을 늘리거나 direct grant를 켜도 객체는 전부 제자리에 있으므로 스크립트는 계속 성공한다. 두 가지를 바꿨다.

1. **매 실행 정본을 다시 적용한다** — realm의 `accessTokenLifespan`, API client의 로그인 차단 네 플래그, portal의 플래그(implicit 포함), audience·`client_id` mapper의 `config`까지. mapper가 access token에 쓰기를 멈춘 경우도 "mapper는 있음"이므로 create-if-missing은 잡지 못한다.
2. **마지막에 live 설정을 되읽어 판정한다** — `tools/check_idp_realm_config.py`가 realm·두 client·default scope를 받아 위 표 전부와 "redirect·origin은 https 또는 loopback"을 검사하고, 어긋나면 **exit 1**로 스크립트를 실패시킨다. 검사기를 찾지 못하면 성공을 보고하지 않고 exit 2다.

카드 209부터 mapper/reference만 운영 중 realm에 재적용할 때는
`SV_IDP_APPLY_MODE=fresh-auth-only`를 쓴다. 이 모드는 사용자 자격 파일을 읽거나 사용자·realm·
client·scope 일반 설정을 변경하지 않고, `fresh-auth-time`·`fresh-auth-amr`와 browser flow의
password/OTP execution reference만 정본으로 만든 뒤 같은 live checker를 실행한다. 전제 realm,
client, scope가 없으면 만들지 않고 exit 2다. 실행 전 관련 mapper/execution JSON을 operator-private
경로에 0600으로 백업하고, rollback은 pre-apply에 없던 객체만 삭제하거나 기존 객체만 exact JSON으로
복원한 뒤 checker를 재실행한다. 사용자 OTP 등록과 실제 token claim 관측은 이 절차에 포함되지 않는다.

되돌리면 실패하는 시험은 `tests/core/test_check_idp_realm_config.py`가 **한 번에 하나씩 완화해** 전부 보고되는지 본다(26가지). 살아 있는 realm에서도 실제로 확인했다(§8).

### 3-5. 비밀은 argv에도 container config에도 남지 않는다

명령줄의 비밀번호는 호스트에서 `ps`를 볼 수 있는 누구나 읽을 수 있고, `docker run -e NAME=$SECRET`은 **거기에 더해 `docker inspect`에 영구히 남긴다**. 파일 권한을 나중에 조이는 것으로는 어느 쪽도 고쳐지지 않는다.

| 무엇 | 전달 방법 |
|---|---|
| PostgreSQL 비밀번호 | `POSTGRES_PASSWORD_FILE` — 값이 아니라 경로만 env에 있다 |
| Keycloak DB·bootstrap admin | `0400` 파일을 mount하고, **launcher가 container 안에서 source**한 뒤 `kc.sh`를 exec한다. 값은 프로세스 안에만 있고 `Config.Env`에는 없다 |
| kcadm 로그인 | container 안에서 같은 파일을 읽어 `KC_CLI_PASSWORD`로 넘긴다. kcadm의 대화형 prompt는 TTY가 없으면 *"Console is not active"* 로 거부하므로 쓸 수 없다 |
| 사용자 비밀번호 재설정 | `users/{id}/reset-password`에 **stdin JSON**. `set-password --new-password`는 container의 프로세스 목록에 값을 남긴다 |

**container마다 필요한 파일만 준다.** 처음 판은 secrets 디렉터리 **전체**를 두 container에 mount했다. 그러면 데이터베이스 container가 Keycloak의 bootstrap admin 비밀번호까지 읽을 수 있다 — 쓸 일이 없는 자격증명이 쓸 일이 없는 곳에서 읽히면 그것만으로 노출 면적이 넓어진다. 지금은 파일 단위 read-only bind다.

| container | 보이는 것 |
|---|---|
| PostgreSQL | `db-password` **하나뿐** |
| Keycloak | `keycloak.env` + launcher (+ 인증서 디렉터리) |

**이 모드들은 uid가 맞아떨어지는 데 의존한다.** 파일은 호스트 로그인 사용자(이 노드에서 uid 1000)의 소유이고 Keycloak 이미지가 uid 1000으로 돌기 때문에 container가 **소유자로서** 읽는다. PostgreSQL 이미지는 root로 시작해 나중에 권한을 내리므로 모드와 무관하게 root가 먼저 읽는다. 로그인 사용자가 uid 1000이 아닌 호스트에서는 Keycloak이 자기 비밀을 읽지 못해 **기동에 실패한다** — 조용히 넘어가지는 않지만 원인이 한눈에 보이지 않는다. 그때 고칠 것은 **모드를 느슨하게 하는 것이 아니라 소유권을 맞추는 것**이다.

실측(§8): 두 container의 `Config.Env`에 비밀 값 **0건**(이름과 파일 경로만), `.Mounts`는 DB가 **password 파일 1개 + 데이터 volume**뿐이고 **`keycloak.env`는 DB 안에서 보이지 않는다**.

**되돌리면 실패하는 시험**: `tests/core/test_idp_scripts_keep_secrets_out_of_argv.py`. 처음 판은 **flag 표기를 정규식으로 맞췄고**, 독립 검토가 그것을 지나가는 다섯 가지를 찾았다 — 따옴표 붙은 `-e "NAME=$X"`, `--env K=V`, `--env=K=V`, `kcadm -s value="$X"`, 소문자 `$password`. 그 위에 두 가지가 더 살아남았다(뒤따르는 `chmod 444`가 앞의 `chmod 400`을 되돌리는 것, `-s credentials=[…]` 안에 숨은 비밀). 새 판을 증명하는 중에 **제가 만든 여덟 번째**도 나왔다 — 이 스크립트는 kcadm을 **wrapper 함수**로 부르므로 문자열 이름에만 걸린 검사는 그 전부를 놓친다.

**표기를 쫓는 것이 애초에 틀린 모양이었다.** 지금 규칙은 표기가 아니라 **shell 확장**에 관한 것이다 — docker나 kcadm에 닿는 명령(함수 정의를 읽어 찾아낸 wrapper 포함)에서 **호스트 shell이 확장하는** 비밀 변수는 누출이다. 차이를 만드는 것은 **단일 인용부호**이고, 그 상태를 **줄을 넘어가며** 추적한다(admin 로그인의 `sh -c` 본문이 여러 줄이라, 줄 단위로 보면 올바른 구성을 누출로 판정한다). heredoc 본문은 건너뛴다 — 비밀을 stdin으로 보내는 것이 여기서는 해결이지 누출이 아니다.

여덟 가지를 **실제 스크립트에 하나씩 주입해 전부 잡히는 것**을 확인했다. 면제 이름(`$SECRETS`는 경로, `$TOKEN_LIFESPAN`은 초)은 이유와 함께 하나씩 열거하고 시험으로 고정해, 면제를 늘리는 것이 눈에 보이는 변경이 되게 했다.

## 4. CP identity 5값

### 4-1. 값

| 설정 | 값 |
|---|---|
| `tenant_id` | **사용자 확정 필요**. 현재 후보는 카드 150 fresh pilot state의 `tenantId`이며, 값은 operator-private 파일에만 둔다 |
| `issuer` | **`https://idp.sv.lan/realms/saintvision`** — 지금 IdP가 실제로 이 값으로 발급한다(§4-2). discovery 문서의 `issuer`·`jwks_uri`도 이 이름이다 |
| `audience` | `sv-api` |
| `client_ids` | `["sv-portal"]` |
| `jwks_file` | CP 호스트의 절대 경로. §5의 재발급이 이 경로를 쓴다. 지금 만들어진 bundle의 `issuer`는 위 값과 정확히 같다 |

### 4-2. 지금 발급되는 토큰 (실측)

`typ=at+jwt` · `alg=RS256` · header key가 정확히 `alg`·`kid`·`typ` · `aud="sv-api"`(**문자열**) · `client_id=sv-portal` · scope에 `inv.api` 포함 · 필수 claim 7종 전부 존재 · 수명 300초 · **`iss=https://idp.sv.lan/realms/saintvision`**. `kid`는 신뢰 bundle의 키와 일치한다.

이 토큰은 **검증된 https 요청으로 발급받았다** — 노드에서 이름을 그 노드 자신의 주소로 고정하고 사내 root로 chain을 검증한 `POST`다. 비밀번호는 노드를 떠나지 않았다.

### 4-3. 전환 뒤 상태를 미리 측정했다

"바꾸면 될 것"이라고 적지 않기 위해, 같은 digest의 Keycloak을 `https` issuer로 **임시 container**에 띄우고 `deploy/intranet/idp-realm.sh`로 같은 realm을 만든 뒤 토큰을 발급해, 이 PC에서 `tools/make_oidc_trust_bundle.py`로 bundle을 만들고 **실제 `AccessTokens.verify`에 통과**시켰다.

- `VERIFIED` — principal이 나오고 `expires_at`이 돌아왔다.
- 같은 verifier가 **payload 한 글자를 바꾼 토큰은 `AUTH-0050`으로 거부**했다.
- 임시 container와 그 자격증명은 삭제했다. 운영 realm에는 같은 스크립트를 다시 돌려 profile·required action 수정만 반영했고, 재실행에서 새로 만들어진 것은 **없다**(멱등).

즉 **토큰 형태에 남은 차이는 없고**, issuer 문자열이 바뀐 상태의 통과는 이미 확인했다. 남은 것은 그 문자열을 실제로 바꿀 수 있게 하는 §6의 여섯 단계다.

### 4-4. 이 측정은 문장이 아니라 증거로 남는다

런북의 "통과했다"는 문장은 시험 통과와 실제 측정을 구분하지 못한다. `tools/collect_oidc_identity_evidence.py`가 그 구분을 만든다 — code SHA·관측 시각·issuer mode·**어느 provider였는지**·세 관측의 판정·임시물 정리 여부를 담은 redacted 증거를 쓴다. 토큰·사용자·키 자체는 들어가지 않고 `kid`는 SHA-256으로만 남는다.

| 관측 | 무엇 |
|---|---|
| `bundleAccepted` | provider의 JWKS가 verifier가 적재하는 bundle이 됐다 |
| `liveTokenVerified` | provider가 실제 발급한 토큰이 `verify`를 통과했다 |
| `tamperedTokenRefused` | **같은** verifier가 한 글자 바꾼 토큰을 거부했다 |

세 번째가 두 번째만큼 중요하다. 전부 받아들이는 verifier도 두 번째를 통과시키므로, 거부를 측정하지 않은 수용 측정은 아무것도 측정하지 않는다. `providerRole`이 `production`인지 `cutover-rehearsal`인지 반드시 기록되며, **`http` issuer로는 PASS를 쓸 수 없다**(verifier가 애초에 거부하므로 그런 PASS는 제품과 모순이다). 증거는 `docs/vault/30_Development/Evidence/oidc-identity/`에 있고 **세 건**이다.

| 증거 | provider | issuer | verdict |
|---|---|---|---|
| `oidc-identity-production-http-20260930` | `production` | `http` | `NOT_OBSERVED` — 전환 전 상태 |
| `oidc-identity-cutover-rehearsal-20260930` | `cutover-rehearsal` | `https` | `PASS` — 임시 instance 예행 |
| **`oidc-identity-production-https-20260930`** | **`production`** | **`https`** | **`PASS`** — 전환 후 운영 IdP |
| **`oidc-identity-production-https-bound-20260930`** | **`production`** | **`https`** | **`PASS`** — schema `:2`, `jwksTransport=out-of-band-file`을 명시 |

다 남기는 이유: 예행의 PASS는 사용자가 로그인할 provider에 대한 주장이 아니고, 전환 전의 `NOT_OBSERVED`는 지워야 할 실패가 아니라 그 시점의 사실이다. 나란히 두면 무엇이 언제 바뀌었는지가 파일 이름만으로 읽힌다.

**이 증거가 말하지 않는 것도 적어 둔다.** 앞의 세 건은 JWKS를 **파일로** 받았으므로 그 키가 어떻게 전달됐는지에 대해 아무것도 말하지 않는다 — 전송을 검증한 것은 §8의 https 확인과 재발급 실행이며, 이 파일들을 그 증거로 읽어서는 안 된다. 그것이 독립 검토가 지적한 지점이고, 이제 수집기가 `jwksTransport`를 **필수로** 기록한다: `out-of-band-file`(전송에 대해 침묵) 또는 `verified-https`(같은 origin에서 가져왔고 **신뢰 anchor의 SHA-256**을 함께 남긴다). 후자는 anchor 없이는 기록될 수 없다.

**`SSL_CERT_FILE`은 pinning이 아니다.** 어떤 CA가 그 이름을 보증할 수 있는지를 정하는 **신뢰 anchor**이고, 어떤 인증서가 나타나야 하는지를 고정하지 않는다. anchor의 해시를 남기는 것은 anchor를 식별 가능하게 하는 일이며 leaf를 고정하는 일이 아니다. 이 문서의 이전 판이 그 둘을 구분하지 않고 적었다.

## 5. 신뢰 bundle과 재발급

`AccessTokens`는 검증 시점에 IdP를 부르지 않는다. 그렇게 하면 IdP의 가용성이 모든 요청의 의존이 되고 그 DNS가 신뢰 경계가 된다. 대신 운영자가 준 **파일**을 읽고, 그 파일이 규격에 맞지 않으면 **기동을 거부한다**. `tools/make_oidc_trust_bundle.py`는 provider JWKS를 그 파일로 바꾸되 **verifier가 거부할 것은 쓰지 않는다**.

- 최상위 키가 정확히 `issuer`·`expiresAt`·`keys`, `expiresAt`은 정수이며 **최대 7일 뒤**, 키 1~8개, `kty=RSA`·`alg=RS256`·`use=sig`, `kid`는 1~128자이고 고유, 모듈러스 2048~4096비트.
- **private 성분이 있는 키는 벗겨 내지 않고 거부한다** — 신뢰 bundle에 개인키가 닿은 것은 형식 문제가 아니라 사고다.
- 서명용이 아닌 키(Keycloak이 함께 내는 암호화 키 등)는 버리고 **버린 개수를 보고한다**.
- `issuer`가 `https://`가 아니면 거부한다. verifier가 그렇게 하므로 **기동이 아니라 터미널에서 먼저 실패하는 편이 낫다**.
- 파일은 `0644`로 쓰고 65536바이트를 넘으면 쓰지 않는다 — 읽는 쪽이 group/other 쓰기 권한과 크기를 검사한다.
- **`--jwks-url`은 issuer에 결속된다** — https, `--issuer`와 같은 origin, userinfo·fragment 금지, **origin을 벗어나는 redirect 거부**, 응답 본문 상한. 이 결속이 없으면 bundle이 "아무 데서나 가져온 키에 정본 issuer를 찍는" 도구가 되고, 만들어진 파일은 완전히 정상으로 보인다. TLS 전 점검은 SSH 터널로 JWKS를 내려받아 `--jwks-file`로 준다.

**재발급은 일 1회다.** `deploy/intranet/reissue-oidc-trust-bundle.sh`와 `deploy/intranet/sv-oidc-trust-bundle.timer`. 7일 만료에 주 1회 작업을 걸면 **한 번의 실패가 곧 장애**다. 매일 돌리면 알아차릴 시간이 6일 남는다. 스크립트는 임시 파일에 먼저 쓰고 다시 읽어 검증한 뒤에만 자리를 바꾸므로, **실패해도 기존 bundle은 그대로다**(§8에서 실제로 확인했다).

### 5-3. 인증서와 신뢰 bundle 경로

**서버 쪽(노드)** — `~/.sv-idp/certs/`

| 파일 | 권한 | 무엇 |
|---|---|---|
| `server-chain.pem` | `0444` | leaf + issuing CA. Keycloak의 `--https-certificate-file` |
| `server-key.pem` | **`0400`** | service private key. 서비스가 쓰는 유일한 사본이며 container에는 read-only mount로만 보인다 |
| `trust-chain.pem` | `0444` | issuing CA + root. 검증하는 쪽이 쓴다 |

leaf는 **ECDSA P-256**, SAN은 `idp.sv.lan`과 노드 주소, 만료 2026-12-28이다.

#### service private key는 사본이 둘이다

v1.2의 이 절은 "노드 안에만 있다"고 적고 바로 다음 문장에서 operator 원본을 언급했다. **두 문장이 모순이었다** — 실제로는 사본이 둘이고, 하나를 없는 것처럼 적으면 폐기 절차가 생기지 않는다. 정확히 적는다.

| 사본 | 어디 | 왜 남겨 두는가 | 폐기·교체 |
|---|---|---|---|
| **서비스 사본** | 노드 `~/.sv-idp/certs/server-key.pem`, `0400`, 소유자만 읽음 | Keycloak이 TLS handshake에 쓴다 | leaf 교체 시 새 key로 덮어쓰고 컨테이너를 재기동한다. 노드를 폐기할 때는 이 파일을 지우는 것으로 끝나지 않는다 — 디스크 폐기 절차를 따른다 |
| **operator 원본** | 카드 150의 operator-private 작업 디렉터리(untracked), 이 PC | **재발급의 입력이다.** 지우면 같은 key로 leaf를 다시 낼 수 없고, CA를 다시 꺼내 새 key부터 만들어야 한다 | 교체 주기에 새 key/leaf를 발급한 뒤 **이전 세대를 지운다**. 세대를 쌓아 두지 않는다 |

**따라서 "노드 안에만 있다"는 서술은 철회한다.** 맞는 서술은 이것이다 — service key는 **노드와 operator 워크스페이스 두 곳에만** 있고, 저장소·PR·코멘트·CI에는 없으며, 그 두 곳 밖으로 사본을 만들지 않는다. 노드로는 SSH로 한 번 전달했고 그 뒤 추가 전달이 없다.

**교체(rotation)** — leaf 만료가 2026-12-28이므로 그 전에 한 번 돌아야 한다. 순서는 §6과 같고, 1단계만 카드 150에 요청하면 된다. 교체 뒤에는 **§4-4의 production 증거를 다시 남긴다** — 새 key로도 verifier가 토큰을 받아들이는지는 측정해야 아는 일이고, 증거 파일 이름에 날짜가 있으므로 이전 것을 지우지 않는다.

**유출이 의심되면** key 폐기만으로는 부족하다. 카드 150의 CA metadata가 긴급 조치를 `replace-trust-bundle-and-leaf`로 적어 두었으므로 leaf와 신뢰 bundle을 함께 바꾸고, CRL 배포가 강제되지 않는 구성이라는 점을 전제로 **이전 leaf를 신뢰하는 쪽이 남지 않게** 하는 것이 실제 조치다.

**클라이언트 쪽(이 PC와 CP 호스트)** — 사내 root를 신뢰해야 한다. 세 소비자가 각각 다른 경로를 본다.

| 소비자 | 어떻게 신뢰시키는가 |
|---|---|
| Python 도구(`tools/make_oidc_trust_bundle.py`, 재발급 스크립트) | `SSL_CERT_FILE`을 `trust-chain.pem`의 절대 경로로 지정한다. `urllib`이 만드는 기본 SSL context가 이 변수를 읽는다. **이것은 신뢰 anchor 지정이고 pinning이 아니다** — 그 CA가 보증한 leaf라면 무엇이든 받아들인다 |
| `curl` (Linux/OpenSSL) | `--cacert <trust-chain.pem>`. **Windows의 curl은 schannel이라 `--cacert`가 이 경우 동작하지 않는다**(`CERT_TRUST_REVOCATION_STATUS_UNKNOWN`) — Windows에서는 root를 신뢰 저장소에 넣는 쪽을 쓴다 |
| 브라우저(Windows) | root 인증서를 **신뢰할 수 있는 루트 인증 기관**에 반입한다. 관리자 권한이 필요해 명령만 만들어 전달했다(§2) |

CP 호스트에서 `deploy/intranet/sv-oidc-trust-bundle.service`가 재발급을 돌릴 때도 같은 `SSL_CERT_FILE`이 필요하다. 그 값이 없으면 스크립트는 **조용히 넘어가지 않고 exit 2로 실패**한다 — 신뢰를 확인하지 못한 fetch로 bundle을 만드는 것보다 낫다.

## 6. TLS 전환 (실행 완료)

"한 줄"이 아니었다. 여섯 단계였고, 여섯 모두 실행했다.

| # | 단계 | 결과 |
|---|---|---|
| 1 | `idp.sv.lan` leaf를 브라우저가 받아들이는 키 종류로 발급 | **완료**(카드 150) — ECDSA P-256, SAN `idp.sv.lan` + 노드 주소 |
| 2 | 노드에 leaf·key 설치 | **완료** — `0400` key, 노드 밖으로 나가지 않음. key와 leaf가 같은 쌍임을 공개 부분 해시 비교로 확인 |
| 3 | Keycloak을 `--hostname=https://idp.sv.lan`·strict·`--https-port=8443`(호스트 443)으로 재기동, realm `sslRequired=external` | **완료** — 평문은 publish하지 않음 |
| 4 | portal redirect·origin을 https + loopback으로 | **완료** — read-back 검사가 매 실행 확인 |
| 5 | 재발급 스크립트를 새 issuer로 | **완료** — https로 2회, 제자리 교체 |
| 6 | `--provider-role production` 증거 | **완료 — `PASS`** |

**세 곳(IdP hostname · bundle `issuer` · CP `identity.issuer`)이 글자 하나까지 같아야 한다.** 지금 앞의 둘은 `https://idp.sv.lan/realms/saintvision`으로 일치하고, 세 번째는 CP가 배포될 때 같은 값을 쓴다. 5-node readiness는 이 전환과 무관하게 계속 `BLOCKED_EXTERNAL`이다.

## 7. 인벤토리

### 7-1. 무엇을 채웠나

`tools/s01_readiness_preflight.py`가 읽는 `s01-readiness-inventory:1` 양식으로 인벤토리를 만들었다. **파일 자체는 저장소에 넣지 않는다** — 이 도구는 자기 보고서에서 IP와 hostname을 스스로 가리며, 그 판단을 문서에서 뒤집을 이유가 없다. 저장소에는 값이 빠진 **형태만** 둔다: `deploy/intranet/inventory.example.json`.

- **실측 3대**: nodeId · hostname · dnsName · ip · installationId · os · role · hardware(CPU·코어·GPU·디스크·NIC) · capacity · allowedResources · allowedFolders · ntp · storageRole.
- **nodeId는 fresh pilot state의 것이다.** v1.0은 은퇴한 이전 파일럿 run의 ID를 적었다 — IP 집합은 같지만 ID는 전부 다른 값이어서 **pair 일치가 0/3**이었다. 현재 파일럿 state의 ID로 다시 묶어 **3/3 일치**(IP 집합·ID 집합·pair 모두)를 확인했다.
- **자리표시 2대**: `dnsName`과 `role`만 채우고(§1과 ADR-100이 이미 정한 것) **나머지 13키는 `null`**. 문자열 `"미확인"`을 넣으면 **FAIL**이고, 키를 `null`로 두면 missing → **BLOCKED**다. 후자가 정직한 상태다.

### 7-2. 측정하지 않은 것은 채우지 않았다

- `certificateSHA256`은 **다섯 대 모두 `null`**이다. 파일럿 CA가 낸 인증서 지문이 지금 존재하기는 하지만, CP가 신뢰할 인증서는 **카드 150의 사내 CA**가 낼 것이고 그때 지문이 바뀐다. 곧 거짓이 될 값을 적는 대신 비웠다.
- `installationId`는 호스트의 machine-id를 고정 문자열과 함께 SHA-256으로 **유도**한 값이다. 호스트에서 같은 방법으로 다시 계산할 수 있고 raw machine-id는 내보내지 않는다.
- `allowedResources`는 측정값이 아니라 **제안**이다 — capacity의 3/4, GPU는 전부. 바꾸기 쉽도록 한 줄 규칙으로 두었다.
- `profile`은 **다섯 대 모두 비웠다.** v1.0은 `lan-observe-v1`을 적었는데 그 값의 출처는 **은퇴한 이전 파일럿의 인벤토리**였고, 그 run의 node ID는 이제 존재하지 않는다. 현재 파일럿에서 profile을 관측하지 않았으므로 적지 않는다.
- `storageRole`은 **관측**으로 정했다. object store container가 실제로 떠 있는 노드만 `provider`이고 `allowedFolders`에 그 데이터 경로를 적었다. 나머지 둘은 지금 아무 데이터도 들고 있지 않으므로 `none`이다.

**관측 수단을 구분해 적는다.** 같은 행의 값이라도 무엇으로 봤는지가 다르다.

| 노드 | 하드웨어·OS·NTP | 파일럿 agent 가동 | 인증서 | profile |
|---|---|---|---|---|
| `node1` | SSH 읽기 전용 **관측** | 컨테이너 **관측**(가동 중) | 미관측 | 미관측 |
| `node2` | SSH 읽기 전용 **관측** | 컨테이너 **관측**(가동 중) | 미관측 | 미관측 |
| `node3` | SSH 읽기 전용 **관측** | **미관측** — 로그인 사용자가 `docker` 그룹에 없어 볼 수 없다. 파일럿 state는 `provisioned`라고 적지만 그것은 등록 기록이고 가동 관측이 아니다 | 미관측 | 미관측 |

미관측 칸은 어떤 PASS의 근거로도 쓰지 않았다 — `certificateSHA256`과 `profile`은 다섯 대 모두 `null`이고, 그래서 lint는 BLOCKED에 머문다.
- `ntp.maxSkewSeconds`는 **1**(운영자 선언 상한)이다. 같은 날 측정한 실제 오프셋은 세 대 모두 1밀리초 미만이었다.

### 7-3. lint 결과 (실행)

```
inventory-lint  BLOCKED  inventory-values-missing
  nodeCount=5  missingFieldCount=74  invalidFieldCount=0
```

**`invalidFieldCount=0`이 핵심이다.** 채운 값 중 규격을 어긴 것이 하나도 없고 BLOCKED의 원인은 오직 "아직 없는 값"이다. 74 = 실측 3대 × (`certificateSHA256` + `profile`) 6개 + 자리표시 2대 × (상위 13 + 중첩 21 = 34). 숫자가 맞아떨어지는지 직접 세어 두었다(v1.0의 71에서 3 늘었다 — `profile`을 비웠기 때문이다).

### 7-4. topology 선택지 (사용자 결정)

[[ADR-100 CP 호스트의 Node 겸임과 5노드 측정 경계]]는 이미 `cp-colocated-plus-four-workers`를 채택했고 이 문서는 그것을 다시 열지 않는다. 다만 **채택된 안이 지금 막혀 있다**는 사실은 적어야 한다.

| 안 | 필요한 것 | 지금 막는 것 |
|---|---|---|
| **A. `cp-colocated-plus-four-workers`** (채택됨) | Ubuntu worker **1대 추가** + CP 겸임 Node **1대** | CP 겸임 후보로 기록된 Windows 장비는 [[S01_Node_인벤토리_실측초안_2026-09-28]]에서 **Docker Desktop Engine API 미달로 BLOCKED**이고 그 장비의 메모리 여유도 작다 |
| **B. `five-workers-dedicated-cp`** | worker **5대 전부** + 노드로 세지 않는 CP 전용 호스트 1대 | Ubuntu **2대 추가**가 필요하다 |

A는 **Ubuntu 1대 + CP 겸임 장비의 Docker 갱신**, B는 **Ubuntu 2대 + CP 전용 호스트**가 있어야 lint가 PASS로 간다. 어느 쪽이든 `certificateSHA256`은 카드 150을 기다린다.
