# 착지 직후 첫 행동 (정본)

## 0. 이 문서의 경계와 규칙

**train 12 이후의 모든 착지에 이 문서를 쓴다.** [[train3-11_착지_직후_첫_행동_2026-10-02]]은 train 11까지의 lane 결속만 다루고 그 판의 명령에 특정 train SHA가 박혀 있다 — **그 문서는 역사로 남기고 지우지 않으며**, 그 안의 §1(lane 결속 메커니즘)·§3(닫히지 않는 OPEN PR 판정)·§4(작업판 갱신 항목)는 지금도 읽을 값이 있다. 이 문서는 **train 12 이후에 달라지는 것**을 적는다.

**세 가지 규칙을 지킨다**(카드 219에서 세운 것):

1. **특정 train SHA를 현재형으로 적지 않는다.** 모든 명령은 착지 직후 **런타임으로 읽은 tip**(`$LAND`)에 묶는다. `tools/post_landing_verify.py`의 `check_ref_tip()`은 remote tip이 `--landed`와 **정확히 같기를** 요구하므로, 박아 둔 SHA는 다음 train에서 전부 거부당한다.
2. **착지 스크립트를 이름으로 지시하지 않는다.** `D:/Project/SaintVisionI-Invion/`의 `merge-land-train3-N-*.sh` 중 **N이 가장 큰 것**을 쓴다 — 각 스크립트가 이전 전부를 대체하고, integration tip이 자기 `OK_BASES`의 알려진 값 중 하나가 아니면 **밀지 않고 멈춘다**.
3. **되돌리지 않는다.** 실패는 §7처럼 기록한다. force-push도, revert도 이 문서의 절차가 아니다.

**이 PC에서 확인한 것**: 아래 셸 블록 전부 `bash -n` exit 0, 그리고 인용한 도구 다섯 개의 `--help`가 실제로 돈다(`post_landing_verify.py`·`record_vf_cl_ci_receipt.py`·`verify_vf_cl_ci_attestation.py`·`check_vf_cl_registry.py`·`assemble_ac11_manifest.py`). `gh attestation verify --help`도 이 PC의 `gh`에 있다. **실행하지 못한 것**: 실제 착지(integration은 이 문서를 쓴 시점에 아직 움직이지 않았다)와 그에 딸린 dispatch·attestation 검증 — 그것들은 착지한 사람이 실행하며, **각 절이 그때 무엇을 보고 무엇을 적는지**를 명령과 함께 적어 두었다.

## 1. 착지 **전**에 한 줄을 남긴다

`--previous`에 들어갈 값은 착지 *직전*의 tip이고, 밀고 난 뒤에는 remote에서 읽을 수 없다.

```bash
git ls-remote origin refs/heads/integration/all-agents-unified | cut -f1
```

받아 적지 못했다면 착지 스크립트의 `OK_BASES`에 후보가 전부 적혀 있다(그 중 **실제 직전 값 하나**만 기록을 사실로 만든다). 스크립트는 그 집합에 없는 tip을 보면 **밀지 않고 멈추므로**, 착지가 성공했다는 것은 직전 tip이 그 집합 안에 있었다는 뜻이다.

## 2. 착지 **직후** — tip을 한 번 읽고 그 값만 쓴다

**§2부터 §5까지는 한 셸 세션이다.** `$LAND`·`$PREVIOUS`가 그 세션에 살아 있어야 한다.

```bash
read -r -p '착지 직전 integration tip (40자 소문자 SHA): ' PREVIOUS
export PREVIOUS
```

```bash
set -euo pipefail
cd "$(git rev-parse --show-toplevel)"
test -f tools/post_landing_verify.py
git fetch origin

PREVIOUS="${PREVIOUS:?착지 직전 tip 40자 소문자 SHA를 PREVIOUS로 export하고 다시 실행}"
LAND=$(git ls-remote origin refs/heads/integration/all-agents-unified | cut -f1)
case "$LAND" in
  [0-9a-f][0-9a-f][0-9a-f][0-9a-f][0-9a-f][0-9a-f][0-9a-f][0-9a-f]*) ;;
  *) echo "integration tip을 읽지 못했다: '$LAND'" >&2; exit 1 ;;
esac
if [ "$LAND" = "$PREVIOUS" ]; then
  echo "tip이 움직이지 않았다 -- 착지 스크립트가 아직 돌지 않았거나 멈췄다" >&2
  exit 1
fi
git merge-base --is-ancestor "$PREVIOUS" "$LAND"   # fast-forward였는지
export LAND
echo "landed=$LAND previous=$PREVIOUS"
```

마지막 `merge-base`가 실패하면 **fast-forward가 아니었다**는 뜻이고, 그 경우 §7로 간다 — 되돌리지 않고 기록한다.

## 3. 여덟 lane을 착지 SHA에 묶는다

메커니즘과 실패 분류는 [[착지 후 검증 절차]]가 정본이다. 여기서는 **런타임 tip에 묶은 명령**만 적는다.

```bash
set -euo pipefail
cd "$(git rev-parse --show-toplevel)"
LAND="${LAND:?§2를 먼저 실행한다}"
PREVIOUS="${PREVIOUS:?§2를 먼저 실행한다}"
python tools/post_landing_verify.py \
  --landed "$LAND" \
  --previous "$PREVIOUS" \
  --out-dir ".work/post-landing/$LAND"
```

`--always-dispatch`는 **쓰지 않는다**(기본은 이미 있는 run을 먼저 찾는다). 결과는 `.work/post-landing/$LAND/`에 남고, 그 디렉터리 경로에 **착지 SHA가 들어가 있어야** 다음 train의 기록과 섞이지 않는다.

## 4. VF-CL-04 attestation — `ciVerified`를 **참으로 만들 수 있는 유일한 경로**

### 4-1. 왜 착지 SHA에서 다시 돌려야 하는가

`docs/vf-cl-registry-manifest.json`의 `cards["VF-CL-04"]`가 이유를 스스로 적는다(읽어서 인용한다): *"An implementation-only commit cannot attest its later Evidence commit or landing SHA, so rule 7 stays false until an exact-head workflow_dispatch run is verified and its receipt plus bundle are recorded."* 그리고 `ciVerifiedChecks`의 마지막 항목은 **`path-absent`: `docs/vf-cl-ci-attestations/VF-CL-04.bundle.json`** 이다 — 즉 **bundle 파일이 생기는 순간 지금의 false 도출이 깨지고**, 참을 주장하려면 **암호학적으로 검증된 것**을 내놓아야 한다. 산문으로 뒤집을 수 없게 만든 장치다.

attestation job은 `.github/workflows/s12-acceptance-evidence.yml`의 두 번째 job(`attest-vf-cl-ci-receipt`)이고 **`workflow_dispatch`에서만 돈다** — PR 코드에는 OIDC 서명 토큰을 주지 않는다(그 job의 주석이 그렇게 적는다). 그래서 **착지 SHA에서 dispatch하는 것이 유일한 경로**다.

### 4-2. dispatch

```bash
set -euo pipefail
cd "$(git rev-parse --show-toplevel)"
LAND="${LAND:?§2를 먼저 실행한다}"
CID="post-landing-vfcl-$LAND"
gh workflow run s12-acceptance-evidence.yml \
  --ref integration/all-agents-unified \
  -f correlation_id="$CID"
echo "correlation_id=$CID"
```

**ref는 branch 이름이고 SHA가 아니다**(GitHub의 `workflow_dispatch`는 ref를 받는다). 그래서 **§2의 `$LAND`가 그 branch의 현재 tip인 동안** 돌려야 하고, run을 찾을 때 그 둘이 같은지 확인한다:

```bash
set -euo pipefail
LAND="${LAND:?§2를 먼저 실행한다}"
CID="${CID:?§4-2의 correlation_id를 CID로 export하고 다시 실행}"
RUN=$(gh run list --workflow=s12-acceptance-evidence.yml --limit 20 \
  --json databaseId,displayTitle,headSha \
  --jq "[.[] | select(.displayTitle==\"$CID\" and .headSha==\"$LAND\")][0].databaseId")
test -n "$RUN"
export RUN
gh run view "$RUN" --json status,conclusion,headSha,event \
  --jq '"\(.status)/\(.conclusion) head=\(.headSha) event=\(.event)"'
```

`event`가 `workflow_dispatch`이고 `headSha`가 `$LAND`여야 한다. 둘 중 하나라도 다르면 **그 run은 이 기록의 근거가 아니다**.

### 4-3. 검증 — 서명·신원·source·bytes

attestation job은 자기 안에서 이미 `tools/verify_vf_cl_ci_attestation.py`로 검증하지만, **기록하는 사람이 다시 검증한다**. artifact를 내려받아:

```bash
set -euo pipefail
cd "$(git rev-parse --show-toplevel)"
LAND="${LAND:?§2를 먼저 실행한다}"
RUN="${RUN:?§4-2의 run id를 RUN으로 export하고 다시 실행}"
OUT=".work/post-landing/$LAND/vfcl"
mkdir -p "$OUT"
gh run download "$RUN" --name "vf-cl-ci-attestation-$LAND" --dir "$OUT"
ls -1 "$OUT"
python tools/verify_vf_cl_ci_attestation.py \
  --receipt "$OUT/VF-CL-04.json" \
  --bundle "$OUT"/*.sigstore.json \
  --expected-head "$LAND" \
  --expected-ref refs/heads/integration/all-agents-unified \
  --output "$OUT/verification.json"
```

그 도구가 하는 일을 자기 docstring으로 인용한다: *"No bundle means no verification. The verifier never accepts a receipt-shaped JSON as a substitute: it asks `gh attestation verify` to validate the signature, repository, signer workflow, source commit and branch, then independently binds the verified subject digest to the exact receipt bytes."*

**사람이 직접 보고 싶으면** 같은 것을 `gh`로 묻는다(이 PC의 `gh`에 있는 flag로 적었다):

```bash
set -euo pipefail
LAND="${LAND:?§2를 먼저 실행한다}"
OUT="${OUT:?§4-3의 OUT을 export하고 다시 실행}"
gh attestation verify "$OUT/VF-CL-04.json" \
  --repo egparadise/SaintVision-Invion \
  --signer-workflow egparadise/SaintVision-Invion/.github/workflows/s12-acceptance-evidence.yml \
  --source-digest "$LAND"
```

### 4-4. 기록하는 위치

| 무엇 | 어디 |
|---|---|
| CI receipt | `docs/vf-cl-ci-receipts/VF-CL-04.json` — `tools/record_vf_cl_ci_receipt.py`가 `--card`·`--workflow`·`--require-step`·`--artifact-prefix`·`--claimed-tree`·세 metadata로 만든다 |
| Sigstore bundle | `docs/vf-cl-ci-attestations/VF-CL-04.bundle.json` — **이 파일이 생기는 것이 `ciVerifiedChecks`의 `path-absent`를 깨고**, 참 주장을 암호학적 근거에 묶는다 |
| 검증 기록 | `.work/post-landing/$LAND/vfcl/verification.json`(저장소 밖) |
| registry | `docs/vf-cl-task-registry.json`의 `VF-CL-04` — `ciVerified`와 **`ciVerifiedRun`**(run을 이름으로 적어야 한다. 규칙 7) |
| 문 | `python tools/check_vf_cl_registry.py` — 이것이 통과해야 주장이 성립한다 |

`record_vf_cl_ci_receipt.py`의 `--workflow`·`--require-step`·`--artifact-prefix`는 **manifest가 적은 값을 그대로 쓴다**: workflow는 `.github/workflows/s12-acceptance-evidence.yml`, artifact prefix는 `s12-acceptance-`, 필수 step 넷은 `Derive the AC-12 acceptance items`·`Hold the bundle to its shape and to this head`·`Record that the two named observations were derived here`·`Upload the acceptance evidence`다.

## 5. AC-11 — 세 lane의 dispatch **순서**

세 lane은 **착지 SHA에서 다시 돌려야 의미가 생긴다**. 축 envelope은 자기 `sourceHeadSha`의 tree에 결속되므로, 착지 전 run으로 만든 봉투는 착지한 tree에 대해 아무것도 말하지 않는다.

| 순서 | lane | dispatch | 왜 그 순서인가 |
|---|---|---|---|
| 1 | `.github/workflows/ac11-security-scan.yml` | `-f correlation_id=…` | 축 봉투의 입력(artifact)을 만든다. 이 lane은 postgres service로 **네 threat report 중 세 개**를 측정한다(`#319`) |
| 2 | `.github/workflows/ac11-accessibility-e2e.yml` | `-f correlation_id=…` | **사용자 기기 수동 인수가 끝난 뒤에만** 의미가 있다(`#302`). 인수 기록이 없으면 그 축은 `NOT_OBSERVED`이고, lane을 먼저 돌려도 그 사실이 바뀌지 않는다 |
| 3 | `.github/workflows/ac11-aggregate.yml` | `-f source_sha="$LAND"` **그리고** `-f correlation_id=…` | **마지막이다.** 다른 lane의 artifact를 읽어 manifest를 세우고 8축을 재계산하므로, 그들 전에 돌리면 할 말이 없다(그 lane에 push trigger를 두지 않은 이유이기도 하다) |

```bash
set -euo pipefail
cd "$(git rev-parse --show-toplevel)"
LAND="${LAND:?§2를 먼저 실행한다}"
for wf in ac11-security-scan.yml ac11-accessibility-e2e.yml; do
  gh workflow run "$wf" --ref integration/all-agents-unified \
    -f correlation_id="post-landing-$wf-$LAND"
done
# 두 lane이 끝난 것을 확인한 뒤에 집계기를 돌린다.
gh workflow run ac11-aggregate.yml --ref integration/all-agents-unified \
  -f source_sha="$LAND" \
  -f correlation_id="post-landing-aggregate-$LAND"
```

**집계기의 답이 `INVALID_RUN`이어도 그것이 결과다.** 이 문서를 쓴 시점의 tree에서 그 lane은 **여덟 축 중 일곱이 absent**라 `INVALID_RUN`이고, 그 사유 줄이 무엇이 빠졌는지 말한다 — 축이 실패한 것이 아니라 봉투가 없는 것이다. 축별 상태와 사유는 `docs/ac11-axis-sources.json`이 정본이다.

## 6. S08 BuildKit은 **켜지 않는다**

두 flag가 있고 **둘 다 기본이 꺼짐**이다.

| flag | 어디 | 켜면 |
|---|---|---|
| `INV_BUILDKIT_REFERENCE_ENABLED` | `services/control-plane/src/inv/buildkit_transport.py` | reference transport가 열린다 |
| `INV_BUILDKIT_PRODUCT_ENABLED` | `services/control-plane/src/inv/build_execution.py` | 제품 dispatch 경로가 열린다 |

**착지 직후에 어느 것도 제품 설정에 넣지 않는다.** 이유는 셋이고 전부 측정된 것이다:

1. 제품 caller를 **부르는 경로가 없다** — `BuildExecutionService`를 구성하는 제품 코드가 0건이다(48 task 재채점 v1.11 §4-8-2).
2. 켜도 **스스로 거부한다** — node-agent의 durable quarantine 기록 경로가 없으면 제품 dispatch는 `RES-0006`으로 멈춘다(`#312` N2). 그 거부가 **의도된 fail-closed**다.
3. 실물 LAN builder는 외부 전제이고, 그것이 오기 전에 flag를 켜면 **증거 없이 열린 경로**가 하나 생길 뿐이다.

**확인만 한다**(값을 바꾸지 않는다):

```bash
set -euo pipefail
cd "$(git rev-parse --show-toplevel)"
grep -rn "INV_BUILDKIT_REFERENCE_ENABLED\|INV_BUILDKIT_PRODUCT_ENABLED" \
  services/control-plane/src/inv/buildkit_transport.py \
  services/control-plane/src/inv/build_execution.py | head -4
```

## 7. 실패하면 **되돌리지 않고 기록한다**

| 실패 | 하지 않는 것 | 하는 것 |
|---|---|---|
| 착지 스크립트가 멈췄다(`OK_BASES` 불일치) | force로 밀지 않는다 | 그때의 tip을 `git ls-remote`로 적고 코디네이터에게 보고한다 — train을 다시 세워야 한다는 뜻이다 |
| `merge-base --is-ancestor`가 실패(§2) | revert하지 않는다 | 두 SHA와 시각을 적는다. fast-forward가 아니었다는 것이 기록의 핵심이다 |
| lane 하나가 red(§3) | 재시도로 덮지 않는다 | `post_landing_verify`의 출력이 이미 run id와 분류를 적는다. 그 디렉터리를 그대로 두고 **어느 lane·어느 run·어느 step**인지 보고한다 |
| attestation 검증 실패(§4-3) | receipt만 기록하지 않는다 | **bundle 없이는 `ciVerified`를 참으로 적지 않는다**(규칙 7). 검증 실패 자체를 기록하고 `ciVerified`는 false로 둔다 |
| 집계기가 `INVALID_RUN`(§5) | 축을 낮추지 않는다 | 사유 줄을 그대로 옮긴다. 무엇이 absent인지가 다음 카드의 입력이다 |

**되돌리지 않는 이유**: 이 절차의 산출물은 "착지한 tree에서 CI가 무엇을 말했는가"이고, 되돌리면 그 질문에 답할 수 있는 상태가 사라진다. 실패한 기록은 **없는 기록보다 강하다**.

## 8. 이 문서가 하지 않는 것 / 실행하지 못한 것

- **lane 결속의 의미·실패 분류·변이 근거를 되풀이하지 않는다** — [[착지 후 검증 절차]]가 정본이다.
- **닫히지 않는 OPEN PR 판정과 두 작업판 갱신 항목을 다시 쓰지 않는다** — [[train3-11_착지_직후_첫_행동_2026-10-02]]의 §3·§4가 그대로 쓰인다(그 절들은 train 번호에 묶여 있지 않다).
- **사용자 조치 전체 목록을 쓰지 않는다** — `#300`의 단일 체크리스트가 정본이다.
- **실제 착지를 실행하지 못했다.** 이 문서를 쓴 시점에 integration은 움직이지 않았고, §3~§5의 dispatch·§4-3의 검증은 **착지한 사람이 처음 실행한다**. 그래서 각 절에 "무엇을 보고 무엇을 적는지"를 명령과 함께 적었다.
- **`gh attestation verify`를 실제 bundle로 돌리지 못했다** — 이 tree에는 bundle이 없다(`ciVerifiedChecks`의 `path-absent`가 그것을 요구한다). 확인한 것은 그 명령과 flag가 이 PC의 `gh`에 있다는 것까지다.
