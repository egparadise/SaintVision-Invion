# 서비스 시작·재시작·복구 절차

- 담당: Claude (Backend·DB·운영 문서)
- 완료 기준: **PC 재시작 후 서비스를 복구하고 오류 원인을 확인할 수 있음**

이 문서는 겪은 것만 적습니다. 추측한 실패 모드는 넣지 않았고, 실제로 만난 것은 어떻게 보였는지까지 적었습니다.

## 0. 이 시스템이 무엇에 의존하는가

| 의존 | 없으면 | 확인 |
|---|---|---|
| PostgreSQL 16 | 전부 정지 | `docker ps`, `psql -c 'select 1'` |
| `inv_kernel` LOGIN 자격증명 | **실행 커널이 커넥션을 못 엽니다** | 아래 §3 |
| `inv.control_epoch` 행 | 커널의 **모든 트랜잭션**이 LEASE-0004 | 아래 §3 |
| `inv.business_projects` 링크 | 프로젝트가 실행 불가 | `GET /v1/workspaces/{id}/execution-readiness` |
| `inv.business_subjects` 매핑 | 로그인은 되는데 **승인 불가** | 같은 엔드포인트 |
| OIDC trust bundle 파일 | 아무도 로그인 못 함 | 아래 §2 |
| Node의 Go 에이전트·컨테이너 이미지 | 원격 실행 불가 | Codex 영역 |

**진단의 출발점은 언제나 `execution-readiness`입니다.** 다섯 전제조건을 한 번에 답하고, 각 미충족 항목마다 **누가 고칠 수 있는지**를 함께 반환합니다. "권한 없음"과 "운영자가 아직 설정을 안 끝냄"은 막힌 사람에게 똑같이 보이는데 **완전히 다른 사람이 움직여야 합니다.**

## 2. 로그인 설정

검증기는 **오프라인**입니다. discovery URL도, 토큰 헤더 기반 키 조회도 없습니다 — IdP의 가용성이 매 요청의 의존성이 되고 그 DNS가 신뢰 경계가 되기 때문입니다.

```bash
export INV_TENANT_ID='...uuid...'
export INV_OIDC_ISSUER='https://idp.example/'      # https 필수
export INV_OIDC_AUDIENCE='inv'
export INV_OIDC_CLIENT_IDS='web,cli'
export INV_OIDC_JWKS_FILE='/etc/inv/jwks.json'     # URL 아님, 파일
```

trust bundle은 `{issuer, expiresAt, keys}` 세 키만 갖고, `expiresAt`은 **7일 이내**여야 하며 RS256 공개키 1~8개만 허용됩니다. 개인키(`d`)가 들어 있으면 거부합니다.

**넷 중 하나라도 빠지면 로그인이 아예 안 됩니다.** 절반만 설정하는 것은 지원하지 않습니다 — 세 개만 설정된 배포는 "인증이 느슨한 배포"가 아니라 "아무도 로그인 못 하는 배포"이고, 그 편이 낫습니다.

bundle이 만료되면 **시작 자체가 실패합니다.** 운영자가 보는 편이 사용자가 보는 것보다 낫기 때문에 의도된 동작입니다.

## 3. 실행 커널을 실제로 켜기

이 절이 없으면 API는 뜨는데 아무것도 실행되지 않습니다.

### 3-1. `inv_kernel`에 LOGIN 자격증명 부여

`inv_kernel`은 마이그레이션이 만드는 **NOLOGIN 그룹 role**입니다. 운영자가 별도 LOGIN role을 만들어 멤버십을 줍니다.

```sql
CREATE ROLE inv_runtime LOGIN PASSWORD '...';
GRANT inv_kernel TO inv_runtime;
```

런타임은 **superuser·BYPASSRLS·스키마 소유자를 모두 거부**합니다(AUTH-0020). 소유자 계정으로 붙이면 동작하지 않습니다 — 이건 버그가 아니라 설계입니다.

### 3-2. recovery epoch 확인

```sql
SELECT epoch FROM inv.control_epoch WHERE singleton;
```

**행이 없으면 커널의 모든 트랜잭션이 LEASE-0004로 실패합니다.** 운영자가 프로비저닝합니다:

```sql
INSERT INTO inv.control_epoch (singleton, epoch) VALUES (true, gen_random_uuid())
  ON CONFLICT (singleton) DO NOTHING;
```

`DO NOTHING`이 중요합니다. epoch를 **굴리는** 것은 재시작 후 화해(reconciliation)를 선언하는 운영자 행위이고, 실수로 덮어쓰면 진행 중이던 모든 예약이 무효가 됩니다.

### 3-3. 프로젝트·주체 링크 (프로젝트마다)

```sql
INSERT INTO inv.business_projects (tenant_id, project_id, enabled) VALUES (:t, :p, true);
INSERT INTO inv.business_subjects (tenant_id, subject_id, user_id, enabled)
  VALUES (:t, 'oidc:<sha256>', :user_id, true);
```

**애플리케이션은 이 두 테이블을 쓸 수 없고, 그게 맞습니다.** 웹 프로세스가 "어떤 프로젝트가 실행 가능한가"를 정할 수 있으면 안 됩니다. 주체 매핑은 **불변이고 1:1**입니다 — 한 사람이 두 신원을 가지면 2인 승인이 1인 승인이 됩니다.

`subject_id`는 `inv.identity.public_subject(issuer, sub)` = `'oidc:' + sha256([issuer, sub])`.

## 4. PC 재시작 후 복구

순서가 있습니다.

1. **PostgreSQL이 살아 있는지.** `docker ps`. 컨테이너가 없으면 여기서 멈춥니다 — 나머지는 전부 이것의 증상입니다.
2. **마이그레이션 head 확인.** `python tools/migration_graph.py --head` 와 DB의 `alembic_version` 비교.
3. **epoch 확인** (§3-2). 재시작으로 사라지지는 않지만, 운영자가 화해하며 굴렸다면 **그 이전에 준비된 binding은 전부 무효**입니다. 이건 정상이고 의도된 동작입니다.
4. **`execution-readiness`로 워크스페이스 하나 확인.** 다섯 항목이 다 충족이면 복구된 것입니다.
5. **어댑터 상태 확인.** `GET /v1/adapters` — 설치·로그인은 **기계의 속성**이라 재시작으로 바뀔 수 있습니다.

### 진행 중이던 작업은 어떻게 되는가

- **커널이 이미 잡은 lease**는 반납될 때까지 유지됩니다. offer를 낮춰도 회수되지 않습니다.
- **취소된 CLI 실행**은 `UNKNOWN`으로 기록됩니다. 프로세스가 사라진 것은 아는데 **그 전에 무엇을 했는지는 모릅니다** — 파일 수정, 커밋, 아직 과금 중인 요청. 그래서 **자동 재시도하지 않습니다.**
- **sealed되지 않은 Run**은 결과 API에서 `sealed: false`로 나옵니다. 빈 결과가 아니라 **결과 없음**입니다.

## 5. 실제로 겪은 장애

추측이 아니라 이 프로젝트에서 일어난 것들입니다.

### Docker 엔진 사망 (`iptables ... resource temporarily unavailable`)

증상: 컨테이너가 전부 사라지고 `docker ps`가 "Bad response from Docker engine". Docker Desktop 재시작으로 엔진은 돌아왔지만 **WSL이 멈춘 채로 남아** 다른 컨테이너들이 함께 내려갔습니다. `wsl --shutdown`은 다른 WSL 작업에 영향을 주므로 하지 않았습니다.

교훈: **로컬 DB가 유일한 검증 경로일 때 Docker 장애는 전면 중단입니다.** 그 기간 동안은 CI가 유일한 검증 수단이었습니다.

### CI 계정 소진

증상: 모든 브랜치·모든 워크플로가 **2~5초 실패**, job의 `steps: 0`, 로그 아카이브 **22바이트**.

**이건 코드 실패처럼 보이지 않습니다** — 단계가 하나도 실행되지 않았다는 뜻입니다. 코드를 디버깅하기 전에 이 세 가지를 봐야 합니다:

```bash
gh api "repos/OWNER/REPO/actions/runs?per_page=6" \
  --jq '.workflow_runs[] | "\(.name) \(.conclusion) \(.created_at) \(.updated_at)"'
```

지속 시간이 전부 한 자릿수 초이고 브랜치를 가리지 않으면 계정 문제입니다.

### 마이그레이션 단계에 DSN이 없음

증상: 마이그레이션이 **엉뚱한 데이터베이스에** 적용됨. `env.py`가 명시적 DSN보다 주변 DSN을 우선하고 있었고, 그 단계에는 DSN이 없었습니다.

지금은 각 마이그레이션 단계가 자기 `INV_MIGRATION_DSN`을 갖습니다. **job 전역 `INV_DATABASE_URL`은 일부러 설정하지 않습니다** — 주변 DSN이 있으면 이 실패가 조용히 다시 일어납니다.

## 8. 복원 리허설 — 실제로 수행했습니다

`recovery_drills` 테이블은 S12부터 있었고 모양도 신중합니다 — 측정값과 목표값을 따로 두고, 숫자 없는 합격을 거부하고, 데이터베이스 합격에 fencing 검사를 요구합니다. **그런데 리허설을 수행하는 것이 없었습니다.** 답을 적을 표만 있고 답을 만들 방법이 없는 상태이고, 그걸 처음 알게 되는 시점은 **대비하려던 바로 그 장애 중**입니다.

`tools/recovery_drill.py`가 끝까지 수행합니다: 덤프 → 폐기 가능한 DB로 복원 → 내용 검증 → RPO·RTO 측정 → **fencing 안전성 확인** → 결과 기록.

### 실측

```
backup      590,148 bytes
restore RTO 6.5 ~ 12.1s     (목표 3600s)
integrity   verified
fencing     safe
```

### 그리고 실패도 확인했습니다 — 이게 중요합니다

덤프 직후 복원하면 **시퀀스가 있던 자리 그대로**라 fencing 검사는 **항상 통과**합니다. 즉 아무것도 증명하지 못합니다. 실제 복구는 **더 이전에 뜬 백업**을 되돌립니다.

`--from-backup`으로 그 상황을 만들었습니다. 백업 이후 lease 7건이 fencing token과 함께 발급된 상태에서 옛 백업을 복원하니:

```
integrity   FAILED
              count differs: tenants
fencing     UNSAFE
              the restored sequence would reissue tokens a live node may hold;
              advance inv.fencing_token_seq by 6 before accepting any command
exit code   1
```

ERR-DESIGN-006 그대로입니다. **복원은 `inv.fencing_token_seq`를 되감지만 토큰 500을 쥔 Node Agent는 되감기지 않습니다.** 복원된 시퀀스가 이미 쓰이고 있는 토큰을 다시 발급하면 fencing이 제공하려던 순서가 사라집니다 — 살아 있는 명령이 낡은 것으로 거부되거나, 더 나쁘게는 새 lease가 아직 쓰이는 토큰보다 낮은 번호를 받습니다.

**복원 후 반드시 할 일**: 위 숫자만큼 시퀀스를 전진시키기 전에는 **어떤 명령도 받아들이지 마십시오.**

```sql
SELECT setval('inv.fencing_token_seq', <복원 전 최대값>, true);
```

### 두 가지 안전장치

- **원본 위에 복원하지 않습니다.** 이 도구가 만든 이름(`inv_drill_` + 32 hex)만 대상이 되고 이름을 확인한 뒤에야 삭제합니다. 리허설을 연습하려던 장애로 바꾸는 유일한 실수입니다.
- **exit code 0은 검증이 아닙니다.** `pg_restore`가 0을 반환하는 건 파일을 파싱했다는 뜻입니다. 빈 데이터베이스를 만들어도 0입니다. 그래서 모델이 선언한 **모든 테이블의 행 수**와 증거를 담는 테이블의 **내용 digest**를 원본과 대조합니다.

### 8-0. 이 배포에는 시점 복구(PITR)가 없습니다 — RPO 목표를 아직 만족할 수 없습니다

위 리허설이 보고하는 "recovery RPO 6초"는 **이 도구가 방금 뜬 백업과의 간격**입니다. 서버를 어떻게 설정하든 거의 0이 나옵니다. 즉 **실패할 수 없는 숫자**이고, AC-12의 RPO 목표에 대한 증거가 될 수 없습니다. 이것을 증거로 쓰는 것은 이 도구에서 네 번이나 제거한 바로 그 결함을 헤드라인 숫자에 그대로 두는 일이었습니다.

실측한 설정 (개발 컨테이너와 `docker-compose.prod.yml` 모두 동일):

```
wal_level        replica
archive_mode     off
archive_command  (disabled)
archive_timeout  0
wal_keep_size    0
data_checksums   off
```

**연속 아카이빙이 꺼져 있으므로 시점 복구가 불가능합니다.** 복구 지점은 마지막 전체 백업뿐이고, 따라서 **운영 RPO는 백업 주기와 같습니다.** 15분 목표를 지금 설정으로 만족하려면 15분마다 전체 덤프를 떠야 하며, 이 절차서는 그런 주기를 규정하고 있지 않습니다.

도구는 이제 두 가지를 구분해 출력합니다.

```
recovery RPO  5.6s for this restore
operational   RPO bound NOT ESTABLISHED
                there is no point-in-time recovery: archive_mode is 'off' ...
```

인수 증거로 쓸 때는 목표를 명시해야 하고, 만족하지 못하면 **거부됩니다**.

```
$ python tools/recovery_drill.py ... --require-operational-rpo 900
REFUSED as acceptance evidence: an operational RPO bound at or under 900s was
required and the server's configuration does not establish one.
exit code 1
```

**`data_checksums`가 꺼져 있습니다.** 이 리허설은 복원본을 **원본과** 대조합니다. 원본에서 이미 조용히 손상된 페이지는 양쪽에서 똑같이 읽히므로 여기의 모든 대조를 통과합니다. 즉 이 도구는 원본이 온전했다고 말해주지 않습니다. `data_checksums`는 initdb 시점에만 켤 수 있으므로(또는 정지 상태에서 `pg_checksums`), 운영 배포 전에 결정해야 합니다.

**해소 담당**: 연속 아카이빙·보관 매체·주기는 운영 결정이며 Codex의 CX-09 릴리스 시험과 함께 정해야 합니다. 정해지기 전에는 이 절차서가 RPO 목표 달성을 주장하지 않습니다.

### 미수행

- **부하·장시간 시험**은 아직입니다.
- 이 리허설은 **로컬 컨테이너**에서 수행했습니다. 운영 장비의 백업 매체·네트워크로는 RTO가 달라집니다.
- **PITR·보관 매체·백업 주기가 정해지지 않아 RPO 목표는 미달성입니다** (8-0).

### 8-1. 복원 도구 보완 — 제 첫 버전이 틀렸던 부분

**권한을 복원하지 않고 "검증됨"이라고 보고했습니다.** `pg_restore --no-privileges`를 쓰고 있었습니다. 실측하면:

```
원본                    : 1,314 table / 7,652 column grants
--no-privileges 복원    :   924 table / 4,816 column grants
```

**390개 테이블 권한과 2,836개 컬럼 권한이 사라집니다.** 그리고 그 데이터베이스는 **시스템이 접속조차 못 합니다** — 런타임이 소유자로 실행되기를 거부하므로 grant를 잃으면 **받아들이는 유일한 role을 잃습니다.** 컬럼 권한이 특히 중요합니다: CHECK로 고정된 sentinel 컬럼 하나에 대한 UPDATE가 **"이 행을 잠글 수 있다"와 "이 행을 바꿀 수 있다"를 가르는 장치**입니다.

이제 권한을 복원하고 **원본과 digest를 대조**하며, 불일치는 무결성 실패입니다.

**`public` 스키마만 세고 있었습니다.** 복원이 되살리려는 것의 대부분 — run·lease·evidence·영수증 — 은 `inv`에 있습니다. 이제 카탈로그에서 두 스키마 전부를 읽으므로 어느 쪽이 테이블을 추가해도 그날부터 세어집니다.

**진단을 숨겼습니다.** 첫 실행이 "pg_dump failed"만 출력했고 실제 원인은 **컨테이너 안에 없는 호스트 포트**였습니다. 두 커밋 전에 제가 다른 도구에서 비판한 바로 그 억제입니다. 이제 오류를 보여주고 비밀번호만 가립니다.

## 9. definer 함수 점검 — 소스가 아니라 운영 DB를 봅니다

SECURITY DEFINER 함수는 소유자로 실행되어 **RLS를 우회**합니다. 세션이 실제로 속한 tenant에 답을 묶지 않으면 **하나하나가 격리 구멍**입니다.

이 저장소는 이미 두 번 그랬습니다 — `project_kernel_link`(0024, 0027이 수정), `subject_kernel_link`(0026, 0028이 수정). **두 수정 다 `CREATE OR REPLACE`였고, 그래서 소스 검토로는 답할 수 없습니다.** 중요한 건 **데이터베이스가 지금 들고 있는 정의**이고, 체인 중간에 멈춘 데이터베이스는 이전 것을 들고 있습니다.

`tools/check_definer_functions.py`가 `pg_proc`를 읽습니다.

```
$ python tools/check_definer_functions.py --dsn ...          # head
  6 SECURITY DEFINER function(s)
  ok  public.apply_resource_offer / business_admin_allowed /
      project_kernel_link / subject_kernel_link / workspace_input_state
  ok  public.node_by_certificate  (allowlisted)
  Every definer function is bound to the session's tenant scope.   exit 0

$ # 0024에서 멈춘 데이터베이스
  UNSAFE public.project_kernel_link(p_tenant_id uuid, p_project_id text)
           takes a tenant id and does not bind it to current_setting(...)
  exit 1
```

`node_by_certificate`는 allowlist입니다 — **인증은 tenant 범위가 존재하기 전에 실행되므로** 묶을 범위가 없고, 정확히 일치하는 64자 지문으로 3개 컬럼만 반환해 열거가 불가능합니다. **규칙을 낮추는 대신 사유와 함께 이름을 적었습니다.**

**배포 절차에 넣으십시오.** 마이그레이션 직후 이 검사가 0이 아니면 그 데이터베이스는 tenant 격리가 깨진 상태입니다.
