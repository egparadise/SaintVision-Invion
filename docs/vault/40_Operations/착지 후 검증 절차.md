# 착지 후 검증 절차

## 0. 이 도구가 답하는 질문 하나

**"지금 integration인 이 tree에서 여섯 lane이 통과하는가?"**

각 PR이 증명한 것은 **그 PR의 head**에서 증명한 것이다. train이 fast-forward로 착지하면 tree는 바뀌고, 그 tree에서 lane이 통과한다는 기록은 아직 없다. 특히 `AC-11 Security Critical High Scan`은 label 또는 수동 dispatch에서만 돌아 **PR run으로는 착지 SHA의 기록을 만들 수 없다** — 48 task 재채점이 그 축을 "측정 가능하나 착지 SHA에 묶인 실행 기록 없음"으로 적어 둔 이유다.

**이 도구는 기록만 한다. 점수를 올리지 않는다.** Evidence JSON에 `promotesScore: false`가 들어가고, 그 값이 아니면 기록 자체를 거부한다.

## 1. 사용법

```
python tools/post_landing_verify.py --landed <착지 SHA 40자> --previous <착지 전 SHA 40자>
```

| 선택지 | 기본값 | 쓸 때 |
|---|---|---|
| `--ref` | `integration/all-agents-unified` | 다른 ref에 착지했을 때 |
| `--out-dir` | `docs/vault/30_Development/Evidence/landing` | 다른 곳에 기록할 때 |
| `--poll-seconds` | `120` | 그대로 두는 편이 낫다(§4-1) |
| `--deadline-seconds` | `14400`(4시간) | dispatch가 push run 뒤에 줄을 섰을 때 늘린다 |
| `--always-dispatch` | 꺼짐 | **환경 문제를 고친 뒤 다시 돌릴 때(§3-2)** |
| `--dry-run` | — | 무엇을 볼지 출력하고 **아무것도 dispatch하지 않고** 끝낸다 |

종료 코드: **0** 전부 통과 · **1** 하나라도 실패하거나 skip됨 · **2** 질문 자체에 답할 수 없음(입력·ref·기록 거부).

착지 직후 첫 실행은 이렇게 한다.

```
python tools/post_landing_verify.py --dry-run --landed <SHA> --previous <이전 SHA>   # 계획 확인
python tools/post_landing_verify.py          --landed <SHA> --previous <이전 SHA>   # 실제
```

## 2. 이 도구가 **하지 않는** 네 가지

이 넷이 기록을 거짓으로 만드는 경로이고, 각각 변이 시험으로 묶여 있다.

### 2-1. ref가 착지 SHA가 아니면 **아무것도 dispatch하지 않는다**

`gh workflow run`은 **지금** ref가 가리키는 것을 돌린다. integration이 이미 다음 train으로 넘어갔으면 그 run은 다른 tree를 기술하는데 Evidence는 우리 SHA를 적게 된다. 그래서 CI 시간을 쓰기 전에 멈춘다(`refIsAtLandedSha` = `MEASURED_FAIL`, 여섯 lane 전부 `NOT_OBSERVED`).

ref tip은 **`git ls-remote`로 읽는다.** `git rev-parse origin/<ref>`는 마지막 fetch 시점의 답이고, **낡은 답이 착지 SHA와 우연히 일치**할 수 있다 — 이 검사가 막으려는 바로 그 공백이다.

### 2-2. run 하나를 고르는 데 **네 가지가 모두 맞아야** 한다

`gh run list`는 "이 workflow의 최근 run"을 돌려줄 뿐이다. 그중 우리가 뜻하는 run을 고르는 조건이 넷이고, **각각이 실제로 틀릴 수 있는 길 하나를 막는다.**

| 조건 | 이것이 없으면 |
|---|---|
| `headSha == 착지 SHA` | 다른 tree에 관한 run을 읽는다 |
| `headBranch == ref` | **같은 commit의 PR run**을 착지 push run으로 읽는다. PR event에서 GitHub은 **PR head를 `headSha`로** 보고하므로, 방금 fast-forward된 branch의 PR run은 **이 commit을 가리키면서 다른 질문**(누군가의 branch 병합)을 기술한다. `main`처럼 **같은 commit을 가리키는 다른 branch**의 run도 같다 |
| `event ∈ {push, workflow_dispatch}` | 같은 혼동이 다른 문으로 들어온다. `pull_request`는 제외된다 |
| `databaseId > dispatch 직전 최대 id` | **같은 SHA에 이미 완료된(그리고 실패한) run**을 "방금 시작한 run의 결과"로 읽는다 |

`gh run list`에 `--branch`를 넘겨 서버에서 먼저 좁히고, **`headBranch`를 코드에서 다시 본다** — 도구에 부탁한 filter는 우리가 관측한 사실이 아니다. 판정 시점에도 `gh run view`가 돌려준 `headSha`·`headBranch`·`event`를 **run 자신에게서 다시 읽는다**(목록은 run을 **찾은** 방법이고, 판정 근거는 run이 **스스로 말하는 것**이다).

### 2-2-1. dispatch한 run은 **correlation id**로 집는다

**목록 관찰로는 이 문제를 닫을 수 없다.** GitHub은 dispatch와 그것이 만든 run을 잇는 식별자를 돌려주지 않는다. 그래서

- "착지 SHA의 가장 큰 id"는 **먼저 등록된 dispatch**를 집는다 — 다른 운영자가 한 박자 먼저 dispatch했다면 그 사람 run이다.
- "이 poll에 후보가 정확히 1개일 때만 결속"도 닫지 못한다. **그 사람 run이 첫 poll에 혼자 보이고 우리 run이 다음 poll에 나타나면**, 첫 poll의 후보는 정확히 1개이고 그것은 우리 것이 아니다.

그래서 **이름을 통로로 쓴다.**

| 쪽 | 무엇 |
|---|---|
| 여섯 workflow | `workflow_dispatch.inputs.correlation_id`(선택, 기본 빈 값)와 `run-name: ${{ inputs.correlation_id \|\| github.workflow }}` |
| 도구 | lane마다 새 uuid를 만들어 `gh workflow run ... -f correlation_id=<uuid>`로 dispatch |
| 결속 | `displayTitle`이 **그 uuid와 정확히 같은** run만 결속한다. 나타날 때까지 **매 poll 목록을 다시 읽고**, deadline까지 없으면 `NOT_OBSERVED` |

**첫 실제 실행에서 확인할 것**: 이 결속은 fake runner와 정적 시험으로만 묶여 있다. `workflow_dispatch`로 `run-name`이 실제로 uuid가 되는지는 **실제 dispatch로만** 확인된다. 그래서 착지 후 첫 실행 뒤 **Evidence의 `correlationId`와 Actions의 run 이름이 같은지 눈으로 확인하고**, 다르면 그 Evidence를 `NOT_OBSERVED`로 읽는다(도구는 이름이 맞는 run만 결속하므로 틀렸다면 애초에 아무것도 결속되지 않는다).

이름만으로 결속하지는 않는다 — **이름은 주장이고**, `headSha`·`headBranch`·`event`가 그 run을 이 증거의 대상으로 만드는 것이다. 넷 모두 맞아야 한다. 한 uuid를 두 run이 들고 있으면(누가 id를 재사용한 경우뿐) 고르지 않고 `NOT_OBSERVED`로 적는다.

### 2-2-2. workflow 변경이 **dispatch 경로 밖에서는 아무것도 바꾸지 않는다**

| 보장 | 어떻게 확인하는가 |
|---|---|
| input이 **`run-name` 밖에서 읽히지 않는다** | 시험이 여섯 파일에서 `correlation_id`가 나오는 줄을 전부 모아 **`run-name` 줄이거나 선언 줄**뿐임을 단언한다. 오직 `run-name`에만 있는 값은 job·step·`if:`·env에 도달할 수 없으므로, **어떤 workflow도 이 값 때문에 다르게 동작할 수 없다** — "diff가 작다"보다 강한 보장이다 |
| input이 **선택**이다 | `required: false`, `default: ''`. 사람이 Actions UI에서 그냥 dispatch해도 아무것도 입력하지 않는다 |
| dispatch 외 event의 run 이름 | id가 없으면 `github.workflow`로 떨어진다. **빈 `run-name`이 GitHub 기본값으로 되돌아가는지에 의존하지 않는다**(실제 dispatch 없이 확인할 수 없는 가정이므로) |
| job·trigger | 변경 0. 여섯 파일의 `jobs` 목록과 `on:` trigger는 그대로다 |

**한 가지 눈에 보이는 대가**: dispatch가 아닌 run(push·PR)의 **표시 이름이 commit 제목에서 workflow 이름으로 바뀐다.** 동작이 아니라 Actions 목록의 표시만 바뀌는 것이고, `run-name:`이 모든 event에 적용되기 때문이다. commit 제목을 유지하는 쪽이 낫다면 `run-name` 한 줄을 바꾸면 되지만, 그 식의 되돌림 동작은 실제 dispatch로만 확인할 수 있다.

## 3. lane 표와 adopt 규칙

| lane | workflow 파일 | 필요한 job |
|---|---|---|
| `backend` | `backend.yml` | `backend` **2건**(3.12·3.14 matrix) · `mlflow-live` |
| `core` | `core.yml` | `core` · `s01-storage-roundtrip` |
| `frontend` | `frontend.yml` | `frontend` |
| `desktopBrowser` | `desktop-browser.yml` | `desktop-browser` |
| `docs` | `docs.yml` | `docs` |
| `securityCriticalHigh` | **`ac11-security-scan.yml`** | `security-critical-high` |

### 3-1. 착지 push run을 **그대로 쓴다** — 두 번째 runner를 띄우지 않는다

여섯 중 **다섯**은 `push`로 `integration/all-agents-unified`를 받으므로, **착지 자체가 이미 그 SHA에서 돌려 놓았다.** 그리고 그 workflow들은 그 ref에 대해 `cancel-in-progress: false`다 — 즉 dispatch는 push run을 **대체하지 않고 뒤에 줄을 선다.** 같은 사실을 알기 위해 runner를 하나 더 쓰고 벽시계 시간을 두 배로 쓰는 셈이다.

그래서 **착지 SHA에 run이 이미 있으면 그것을 채택하고(adopt), 없는 lane만 dispatch한다.** 실제로 dispatch되는 것은 push trigger가 없는 **AC-11 하나**다. Evidence의 `adoptedWorkflows`·`dispatchedWorkflows`가 어느 쪽이었는지 적는다.

### 3-2. 그래서 **고친 뒤 다시 돌릴 때는 `--always-dispatch`가 필요하다**

이것이 adopt 설계의 대가다. 환경 문제(§4) 때문에 lane이 실패했다면, **그 실패한 run이 여전히 착지 SHA의 run**이다. 그냥 다시 돌리면 도구는 그 실패를 다시 채택해 같은 실패를 보고한다. 고친 뒤에는 이렇게 한다.

```
python tools/post_landing_verify.py --always-dispatch --landed <SHA> --previous <이전 SHA>
```

`--always-dispatch`는 모든 lane을 새로 띄우고, §2-2의 id 하한이 **새 run만** 집어낸다.

## 4. 실패 시 대응

먼저 가릴 것: **착지한 tree의 결함인가, 그 run이 돌던 환경의 결함인가.** 둘은 대응이 정반대다.

### 4-1. 월 경계 파티션 — **착지 결함이 아니다**

`resource_snapshots`·`audit_events`·`evidence_envelopes` 세 표는 **월 단위 range partition**이고 **DEFAULT partition이 없다**(`src/saintvision/db/partitions.py`). DEFAULT에 행이 들어가면 나중에 진짜 partition을 붙일 수 없게 되므로 의도적으로 없다. 그리고 Evidence 쓰기와 success 전이가 **같은 transaction**(ADR-008)이므로, partition이 없으면 **Run이 완료되지 못한다.**

**이 절은 2026-10-01에 실제로 일어난 것을 적는다.** 처음 작성한 설명은 방향이 틀렸고, 그날 CI가 정정했다(§4-1-3).

#### 4-1-1. 관측된 모양 — 제공 창이 **고정 시계를 지나쳐 갔다**

| | |
|---|---|
| **증상** | `PartitionExhausted: partition lead below minimum 1 month(s): resource_snapshots=0mo, audit_events=0mo, evidence_envelopes=0mo` 와 `CheckViolation: no partition of relation "resource_snapshots" found for row / DETAIL: Partition key of the failing row contains (observed_at) = (2026-09-10 06:59:30+00)` |
| **규모** | Backend run `36800565482`(2026-10-01T01:36Z) **82 failed · 81 errors**, 3.12·3.14가 **같은 수치** — 즉 flaky가 아니라 결정적이다 |
| **원인** | migration은 partition을 **벽시계 월부터 앞으로** 만든다(`migrations/versions/0001_s02_baseline.py::_create_initial_partitions`, `lead_months=3`). 시험은 **고정 시계**로 쓴다(`tests/conftest.py::FROZEN_NOW = 2026-09-09`). 9월 30일까지는 제공 창이 9월을 덮었고, **10월 1일에 창이 9월을 떠났다** |
| **그래서** | 시작 gate는 고정 시계(9월)로 묻는데 `_p202609`가 없으니 `months_ahead=0`이고, 9월 날짜 행은 routing에서 떨어진다 |

**즉 이 저장소에서 실제로 깨지는 방향은 "앞으로 넘어가는 것"이 아니라 "창이 과거의 고정 시계를 지나치는 것"이다.** 시간이 지나면 **아무 코드 변경 없이** 어느 날 갑자기 red가 된다.

#### 4-1-2. 이미 train에 고쳐져 있다

`a18638bb test(db): provision the frozen clock partition` 이 `migrated` fixture에 이 한 줄을 넣는다.

```python
ensure_partitions(connection, now=FROZEN_NOW, lead_months=0)
```

이 commit은 **`73fa1274`(train 4d)에 들어 있고 `6fc0428b`에는 없다.** 그래서 2026-10-01에 **`6fc0428b` 기반 branch는 전부 red이고 `73fa1274` 기반은 green이었다**(`coord/train4d-ci-1004` run `36799292219` success). 착지 후 검증에서 이 모양을 보면 **먼저 `a18638bb`가 그 tree에 있는지 확인한다.**

#### 4-1-3. 또 하나의 모양 — 앞으로 넘어가는 경우(운영 DB)

고정 시계가 없는 **운영 DB**에서는 반대 방향이 가능하다. 시작 gate는 `minimum_months=1`이라 **당월 partition만 있어도 통과**하므로, 월말에 시작한 긴 작업이 월을 넘는 순간 INSERT에서 처음 발견된다 — **gate 통과와 insert 실패가 양립한다.** 이 문서의 1.0판은 이 모양만 적었고, **실제로 일어난 것은 4-1-1이었다.** 둘 다 "DEFAULT partition이 없다"의 결과지만 **대응의 첫 질문이 다르다**(아래).

#### 4-1-4. 대응

1. **방향을 먼저 가린다.** 실패한 행의 partition key가 **제공 창보다 과거**인가(4-1-1), **미래**인가(4-1-3)? `CheckViolation`의 `DETAIL` 한 줄이 그것을 말해 준다.
2. `partition_status`로 `months_ahead`와 `latest_bound`를 본다.
3. 과거 쪽이면 **그 달을** 제공한다(`ensure_partitions(now=<그 달>, lead_months=0)`). 미래 쪽이면 `ensure_partitions(lead_months=3)` — 월 작업이 **두 번 연속 실패해도 버티는** 값이다.
4. **`--always-dispatch`로 다시 돌린다**(§3-2).

**하지 말 것**: train을 되돌리지 말 것 — tree는 멀쩡하다. **DEFAULT partition을 만들지 말 것** — 나중에 진짜 partition을 붙이지 못하게 된다.

**드랍 작업과 분리**: 생성과 보존 drop은 **다른 transaction**이다. drop이 실패해도 생성을 막지 않는다.

### 4-2. 그 밖의 실패를 읽는 법

| Evidence가 적은 것 | 뜻 | 첫 대응 |
|---|---|---|
| `skippedJobs`가 비어 있지 않다 | run은 green인데 **그 축이 관측되지 않았다** | job의 `if:` gate와 dispatch event를 확인. label 전용으로 바뀌었는지 본다 |
| `missingJobs` | job이 이름이 바뀌었거나 사라졌다 | lane 표(§3)와 workflow를 맞춘다. **시험이 이것을 잡는다**(§5) |
| `jobsNotPassed`에 `failure` | **착지한 tree의 결함일 가능성이 높다** | 그 lane의 log를 본다. train 되돌림은 코디네이터 결정 |
| `no run carrying this dispatch's correlation id completed` | 우리 uuid를 든 run이 deadline까지 완료되지 않았다(§2-2-1) | Actions에서 그 uuid 이름의 run을 찾아 상태를 보고, `--deadline-seconds`를 늘려 다시 돌린다 |
| `two runs carry this dispatch's correlation id` | 한 uuid를 두 run이 들고 있다 — id 재사용뿐이다 | `--always-dispatch`로 새 uuid를 받아 다시 돌린다 |
| `the run is not a run of the integration ref` | 고른 run의 `headBranch`가 ref가 아니다 | 보통 PR run이 섞인 경우다. ref와 착지 SHA를 다시 확인한다 |
| `the run did not complete within the deadline` | 실패가 아니라 **관측 실패**다 | `--deadline-seconds`를 늘린다. dispatch가 push run 뒤에 줄을 섰는지 본다(§3-1) |
| `the run's headSha is not the landed SHA` | 사이에 ref가 움직였다 | 새 tip으로 다시 시작한다. 이 Evidence는 폐기하지 말고 **그대로 둔다** |
| `a commit is missing from this clone` | ancestry를 **판정할 수 없다**(실패가 아니다) | `git fetch origin <ref>` 뒤 다시 돌린다. shallow clone이면 깊이를 늘린다 |
| 종료 코드 **2**, `refused: ...` | 입력이나 기록이 거부됐다 | 메시지 그대로 고친다. SHA는 **40자 전체**여야 한다 |

### 4-3. 기록이 거부되는 경우

- **`uncommitted tracked changes`**: 도구 자신의 출력(Evidence 파일)은 untracked이므로 막지 않지만, **추적 중인 파일의 수정**은 막는다. 그러면 기록이 가리키는 commit과 실제로 돌린 collector가 다르다.
- **`refusing to overwrite existing evidence`**: 같은 label로 두 번 쓰지 않는다. `--label`로 구분하거나 기본 label(시각 포함)을 쓴다.
- **`passed without naming a run`**: 통과한 lane은 **run id를 반드시 적는다.** 나중에 다시 확인할 수 없는 통과는 기록하지 않는다.

## 5. 이 도구를 믿는 근거

`tests/core/test_post_landing_verify.py` — **77건.** `gh`·`git`을 **주입된 runner로 fake**하므로 **실제 dispatch가 일어나지 않는다.** fake는 **모든 명령을 기록**하고, 그것이 핵심 단언이다. 결과만 보는 시험은 "runner 여섯 개를 띄우고 나서 올바르게 보고하는 도구"에도 통과한다.

묶여 있는 것 중 중요한 것:

- 착지 SHA에 run이 있는 lane은 **dispatch되지 않는다**(명령 기록으로 단언).
- ref가 움직였으면 `gh run list`조차 부르지 않는다.
- skip된 job, 빠진 job, matrix 한쪽만 통과, 다른 SHA의 run, 실패한 dispatch, 완료되지 않은 run이 각각 올바른 상태가 된다.
- **같은 SHA의 낡은 완료 run을 방금 dispatch한 run으로 착각하지 않는다**(§2-2).
- lane 표의 **workflow 파일이 실제로 존재하고**, 적어 둔 **job id가 그 파일에 있고**, 여섯 lane 모두 **dispatch 가능**하다 — workflow 이름이 바뀌면 착지 3시간 뒤가 아니라 **여기서** 깨진다.
- `--dry-run`은 명령을 **하나도** 실행하지 않는다.

**변이 24종 전부 사망**(한 번에 하나, 매 회 원복·바이트 대조). 그중 셋은 **workflow 파일**을 대상으로 한다 — input을 안 받게 하기, `run-name`이 id를 안 싣게 하기, **input을 job의 env로 흘리기**.

**변이 중 둘은 처음에 생존했고 그것이 매번 시험의 결함이었다.** (1) id 하한을 지워도 통과했는데, 시험이 "낡은 run이 **다른** SHA에 있는" 세계만 만들었기 때문이다 — 같은 SHA에 완료 상태로 두자 죽었다. (2) 그 뒤 **순차 경쟁**(남의 dispatch가 첫 poll에 혼자 보이고 우리 것이 다음 poll에 나타나는 경우)에서는 "후보가 하나면 결속"이 남의 run을 잡았다 — 목록 관찰로는 닫히지 않아 correlation id로 바꿨고(§2-2-1), 그 probe가 회귀 시험으로 남아 있다.
