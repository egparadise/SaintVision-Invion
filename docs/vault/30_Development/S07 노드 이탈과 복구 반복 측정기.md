# S07 노드 이탈과 복구 반복 측정기

`tools/measure_s07_recovery.py`는 실제 PostgreSQL migration head에서 매 실행마다 난수 disposable database와 난수 application login role을 만들고 정리한다. 각 반복은 N개의 합성 measured node를 만들고 한 node의 heartbeat만 중단한다. 살아 있는 node는 제품의 heartbeat·resource observation 경로로 계속 갱신한다.

v1.2는 기존 synthetic 기본 동작을 바꾸지 않고 [[S07 5노드 실 Node adapter 사양]]을 후속 구현 계약으로 연결한다. 제안된 `--adapter five-node-lab --inventory ... --dry-run`은 #101 inventory와 PostgreSQL 등록/heartbeat/profile을 읽기 전용으로 대조하고 CP 겸임 Node를 disruption target에서 제외할 뿐, 아직 구현되거나 실행되지 않았다.

측정 순서는 다음과 같다.

1. 각 node에 CPU offer와 현재 observation을 만들고, 합성 shard location에 두 개의 verified replica를 둔다.
2. 실제 `mark_lost_nodes`를 poll해 departure 시각부터 `lost` 전이까지 wall-clock 지연을 잰다. 같은 트랜잭션에서 떠난 node의 replica가 `stale`인지 확인한다.
3. 실제 `locations_needing_repair`가 모든 부족 shard를 찾는지 확인하고, 15초 freshness로 survivor replacement candidate를 다시 계산한다. fresh candidate가 없으면 복구를 진행하지 않는다.
4. dev 방법 검증에서만 owner fixture가 verified replacement row를 넣고 실제 `replica_health`가 healthy로 복귀했는지 센다. 이는 bytes transfer나 `inv.shard_recovery` 실행 재생이 아니며 `operationalAcceptanceAssessed=false`로 고정된다.
5. JSON에는 반복별 지연·candidate·stale·시도/복구 수와 min/p50/p95/max·성공률·finding을, JUnit에는 실행 결과를 남긴다. 기준 미달도 JSON을 먼저 보존한 뒤 JUnit failure와 non-zero exit로 드러낸다. `measurementClock=harness-process-wall-clock-utc`는 지연이 PostgreSQL 시계가 아니라 하네스 프로세스의 `datetime.now(UTC)` 두 표본 차이임을 명시한다.
6. JSON의 최상위 `codeSha`와 `provenance`는 실행 checkout SHA, integration SHA/동기 여부, working tree/content clean 여부, KST 수집 시각과 executor를 기계적으로 남긴다.

## 판정 경계와 finding

- **F-S07-02:** 현재 public replica repair는 상태 전이와 계획까지만 제공한다. 합성 verified replacement 성공률은 하네스와 DB 경계를 검증하지만 실제 bytes 이동, checksum 재계산, execution shard replay 성공률 95%를 증명하지 않는다.
- **F-S07-03 / O4 결정:** liveness 술어 `last_seen < now - timeout`은 변경하지 않는다. AC-07의 “60초 감지”는 **liveness timeout 60초 설정 시 감지 지연 ≤ 60초 + poll 간격**으로 정의한다. 따라서 `--max-detection-seconds` 생략 시 기본값은 timeout+poll이고, 명시값은 그대로 존중한다. dev PC의 60.066591초/JUnit red는 과거의 정확 60초 상한 판정 기록으로 보존한다.
- 15초 kernel freshness는 survivor가 heartbeat와 observation을 계속 보내면 유지된다. 측정기는 이를 실제 제품 경로로 갱신하며, fresh candidate가 0이면 F-S07-01을 기록하고 복구를 fail-closed한다.
- shard recovery의 project root/project resource lock 경합은 이 하네스가 재지 않는다. JSON의 `projectLockContentionMeasured=false`를 물리 랩 결과에서도 지우지 않는다.

## dev PC 예비값

N=3, R=3, 축약 timeout 1초, poll 0.1초, 최대 1.5초에서 감지 min/p50/p95/max는 1.006620/1.028969/1.116285/1.116285초였다. 떠난 replica stale 3/3, fresh replacement candidate 3/3, 합성 shard proxy 3/3(1.0)이었다. migration·난수 role 정리를 포함한 pytest는 1 passed, JUnit exit 0이다. 이 값은 5노드·60초·물리 bytes 복구 판정이 아니다.

## 5-node 랩 재실행 한 줄

전용 opt-in 5-node lane은 물리 5-node lab의 수동 workflow에서만 명시적 DSN·topology로 실행하며 기본 Backend/Core pytest 수집에는 넣지 않는다. 아래 한 줄은 lab PostgreSQL에서 동일한 **합성 N=5 측정 shape**를 재현한다. 물리 node agent 중단·실제 bytes transfer를 자동화하지 않으므로 결과는 여전히 운영 인수와 분리한다.

`$env:PYTHONPATH='src;services/control-plane/src'; $env:PYTHONUTF8='1'; .venv\Scripts\python.exe tools\measure_s07_recovery.py --nodes 5 --repetitions 20 --liveness-timeout-seconds 60 --poll-interval-seconds 0.1 --target-recovery-success-rate 0.95 --json-out .work\s07-lab-5node.json --junit-out .work\s07-lab-5node.xml`

위 명령은 여전히 **합성 N=5**다. 물리 준비 상태를 합성 row 없이 확인할 미래 인터페이스는 아래와 같으며 현재는 사양일 뿐 복사·실행할 수 없다.

`python tools/measure_s07_recovery.py --adapter five-node-lab --inventory "$LAB_INVENTORY_PATH" --dry-run --json-out "$LAB_EVIDENCE_ROOT/preflight/s07-five-node.json"`

이 preflight가 green이어도 실제 Node process 중단·이탈 20회·bytes/checksum/replay 복구는 별도 승인과 구현이 필요하다.
