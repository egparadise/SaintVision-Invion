**환경 조치 후 재판별**(harness f4b3f73, digest b93b5ef1f944, 조용한 조건, 증거 `.work/postod-quiet-determination-tests.{xml,json}`): **4 passed / 2 failed / 2 skipped**(사용자 실측; Codex 증거 대조로 아래 정정 반영).

확정적으로 말할 수 있는 것(과잉 해석 배제):
- **이번 실행 NTSTATUS 0xC0000142 = 0건**(증거 XML grep: 3221225794·C0000142 모두 0회). 이전 실행들의 host-init 실패가 이번 실행에는 관측되지 않았다.
- **핸들 실측**: 641,442 → 2,421(OneDrive 재시작 후). 
- **인과 미확정 — 엄밀한 통제 실험 아님**: 이번 4차는 harness(f4b3f73)가 이전 실행과 다르고, 변경된 변수가 최소 셋(OneDrive 재시작·잔재 컨테이너 2개 제거·조용한 구간 확보)이라 **한 변수만 바꾼 통제 실험이 아니다.** 따라서 host-init 소거를 OneDrive 단일 원인으로 귀속할 수 없다 — 확정은 "이번 실행 host-init 0건"과 "핸들 641,442→2,421" 두 관측뿐이다.
- **R5-01에 대해 이번 실행이 보여준 범위**: timeout 케이스가 `host condition prevented verification (unverified, not failed)` + `docker operation timed out 90s`로 **skip**된다는 것 — 즉 timeout이 실패가 아니라 이유 있는 미검증으로 기록됨. **본문 실패+cleanup 실패가 겹치는 보존 시나리오까지 이번 실행이 검증한 것은 아니다**(그 근거는 내 기존 회귀 `tests/test_vf_docker.py`이지 이번 실행이 아니다).

**판정 갱신(케이스별)**: **신규 검증 3건** — writable·business(이전 **host-init 계층** 미도달), unreadable(이전 **timeout 계층** 미도달·별도) → §1 승격. **범주 변경 2건** — public-signing-key·business-workspace = daemon i/o timeout(CLI 실행됨, daemon 응답; 환경/부하 조건이지 제품 보안 단언 실패 아님 — 제품 결함 여전히 0). **미검증 유지 1건** — business-kernel-role. workspace는 3차 pass→4차 skip(부하 변동). (b5f770a host-init 5건 = writable·public-signing-key·business·business-workspace·business-kernel-role; unreadable만 timeout — 사용자 재파싱 정정.)

- **daemon i/o timeout 범주(관측)**: host-init(프로세스 미실행)과 달리 CLI가 실행돼 daemon이 i/o timeout으로 응답 — 여전히 **환경/부하 조건이지 제품 단언 실패가 아니다**(증거 stderr에 falsifiable). 현재 `is_infrastructure_failure`는 host-init+TimeoutExpired만 미검증(skip)으로 보고 daemon-error는 fail 처리하므로 이 2건이 **failed로 기록**된다. **제안(미구현)**: daemon i/o-timeout 계열(`i/o timeout`/`context deadline exceeded` 등 timeout류만 좁게)을 인프라(미검증)로 분류해 skip 처리하면 "환경이 실패로 위장" 잔여를 닫는다 — 실 docker 오류를 가리지 않도록 좁게. 사용자/Codex 판단 대기(분류기는 Codex 검토 접점).

### 2.2 잔여 판별 조건 (business-kernel-role)

- **관측 사실(확정)**: 핸들 641,442→2,421(265배 감소, 재시작 후), 가용 RAM 896→938MB(거의 불변), 이번 실행 host-init 0건. business-kernel-role은 여전히 timeout으로 미도달.
- **해석(hedged, 미확정)**: host-init 0건과 핸들 감소가 같은 실행에서 관측됐으나 변수가 여럿이라 인과는 미확정. business-kernel-role이 여전히 timeout인 것은 **RAM이 거의 불변인 점과 정합적**이라 잔여 요인이 메모리일 **가능성**을 시사(확정 아님).
- **선행 조건(갱신)**: 잔여 판별에는 **메모리 여유** 확보가 관건으로 보임 — 동시 컨테이너/프로세스 메모리 압박 완화. 사용자 환경 몫.
- **재실행 대상/명령**: 3차와 동일(`run_vf_security_tests.py` 또는 `docker_host` lane의 `test_server_container.py`). timeout이면 R5-01이 미검증(skip)으로 정확히 기록.
- **판별 기준**: business-kernel-role이 보안 단언(잘못된 kernel DB role이 INV_BUSINESS_DSN으로 쓰일 때 DB가 거부)에 **도달**해 pass/fail이 나오면 판별. 도달 못 하면 여전히 미검증.
- **착지와의 관계**: 미검증은 **호스트 조건 문제이지 브랜치 착지 blocker가 아니다**(착지 완료, 이 판별은 운영 인수 트랙).
