## 구현된 내부 기능과 검증의 경계

| 기능 | 구현 내용 | 확인한 증거와 한계 |
|---|---|---|
| 명시적 독립 샤드 계획 | 1~16개, 각기 다른 Run/command, `splittable=True`, `communication=none`, scope·사전 승인·Lease/fence 검사 | 선언 없는 분할 및 MPI/NCCL 거절 시험. 16개 최대치 실장비 시험은 없음 |
| 계획의 원자 등록 | plan/claim/queue/link/outbox를 하나의 transaction으로 저장, 내용 digest와 중복 제출 검사 | 두 번째 admission 실패 시 앞의 claim/queue/plan rollback; 4개 동시 제출에서 queue 한 세트 |
| 실제 프로세스 전달 | durable worker → mTLS → Go Node → 격리 Docker → stop receipt | 한 합성 Node에서 두 샤드 순차 실행, receipt 2개 및 Lease 반환. 여러 물리 Node 동시 실행/gang scheduling 증거는 아님 |
| 성공과 물리 종료 구분 | `allPhysicallyStopped`와 `allSucceeded` 분리 | 종료 receipt만 있으면 결과 성공은 false, manifest 없음 |
| 결과 manifest | 모든 현재 attempt의 Evidence·결과 commitment·ready object가 있어야 index 순 결과 목록 및 digest 반환 | trusted verifier의 합성 byte를 실행 전달 전에 준비하는 시험. 실제 컨테이너 결과 수집/계산 reducer/부모 Run 성공은 아님 |
| 전체 취소 요청 | 현재 project 권한 검사, 비종료 Run의 일괄 cancel, replay, transaction rollback | 취소 후 기존 Lease 4개 유지 및 다음 queue operation=cancel 확인까지만 시험. 전체 물리 종료/자원 회수 여정은 별도 |
| 실패 receipt 반영 | 현재 attempt의 비정상 receipt를 failed로 반영하고 중복 반영/자동 재실행 방지 | 이 샤드 시험은 trusted receipt fixture 사용. 실제 비정상 컨테이너 receipt 시험은 별도 Node suite에 있음. 자동 호출 연결은 없음 |

**원자성의 범위:** `enqueue` 전에 개별 Lease가 이미 예약되어 있다. admission 실패 시험은 계획/claim/queue가 0으로 되돌아가도 예약 4개가 남는 것을 명시한다. 따라서 배치·예약·승인·계획 생성 전체가 한 transaction이라고 보고하면 안 된다. 전송 여부를 증명하는 안전한 미시작 취소/보상 계약이 필요하다.

## Adapter에서 반드시 맞출 차이

- Claude API는 shardCount 1~1024, Codex runtime은 1~16이다. 초기 실행 계약은 16 이하로 제한하고 초과 요청을 queue 전에 명시적으로 거절해야 한다. 임의로 잘라 일부만 실행하면 안 된다.
- Claude 계획은 한 Run을 참조하지만 Codex는 샤드마다 서로 다른 Run/command를 요구한다. parent/child 관계와 `placed/running/completed` 대 정본 Run/Evidence 상태를 매핑해야 한다.
- 계획의 CPU cores는 float, 정본 CPU 예약은 정수 millis다. 부정확한 반올림/자원 축소 없이 단위 변환과 유효 범위를 검증해야 한다.
- `data_parallel/sharded` 문자열이나 `splittableDeclared`만으로 독립 실행 또는 통신 지원을 증명할 수 없다. workload별 통신 요구를 명시하고 현재 미지원 profile은 거절한다.
- Claude idle-first 후보와 정본 가중치 Scheduler/현재 관측/quota를 조율해야 한다. 설명용 계획만으로 자원을 확보했다고 표시하지 않는다.
- `ResultStore.prepare`는 유효한 실행 권한과 stop receipt의 CP 기록 전에 필요하다. 현재 NodeDelivery는 receipt를 즉시 기록하고 Node는 컨테이너 삭제 확인 뒤 receipt를 반환한다. 출력은 삭제 전에 별도 보존해야 하며 현재 합성 결과 시험을 실제 출력 수집 성공으로 대체할 수 없다.
