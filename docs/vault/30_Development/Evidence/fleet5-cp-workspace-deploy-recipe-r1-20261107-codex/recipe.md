# PC3 workspace API deployment recipe R1

This is a source recipe, with a concrete portal defect and a cutover constraint. A workspace-enabled API can run on Linux PC3 with the existing candidate environment, offline public JWKS and two restricted database roles. Configuring that API alone cannot make the fixed portal dispatch a first Workspace Run: its request disagrees with the kernel contract. No operation is delegated or performed here.

`identity` accepts exactly the constructor fields `tenant_id`, `issuer`, `audience`, `client_ids`, `jwks_file`. It requires future expiry no more than seven days away, one to eight unique-kid RSA2048–4096 public RS256 signing keys and no private `d`. A raw Keycloak `{"keys":...}` document is insufficient. Root copies an approved current public bundle; there is no discovery, `jku` lookup or issuer HTTP fetch. PC3 loopback issuer reachability is therefore unnecessary for API token verification. This does not fix the browser's separate IdP certificate trust or prove browser selection/flicker acceptance. Bindings **offline-jwks**, **offline-token**, **business-identity**.

TLS uses a separate CP client certificate/key and explicit Node-server CA, with TLS1.3/strict chain and endpoint identity/hash checks. `workingRoot` and `restoreRoot` must already exist as absolute private Linux service-owned directories; checks use euid, permissions, nofollow handles and pinned inode/device. The object root also requires matching service ownership/private permissions and stable inode/device. Root uses fresh owned application paths separate from every old Node journal/state and from all Node mounts. API and worker need the same approved service identity to access these roots. They need no Docker socket. The example pairs `snapshotObjectRoot`/`restoreRoot` and gives the worker `outputRoot` equal to the same object root so API result reads can resolve worker publications. Without a provider, `OutputIngestion.once` returns idle; successful process exit alone will not publish completion. This local service store is not contributed storage or a host-path workload grant. ## Current portal routing and mandatory constraint

At the fixed source, API callers pass relative `/v1/...` paths to `fetch(endpoint)`; there is no frontend API-base setting. `window.__SAINTVISION_CONFIG__` configures OIDC, not the API upstream. The Vite server proxies `/v1` to startup-time `VITE_API_PROXY_TARGET`, default`http://127.0.0.1:8080`; the source's default browser port is3000, whereas current3100 is a Root runtime fact. The actual running3100 launch/config bytes were not among authorized public inputs, so this worker cannot claim its currently bound upstream or launcher. Bindings **web-api**, **web-auth**, **vite-proxy**, **web-scripts**.

For a Vite-backed3100 portal, the smallest future route is an explicitly Root-owned pinned **main-loopback18080 -> PC3-loopback8080** SSH forward, then `VITE_API_PROXY_TARGET=http://127.0.0.1:18080` on the portal's verified launcher. Port18080 is a proposed unreserved slot. This preserves browser origin/SSO callback and carries bearer headers through same-origin `/v1`; the API exact Origin allowlist must match the actual browser. Changing only PC3 config or `auth-config.js` cannot change an already-running Vite proxy. Applying the environment requires a new/reconfigured portal process; no hot-update mechanism is present in this source. That main Node/app operation is **outside the present restriction**, so cutover remains Root-only and unapplied. No transparent takeover of main8080, process kill, new browser origin or IdP change is inferred. A frontend rebuild is unnecessary merely to change Vite's proxy target, but the UI repair below needs an updated build/deployment, produced away from restricted main.

If the actual3100 server is the production Nginx layout instead, its [the portal upstream file](https://github.com/egparadise/SaintVision-Invion/blob/1efea494f026e932360c35ae811b6423d874a2e7/deploy/intranet/portal/conf.d/upstream.conf#L1-L7) selects `control_plane`; REST, events and workspace WebSockets all use `https://control_plane` with explicit CA verification and name`cp.sv.lan`. Pointing that host at a plain HTTP PC3 API is not sufficient: Root needs an already approved matching TLS ingress and controlled proxy reload. This alternate is source-supported but not claimed to be the actual3100 process. Bindings **nginx-routes**, **nginx-upstream**.

Events are `/v1/projects/{project}/runs/{run_id}/events`, authenticated bearer SSE, Last-Event-ID, repeated grant/token checks and a25-second stream. Nginx has unbuffered event forwarding. The general frontend SSE helper does not inject Bearer and has no consumers in fixed `apps/web/src`; actual Studio uses authenticated Run polling. No SSE UI acceptance is claimed. WebTerminal requests a one-use ticket and uses the returned `/v1/workspaces/{workspace}/terminals/{session}` path on the browser host (special port3000 shortcut goes127.0.0.1:8080;3100 uses its own host), with `inv-terminal-v1` and ticket in the first frame. Vite has no explicit `ws:true` in this source; no WebSocket forwarding acceptance is inferred. The CPU pilot has terminal disabled, so enabling it is not part of this minimal route. Bindings **api-events**, **web-sse**, **web-run-poll**, **web-ws**, **api-terminal**.
