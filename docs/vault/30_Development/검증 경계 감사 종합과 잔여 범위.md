## 공통 구조와 반복 이유에 대한 관찰

가장 흔한 구조는 서로 다른 사실을 하나의 성공 값으로 대신하는 것이다. factory를 얻지 못함과 의도된 거부, 프로세스 종료0과 본문 실행/증거 완성, HTTP 필드 일치와 실제장비 관측, hash를 계산함과 실제 원본을 확인함은 다르다. API smoke 자체는 유효해도 명칭·최종 배너가 범위를 넓히면 인수 근거가 부풀려진다.

소스로 확인한 반복 요인은 (1) bool/exitcode/PASS라는 좁은 출력 모델, (2) 고정 파일명과 실행 귀속 부재, (3) 보안 진단 억제나 best-effort 정책이 오류 종류를 합치는 넓은 예외 처리, (4) 단계마다 수작업으로 붙인 검사가 한 곳에서 빠지는 일관성 문제다. LAUNCH에서 네 단계 중 TLS만 빠진 것은 이 마지막 유형의 구체 사례다. 이를 특정 작성자의 능력·동기나 조직 전체 문화로 일반화할 근거는 없다.

또한 정상 경로 시험은 통과하면서 이 결함들이 남아 있었다. 음성 대조군이 실제 runner/helper를 지나지 않거나, 목표 단언 도달 전제 자체가 시험되지 않으면 기존 pass 수가 경계의 빈틈을 드러내지 못한다. 재사용 fixture도 내부 오류 없이 성공하는 경우만 보면 부분할당·teardown 실패를 놓친다. 이는 표본에 대한 설명이며 발생 빈도·저장소 전체 결함률·호스트 자원 고갈의 인과를 추정하지 않는다.

실천 기준은 요청범위/실제 도달/관측/증거저장/정리/최종판정을 별도로 기록하고, 각각에 실패 대조군을 둔다는 것이다. 문서의 독립검토·CI·운영 인수도 같은 이유로 합치지 않는다.
