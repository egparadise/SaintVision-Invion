# S05 배치 잠금 입도 결정 제안

> [!warning] 결정 상태
> 코디네이터의 2026-09-23 03:30 KST **(b) legacy 유지·5노드 후 재판단**은 계속 유효하다. Card24 B′ 교정 실험은 세 판정 조건을 모두 실패해 승격하지 않았고 다음 설계 후보를 B(project별 bounded semaphore)로 확정했다. B는 아직 사양 착수 근거만 있고 구현 승인은 아니다. `placementShortCommit` 기본 off, candidate budget 기본 500ms, S05-DB `review`, 20동시 초과·50동시·5노드 미승격을 유지한다.

## v1.6 — 옵션 B 사양 작성, 구현 대기

[[S05 project별 bounded semaphore 사양]]은 canonical tenant+project별 process-local non-blocking 상한을 정의한다. Claude 카드 28 F-1에 따라 Card24 `767.708ms`는 queue observer를 포함한 상한으로 정정했다. sampler-off candidate 1500×1은 20/20·timeout 0, hold p50/p95/max 55.469/155.873/234.974ms였다. 보수적 max에서 N=4의 최장 예상 구간 469.948ms는 500ms 안이고 N=5의 704.922ms는 넘으므로 첫 옵션 B 실험값을 4로 정한다. 실제 semaphore 20×3 전 zero-timeout은 주장하지 않는다. [[s05-card25-sampler-off-6c389a1d.json]].

diagnostic on/off에 따른 큰 측정 차이로 F-1 관측자 효과는 확인됐지만 차이 전부를 `pg_blocking_pids` 하나에 귀속하지 않는다. Claude 카드 32는 sampler-off candidate 1500×1 재현 wave 1회를 조건으로 N=4 산술과 단일-wave 한계를 검토한다. 추가 wave는 그 승인 전 실행하지 않는다.

permit은 exact replay 분류 뒤 신규 예약에만 적용하고 root transaction commit/rollback 뒤 반환한다. `BoundDatabase` 조기 release, permit 누수, cross-tenant coupling을 금지한다. process P개에서는 최악 `P×N`이므로 전역 FIFO·multi-CP 상한을 주장하지 않는다. semaphore reject도 외부 실패 합계에 포함해 빠른 503으로 timeout을 숨기지 않는다. 현재는 docs-only이며 Claude 검토와 코디네이터 별도 승인 전 구현·시험·20동시 측정을 하지 않는다. [[2026-09-23_13-28-00_KST_S05_bounded_semaphore_사양_Codex]].

## v1.4 초안 — F-S05-02 기전 확정과 B′→B 우선

Card21은 같은 코드 SHA `40b24329`에서 PostgreSQL 16 disposable DB 두 개를 사용해 legacy 20×1과 idempotency→projects FK만 제거한 대조 legacy 20×1을 실행했다. 원본은 20/20 성공, depth 1, transaction acquired segment 190, tuple segment 0, `pgrowlocks`의 Key Share+For No Key Update, `55P03` 0이었다. FK-DROP 대조군은 2/20 성공, depth 19, tuple segment와 최대 499.957ms 대기, `55P03` 18이었다. 두 단일 파일은 exit 0, DB/role 잔존 0이며 20동시 초과·candidate·50동시는 실행하지 않았다. [[s05-lock-wait-card21-40b24329.json]].

따라서 F-S05-02의 기전은 제품 경로에서 **실험으로 지지됐다**. idempotency INSERT의 FK RI KEY SHARE가 이후 project `FOR NO KEY UPDATE`의 tuple-lock FIFO를 우회해 waiter가 현재 holder xid를 직접 기다린다. holder 교체마다 `lock_timeout` 500ms가 새 구간에 다시 적용되므로 원본은 `55P03` 없이 완료할 수 있고, 비FIFO 재경쟁에서 대기 합이 `statement_timeout` 2초에 닿으면 과거 wave처럼 `57014`가 된다. candidate limits 행은 같은 선행 FK 잠금이 없어 FIFO가 누적되며 한 구간이 약 500ms를 넘으면 `55P03`이 된다. 이 인과는 [[S05 log_lock_waits opt-in 재실행 설계]] v1.2, Claude 카드 23 설계 검토, 이 구현/실측, 후속 Claude 카드 24를 근거 묶음으로 삼는다.

### 우선 옵션 B′ — candidate limits 대기 예산 500→약 1500ms

- **불변식:** limits `FOR UPDATE`·FIFO, idempotency/fencing/epoch/RLS, ceiling·offered·active의 같은 transaction 원자성, 기존 `RES-0007`/503/retryable 표면을 유지한다. `statement_timeout=2s`보다 짧은 상한과 exact replay를 유지한다.
- **변경 범위:** `placementShortCommit=true` 내부 candidate limits lock statement에만 명시적 1500ms 이하 예산을 적용한다. legacy와 다른 커널 transaction, direct lease, 공개 schema·route·오류 코드는 바꾸지 않는다. 기본 flag는 off다.
- **위험:** fail-fast가 최대 약 1.5초로 느려지고 깊은 FIFO 큐는 여전히 `55P03` 또는 2초 `57014`에 닿을 수 있다. timeout만 늘려 throughput을 해결했다는 주장은 금지한다.
- **판정 기준:** 대칭 legacy/candidate 20동시 각 3회에서 외부 `55P03+57014` 합계가 legacy 이하, 요청 P95 중앙값이 legacy 대비 비악화, 성공 request의 post-acquire hold P95가 legacy 대비 비악화여야 한다. 성공 수만으로 통과시키지 않으며 queue depth·wait p95·timeout statement를 함께 기록한다.
- **롤백:** 내부 설정 flag를 끄고 candidate 전용 예산을 제거해 공통 500ms로 복귀한다. migration·데이터 cleanup은 없다.

### 후속 옵션 B — project별 bounded semaphore fail-fast 상한

- **불변식:** semaphore는 DB의 idempotency·Run·ceiling·Lease 원자성을 대체하지 않고 lock 진입 전 부하 상한만 둔다. permit은 tenant+project로 격리하고 exception/cancel/process 종료에서 반드시 반환하며 기존 retryable `RES-0007`만 사용한다.
- **변경 범위:** 단일 CP 현재 토폴로지에서는 process-local bounded semaphore와 queue-depth/거절 metric, 기본 off flag를 추가한다. 다중 CP로 확장하기 전에는 분산 상한이라고 주장하지 않으며 그때 별도 정본·복구 설계를 결정한다.
- **위험:** permit 누수·idempotent replay 재진입·project 간 불공정, 너무 낮은 상한의 불필요한 503, 너무 높은 상한의 FIFO cascade가 있다.
- **판정 기준:** B′와 같은 20×3 비교에서 외부 timeout 합계 legacy 이하, 요청 P95 비악화, hold P95 비악화를 모두 만족하고, permit 누수 0·project/tenant 격리·같은 key replay·cancel/exception 반환 반례가 통과해야 한다.
- **롤백:** admission flag off 후 신규 진입을 즉시 우회하고 process-local permit 상태를 폐기한다. committed Lease는 건드리지 않는다.

### 옵션 A — 기전 확인용으로만 유지

선행 약한 잠금과 최종 `FOR NO KEY UPDATE` 전환은 Card21이 확인한 비FIFO 기전을 candidate에 재현할 수 있지만, 기아·thundering herd·2초 `57014`를 다시 만들고 fail-fast 목표와 충돌한다. 제품 정책 후보가 아니며 별도 disposable probe 외 구현하지 않는다.

v1.4의 정책 우선순위는 Card21 판정과 **순서 비의존**이다. 구현은 Claude 카드 24가 코드·증거·문서 정직성을 승인하고 코디네이터가 별도 카드를 연 뒤에만 시작한다.

## v1.3 확정 — 결정 (b)와 P1/P2 결과

`placementShortCommit` flag-on 경로에서 database contention에 대한 내부 3회 retry를 제거했다. stale speculative decision의 최대 3회 재계획은 안전한 상태 재검증이므로 유지한다. limit row의 `55P03`은 첫 발생에서 기존 `RES-0007` / HTTP 503 / `retryable=true`로 반환되며 새 오류 코드·응답 필드·route는 없다. report schema v1.5는 legacy/candidate 모두 lock 획득 전 client elapsed와 획득 후 transaction-tail hold를 분리하고 parameter-free SQL observer의 slow/error statement를 남긴다.

개발 PC·합성 Node 1개·실 PostgreSQL·20동시·각 1회 카드 18 결과는 다음과 같다. legacy phase mark를 project limits 획득 뒤로 옮겼고, 두 mode 모두 hold는 **잠금 획득 뒤부터 transaction 종료까지** 같은 경계로 잰다.

| 모드 | 성공/실패·process exit | 요청 전체 P95 | 획득 후 hold P95 | lock 획득 client elapsed P95 | SQL timeout statement |
|---|---|---:|---:|---:|---|
| legacy / flag off | 20/0 · exit 0 | 1885.489ms | **289.365ms** | **1453.658ms** | `55P03` 0, `57014` 0 |
| candidate / fail-fast | 8/12 · exit 1 | 1054.907ms | **170.766ms**(성공 8개) | **528.705ms** | `project_resource_limits ... FOR UPDATE`, `55P03` 12 |

hold 289.365→170.766ms는 같은 계측 경계에서 방향상 감소했지만 candidate가 성공 8개만 남긴 **survivor 표본**이고 1회 측정이므로 옵션 1의 성능 통과 증거가 아니다. 외부 timeout은 0→12로 악화해 단계 3은 계속 미통과다. fencing 유일성과 no-overbooking은 두 mode 모두 true였으며 50동시·물리 5노드는 실행하지 않았다. 정본 수치는 [[s05-symmetric-metrics-card18.json]]에 있다.

### 같은 lock_timeout인데 legacy 1454ms와 candidate 55P03가 갈린 이유

코드에는 mode별 면제나 다른 설정 경로가 없다. 둘 다 같은 `Database.transaction`에서 `SET LOCAL lock_timeout='500ms'`, `statement_timeout='2s'` 뒤 placement SQL을 실행한다. SQL observer가 확인한 것은 다음 두 사실이다.

- legacy의 가장 느린 성공 event는 `projects ... FOR NO KEY UPDATE`이며 client-observed elapsed 최대 1492.238ms다.
- candidate 실패 12건은 전부 `project_resource_limits ... FOR UPDATE`에서 `55P03`, observer phase `placement-limit-row-wait`다.

그러나 report의 acquire elapsed는 SQL 호출 전후의 **client wall clock**이라 server heavyweight-lock wait만 재지 않는다. Python thread가 query 완료 뒤 다시 실행될 때까지의 scheduling/return delay도 포함하며 카드 18 실행은 backend별 `pg_stat_activity.wait_event` timeline을 수집하지 않았다. 따라서 legacy의 1453.658ms를 “같은 한 lock을 1.45초 연속 기다렸는데 lock_timeout을 면제받았다”고 해석할 수 없다. 설정 면제는 코드에서 확인되지 않았다.

Claude 카드 20의 제품 커널과 무관한 PG probe가 가설을 좁혔다. `lock_timeout=500ms`에서 holder chain depth 2 waiter는 서로 다른 lock 대기 구간을 거치며 타이머가 구간별로 다시 적용돼 총 728ms 뒤 획득했다. depth 3에서는 앞선 holder 시간이 한 대기 구간에 누적돼 각 holder가 500ms 미만이어도 `55P03`이 발생했다.

Card19의 실제 legacy 20동시 wave는 0.793ms arrival spread, 20/20 성공, request/acquire/hold P95 2142.809/1588.193/151.225ms였다. 5ms `pg_stat_activity` 표본 98개에서 max active 20, project-lock waiter 19, blocking chain depth 1, timeout 0을 관측했다. 이 wave 단독으로는 `log_lock_waits=off`라 원인이 미확정이었으나, Card21의 server log+pgrowlocks+FK-DROP 대조군이 위 v1.4 기전을 지지해 그 미확정 경계를 닫았다. [[2026-09-23_05-55-00_KST_S05_legacy_큐깊이_실측_Codex]], [[s05-legacy-queue-card19]], [[s05-lock-wait-card21-40b24329.json]].

Claude 카드 21의 커널 무관 probe가 제시한 정적 순서(`approvals.py:86` → `0001_core.sql:71` FK → `placement.py:132`)는 Card21 제품 경로 대조 시험에서 지지됐다. 원본의 19 waiter는 holder xid 교체를 0~18회 기록했고 tuple segment는 0이었으며, FK 제거만으로 depth 19 tuple FIFO와 `55P03` 18건이 나타났다.

후속 진단의 실행 경계·server log와 `pgrowlocks('inv.projects')` 상관·FK-DROP 반증·판정 기준은 [[S05 log_lock_waits opt-in 재실행 설계]] v1.2에 고정했다. 5ms sampler는 명목값이며 Card21 실제 p50/p95는 legacy 15.332/90.937ms, 대조군 29.270/980.542ms였다. 따라서 표본 밖 전이는 server log로 보완했고, raw PID/xid/log/DSN은 보존하지 않았다. disposable DB별 session default만 사용했고 `ALTER SYSTEM`·config reload·운영 DB 영향은 없었다.

다음 검토 순서는 위 v1.4의 B′→B다. A의 `FOR NO KEY UPDATE` 전환은 기전 확인용으로만 남긴다. 모두 별도 결정 전에는 구현하지 않으며 공개 retryable 계약, idempotency·fencing·RLS·원자성을 유지해야 한다.

> [!note] 계측 경계 O2/O3
> `BoundDatabase`가 caller-owned outer transaction에서 stale speculative winner를 savepoint rollback한 뒤 attempt 2로 재시도하면, transaction finalizer는 마지막 phase만 방출하므로 attempt 1의 post-acquire hold sample은 현재 누락된다. 카드 18 benchmark는 attempt마다 독립 `Database.transaction`을 사용해 이 경계의 영향을 받지 않았지만 model-retry 같은 nested 경로의 hold 집계는 attempt coverage가 불완전하다. 또한 운영 `app.py`는 `placement_metric_sink`를 주입하지 않으며 `record_placement_metric`의 logger fallback은 `placementShortCommit=true`일 때만 동작한다. 따라서 기본 legacy 운영 경로의 `legacyLockWait`/hold metric은 아직 자동 수집되지 않고, 현 수치는 benchmark가 명시적으로 sink를 주입한 evidence다. 두 제한을 해결하기 전 운영 dashboard 수치라고 부르지 않는다.

### 보류한 옵션 (a) — limit-row 입도 변경

- 후보는 kind별 ceiling/usage 행 또는 versioned usage CAS다. 그러나 모든 현재 요청이 CPU와 memory를 함께 예약하므로 단순히 두 kind 행으로 나누면 두 행을 모두 잠가 동일 hotspot을 남길 수 있다. 구현 전 실제 lock graph와 다중 Node 요청 조합으로 이득을 증명해야 한다.

- 롤백은 기본 off flag로 legacy row 읽기/기존 canonical lease 계산에 복귀하고, dual-write 중에는 parity 불일치 시 즉시 중단한다. additive table은 감사·복구를 위해 남기고 정상 Lease를 삭제하지 않으며 usage는 active Lease에서 재조정한다.

## 3. 옵션 1 — speculative read + 짧은 commit (조건부 권고)

### 3.1 설계

1. **speculative read:** 잠금 없이 permitted pool, observation, offered/active, policy를 읽고 후보·Explain·decision input을 계산한다. 아직 예약 권한은 없다.
2. **final commit:** idempotency와 Run을 잠그고 canonical admission 검사를 수행한 뒤 project limits와 선택 Node/Resource만 정렬해 잠근다.
3. 같은 transaction에서 membership/grant, ceiling, resource `active_total`/offered fit, Node epoch/heartbeat/skew/channel, observation receivedAt를 다시 읽는다.
4. speculative 입력과 하나라도 다르면 stale winner를 그대로 쓰거나 `RES-0001`로 끝내지 않는다. side effect 없이 rollback한 뒤 후보 계산부터 bounded retry한다.
5. 일치하면 기존 Lease·event·ledger·응답을 한 transaction으로 commit한다.

핵심 성공 지표는 project row 존재 여부가 아니라 **transaction별 project/limit/node/resource 잠금 최초 획득부터 commit/rollback까지의 잠금 보유 시간**이다. 개발 PC와 5노드 랩에서 요청별 lock-wait 포함 총 지연과 별도로 이 구간의 p50/p95/max, retry 횟수, SQLSTATE를 수집해야 한다. 옵션 1은 이 시간이 줄어야만 2초 statement timeout 도달을 늦추거나 제거한다.

### 3.2 남은 네 쟁점에 대한 설계 응답

| 쟁점 | v1.1 설계 응답 |
|---|---|
| decision digest / active fit | 기존 digest가 limits version·관측은 담지만 `active_total`/최종 fit 변화 자체를 충분히 대표하지 않는다. final commit은 각 resource의 current active+need ≤ offered와 project kind별 active+need ≤ ceiling을 다시 계산한다. 불일치나 no-fit은 후보 전체를 다시 계산하는 retry 사유이며 stale winner를 그대로 `RES-0001`로 확정하지 않는다. |
| Node/Resource row 병목 | 단일 Node pool에서는 선택 Node/Resource row가 모든 요청에 공통이라 project row를 제거해도 이득이 0일 수 있다. 다중 Node에서는 서로 다른 선택 집합만 병렬화 가능하다. 20동시 17/20 결과는 현 병목을 입증하지만 어느 row의 hold가 지배적인지는 아직 미측정이다. row별 wait/hold 계측 뒤 판단한다. |
| `leases.py:176` 두 번째 project lock | placement가 이미 project/limits/resources를 잠근 뒤 `_reserve_locked`가 project row와 limits/resources를 다시 잠근다. 동일 transaction에서는 재획득 자체보다 중복 primitive와 순서 불일치가 문제다. placement/direct lease가 하나의 canonical commit primitive를 호출하고 project mutex 정책을 한 곳에서만 적용하도록 합친다. |
| `require_*` 순서 | direct lease는 Run 뒤 `require_execution`→recovery→handoff→start를 거쳐 project/resources를 잠그지만 placement는 외부에서 project/resources를 먼저 잠근 뒤 내부 `require_*`를 호출한다. 네 admission 검사를 side effect 없는 한 묶음으로 Run 직후, project/node/resource writer lock 전에 실행하고 final commit 직전 필요한 mutable 근거만 잠금 재검증한다. 두 진입점의 순서를 동일하게 고정한다. |

### 3.3 retry와 계약

v1.1 설계 당시 항목이다. database contention의 내부 retry는 v1.3 fail-fast에서 제거됐고, 아래 bounded retry 설명은 stale speculative decision 재계획에만 남는다.

- retry 대상은 기존 `RES-0007`이면서 `retryable=true`인 contention 결과다. `55P03`과 `57014`를 evidence에는 구분하되 공개 오류 코드는 유지한다.
- 같은 principal·idempotency key·canonical body만 재사용하며 매 시도 새 transaction에서 권한·admission·epoch·freshness·fit을 다시 읽는다.
- 횟수와 총 wall-clock 상한을 두고 exhaustion은 기존 `RES-0007`로 반환한다. 임의 jitter로 후보 순서를 바꾸거나 `SKIP LOCKED`로 결정성을 훼손하지 않는다.
- 현재는 새 ProblemDetails 코드나 schema 변경이 필요 없다. 오류 표면을 바꿔야 하는 구현이 생기면 별도 계약 결정을 먼저 낸다.

### 3.4 변경 범위와 롤백

- migration: 1차 없음. 기존 limits·active Lease를 정본으로 유지한다.
- 코드: `placement.py`의 speculative/final validator 분리, `leases.py`의 공통 canonical commit primitive, lock hold 계측, legacy `project_serial` feature flag.
- 시험: exact replay/changed body, same Run, ceiling/offer, `55P03`/`57014`, epoch flip, heartbeat stale, membership/grant revoke, 네 `require_*`, direct lease 혼합, retry exhaustion, rollback 잔존 0.
- 배포: candidate 기본 off. 오류율·timeout·deadlock·retry·ceiling mismatch·lock-hold p95가 승인 임계치를 넘으면 `project_serial`로 되돌린다. 정상 Lease는 삭제하지 않는다.

## 4. 옵션 2 — batch 예약 API

예: `POST /v1/projects/{project}/placement-batches`에 1~50개 item을 제출하고 **all-or-nothing**으로 처리한다. 하나라도 권한·freshness·capacity·policy 검증에 실패하면 Lease·event·ledger를 모두 rollback한다.

- batch key는 canonical ordered item list의 request hash와 exact replay를 소유한다.
- 모든 item은 같은 tenant/project/principal이어야 하고 각 Run admission을 재검증한다.
- fencing은 각 Lease에 현재 epoch+단조 sequence로 발급하며 sequence gap은 허용하되 재사용하지 않는다.
- 새 route/schema/fixtures/TS·Go·Python binding과 max 50·원자성·오류 의미 결정이 필요하다.
- batch 자체도 Node/Resource lock hold가 길어질 수 있고, 50개 독립 요청의 AC-05를 한 요청으로 바꿔 통과 처리할 수 없다.

롤백은 route feature flag를 끄고 기존 단건 endpoint를 유지한다. 성공한 Lease는 삭제하지 않으며 durable batch table을 추가했다면 감사 이력을 위해 additive schema는 남기고 쓰기만 중단한다.

## 5. 옵션 3 — freshness 정책 변경 기각

- 15초 창 확대는 heartbeat가 끊겼거나 격리·epoch가 바뀐 Node의 오래된 capacity를 더 오래 허용한다.
- 요청 진입 시 snapshot을 동결하면 lock wait 뒤 stale observation을 commit한다.
- 20동시 실측 실패는 15초 freshness가 아니라 2초 statement timeout이다. freshness를 바꿔도 경합·잠금 보유 시간·P95는 고쳐지지 않는다.

freshness 자체를 바꾸려면 별도의 failure detector·격리·운영 SLO 결정이 필요하다.
