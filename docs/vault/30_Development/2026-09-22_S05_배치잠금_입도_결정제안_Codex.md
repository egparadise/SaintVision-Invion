# S05 배치 잠금 입도 결정 제안

> [!warning] 결정 상태
> 코디네이터는 2026-09-23 03:30 KST **(b) legacy 유지·5노드 후 재판단**을 채택했다. `placementShortCommit`은 기본 off, S05-DB는 `review`, 20동시 초과·50동시와 5노드 승격은 보류한다. 카드 18 P1/P2에서 대칭 hold·acquire elapsed와 SQL timeout statement를 계측했으며, 다음 후보인 candidate lock-timeout 예산/queue 깊이 상한은 Claude 검토 뒤 별도 결정한다.

## v1.3 확정 — 결정 (b)와 P1/P2 결과

`placementShortCommit` flag-on 경로에서 database contention에 대한 내부 3회 retry를 제거했다. stale speculative decision의 최대 3회 재계획은 안전한 상태 재검증이므로 유지한다. limit row의 `55P03`은 첫 발생에서 기존 `RES-0007` / HTTP 503 / `retryable=true`로 반환되며 새 오류 코드·응답 필드·route는 없다. report schema v1.5는 legacy/candidate 모두 lock 획득 전 client elapsed와 획득 후 transaction-tail hold를 분리하고 parameter-free SQL observer의 slow/error statement를 남긴다.

개발 PC·합성 Node 1개·실 PostgreSQL·20동시·각 1회 카드 18 결과는 다음과 같다. legacy phase mark를 project limits 획득 뒤로 옮겼고, 두 mode 모두 hold는 **잠금 획득 뒤부터 transaction 종료까지** 같은 경계로 잰다.

| 모드 | 성공/실패·process exit | 요청 전체 P95 | 획득 후 hold P95 | lock 획득 client elapsed P95 | SQL timeout statement |
|---|---|---:|---:|---:|---|
| legacy / flag off | 20/0 · exit 0 | 1885.489ms | **289.365ms** | **1453.658ms** | `55P03` 0, `57014` 0 |
| candidate / fail-fast | 8/12 · exit 1 | 1054.907ms | **170.766ms**(성공 8개) | **528.705ms** | `project_resource_limits ... FOR UPDATE`, `55P03` 12 |

hold 289.365→170.766ms는 같은 계측 경계에서 방향상 감소했지만 candidate가 성공 8개만 남긴 **survivor 표본**이고 1회 측정이므로 옵션 1의 성능 통과 증거가 아니다. 외부 timeout은 0→12로 악화해 단계 3은 계속 미통과다. fencing 유일성과 no-overbooking은 두 mode 모두 true였으며 50동시·물리 5노드는 실행하지 않았다. 정본 수치는 [[s05-symmetric-metrics-card18.json]]에 있다.

### 같은 lock_timeout인데 legacy 1454ms와 candidate 55P03가 갈린 이유

코드에는 mode별 면제나 다른 설정 경로가 없다. 둘 다 같은 `Database.transaction`에서 `SET LOCAL lock_timeout='500ms'`, `statement_timeout='2s'` 뒤 placement SQL을 실행한다. SQL observer가 확인한 것은 다음 두 사실이다.

- legacy의 가장 느린 성공 event는 `projects ... FOR NO KEY UPDATE`이며 client-observed elapsed 최대 1492.238ms다.
- candidate 실패 12건은 전부 `project_resource_limits ... FOR UPDATE`에서 `55P03`, observer phase `placement-limit-row-wait`다.

그러나 report의 acquire elapsed는 SQL 호출 전후의 **client wall clock**이라 server heavyweight-lock wait만 재지 않는다. Python thread가 query 완료 뒤 다시 실행될 때까지의 scheduling/return delay도 포함하며 이번 실행은 backend PID별 `pg_stat_activity.wait_event` timeline을 수집하지 않았다. 따라서 legacy의 1453.658ms를 “같은 한 lock을 1.45초 기다렸는데 lock_timeout을 면제받았다”고 해석할 수 없다. 설정 면제는 코드에서 확인되지 않았고 실제 server-side wait 구간이 500ms 미만이었는지, CPU/thread scheduling이 나머지를 만들었는지는 **미확정**이다. 이는 [[2026-09-23_01-05-00_KST_F-S05-02_57014_원인분리_Codex]]의 경계를 유지한다. 카드 18 두 wave에는 `57014`가 없어 새 statement 귀속도 하지 않는다.

다음 검토 후보는 새 migration이 아니라 **candidate 대기 정책**이다. (1) 현재 transaction 전체의 2초 예산 안에서 limit-row `lock_timeout`만 bounded 조정하거나 (2) 서버 진입 전 project별 queue 깊이 상한으로 20개가 같은 row에 동시에 줄 서지 않게 하는 선택지를 비교한다. 공개 retryable 계약, idempotency·fencing·RLS·원자성은 유지해야 하며 아직 결정·구현하지 않는다.

### 보류한 옵션 (a) — limit-row 입도 변경

- 후보는 kind별 ceiling/usage 행 또는 versioned usage CAS다. 그러나 모든 현재 요청이 CPU와 memory를 함께 예약하므로 단순히 두 kind 행으로 나누면 두 행을 모두 잠가 동일 hotspot을 남길 수 있다. 구현 전 실제 lock graph와 다중 Node 요청 조합으로 이득을 증명해야 한다.
- additive migration은 `(tenant, project, kind)`별 limit/usage/version 정본, 기존 limits backfill, RLS·FK·DEFERRABLE 여부, direct lease와 placement의 한 잠금 순서를 설계한다. lease reserve/release/stop, expiry/reconcile, restore, containment, model-retry가 같은 counter를 원자적으로 증감·복구해야 한다.
- multi-kind CAS는 CPU만 성공하고 memory가 실패하는 부분 예약을 허용하지 않는다. idempotency, fencing/epoch, exact replay, active lease 합계와 usage parity, crash-before/after-commit, stale version, 두 tenant RLS, release 중복을 실 PG에서 검증한다.
- 공개 HTTP/ProblemDetails 계약은 유지하는 것이 목표다. 새 오류 코드, backoff header, batch 의미가 필요하면 이 옵션과 분리해 계약 결정을 먼저 낸다.
- 롤백은 기본 off flag로 legacy row 읽기/기존 canonical lease 계산에 복귀하고, dual-write 중에는 parity 불일치 시 즉시 중단한다. additive table은 감사·복구를 위해 남기고 정상 Lease를 삭제하지 않으며 usage는 active Lease에서 재조정한다.

### 채택한 옵션 (b) — legacy 유지 후 5노드 재판단

- `placementShortCommit=false`를 유지하고 새 migration·counter 정본을 만들지 않는다. inventory-bound 5노드 adapter와 lane이 준비된 뒤 legacy 20동시 canary를 먼저 실행하며, 50동시는 별도 승인 전 금지한다.
- 장점은 현재 계약·복구 writer·counter drift 위험을 늘리지 않는 것이다. 단점은 개발 PC 최종 세트에서 이미 20동시 `57014` 2건과 P95 변동을 관측했으므로 AC-05 개선을 약속하지 못한다는 점이다.
- 물리 lane 결과는 개발 PC 합성 Node 수치를 대체하지 않고 별도 증거로 남긴다. 결과가 red이면 S05-DB `review`를 유지하고 option (a) 또는 batch 계약을 다시 결정한다.

## v1.2 당시 구현 판정 — F-S05-03 경합 재배치

> [!note] 역사적 기준선
> 이 절의 내부 bounded retry와 20/20 결과는 카드 14 당시 기준선이다. 현재 동작과 결정 요청은 위 v1.3 절이 정본이다.

`placementShortCommit`은 기본값 `false`인 운영자 설정이다. flag on에서는 무잠금 speculative read 뒤 idempotency → Run/네 admission 검사 → project ceiling → 선택 Node/Resource 순으로 final commit하고, 선택 집합의 membership·관측·epoch·channel·offered를 digest로 재검증한다. `active_total` 변화만으로 winner를 버리지 않고 잠긴 resource에서 fit을 다시 계산하며, no-fit 또는 나머지 mutable 입력 변경만 side effect 없는 savepoint rollback 뒤 후보 계산부터 최대 3회 재시도한다. placement와 direct lease는 canonical admission/prepared primitive를 공유한다. 공개 응답·오류 schema는 바뀌지 않았다.

개발 PC·합성 Node·실 PostgreSQL·20동시·각 3회 결과는 다음과 같다. 두 모드 모두 매 회 20/20 성공·exit 0이었고, 50동시와 물리 5노드는 실행하지 않았다.

| 모드 | 요청 성공 P95(ms) 3회 | 요청 P95 중앙값 | commit lock-hold P95(ms) 3회 | hold P95 중앙값 | 내부 `55P03+57014` |
|---|---|---:|---|---:|---|
| legacy / flag off | 2342.143 / 1607.483 / 1771.763 | **1771.763ms** | 1803.721 / 1325.524 / 1399.883 | **1399.883ms** | 0 / 0 / 0 |
| candidate / flag on | 1862.488 / 1697.737 / 1656.683 | **1697.737ms** | 118.644 / 130.355 / 122.126 | **122.126ms** | 14 / 10 / 11, 모두 limit-row `55P03` |

당시에는 조건 1인 hold P95 감소를 충족으로 판정했지만 카드 19 F-C1이 legacy는 대기 포함, candidate는 대기 제외였음을 확인해 그 판정을 철회한다. 요청 P95 중앙값 개선은 **74.026ms(약 4.2%)**로 작고 조건 2인 timeout 감소는 악화됐다. candidate는 project mutex의 긴 임계구역을 줄였으나 `project_resource_limits ... FOR UPDATE` 대기로 경합을 옮겼고, 내부 bounded retry가 이를 숨겨 외부 실패만 0건으로 만들었다. 성공 수만으로 판정하지 않는다는 원칙에 따라 단계 3은 **미통과**다. report schema v1.3은 요청별 limit-row 획득 시도·timeout retry 횟수와 대기 p50/p95/max를 식별자 없이 분리한다. 단계 3 원본에는 이 대기 시간 필드가 없으므로 값을 소급 생성하지 않았고, 후속 3동시 계측 smoke에서 p50/p95/max 42.859/162.104/162.104ms·retry 0·exit 0을 확인했다. 상세 근거는 [[2026-09-23_01-40-00_KST_S05_short-commit_구현과_F-S05-03_Codex]], [[s05-short-commit-stage3-a0f7dba2.json]], [[2026-09-23_02-55-00_KST_Codex카드16_fail-fast_F-R1_F-R2_a28915bc_독립검토_Claude]]다.

다음 후보는 아직 결정이 아닌 검토 옵션이다.

1. **limit-row 잠금 입도/배치 갱신:** project ceiling 원자성을 유지하면서 limit-row 보유 구간 또는 갱신 단위를 줄인다. 다중 Node에서 다른 resource lock 집합을 병렬화하되 direct lease와 동일한 교착 없는 순서를 증명해야 하며, 필요하면 additive migration·계약 영향부터 결정한다.
2. **커널 내부 retry 제거·fail-fast:** 첫 `RES-0007`을 그대로 503/retryable로 반환하고 클라이언트가 같은 idempotency key/body로 재시도하게 한다. 숨은 retry 폭증은 막지만 요청 성공률·지연 책임과 backoff 정책을 API/운영 문서에서 명확히 해야 한다.

어느 후보도 Claude 카드 18 구현 검토와 코디네이터 결정 전에는 구현하지 않는다.

## 0. v1.1 인과 정정과 현재 실패 모드

두 전제를 실측으로 함께 바로잡는다. 작성자나 검토자의 책임을 돌리는 대신, 당시 확인 가능한 코드와 새 시험이 결론을 어떻게 바꿨는지 기록한다.

1. Codex의 v1.0은 project 직렬 대기가 15초 freshness 창을 넘겨 `RES-0003`을 만든다고 서술했다. 그러나 모든 커널 transaction에는 `lock_timeout=500ms`, `statement_timeout=2s`가 먼저 적용된다. 현재 코드에서 그 15초 경로가 실제 경합 실패의 선행 원인이라는 주장은 틀렸고 철회한다.
2. Claude의 PR #74 검토는 500ms 경계를 정확히 지적했으나 `LockNotAvailable`이 매핑되지 않아 계약 변경이 필요하다고 전제했다. `inv/db.py`는 이미 `LockNotAvailable`, `QueryCanceled`, `DeadlockDetected`를 `RES-0007`, HTTP 503, `retryable=true`로 매핑한다. 실 PG 주입 시험도 이를 확인했으므로 CE-2의 계약 변경 반례는 소멸한다.

실 PG 주입 시험은 project row를 `FOR UPDATE`로 잡은 연결이 `pg_sleep(1.2)`를 수행하는 동안 reserve 한 건을 호출했다. `tests/integration/test_placement.py::test_project_lock_timeout_is_retryable_res_0007_problem`은 **1 passed / exit 0**이며 실제 표면은 `RES-0007` / 503 / `retryable=true` / `LockNotAvailable` / SQLSTATE `55P03`, Lease·idempotency 잔존 0이다. 최초 Docker 전용 fixture 연결 시도는 1 skipped로 실측에서 제외했다.

| 동시 요청 | 라운드 | 성공/실패 | 성공 P95 | 실패 표면 | 판정 경계 |
|---:|---:|---:|---:|---|---|
| 3 | 2 | 3/3 × 2, 실패 0 | **861.651ms** | 없음 | 개발 PC·합성 Node 예비값 |
| 10 | 2 | 10/10 × 2, 실패 0 | **1,738.762ms** | 없음 | 2초에 근접, AC 판정 아님 |
| 20 | 1 | **17 성공 / 3 실패** | **2,417.912ms** | 3건 모두 `RES-0007` / 503 / retryable / `QueryCanceled` / SQLSTATE `57014` statement timeout | 현 코드의 실측 실패 모드 |
| 50 | 0 | **미실행·미측정** | 미측정 | 미측정 | 별도 승인 전 실행 금지 |

20동시 실패 request index는 5·7·16, 완료 순번은 17·19·18이고 각 lock-wait 포함 지연은 2,372.379ms·2,372.816ms·2,372.381ms다. 활성 resource 합계는 기대값과 일치했고 fencing 유일성·no-overbooking은 true였다. 단일 라운드이므로 결정성·idempotent replay는 미측정이다. 분리 프로세스가 감시기 연결 전에 종료돼 peak working set도 **미측정**이며 재실행해 채우지 않았다. 20동시 report의 `codeSHA=a4bf2cee`는 시작 HEAD이고 하네스 변경은 당시 working tree였으므로, 재현 정본은 이 변경의 R1 착지 SHA다.

따라서 현재 실패 모드는 “freshness 15초 초과”가 아니라 **project/resource 경합 뒤 개별 SQL이 transaction의 2초 statement timeout에 도달해 `RES-0007`로 끝나는 것**이다. 500ms lock timeout과 2초 statement timeout 모두 동일한 기존 ProblemDetails 표면이므로 옵션 1의 bounded retry는 새 오류 계약 없이 `RES-0007 && retryable=true`를 기준으로 삼을 수 있다.

## 1. 결정할 것

- **옵션 1 — project 임계구역 입도 완화:** 기존 단건 계약을 유지하고 speculative candidate 계산 뒤 **잠금 보유 시간이 짧은 commit 구간**에서 현재 상태를 전부 재검증한다.
- **옵션 2 — batch 예약 API:** 한 project의 1~50개 Run을 한 요청·한 원자 commit으로 예약하는 새 계약을 만든다.
- **옵션 3 — freshness 정책 변경:** 성능 우회책으로는 기각한다.

Codex의 조건부 권고는 옵션 1이다. 단, project row 하나를 제거하는 변경이 아니라 reserve transaction의 잠금 보유 시간을 계측하고 줄이는 설계여야 하며, 아래 네 쟁점을 시험으로 닫기 전 구현 승인이 아니다.

## 2. 공통 보존 불변식

| 불변식 | 보존 조건 | 위반 위험 |
|---|---|---|
| fencing / epoch | Lease fencing sequence는 현재 recovery epoch에서만 발급하고 재사용하지 않는다. commit 직전 epoch·heartbeat·channel·clock skew를 다시 확인한다. | 복구 전 writer나 stale Node가 새 작업을 수락한다. |
| idempotency | operation+principal+key와 canonical request hash를 잠그고 성공 Lease·event·응답을 같은 transaction으로 commit한다. 같은 key/body는 exact replay, 다른 body는 충돌이다. | 중복 Lease, 다른 replay 응답, 부분 기록이 생긴다. |
| 예약 원자성 | ceiling·offered·active·Run 단일 활성 예약을 잠근 현재 상태에서 검증하고 모든 Lease/event/ledger를 전부 commit 또는 rollback한다. | overbooking, 일부 slice만 예약, event 불일치가 생긴다. |
| freshness 의미 | 최종 검증 시각 기준 15초 이내 observation만 사용한다. timeout을 피하려고 창을 늘리거나 요청 진입 시각에 동결하지 않는다. | stale capacity·격리 Node를 선택한다. |
| RLS 경계 | runtime non-owner, forced RLS, transaction-local tenant GUC를 유지하고 membership/current grant/can_request를 final transaction에서 재검증한다. | 다른 tenant/project 또는 폐기 권한으로 예약한다. |
| 결정성 | 같은 유효 snapshot·policy·request·활성 사용량은 같은 후보 순서와 Explain을 낸다. 입력이 바뀌면 이전 winner를 재사용하지 않는다. | stale winner나 재현 불가능한 Explain이 기록된다. |
| 잠금 순서 | idempotency → Run/admission → project ceiling → Node 정렬 → Resource 정렬의 한 방향을 모든 writer가 공유한다. | deadlock·starvation이 발생한다. |

## 3. 옵션 1 — speculative read + 짧은 commit (조건부 권고)

### 3.1 설계

1. **speculative read:** 잠금 없이 permitted pool, observation, offered/active, policy를 읽고 후보·Explain·decision input을 계산한다. 아직 예약 권한은 없다.
2. **final commit:** idempotency와 Run을 잠그고 canonical admission 검사를 수행한 뒤 project limits와 선택 Node/Resource만 정렬해 잠근다.
3. 같은 transaction에서 membership/grant, ceiling, resource `active_total`/offered fit, Node epoch/heartbeat/skew/channel, observation receivedAt를 다시 읽는다.
4. speculative 입력과 하나라도 다르면 stale winner를 그대로 쓰거나 `RES-0001`로 끝내지 않는다. side effect 없이 rollback한 뒤 후보 계산부터 bounded retry한다.
5. 일치하면 기존 Lease·event·ledger·응답을 한 transaction으로 commit한다.

핵심 성공 지표는 project row 존재 여부가 아니라 **transaction별 project/limit/node/resource 잠금 최초 획득부터 commit/rollback까지의 잠금 보유 시간**이다. 개발 PC와 5노드 랩에서 요청별 lock-wait 포함 총 지연과 별도로 이 구간의 p50/p95/max, retry 횟수, SQLSTATE를 수집해야 한다. 옵션 1은 이 시간이 줄어야만 2초 statement timeout 도달을 늦추거나 제거한다.

### 3.2 남은 네 쟁점에 대한 설계 응답

| 쟁점 | v1.1 설계 응답 |
|---|---|
| decision digest / active fit | 기존 digest가 limits version·관측은 담지만 `active_total`/최종 fit 변화 자체를 충분히 대표하지 않는다. final commit은 각 resource의 current active+need ≤ offered와 project kind별 active+need ≤ ceiling을 다시 계산한다. 불일치나 no-fit은 후보 전체를 다시 계산하는 retry 사유이며 stale winner를 그대로 `RES-0001`로 확정하지 않는다. |
| Node/Resource row 병목 | 단일 Node pool에서는 선택 Node/Resource row가 모든 요청에 공통이라 project row를 제거해도 이득이 0일 수 있다. 다중 Node에서는 서로 다른 선택 집합만 병렬화 가능하다. 20동시 17/20 결과는 현 병목을 입증하지만 어느 row의 hold가 지배적인지는 아직 미측정이다. row별 wait/hold 계측 뒤 판단한다. |
| `leases.py:176` 두 번째 project lock | placement가 이미 project/limits/resources를 잠근 뒤 `_reserve_locked`가 project row와 limits/resources를 다시 잠근다. 동일 transaction에서는 재획득 자체보다 중복 primitive와 순서 불일치가 문제다. placement/direct lease가 하나의 canonical commit primitive를 호출하고 project mutex 정책을 한 곳에서만 적용하도록 합친다. |
| `require_*` 순서 | direct lease는 Run 뒤 `require_execution`→recovery→handoff→start를 거쳐 project/resources를 잠그지만 placement는 외부에서 project/resources를 먼저 잠근 뒤 내부 `require_*`를 호출한다. 네 admission 검사를 side effect 없는 한 묶음으로 Run 직후, project/node/resource writer lock 전에 실행하고 final commit 직전 필요한 mutable 근거만 잠금 재검증한다. 두 진입점의 순서를 동일하게 고정한다. |

### 3.3 retry와 계약

v1.1 설계 당시 항목이다. database contention의 내부 retry는 v1.3 fail-fast에서 제거됐고, 아래 bounded retry 설명은 stale speculative decision 재계획에만 남는다.

- retry 대상은 기존 `RES-0007`이면서 `retryable=true`인 contention 결과다. `55P03`과 `57014`를 evidence에는 구분하되 공개 오류 코드는 유지한다.
- 같은 principal·idempotency key·canonical body만 재사용하며 매 시도 새 transaction에서 권한·admission·epoch·freshness·fit을 다시 읽는다.
- 횟수와 총 wall-clock 상한을 두고 exhaustion은 기존 `RES-0007`로 반환한다. 임의 jitter로 후보 순서를 바꾸거나 `SKIP LOCKED`로 결정성을 훼손하지 않는다.
- 현재는 새 ProblemDetails 코드나 schema 변경이 필요 없다. 오류 표면을 바꿔야 하는 구현이 생기면 별도 계약 결정을 먼저 낸다.

### 3.4 변경 범위와 롤백

- migration: 1차 없음. 기존 limits·active Lease를 정본으로 유지한다.
- 코드: `placement.py`의 speculative/final validator 분리, `leases.py`의 공통 canonical commit primitive, lock hold 계측, legacy `project_serial` feature flag.
- 시험: exact replay/changed body, same Run, ceiling/offer, `55P03`/`57014`, epoch flip, heartbeat stale, membership/grant revoke, 네 `require_*`, direct lease 혼합, retry exhaustion, rollback 잔존 0.
- 배포: candidate 기본 off. 오류율·timeout·deadlock·retry·ceiling mismatch·lock-hold p95가 승인 임계치를 넘으면 `project_serial`로 되돌린다. 정상 Lease는 삭제하지 않는다.

## 4. 옵션 2 — batch 예약 API

예: `POST /v1/projects/{project}/placement-batches`에 1~50개 item을 제출하고 **all-or-nothing**으로 처리한다. 하나라도 권한·freshness·capacity·policy 검증에 실패하면 Lease·event·ledger를 모두 rollback한다.

- batch key는 canonical ordered item list의 request hash와 exact replay를 소유한다.
- 모든 item은 같은 tenant/project/principal이어야 하고 각 Run admission을 재검증한다.
- fencing은 각 Lease에 현재 epoch+단조 sequence로 발급하며 sequence gap은 허용하되 재사용하지 않는다.
- 새 route/schema/fixtures/TS·Go·Python binding과 max 50·원자성·오류 의미 결정이 필요하다.
- batch 자체도 Node/Resource lock hold가 길어질 수 있고, 50개 독립 요청의 AC-05를 한 요청으로 바꿔 통과 처리할 수 없다.

롤백은 route feature flag를 끄고 기존 단건 endpoint를 유지한다. 성공한 Lease는 삭제하지 않으며 durable batch table을 추가했다면 감사 이력을 위해 additive schema는 남기고 쓰기만 중단한다.

## 5. 옵션 3 — freshness 정책 변경 기각

- 15초 창 확대는 heartbeat가 끊겼거나 격리·epoch가 바뀐 Node의 오래된 capacity를 더 오래 허용한다.
- 요청 진입 시 snapshot을 동결하면 lock wait 뒤 stale observation을 commit한다.
- 20동시 실측 실패는 15초 freshness가 아니라 2초 statement timeout이다. freshness를 바꿔도 경합·잠금 보유 시간·P95는 고쳐지지 않는다.

freshness 자체를 바꾸려면 별도의 failure detector·격리·운영 SLO 결정이 필요하다.

## 6. 5노드 랩 검증

- legacy와 candidate를 같은 migration/policy/fixture에서 실행하고 실제 5개 Node heartbeat/resource observation을 사용한다.
- 50개 독립 요청을 barrier 시작해 요청별 총 지연, SQLSTATE, retry, snapshot age, 결과, node/resource/fencing, Explain digest를 JSON/JUnit으로 남긴다.
- transaction별 project/limit/node/resource **잠금 보유 시간 p50/p95/max**와 timeout 발생 row를 별도 지표로 남긴다.
- 반복 wave 사이 stop receipt/release와 active Lease 0을 확인한다.
- acceptance: 50/50 성공, overbooking 0, duplicate active Run 0, stale epoch 수락 0, exact replay, committed snapshot 결정성, 성공 P95 2초 이하.
- chaos: final 검증 직전 membership/grant revoke, epoch flip, heartbeat stale, limit/offer 감소, transaction rollback, 두 tenant 혼합.
