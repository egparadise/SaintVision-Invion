# S05 배치 잠금 입도 결정 제안

> [!warning] 제안서 상태
> 3·10동시는 성공했고 50동시는 미측정이다. 이 문서는 성능 장애를 확정하는 문서가 아니라 코드상 위험을 예방적으로 다루는 ERR-DESIGN/GOV 결정 초안이다. Claude 검토와 코디네이터 결정 전 구현하지 않는다.

## 1. 근거와 판정 경계

| 조건 | 유효 결과 | 해석 |
|---|---|---|
| 개발 PC 1대·합성 measured-node·3동시 | 3/3 성공 × 2, 오류 0, worst P95 **861.651ms** | 하네스가 reserve·report까지 도달, 불변식 4종 true |
| 같은 조건·10동시 | 10/10 성공 × 2, 오류 0, worst P95 **1,738.762ms** | AC-05 2초에 근접하지만 통과/실패 판정 아님 |
| 50동시 | **미실행·미측정** | 성공·실패·P95·freshness 초과 순번을 추정하지 않음 |
| 물리 5노드 | 미측정 | S05-DB `review`, AC-05 판정 금지 |

기존 78.15초/61.69초 `RES-0003` 수치는 exact SHA 재현성이 없어 [[2026-09-22_22-38-00_KST_S05-DB_50동시배치_예비측정_F-S05-01_Codex]] v1.1.0에서 철회했다. 현재 결정 근거는 위 측정값과 project lock 뒤 current time/freshness 15초 검사라는 코드 경로다.

## 2. 결정할 것

- **옵션 1 — project 임계구역 입도 완화:** 기존 단건 계약을 유지하고 speculative candidate 계산 뒤 짧은 commit 구간에서 현재 상태를 재검증한다.
- **옵션 2 — batch 예약 API:** 한 project의 1~50개 Run을 한 요청·한 원자 commit으로 예약하는 새 계약을 만든다.
- **옵션 3 — freshness 정책 변경:** 기각한다.

Codex 권고는 **옵션 1의 상세 설계 검토를 먼저 승인**하는 것이다. 아직 구현 승인이나 성능 달성 선언은 아니다.

## 3. 공통 보존 불변식

| 불변식 | 보존 조건 | 위반 위험 |
|---|---|---|
| fencing / epoch | Lease fencing sequence는 현재 recovery epoch에서만 발급하고 재사용하지 않는다. commit 직전 epoch·heartbeat·channel·clock skew를 다시 확인한다. | 복구 전 writer나 stale Node가 새 작업을 수락한다. |
| idempotency | operation+principal+key와 canonical request hash를 잠그고 성공 Lease·event·응답을 같은 transaction으로 commit한다. 같은 key/body는 exact replay, 다른 body는 충돌이다. | 중복 Lease, 다른 replay 응답, 부분 기록이 생긴다. |
| 예약 원자성 | ceiling·offered·active·Run 단일 활성 예약을 잠근 현재 상태에서 검증하고 모든 Lease/event/ledger를 전부 commit 또는 rollback한다. | overbooking, 일부 slice만 예약, event 불일치가 생긴다. |
| freshness 의미 | queue 진입이 아니라 최종 검증 시각 기준 15초 이내 observation만 사용한다. lock wait 뒤 receivedAt을 다시 읽는다. | stale capacity·격리 Node를 선택한다. |
| RLS 경계 | runtime non-owner, forced RLS, transaction-local tenant GUC를 유지하고 membership/current grant/can_request를 final transaction에서 재검증한다. | 다른 tenant/project 또는 폐기 권한으로 예약한다. |
| 결정성 | 같은 유효 snapshot·policy·request는 같은 후보 순서와 Explain을 낸다. input이 바뀌면 이전 Explain을 쓰지 않는다. | 재현 불가능한 placement/snapshot ID가 기록된다. |
| 잠금 순서 | idempotency → Run → project ceiling → Node 정렬 → Resource 정렬의 한 방향을 모든 writer가 공유한다. | deadlock·starvation이 발생한다. |

## 4. 옵션 1 — 짧은 commit 임계구역 (권고)

### 설계

1. **speculative read:** 잠금 없이 permitted pool, 관측, offered/active, policy를 읽고 후보·Explain·decision-input digest를 계산한다. 아직 예약 권한은 없다.
2. **final commit:** idempotency와 Run을 잠근 뒤 project limits를 가능한 늦게 잠그고 선택 Node/Resource를 canonical order로 잠근다.
3. membership/grant, ceiling/current active, Node epoch/heartbeat/skew/channel, resource offered와 전체 decision-input digest를 다시 읽는다.
4. 바뀌었으면 side effect 없이 rollback하고 bounded retry한다. 상한을 넘으면 명시적 retryable conflict로 끝내며 freshness를 늘리지 않는다.
5. 일치하면 기존 Lease·event·ledger를 같은 transaction으로 commit한다.

`inv.projects FOR NO KEY UPDATE`는 project 생성·첫 limits provisioning 같은 lifecycle 경로에는 유지한다. steady-state placement에서 project row만 없애는 것으로 끝내지 않고, limits lock도 final commit 구간으로 옮긴다. direct `LeaseStore.reserve`와 placement는 공통 commit primitive와 같은 lock order를 써야 한다.

### 위반 위험과 방어

| 위험 | 방어 |
|---|---|
| speculative winner가 stale | selected resource만 eligibility 확인하지 않고 full decision-input digest가 다르면 전체 재계산 |
| ceiling 경합 | limits row 아래 현재 active total을 다시 계산하고 Lease insert까지 잠금 유지 |
| retry가 idempotency 파괴 | 실패 시 ledger insert/update도 rollback, 성공한 한 시도만 response 저장 |
| 권한 폐기 경합 | membership/grant를 final transaction에서 현재 값으로 잠금 재검증 |
| livelock | retry 횟수·총 시간 상한과 conflict 원인 관측, `SKIP LOCKED`로 결과 임의 변경 금지 |

### 변경 범위

- migration: **1차 없음**. 기존 limits와 active Lease를 정본으로 유지한다. usage counter/CAS table은 release·reconcile·restore 동기화가 필요하므로 별도 결정이다.
- 계약: HTTP/schema/generated binding 변경 없음. 새 retryable 오류가 필요하면 구현 전에 계약 변경을 먼저 보고한다.
- 코드: `placement.py`의 speculative/final validator 분리, `leases.py`의 공통 canonical commit primitive, legacy `project_serial` feature flag 유지.
- 시험: same-key replay/changed-body, ceiling·동일 Run 경합, epoch flip, heartbeat stale, membership/grant revoke, offer 감소, direct lease 혼합, retry exhaustion, rollback 잔존 0을 실 PG로 검증한다.

### 롤백

candidate는 기본 off로 배포한다. 오류율·deadlock·retry·ceiling mismatch 경보가 임계치를 넘으면 설정만 `project_serial`로 되돌린다. migration이 없으므로 schema rollback이 없고 이미 생성된 정상 Lease는 기존 lifecycle로 종료한다.

## 5. 옵션 2 — batch 예약 API

### 설계

예: `POST /v1/projects/{project}/placement-batches`에 1~50개 item을 제출한다. 의미는 **all-or-nothing**이다. 하나라도 권한·freshness·capacity·policy 검증에 실패하면 Lease·event·ledger를 전부 rollback한다.

- 한 batch key가 canonical ordered item list의 request hash와 exact replay를 소유한다.
- 모든 item은 같은 tenant/project/principal이어야 하고 각 Run grant/input을 재검증한다.
- fencing은 각 Lease에 현재 epoch+단조 sequence로 발급하며 sequence gap은 허용하되 재사용하지 않는다.
- batch latency는 별도 지표다. 이를 50독립 요청 AC 성공으로 대체하지 않는다.

### 변경 범위와 위험

- migration: minimal all-or-nothing은 기존 ledger/Lease로 가능해 필수 아님. durable batch status/부분 재개가 필요하면 batch header/item table과 forced RLS migration이 필요하다.
- 계약: 새 request/response/error schema, route, fixtures, TS/Go/Python binding, max 50과 all-or-nothing 문구가 필요하다.
- 시험: 1/50 item, duplicate Run, 일부 no-fit/unauthorized/stale, exact replay, changed-body, 전부 rollback, payload limit, direct endpoint 경합.
- 위험: 한 item이 전체 batch를 실패시키고 lock hold/blast radius가 커지며, 독립 요청 성능 문제를 한 요청으로 숨길 수 있다.

### 롤백

route를 feature flag로 끄고 기존 단건 endpoint를 유지한다. 성공한 Lease는 삭제하지 않는다. batch table을 추가했다면 감사 이력을 위해 additive schema는 남기고 쓰기만 중단한다.

## 6. 옵션 3 — freshness 변경 기각

- 15초 창 확대는 heartbeat가 끊겼거나 격리·epoch가 바뀐 Node의 오래된 capacity를 더 오래 허용한다.
- 요청 진입 시 snapshot을 동결하면 긴 lock wait 뒤에도 stale observation을 commit한다.
- 둘 다 project queueing을 줄이지 않으므로 P95 2초 문제를 해결하지 않고 `RES-0003`만 늦추거나 숨긴다.

freshness 자체를 바꾸려면 별도의 failure detector·격리·운영 SLO 결정이 필요하며 성능 우회책으로 쓰지 않는다.

## 7. 5노드 랩 검증

- legacy와 candidate를 같은 migration/policy/fixture에서 실행하고 실제 5개 Node heartbeat/resource observation을 사용한다.
- 50개 **독립 요청**을 barrier 시작해 요청별 lock wait·총 지연·retry·snapshot age·결과·node/resource/fencing·Explain digest를 JSON/JUnit으로 남긴다.
- 반복 wave 사이 stop receipt/release와 active Lease 0을 확인한다.
- acceptance: 50/50 성공, overbooking 0, duplicate active Run 0, stale epoch 수락 0, exact replay, committed snapshot 결정성, P95 2초 이하.
- chaos: final 검증 직전 membership/grant revoke, epoch flip, heartbeat stale, limit/offer 감소, transaction rollback, 두 tenant 혼합.
- 실패를 snapshot 정규화·freshness 연장으로 숨기지 않는다.
