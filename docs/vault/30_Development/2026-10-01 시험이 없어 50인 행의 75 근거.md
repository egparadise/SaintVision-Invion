# 2026-10-01 시험이 없어 50인 행의 75 근거

## 0. 한 줄 답

| 행 | v1.6 | 이 카드 뒤 | 근거 |
|---|---:|---:|---|
| **S02-ST** | 50 | **75** | **이미 있었다** — `tests/core/test_storage_list_response_contract.py` |
| **S09-ST** | 50 | **75** | **이미 있었다** — `tests/test_context_eval.py` |
| **S08-BE** | 50 | **75** | **새로 썼다** — `tests/core/test_s08_be_kill_switch_buildkit_gpu_refusals.py` (48건, 변이 7종 사살) |

**셋 중 둘은 시험이 없던 것이 아니라 제가 찾지 못한 것이었다.** 그 사실과 원인이 이 문서의 절반이다.

## 1. 정정 — [[2026-09-28 48 task 진행률 재채점]] v1.6의 검색이 **파일명만** 봤다

v1.6 §4-3-5는 세 행을 "task 고유 시험 없음"으로 50에 두었고, 그 판단의 근거는 이것이었다.

```
git ls-tree -r --name-only <tree> -- tests/ | grep -icE "storage_policy|contribution"   -> 0
git ls-tree -r --name-only <tree> -- tests/ | grep -icE "kill|switch|gpu|buildkit|roof" -> 0
```

**`git ls-tree --name-only`는 파일 이름만 돌려준다.** 그래서 `storage-contributions-response.json`을 **내용으로** 다루는 `test_storage_list_response_contract.py`가 검색에 걸리지 않았다. 이름에 `contribution`이 없기 때문이다.

내용으로 다시 검색하자 두 행의 시험이 나왔다.

```
grep -rln -iE "storage/locations|DataLocationPage|data_locations" tests/
  -> tests/core/test_storage_list_response_contract.py
grep -rln -iE "trace.*artifact|artifact.*trace|eval.*artifact" tests/
  -> tests/test_context_eval.py
```

**이것은 v1.2가 고친 것과 같은 실수다.** 그때는 `2,775`를 markdown에서만 검색해 "task별 baseline이 없다"고 단언했고, baseline은 Evidence 디렉터리의 JSON에 있었다. v1.2는 그 교훈을 "**결론을 검색 범위 하나로 내린 것이 잘못이었다**"라고 적었다. v1.6에서 같은 형태로 다시 틀렸다 — 이번에는 범위가 **파일명**이었다.

`S08-BE`만은 내용 검색으로도 **이 행의 것이** 나오지 않았다(§4). 그래서 세 행 중 하나만 새 시험이 필요했다.

## 2. 방법 — 행마다 "무엇을 관측하면 75인가"를 먼저 적는다

[[2026-09-18_Codex_진척률재채점]] rubric의 75는 **"상당한 구현과 관련 로컬/고정 SHA 시험 확보"** 다. v1.6이 표 전체에 적용한 규칙을 그대로 쓴다.

1. **시험 건수는 점수가 아니다.** 48건을 더했다는 것이 75의 근거가 아니고, 그 시험이 **이 행의 수용 기준을 관측한다**는 것이 근거다.
2. **한 시험이 두 행을 funding하지 않는다.** 후보마다 재채점 문서에서 인용 횟수를 세어 **0인 것만** 썼다.
3. **75의 천장 사유는 유지된다.** 세 행 모두 100은 외부 전제·운영 인수를 기다리고, 이 카드는 그것을 건드리지 않는다.
4. **없는 것을 있다고 적지 않는다.** 하드웨어가 필요한 관측은 시험으로 흉내내지 않는다.

## 3. S02-ST — 제공 폴더·DataLocation 카탈로그

**무엇을 관측하면 75인가**: 카탈로그의 두 응답 계약(제공 폴더 = contributions, DataLocation = locations)이 **정본 fixture와 한 글자도 다르지 않게** 고정되고, 모양이 **어긋나면 거부**되고, 실제 FastAPI 경로가 그 fixture를 직렬화하는 것.

**이미 있다** — `tests/core/test_storage_list_response_contract.py`:

| 시험 | 관측 |
|---|---|
| `test_shared_storage_fixture_matches_strict_page_contract` | `ContributionPageResponse`·`DataLocationPageResponse`가 `contracts/fixtures`의 정본과 **왕복 동일**(`model_dump(by_alias=True) == payload`) |
| `test_storage_fixture_shape_drift_is_rejected` | 네 변이 — `missing-page-cursor`·`extra-page-field`·`missing-item-field`·`extra-item-field` — 를 **두 모델 각각** 거부 |
| `test_fastapi_storage_list_response_serializes_the_shared_fixture` | 실제 route가 그 fixture를 직렬화 |

파일 머리의 한 줄이 이 행의 성격을 그대로 적는다 — "Storage list responses share one strict fixture across provider and UI."

**100이 아닌 이유**: registry의 요구 증거는 "실제 API·브라우저 여정·인증 실패 기록"이다. 계약은 고정됐고 **여정과 인수가 남았다**(`G-20`, 사용자 결정 U1·U5·U6).

**중복 funding 아님**: 재채점 문서에서 이 파일 인용 **0회**.

## 4. S09-ST — diff·테스트·trace Artifact 연결

**무엇을 관측하면 75인가**: trace와 기록의 결속이 **깨지지 않는다는 것** — bundle이 모델이 본 것을 재현하고, 봉인된 기록을 다시 쓸 수 없고, 고정 digest가 나중의 덮어쓰기를 **탐지**하고, 금지 행동 위반이 평균으로 **지워지지 않는** 것.

**이미 있다** — `tests/test_context_eval.py`(시험 함수 **27개**). 파일 머리가 그 주장을 스스로 적는다.

> "S09 context, run record and evaluation against a real PostgreSQL. The claims tested here are the ones ADR-009, ADR-010 and AC-09 rest on: a bundle reproduces what the model saw, a sealed record cannot be rewritten, a pinned digest detects a later overwrite, and **a forbidden-behaviour violation cannot be averaged away**."

마지막 항목이 registry가 요구하는 **"금지 행동 시험"** 과 같은 것이고, 앞의 셋이 **"trace Artifact 연결"** 이다. 실 PostgreSQL에 대한 시험이므로 고정 SHA 검증 조건도 만족한다.

**100이 아닌 이유**: "golden eval·분류별 성적"의 운영 인수가 남는다(`G-24`·`G-26`).

**중복 funding 아님**: 인용 **0회**. `S09-DB`는 `test_eval_run_route.py`·`test_eval_suite_project_scope_migration.py`·`integration/test_eval_run_real_pg.py`를 쓰고 이 파일을 쓰지 않는다.

## 5. S08-BE — ROOF·kill switch·BuildKit·단일 GPU

여기만 **새 시험이 필요했다.** 내용 검색에서 나온 파일들은 둘 중 하나였다 — `tests/integration/test_containment.py`는 **이미 `S07-BE`의 근거**이고(한 시험을 두 번 세지 않는다), `tests/integration/test_workspace_api.py`는 `S06` 영역이다.

### 5-1. 먼저 — 구현은 **있다**

v1.6이 "시험 0건"이라고 적은 것이 "구현 0건"으로 읽히면 안 된다. 네 낱말 모두 코드가 있다.

| 낱말 | 어디에 |
|---|---|
| ROOF | `src/saintvision/adapters/cli.py` · `src/saintvision/services/pilot.py` · `src/saintvision/services/replica_observation.py` |
| kill switch | `services/control-plane/src/inv/containment.py` · `services/control-plane/src/inv/app.py` |
| BuildKit | `services/control-plane/src/inv/workspace_api.py` |
| GPU | `src/saintvision/api/schemas.py` · `src/saintvision/api/v1/pools.py` · `src/saintvision/db/models/discovery.py` |

### 5-2. 무엇을 관측하면 75인가

**GPU는 단위 시험에 대여할 수 없다.** 그래서 이 행의 75는 하드웨어가 아니라 **설계가 의지하는 거부(refusal)** 다. 거부는 하드웨어 없이 관측된다.

| 관측 | 왜 이것이 이 행의 것인가 |
|---|---|
| 제어 행이 **없는** tenant는 **정지**된다 | kill switch가 gate인지 아닌지를 가르는 경우다. 관대한 해석은 "controls가 기록되지 않았으니 실행 허용"이고, 그것은 kill switch의 반대다 |
| 활성 kill switch가 실행을 멈춘다 / 해제되면 허용한다 | gate가 늘 닫혀 있는 것이 아님까지 확인한다 |
| gate가 `inv.tenant_controls.kill_switch`를 읽는다 | 다른 것을 읽는 gate는 이 gate가 아니다. 표 이름이 migration과의 계약이다 |
| 모르는 operation은 **모르는 operation으로서** 거부된다 | `kill`·`clear`·`drain`·`resume` 넷뿐이다 |
| tenant 전역(kill·clear)은 Node를 지목할 수 없고, Node 단위(drain·resume)는 지목해야 한다 | 범위를 틀리게 적은 요청은 다른 행위를 기술한다 |
| idempotency key가 **작업 전에** 요구된다 | 재전송 보호가 DB 뒤가 아니라 앞에 있다 |
| `ContainmentInput` 계약(`additionalProperties: false`, reason enum, uuid) | 밀반입된 필드가 거부된다 |
| 운영자 profile이 **임의의 OS/GPU/BuildKit capability를 증명하지 않는다** | `RestrictedWorkspaceRuntime`의 docstring이 그렇게 적고, cpu·memory **정확히 둘**과 policy version만 받는다. `gpu`·`buildkit` 할당을 끼운 요청은 Node로 넘기기 전에 **여기서** 거부된다 |
| cpu와 memory는 **서로 다른** 자원이어야 한다 | 한 식별자를 두 번 쓰면 하나가 둘로 보인다 |

### 5-3. 새 시험 — `tests/core/test_s08_be_kill_switch_buildkit_gpu_refusals.py`

**48 passed.** PostgreSQL·Docker·GPU **모두 필요 없다** — 위 거부들은 DB 앞에서 결정되므로, gate 질의 하나에 답하는 연결 stub과 transaction 진입 시점에 멈추는 db stub으로 충분하다. 허용돼야 하는 네 모양은 **DB에 도달하는 것으로** 통과를 증명한다(stub이 그 자리에서 멈춘다).

**파일 이름에 `kill_switch`·`buildkit`·`gpu`를 넣었다** — §1의 실수가 다음 사람에게 반복되지 않도록, 파일명 검색으로도 찾히게.

### 5-4. 변이 7종 전부 죽는다

| 변이 | 결과 |
|---|---|
| 제어 행이 없으면 kill switch가 **열린다**(fail-open) | **사망** |
| 활성 kill switch가 실행을 멈추지 않는다 | **사망** |
| 아무 operation 이름이나 받아들인다 | **사망** |
| 범위가 operation과 무관해진다 | **사망** |
| idempotency key가 필요 없어진다 | **사망** |
| 밀반입된 capability 할당을 받아들인다 | **사망** |
| cpu와 memory가 같아도 된다 | **사망** |

**그중 하나는 처음에 생존했고, 그것이 제 시험의 결함이었다.** "아무 operation 이름이나 받아들인다" 변이를 넣었을 때 48건이 전부 통과했다 — 이 guard를 지우면 **범위 guard가 대신 거부**하고, 두 guard가 **같은 `VAL-0003`/422**를 낸다. 제 단언이 코드와 status만 봤으므로 **틀린 이유로 통과**했다. `detail`에 `"unknown containment operation"`이 있는지까지 단언하자 변이가 죽었다.

**100이 아닌 이유**: 실 단일 GPU 장비와 보안 시나리오·복원 보고의 운영 인수가 남는다(`G-19`).

## 6. 하지 않은 것

- **점수를 올리지 않았다.** [[2026-09-28 48 task 진행률 재채점]]은 **#258에서 검토 중**이고, 두 branch에서 같은 문서를 고치면 충돌한다. #258이 착지한 뒤 v1.7에서 세 행을 50 → 75로 옮기고 §1의 검색 정정을 §4-3-5에 반영한다. **그 편집이 기계적이도록 이 문서에 행·근거·인용 0회 확인을 전부 적어 두었다.**
- **`S02-ST`·`S09-ST`에 새 시험을 쓰지 않았다.** 이미 있는 것을 중복으로 쓰는 것은 시험 수로 점수를 올리는 일이다.
- **`tests/core/test_storage_list_response_contract.py`를 로컬에서 돌리지 않았다.** 이 PC에 `httpx2`가 없어 starlette `TestClient`가 수집 단계에서 실패한다 — **제 환경 결함이고 제품 결함이 아니다.** 내용과 CI 수집 여부(backend·core 어느 `--ignore` 목록에도 없다)는 확인했고, 실행은 hosted CI 몫이다.
- **`G-19`·`G-20`·`G-24`·`G-26`을 건드리지 않았다.** 세 행의 100은 그대로 외부 전제를 기다린다.
- **제품 코드·migration 변경 0.** 변이는 주입 후 전부 원본으로 복원했다(각 회 대조 확인).
