## 1. 병합 순서 — 스냅샷 시점 72 PR

**이 표는 고정된 스냅샷이다.** 목록은 그 뒤에도 늘었다(조정자가 **#206**을 더해 **73건**). 실행 직전에는 스냅샷 파일 자체가 정본이고, 이 표는 그 시점에 무엇이 어떤 순서로 있었는지의 기록이다.

`m`은 `gh pr merge <pr> --merge --match-head-commit <sha>`다. **`--match-head-commit`이 pinned head**이므로, 그 사이에 lane이 push하면 병합이 거부된다(그것이 의도다 — 승인된 head만 들어간다). 스크립트는 `set -e`로 **첫 실패에서 멈춘다.**

**retarget이 필요한 이유**: 저장소가 `delete_branch_on_merge=false`이므로 GitHub이 stacked PR의 base를 자동으로 옮겨 주지 않는다. base가 이미 병합된 부모 branch면 병합이 **integration이 아니라 그 부모 branch로 들어간다.** 그래서 `r`이 먼저 `--base integration/all-agents-unified`로 바꾼다.

## 5. 사용자가 할 일 — 병합 목록 실행

**스크립트는 병합하지 않는다.** `gh pr merge` 명령을 순서대로 실행하는 shell 파일이고, **실행하는 주체는 사용자**다(agent는 병합하지 않는다는 규칙).

1. **읽는다**: `merge-train-snapshot-1755.sh` 136행. 각 `m` 줄의 pinned head가 지금의 PR head와 같은지 보고 싶으면 `gh pr view <n> --json headRefOid`.
2. **실행한다**: `bash merge-train-snapshot-1755.sh`. `set -e`이므로 **첫 실패에서 멈춘다.**
3. **멈추면**: 실패한 PR 번호를 조정자에게 알린다. 실패 유형은 둘이다 —
   - `--match-head-commit` 불일치 → 그 lane이 승인 뒤 push했다. **재승인이 필요하다.**
   - 충돌 → 그 lane이 rebase(또는 선해소 merge)를 해야 한다.
4. **retarget 18건은 스크립트가 알아서** 한다(`r` 줄). 직접 할 필요는 없다.
5. **merge commit 전용 5건**(#170·#177·#185·#190·#192)은 스크립트가 `--merge`를 쓰므로 그대로 두면 된다. **UI에서 squash를 고르면 안 된다.**
6. 목록이 끝나면 `integration/all-agents-unified`가 72 PR을 품는다. 그 뒤 §3의 목록 밖 PR들이 새 base 위에서 다시 정렬된다.
