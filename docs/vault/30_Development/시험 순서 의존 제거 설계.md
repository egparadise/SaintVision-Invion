# 시험 순서 의존 제거 설계 (1쪽)

> [!warning] 배경
> PR #126이 recovery drill 19건을 공유 pytest 세션에서 돌리자 14건이 실패했다. Codex 재현(#126 코멘트): `tests/integration/test_postgres.py::test_shard_completion_rejects_invalid_EvidenceEnvelope_atomically`가 `ALTER TABLE … DISABLE TRIGGER ALL` 뒤 `inv.execution_attempts` 부모가 없는 `inv.result_commitments` row를 넣고 **정리하지 않아**, 그 뒤 `pg_restore`가 FK `result_commitments_…_fkey`에서 실패. #126은 recovery 파일을 새 세션에서 먼저 돌려 우회했다. 이 카드는 원인을 없앤다.

## 2. 규칙과 도구 (`tests/db_integrity.py`)

| 규칙 | 구현 |
|---|---|
| 트리거를 끄면 반드시 다시 켠다 | `suspended_triggers(conn, "schema.table", "USER"\|"ALL"\|<name>)` — ENABLE을 `finally`에서. 테이블·spec은 정규식 검증 후 `sql.Identifier`로 조립 |
| 시험이 만든 비정상 상태는 시험 끝에서 되돌린다 | `preserved_rows(owner_dsn, (table, where, params), …)` — 진입 시 `to_jsonb(t)`로 대상 row 스냅샷, 종료(finally) 시 대상 DELETE 후 스냅샷을 `jsonb_populate_record`로 그대로 재삽입, 그동안만 `DISABLE TRIGGER ALL`(FK·immutable 트리거 우회), 역순. 진입 시 없던 row(합성 orphan)는 삭제만 된다. **서빙 코드가 손상을 보는 시점(블록 안)에는 아무것도 바꾸지 않으므로 음성 단언 의미는 동일** |
| 관측하지 않은 것은 깨끗하다고 치지 않는다 | `database_integrity_violations(owner_dsn)`: `BEGIN READ ONLY`, 실행 role이 superuser/BYPASSRLS가 아니면 **RuntimeError**(RLS가 숨긴 row는 깨끗한 게 아님). pg_constraint에서 validated FK 전부 → MATCH SIMPLE orphan count, validated CHECK 전부 → `NOT (expr)` count, `pg_trigger.tgenabled='D'` 전부. 대상 schema `inv`·`public` |
| 세션 끝에 감사, 실패는 조용히 지나가지 않는다 | `tests/integration/conftest.py` `drop_database()`와 `tests/conftest.py` `database_url` teardown: 감사 → DROP(감사 결과와 무관하게 항상) → `assert not findings`. 감사 자체의 예외도 `audit-error` finding으로 실패 |
| 되돌림은 헬퍼로만 | PG-free ratchet: 헬퍼 밖 `DISABLE/ENABLE TRIGGER` 0건, 조사된 5개 사이트가 헬퍼를 import, 두 conftest가 DROP 전에 감사 |

## 3. 수정 (음성 단언 불변)

- `test_postgres.py` 원인 시험: 합성 8 테이블 대상(`result_completions`·`result_commitments`·`shard_commands`·`storage_objects`·`storage_budgets`·`shard_parents`·`shard_plans`·`runs`)을 `preserved_rows`로 감싸고 트리거 정지는 `suspended_triggers`. 블록 안에서 감사가 **orphan을 실제로 본다**는 단언 추가(손상이 진짜였음을 증명). 바로 다음 시험 `test_invalid_envelope_scenario_leaves_no_physical_inconsistency`가 같은 세션에서 감사 0건을 단언(파일 내 순서로 #126 재현).
- 나머지 4개 파일: 손상 대상 row를 `preserved_rows`로 보존, 트리거는 `suspended_triggers`. `test_shard_recovery`는 row가 유효하므로 트리거 finally만.
- 새 실PG 시험 `tests/integration/test_db_integrity_hygiene.py` 5건: 마이그레이션 직후 감사 0, orphan이 블록 안에서 보이고 밖에서 사라짐, 블록이 예외로 끝나도 row 원상 복구, 비활성 트리거 감지·`suspended_triggers` 잔존 0, 런타임 role로는 감사 거부.
- PG-free `tests/test_db_integrity_static.py` 14건: ratchet 3, fake connection으로 restore 프로토콜(역순·ALL 정지·예외 시 ENABLE) 4, 식별자 검증 7, SQL 렌더링 1.

## 4. 검증·경계·인계

- 이 PC 가용 메모리 ~1.0GB(<1.5GB) → 실 PG 로컬 실행 없음. 근거는 PG-free 14 passed + `--collect-only` 85 collected(수정 5파일 + 신규) + hosted Backend(`tests/integration` 실PG·세션 종료 감사 포함)·hosted Core(recovery drill focused + 전체 suite) 결과.
- 위험: 세션 종료 감사가 기존에 몰랐던 위반을 드러내면 hosted가 red가 된다 — 그것이 이 카드의 목적이며, 그 경우 위반 시험을 같은 규칙으로 고친다(감사 완화 금지).
- #126과의 관계: #126의 "recovery 파일 새 세션 선행"은 그대로 두어도 된다(방어 중첩). 이 PR이 병합되면 공유 세션에서도 pg_restore가 성공해야 하며, 그 확인은 Core 전체 suite에 recovery 파일을 되돌리는 후속 카드(Codex owner 판단)에서 한다.
