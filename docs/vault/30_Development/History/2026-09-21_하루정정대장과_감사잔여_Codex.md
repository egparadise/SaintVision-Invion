사용자가 14개 conflict를 해소한 직후 check 0/0을 확인했지만, 후속 정본 문서 추가/수정 뒤 Codex read-only check는 **7 no-baseline, exit 1**을 반환했다. 대상은 전체 진행 현황, Codex 작업 현황, 검증 상태 지도, 이 sync history, 앞선 sync/SSR 감사 history, UI-FB review history, 검증경계 종합이다. `--apply`는 실행하지 않았다. 따라서 최신 document changes가 vault에 동기화됐다고 말하지 않고, 해당 목록에 대한 사용자 편집 대조와 승인된 resolution 절차가 다음 단계다.

## API mock/backend 계약 설계 제안

현재 `tools/export_schemas.py`는 `src/saintvision/api/schemas.py`의 Pydantic `Strict` 모델에서 `contracts/*.schema.json`을 생성하고 backend workflow가 drift를 검사한다. 이를 신규 framework로 교체하지 말고 endpoint 응답까지 확장하는 안을 권고한다. 현재 `/v1/discovery/candidates`는 `dict` 응답이며 frontend `DiscoveryCandidate`는 수기 타입이다. `test_route_coverage.py`의 해당 테스트는 source 문자열/필드 선언을 대조하지만 serialized route body의 검증은 아니다.

단계안: (1) 후보 row 및 `{items, note}` envelope를 strict response model로 선언하고 FastAPI `response_model`에 지정, (2) 기존 exporter에서 canonical JSON Schema 및 drift check, (3) frontend type 또는 runtime fixture validator를 동일 schema/OpenAPI에서 생성, (4) DB 의존 없이 dependency override/TestClient로 실제 handler serialization을 provider contract test에서 검증, (5) adapter test는 canonical fixture를 소비하면서 adapter 변환/오류 처리를 검사한다. live DB가 없어도 schema generation/provider serialization은 CI에서 실행 가능하게 둔다. `route_coverage.py`는 기존 한계처럼 path shape 전용이며, method/response payload coverage는 별도 인접 gate로 추가한다. 이는 proposal이고 코드·task assignment는 만들지 않았다. 세부: [[2026-09-21_UI_FB_contract_readiness_review_Codex]].

## Obsidian state 후속 측정 정정

앞선 migration 뒤 관측된 `C:\vw`의 1373/0/0은 중간 실행이라 최종 상태로 인용하지 않는다. 같은 코드 tip `507a486`에서 main의 `--check`는 1373 managed/6 pending/0 conflicts, `C:\vw`의 `--check`는 1373/5/0이며 각각 exit 0이다. main에만 수정된 이 history 문서 한 건이 pending 수 차이다. 양쪽은 `--git-common-dir` 아래 같은 `.git/obsidian-sync-state.json`을 공유하며 어떠한 pending export도 적용하지 않았다. 이 측정은 동일 source snapshot pair가 아니라는 범위를 명시한다. 상세: [[2026-09-21_sync_common_state_UI_FB_boundary_Codex]].
