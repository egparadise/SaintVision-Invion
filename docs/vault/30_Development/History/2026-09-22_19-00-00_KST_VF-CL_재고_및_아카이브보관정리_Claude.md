## 2. 구현 항목: `tools/pitr_archive_retention.py` (코디네이터 승인, 조건 4개 충족)

- **왜 이것**: Codex 계약·물리 자원 불필요, 결정(2026-09-22 보관 7일 파일럿)과 runbook §4의 "정리 절차 미작성"을 직접 닫는다. PITR 변경안 §"아카이브 대상 저장소 요구"(연속 증가 → 보관/정리 정책 필수)의 빈칸.
- **설계**: 파일시스템 전용(DSN 없음, 다운로드 없음). 입력 = WAL 아카이브 디렉터리 + base backup 디렉터리(각 `backup_label`의 `START WAL LOCATION … (file <SEG>)`·`START TIME`). **순수 계획 함수** `plan(archive, backups, retention_days, now)` → JSON. **기본 dry-run**, `--apply`는 명시 플래그이며 삭제 전 같은 계획 JSON을 먼저 출력(조건 1).
- **불변식**(조건 2, 시험으로 고정): ① 최신 base backup은 나이와 무관하게 항상 보존 ② 보존 backup들의 **최소 START 세그먼트 이후 WAL은 어떤 입력에서도 삭제 후보에 안 들어감**(경계 세그먼트 자체 보존) ③ `.history`/`.partial`·다른 timeline은 후보 아님 ④ base backup이 0개면 아무것도 안 지움(base 없는 아카이브는 이미 복구 불가라 삭제가 도움이 안 됨) ⑤ `retention_days ≥ 1`.
- **시험** `tests/test_pitr_archive_retention.py` **9 passed**(DB 불필요, 0.4s): 빈 아카이브·최신 backup 보존·경계 보존·만료 backup+WAL 삭제·history/partial/타 timeline·무작위 300 아카이브 속성 시험·CLI dry-run 무삭제→`--apply` 정확 삭제 라운드트립·이미 없는 경로 멱등. 이웃 `test_pitr_readiness`·`test_pitr_boundary` 19 passed / 1 skip 불변.
- **시험이 잡은 도구 결함(기록)**: 첫 구현은 경계를 "시간상 가장 오래된 backup의 START"로 잡았다. 속성 시험이 라벨 시각과 WAL 위치가 어긋난 입력에서 **보존 backup의 WAL이 삭제 후보에 들어가는** 반례를 냈고, 경계를 **보존 backup들의 최소 START**로 고쳐 통과. 눈으로는 안 보이던 것 — 규칙 "답을 아는 자리에 대보라"의 한 사례.
- **runbook §4 정합**(조건 3): 보관 7일 결정 문장 뒤에 도구 명령·dry-run/apply·불변식을 한 줄로 추가(v1.2.0 본문, status review).
