# 검증 경계 감사 — 우선순위 3 잔여

검증 경계 감사 종합의 우선순위 3 잔여(나머지 DB·credential fixture의 `raises` 범위, cleanup, 동시성, 실 driver 오류. 그동안 핵심 표본만 봤고 전수 미완)를 **전수**로 수행했다. 기준은 이번 세션의 네 형태:
① `except Exception`이 의도 외 원인까지 삼켜 내부 결함을 정상 거부로 위장 · ② `pytest.skip`=`Skipped`=BaseException이라 `except Exception`에 안 잡히는 비대칭 · ③ `finally`가 앞 실패로 뒤 정리를 건너뜀 · ④ `pytest.raises` 범위 과다(`match` 없으면 같은 타입 아무 예외나 통과).

**방법**: 3개 슬라이스(핵심 fixture / credential·registry 통합 테스트 / credential·migration 도구·src)를 병렬 카탈로그한 뒤, 모든 REAL-DEFECT를 **내가 소스로 직접 재확인**했다. 값은 옮기지 않고 경로·성격·짧은 해시만 기록한다. 통합 tip 기준(`origin/integration/all-agents-unified` 병합 상태)에서 판정했다.

## 적용한 수정 (소스 검증. 실행 경계 명시)
1. **`tools/check_migration_upgrade.py`** 최상위 핸들러 (형태 ①) — `except Exception`이 AssertionError(진짜 검증 실패)와 KeyError/psycopg 오류(내부 결함)를 모두 "validation failed"로 보고하던 것을, `except AssertionError`(검증 실패)와 `except Exception`(내부 오류, `type(exc).__name__`만 표기)으로 분리. **전파·값누출 불변**(둘 다 SystemExit로 변환·값 억제 유지) — 메시지 카테고리만 보존. `py_compile` OK. *[Claude-실행: 구문]*
2. **`tests/integration/test_credential_backend.py:296`** (형태 ④ high) — `pytest.raises(psycopg.Error)`(base) → `pytest.raises(psycopg.errors.CheckViolation, match="immutable record")`. 의도된 실패는 append-only 트리거 `inv.immutable_record()` 뿐인데(직접 확인: `services/control-plane/src/inv/migrations/0001_core.sql:116` = `RAISE EXCEPTION 'immutable record' USING ERRCODE='23514'` → 23514=CheckViolation), base 타입이라 InsufficientPrivilege(42501)·UndefinedColumn·연결오류가 "불변성 강제"로 위장 통과할 수 있었다. 형제 `test_provisioning_integrity.py:94`가 이미 `CheckViolation`을 쓰던 것과 정합. **strictly tightening + break-when-vacuous**(트리거가 사라지면 UPDATE 성공→DID NOT RAISE 실패; 권한 회귀는 InsufficientPrivilege→이제 실패).
3. **`tests/integration/test_provisioning_integrity.py:94`** (형태 ④ 강화) — 기존 `CheckViolation`에 `match="immutable record"` 추가(self-enforcing). 같은 트리거·소스 검증. 그 테이블의 다른 CHECK(reason 길이/grant_scope/jsonb)가 미래에 걸려도 불변성 단언으로 위장 못 하게.
4. **`tests/core/test_sandbox_contracts.py:62`** (형태 ④, **venv 실행 검증**) — 11-field isolation-downgrade funnel `pytest.raises(DomainError)`(match 없음)에 **양성 대조**(수정 전 compiled plan이 유효함을 먼저 단언)와 `match="VAL-0002"`를 추가. 실측 결과 11 field가 **모두 단일 스키마 코드 `VAL-0002`**를 뱉어 per-field 구분은 층 구조상 불가하나, 양성 대조가 없으면 compile_launch가 언젠가 무효 plan을 내는 순간 11건이 전부 공허 통과한다 — 그 공허성을 닫았다. `.venv` 실행 26 passed + 되돌림 대조(틀린 match는 AssertionError로 실패)로 공허하지 않음 확인. *[Claude-실행: .venv pytest]*

**실행 경계 — 세 상태 구분 (v1.0.0 정정. 아래 정정 절 참조)**: 2·3은 실 PostgreSQL 필요(`@pytest.mark.postgres`/`INV_TEST_ADMIN_DSN` 게이트)라 **판정(실행됨)은 PG 환경 대기**다. 단 이는 "수집 불가"가 아니라 **수집됨 + 이유 보이는 skip**이다: `.venv/Scripts/python.exe -m pytest`로 돌리면 두 파일 **69 collected, 69 skipped**이며 각 skip에 `Set INV_TEST_ADMIN_DSN...` 이유가 출력된다(즉 파싱·import 성공 = 내 `match=` 편집 유효). 4는 PG 불필요·`.venv`로 판정 완료. `psycopg.errors.CheckViolation` 접근성·`23514→CheckViolation`도 `.venv`로 실측.

## 기록·인계 (직접 수정 안 함 — 소유 경계)
`provision_credentials.py`·`plan_lan_migration.py`는 credential/migration **보안·복구 도구**이고, 올바른 수정이 **전파 의미(무엇이 crash/deny 되는지)**를 바꾼다. CLAUDE.md상 고난도 보안 변경은 Codex 계약이므로 **수정안과 함께 인계**한다(값누출 방어를 내가 약화시키지 않기 위해서다).

- **`tools/provision_credentials.py:301` (형태 ① 주 — 두 파일 나란히 재확인)** — `provision()`는 본문 전체(`:135` `try:` ~ `:300`)를 한 `try`로 감싸고 `:301 except Exception: raise ProvisioningDenied() from None`로 닫는다. 그 안의 의도된 거부는 **명시적 `raise ProvisioningDenied()`**(`:145` 권한, `:151` epoch, `:161` gate/run, `:174` grant, `:181` expiry …)다. catch-all은 이들 외에 (a) `psycopg.connect(...timeout)` 실패/DB-down (b) `:179 fetchone()["valid"]`류 TypeError/KeyError (c) `psycopg.Error` (d) **임의 내부 호출이 던지는 예외**(예: `admin.event(...)` 감사 기록)를 모두 한 "denied"로 붕괴하고 `from None`으로 원인을 지운다.

  **정답 형제 대조(확인)**: `provision_account.py:244-257`은 `except ProvisioningRefused`(거부, 사유 출력) / `except psycopg.Error`(DB 실패, `sqlstate`만) **두 typed 분기 + catch-all 없음** — 예기치 못한 `KeyError`/`TypeError`는 traceback으로 크래시(거부로 위장 안 됨). 카테고리 완전 보존.

  **그러나 그대로 복제하면 안 된다(내 이전 서술 정정·보강)**: `:301`의 catch-all은 형태 ① 결함인 동시에 **의도적 이중 역할**이 있다 — 임의 실패 메시지의 **비밀 스크러빙** + **롤백 보장**. `test_credential_provision.py:140-153`(`test_audit_failure_rolls_back_rotation`)이 `admin.event`를 monkeypatch해 `RuntimeError("synthetic-private-detail")`를 주입하고, 표면 예외에 그 비밀이 **없음**과 롤백(count==0, secret intact)을 단언한다. 형제 패턴을 **verbatim 복제하면 이 RuntimeError가 그대로 전파돼 (1) `pytest.raises(ProvisioningDenied)` 실패 (2) 메시지의 비밀 재노출**이 된다.

  **정답 수정안(양쪽 보존)**: ① 명시적 `ProvisioningDenied`는 그대로 전파(의도 거부 — 불변) ② `psycopg.Error`는 별도 DB-실패 신호(`sqlstate`만) ③ 그 외 예기치 못한 예외는 **raw 재전파가 아니라** 비밀 없는 별도 "internal error" 결과로(값·args 없이 `type(exc).__name__`만) — 카테고리·비밀 스크러빙·롤백 **동시 보존**.

  **전파 영향 caller(실측)**: `provision()` 호출자는 `main():331`, `tests/integration/test_credential_provision.py:50`(헬퍼 `call`), `:202`뿐. ㉠ `main()`의 외곽 `:334 except Exception`이 **모든 신형 타입을 흡수**해 credential-free `refused`·return 2 유지 → **CLI 동작 불변**(원하면 main도 카테고리 표기하도록 별도 정련). ㉡ **영향받는 유일 시험 = `test_audit_failure_rolls_back_rotation:148`** — 내부 비-정책 실패를 `ProvisioningDenied`로 기대하므로, ③ 신설 시 기대 타입을 그 "internal error"로 갱신하되 **비밀-부재·롤백 두 단언은 유지**해야 한다. ㉢ 명시적-거부 경로 시험(`:115/:192/:201/:271/:280/:128`)은 `provision()` 안에서 직접 `raise ProvisioningDenied()`하므로 **무영향**. (Codex 계약 구현 시 이 한 시험만 함께 갱신하면 된다.)
- **`tools/plan_lan_migration.py:66` (형태 ① 중)** — `main()`의 `except Exception`이 `gap_plan`의 의도된 `ValueError`(불일치 메타)를 DB-down·버전파일 부재(`OSError`)·내부 버그와 한 exit-2 메시지로 붕괴. 수정안: `psycopg.Error`/예상 `ValueError`를 구분 메시지로, 그 외는 재전파/타입명 표기.

3. **provision_credentials:301 보강** — v1.0.0은 "형제 패턴 그대로 적용"이라 단순화했으나, `:301` catch-all은 결함인 동시에 **비밀 스크러빙+롤백**이라는 의도적 역할이 있어 verbatim 복제 시 `test_audit_failure_rolls_back_rotation`이 깨지고 비밀이 재노출된다(위 기록·인계 절에 정답 수정안·영향 caller 실측 반영).

immutable 트리거 메시지 확인 중, 초기 grep을 `migrations/**`로 한정해 실제 정의(`services/control-plane/src/inv/migrations/0001_core.sql`)를 놓쳤다. 직접 그 파일을 읽어 메시지·ERRCODE를 확정했다. 서브에이전트 주장은 소스로 재확인해야 하고, 이 저장소는 alembic(`migrations/versions`)과 control-plane SQL 두 계열이 있어 **검색 경로를 둘 다 봐야** 한다. `judge-integration-files-from-origin-not-worktree`와 같은 결의 교훈.
