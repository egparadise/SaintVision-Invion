# a681da3 물리 PITR 리허설 재검토

base9251f18, 후보 a681da31ee99422eb1ef9d6455f28495291c368b, owner Codex(검토), 수정 owner Claude. branch agent/codex/model-registry-binding, agent-delivery1.1.0/core-reliability1.0.0 적용. 사용자 소스/증거 텍스트 검토 수신이며 사용자 리허설 재실행은 없었다. Codex도 실제 Docker/PG 리허설은 실행하지 않았다.

- 제출 텍스트는 basebackup rc0, pg_ctl rc0, in_recovery=f, archive recovery complete, restoredRows=[before]를 보고한다. Claude 실행 증거로 수신하며 복원 성공의 관측을 부정하지 않는다. 단, 아래 결함 때문에 이 스크립트의 exit0만으로 모든 선행조건과 목표도달이 강제됐다고 할 수 없다.
- R1-02: 기존 MinIO가 same-host임을 명시하고 off-host 보장을 철회한 부분은 소스 검토상 해소.
- R1-03: 이미 있는 동일 파일 cmp 성공/다른 파일 cmp 실패는 단순 재호출 문제를 고친다. fsync 부재와 single-host 한계를 명시한 점은 수용. 전체 생산용 내구성/경합 안전성을 실증한 것으로 보지 않는다. 임시파일 고정이름/확인 후 mv의 경합 및 crash 내구성은 아직 별도 검증 없음.

## PITR-R2-01 / P1 — 선행 실패·목표 미도달을 강제하지 않는 합격 판정

최상위는 set -u뿐이고 내부 sh -s에는 오류 종료 정책도 없다. basebackup/pg_ctl 종료 코드는 echo만 한다. psql은 ON_ERROR_STOP 설정이 없고 INSERT before/after 및 시간조회·WAL 전환 성공을 검사하지 않는다. docker exec -i의 실패도 최상위에서 검사하지 않는다. in_recovery가 f가 아니어도 루프 종료 후 인쇄만 한다. 최종 PASS 조건은 ROWS=before 하나다.

최소 반례: after INSERT가 실패하면 원본에도 after가 없을 수 있다. 복원 결과 before만으로는 목표 이후 데이터의 배제를 시험했다고 할 수 없다. 복원 서버가 읽기 가능한 recovery/pause 상태라도 결과 행만 맞으면 현재 판정은 승격/목표도달을 강제하지 않는다.

실측 범위: Git Bash에서 실제 소스의 after INSERT와 최종 if/exit 문장을 추출하고 psql 실패(return1)와 ROWS=before를 주입했다. 출력 injectedAfterInsertExit=1 뒤 PASS, 최종exit0. Evidence/pitr-review/a681da3-failure-path.json에 정확한 추출script/결과/범위 기록. 이는 전체 DB 리허설이나 실제 제출 실행 실패 재현이 아니라 누락된 판정 경계의 합성 실증이다.

수정 조건: 모든 필수 단계의 exit를 검사하고 SQL은 ON_ERROR_STOP으로 실패를 전달한다. 원본 A/B 커밋과 T1 앞뒤 순서를 별도 관측·검사하며 복원 시작/목표도달/최종 in_recovery=f와 A존재/B부재 모두 합격조건에 넣는다. 실패한 A/B INSERT, basebackup, restore start, promotion timeout을 주입해 각각 nonzero·비PASS가 되는 음성 회귀를 제출한다. 실제 성공 리허설도 수정 harness SHA/명령/최종exit/원본 및 복원 상태와 함께 보존한다.

## PITR-R2-02 / P2 — 무차별 변경 명령 재시도와 소유권 없는 cleanup

dk()는 모든 docker 실패를 daemon busy라고 부르고 최대5회 재시도한다. docker run처럼 변경 명령도 동일하며 실패가 mutation 전에 일어났는지 구분하지 않는다. 이는 앞서 loader 단계로만 재시도를 좁힌 원칙을 따르지 않는다. 이름은 pitr-probe-$$이고 EXIT cleanup은 생성 성공/불변 container ID/owner label 확인 없이 이름에 rm -f를 실행한다. 이름 충돌로 run 실패 시 기존 같은 이름 컨테이너를 지울 수 있는 경로다. 이번에는 Docker로 이 파괴 경로를 실행하지 않았다.

수정 조건: 변경 요청의 불명확 실패는 무작정 재시도하지 않는다. 고유 run token/소유 라벨과 생성된 container ID를 추적하고, 생성되지 않은 대상을 cleanup하지 않는다. cleanup 실패도 보고하며 검증 결과를 덮지 않는다. 이름충돌/시작 후 응답실패/cleanup 실패를 stub으로 검증한다. 분류되지 않은 모든 실패를 daemon busy라고 기록하지 않는다.

제안 v1.2.0 영향 항목에는 idle에도300초마다16MB, idle floor, wal_keep_size가 미아카이브 재활용을 방지한다는 설명이 남았다. override에도 archive_timeout의 RPO ceiling/900초 여유 주석이 남았다. 세그먼트 전환은 활동 조건이 있고 저장소 전송 지연·실패가 있으므로 timeout만으로 RPO 상한을 보장하지 않는다. 마지막 다음담당의 --require-operational-rpo 재확인도 본문 fail-closed 설명과 여전히 모순이다. 원래 R1-04의 정정 조건과 공식 PG16 문서 근거를 유지한다.
