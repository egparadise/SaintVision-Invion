# 결론

입력 하나만으로 다음 스프린트 전체가 열리는 구조는 아니다. S02의 네 영역은
S01-FE·S01-BE·S01-DB·S01-ST를 모두 선행으로 요구한다. 따라서 실제 첫 관문은
**IdP/CA/DNS 묶음으로 S01-BE를 닫고, 물리 장비/Storage 값 묶음으로 S01-ST를
닫는 것**이다. S01-DB는 이미 done이고 S01-FE는 review다.

아래 숫자는 완료 수가 아니다. `docs/task-registry.json`의 dependency closure를 센
**후속 과제가 dependency상 후보가 되는 수**이며, 각 과제의 자체 증거가 추가로
필요하다.

## 직접 영향

| 사용자 입력 | 직접 풀리는 범위 | 현재 남은 별도 증거 |
|---|---|---|
| 물리 장비 5대 | S01-ST 장비 inventory, S02-BE의 mTLS/heartbeat 실장비, S02-DB의 운영 인수(5대 등록·계정/제공량), S02-ST의 실제 제공 폴더/장비, S02-FE의 실제 Node 관측 여정 | 장비별 설치·인증·관측 결과와 브라우저/API 증거. S02-DB의 소프트웨어/실PG 증거 자체는 이미 사용자 입력 없이 충족됨 |
| IdP | S01-BE의 issuer/audience/JWKS·운영 로그인, S02-BE의 OIDC 등록 | CA/DNS, 실 브라우저 로그인 및 운영 subject 인수 |
| CA | S01-BE의 인증서/권한 경계, S02-BE의 mTLS 등록 | 실제 장비 인증서 발급·회전·폐기 인수 |
| DNS | S01-BE의 운영 endpoint/권한 경계, 운영 로그인·S02-FE 접근 경로 | TLS/실망 환경과 브라우저 네트워크 증거 |
| Storage 제품 값 | S01-ST의 제품·URI·보존·검증·장비 inventory, S02-ST의 실제 제공 폴더/DataLocation | 실제 제품 계정·허용 경로·보존/복구 및 제품 통합 증거 |
| 다운로드 정본 결정 | S03-ST의 Artifact 기본 전송 정본 하나(`DB receipt` vs 저장 파일) | S03-ST 구현·전송·checksum/권한 시험. S03의 다른 세 영역과 S02 선행은 별도 |

직접 영향은 의미상 분류다. registry는 S01-BE/ST의 사용자 입력 종류를 각각 별도
필드로 기록하지 않으므로, 현재 브리프와 S01/S02 작업 문서의 차단 사유를 함께
대조했다.

## Registry dependency 사슬

`docs/task-registry.json`을 기준으로 계산한 결과:

- S01-BE를 선행으로 요구하는 후속 과제: **44개(S02~S12)**
- S01-ST를 선행으로 요구하는 후속 과제: **44개(S02~S12)**
- S02-BE 또는 S02-ST를 선행으로 요구하는 후속 과제: **40개(S03~S12)**
- S03-ST를 선행으로 요구하는 후속 과제: **36개(S04~S12)**

따라서 S01-BE와 S01-ST가 모두 닫히면 S02~S12의 44개가 dependency상 다음 단계로
갈 수 있다. 이것은 44개가 완료된다는 뜻이 아니다. 각 과제의 자체 증거는 여전히
필요하다. 예를 들어 S04는 선행 해소 뒤에도 만료 승인·취소·중복·재전송 경합
증거가 필요하고, Claude가 별도로 만든 166건 결과가 그 증거 후보이다.

다운로드 정본 결정은 registry 사슬에서 S03-ST 하나의 직접 게이트이고, 그 뒤
S04~S12 **36개**에 전달되는 의존 게이트다. 다만 S02와 S03의 다른 영역이 먼저
충족되어야 하므로 이 결정만으로 즉시 36개를 닫을 수는 없다.

## 사용자 의사결정 순서

1. **동시에 준비할 첫 묶음:** IdP+CA+DNS와 물리 장비+Storage 값을 각각 준비해
   S01-BE와 S01-ST를 닫는다. 이 두 묶음이 S02 전체를 여는 실제 관문이다.
2. **그 다음:** 장비/IdP가 실제로 들어오면 S02-BE·DB·ST·FE의 API·인증·브라우저
   증거를 생성한다. S02-DB의 일회용 PG 증거는 이미 있으므로 사용자 입력 자체는
   필요하지 않다.
3. **S03 진입 후:** 다운로드 정본을 결정한다. 현재 `result_view.py`는 DB receipt
   바이트를 전송하므로, 저장 파일을 정본으로 할지 receipt를 정본으로 할지는
   Codex가 추정해 바꿀 수 없다.
4. **후속 스프린트:** 선행이 풀려도 각 스프린트의 경합·부하·복구·브라우저·실장비
   증거를 별도로 생산한다. 선행 해소를 완료로 세지 않는다.

단일 입력의 registry closure 수는 IdP/CA/DNS 각각 S01-BE의 44개 사슬, 물리/Storage
각각 S01-ST의 44개 사슬로 대칭이다. 그러므로 “무엇 하나가 가장 많이 푸나”에 대한
정직한 답은 **단일 항목이 아니라 S01-BE+S01-ST 두 묶음**이다. 하나만 먼저 시작해야
한다면 공급 리드타임이 긴 물리 장비/Storage를 먼저 준비하면서 IdP·CA·DNS를 병행하는
것이 합리적이지만, 어느 한쪽만으로 S02가 열리는 것은 아니다.

## 범위와 한계

- 이 문서는 task 수와 dependency 사슬을 세었다. 진척률 산식을 바꾸지 않는다.
- “직접 풀림”은 해당 입력이 없어서 현재 증거를 만들 수 없는 범위이고,
  “사슬로 풀림”은 registry 선행만 해소되는 범위다. 후자의 자체 증거까지 자동
  충족한다고 주장하지 않는다.
- 실제 IdP/CA/DNS, 물리 5대, Storage 제품 계정과 다운로드 정본 선택은 사용자/운영
  결정 또는 인수 범위다. 이 문서가 값을 대신 정하지 않는다.
