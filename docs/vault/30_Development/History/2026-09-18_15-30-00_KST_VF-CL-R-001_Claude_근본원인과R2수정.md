# VF-CL-R-001 근본 원인 규명, 심각도 재평가, R2 수정 (Claude)

내 진단 복원(은폐 제거)이 이 finding의 실제 근본 원인을 드러냈고, 그것이 finding의 전제를 바꾼다. Codex가 내 1차 remediation을 검토해 P1 하나(R2-01)와 P2 하나(R2-02)를 잡았고, 둘 다 타당해 수정했다.

## 근본 원인 (전제 변경)

사용자가 내 브랜치를 동일 digest로 clean worktree에서 직접 돌렸고, 은폐를 걷어낸 덕에 traceback이 그대로 나왔다: `run_vf_security_tests.py`의 docker inspect가 **exit 3221225794 = 0xC0000142 = Windows STATUS_DLL_INIT_FAILED**로 죽었다. docker daemon 오류가 아니라 **docker.exe 프로세스가 초기화조차 못 한 것**이다. daemon은 건강했다(직후 docker version 정상, inspect 10/10 재현 실패 — 간헐적).

즉 지금까지 'docker-daemon-io-timeout'으로 분류된 것들은 **daemon 문제가 아니라 호스트의 프로세스 생성 실패**일 가능성이 높다. 이것이 세 현상을 한 번에 설명한다: daemon 건강 검사가 항상 통과하는 이유, 실패가 간헐적이고 케이스를 옮겨 다니는 이유, 그리고 내 컨테이너 정리가 부분효과만 낸 이유(RAM 압박은 줄었으나 프로세스 생성 압박은 그대로).

### OneDrive — 상관 (인과 아님)

사용자 실측(정정판): 프로세스 380개, 가용 RAM 2,224MB/8GB, OneDrive 핸들 시각별 11:45경 463,776 → 11:58경 476,020 → 12:02:27 481,629 → 12:03:57 481,600. Agent 쓰기 버스트 20분간 +17,853, 조용한 90초에 −29. **일정 속도로 새는 고전적 누수가 아니라 쓰기 버스트와 상관해 증감하는 패턴**이므로 '누수'는 과한 표현. 다만 481,600은 2위 System 7,682의 60배로 수준은 비정상. 이 프로젝트 Obsidian vault가 OneDrive 동기화 경로(AGENTS.md 45행이 공유 정본으로 지정)에 있고 Agent 셋이 매 사이클 문서를 써 OneDrive가 동기화하며 핸들을 쌓는다 — **확정 인과가 아니라 상관**으로 다룬다. 핸들 수준 자체의 조치는 사용자 환경 몫(사용자가 처리).

## 심각도 재평가

- **1차 판정**: Medium/P2 — "컨테이너 누수가 미실행 보안 단언을 환경으로 오분류".
- **재평가**: 실제 근본 원인은 **호스트 프로세스 생성 실패**(NTSTATUS)로, 제품/시험 결함이 아니라 호스트 자원 압박(OneDrive 상관)이다.
  - 이미지-시험 실패는 **제품 결함 아님**(프로세스가 시작조차 못 함, 확정).
  - 내가 1차에 고친 컨테이너 누수도 근본 원인 아님(RAM만 완화).
  - **내 영역의 실제 결함**: (a) 진단 분류기가 host-init을 daemon과 구분 못 함, (b) 간헐적 host-init에 재시도 없음, (c) 내 1차 prune이 동시성 비안전(R2-01). (a)(b)(c) 전부 수정.
- **재평가 심각도**: 제품/시험-side 잔여는 **Low/P3** — 하네스가 이제 host-init을 올바로 분류·재시도하고, 근본 조건은 환경적(사용자 처리). 보안 단언은 호스트 건강 + 재시도로 실제 실행될 것이다. (내가 도입한 R2-01은 별도로 P1이었고 해결됨.)

## R2 수정 (Codex 검토 반영)

- **VF-CL-R2-01 (P1, 동시 실행 자원 삭제)**: 1차 prune이 전역 kernel-test 라벨로 created/dead/exited를 열거 후 `docker rm -f` — 공유 3-Agent 호스트에서 다른 실행의 갓 생성/막 running 컨테이너를 강제 삭제할 수 있었다. **동시성 안전 재설계**: `exited`만, **30분 age 임계 초과**만(동시 실행 컨테이너는 recent이고 그 자신의 finally가 처리), **비강제 `docker rm`**(running 거부). network는 빈 것만. 시험이 running 동시 컨테이너가 age gate off에도 생존, recent exited 보존·old 제거를 실증.
- **VF-CL-R2-02 (P2, best-effort 불일치)**: 사전 prune이 try/finally 밖이고 run()의 TimeoutExpired/OSError를 안 잡아 오류 가림 재도입 위험. prune 호출을 try/except로 감싸 prune 실패가 run을 중단하지 않게.

## Image lane 판별 결과 (2026-09-18) — 진단은 성공, 재시도는 지속적 압박을 못 넘음

사용자가 b5f770a(docker_diag.py 적용)를 clean worktree·동일 digest로 8케이스 실행했다. **진단 복원은 완벽히 작동**했다: 증거 JSON의 cleanup이 이제 `host process-creation failed (NTSTATUS 0xC0000142); the OS could not start the process -- host resource/handle pressure, not a docker/daemon error`로 나온다. 예전의 'diagnostics suppressed'와 달리 완전히 반증 가능해졌다.

- **결과**: 2 passed / 6 failed.
- **실패 분해**: `writable`·`public-signing-key`·`business`·`business-workspace`·`business-kernel-role` 5건 = NTSTATUS 0xC0000142(실패 지점 `docker volume create` 또는 `docker inspect`). `unreadable` 1건 = `docker run`에서 TimeoutExpired.
- **판정 1 — 제품 보안 단언 실패 0건 (재확인)**: 모든 실패가 host process-creation 실패 아니면 timeout. 제품 결함은 이번에도 없다(단, 아래처럼 대부분이 *미도달*이라 통과로도 볼 수 없다).
- **판정 2 — host-init 재시도가 5건을 구제하지 못함**: 앞선 "10/10 재현 실패 → 재시도 유효" 가설은 *일시적* 압박 전제였다. 실제로는 **압박이 지속적**일 때 즉시 재시도로 넘지 못한다. 게다가 시험 실행 자체가 프로세스 생성 압박을 더해 앞선 3 passed가 이번엔 2 passed로 **악화**됐다 — 재시도(추가 process-creation)는 이 조건에서 무익할 뿐 아니라 역효과다.

### 마무리 조치 (내 owner 영역, 사용자 요청 3건)

1. **재시도 정책 재검토 → "최소 1회 일시적 완충"으로 축소, 정직한 주 메커니즘은 미검증 기록**. `docker_diag.run`의 기본 `retries`를 2→**1**로 낮추고 backoff를 키우지 않는다(지속적 압박은 초 단위로 안 풀리고, 대기·재시도는 자원만 더 문다). 대신 **infrastructure 실패(host-init OR timeout)를 분류해 미검증으로 정확히 기록**한다 — 사용자가 기운 "후자"가 옳다. `run_vf_security_tests.py`에 **선행 host 검사**(`docker version` 프로브)를 넣어 이미 압박된 호스트를 사전에 `unverified`(exit 125)로 기록하고, 컨테이너 생성/inspect가 infrastructure 실패면 `_HarnessUnavailable`로 잡아 실패(exit 1)·시험 timeout(exit 124)과 구분해 기록한다. `test_server_container.py`의 `docker()`는 infrastructure 실패 시 `pytest.skip`으로 **미검증을 미검증으로** 남기고(제품 결함으로 오기록하지 않음), 실 docker/제품 오류만 loud fail.
2. **TimeoutExpired 분류 gap 폐쇄**. `docker_diag.run`이 `subprocess.TimeoutExpired`를 잡아 분류된 결과(returncode 124 + `.timed_out`)로 반환하고 절대 raw 전파하지 않는다 — 이것이 러너를 `run_vf_security_tests.py`에서 죽인, 내가 없앤 오류 가림과 같은 종류의 구멍이었다. timeout은 재시도하지 않는다(이미 전체 timeout을 소진). `is_infrastructure_failure`가 host-init과 timeout을 하나의 "미검증" 판별로 통합한다.
3. **본 문서 마무리(아래 미검증 판정)**.

### 미검증은 미검증으로 — 최종 판정

제품 결함 0건은 확인됐다. 그러나 **8건 중 실제 통과는 2건뿐**이고, 나머지 6건(`business-kernel-role`의 DB role 거부 단언 포함)은 **보안 단언에 도달하지 못했다**. 따라서 이들은 통과도 실패도 아닌 **미검증(unverified)**으로 유지한다. 하네스는 이제 이 미검증을 `pytest.skip`/`exit 125`/증거 JSON의 `unverified` 필드로 **정직하게 기록**하므로, 다음 실행부터는 미도달이 거짓 실패나 은폐로 나타나지 않는다.

## Codex R3 재검토 수정 (2026-09-18) — 재시도 안전성·마스킹 완결성

Codex가 b5f770a를 재검토해 R2-01/R2-02는 소스로 해소 확인, blocker 3건이 유지됐다. 셋 다 근거가 구체적이라 수정했다(브랜치 전체 보류였고, Codex는 prune만 fork하지 않고 일관 수정본을 재검토하기로 함).

- **R3-01 (P1, 재시도 안전성)**: `is_host_process_init_failure`가 *모든* error-severity NTSTATUS(>= 0xC0000000)와 `-9`를 초기화 실패로 분류했다. Codex가 mock `0xC0000005`(access violation = 실행 후 crash)로 `docker run` 2회 호출을 재현 — **변경 명령이 이미 한 번 실행됐는데 재시도하면 중복 자원**(volume create/run에서 특히). `-9`(POSIX SIGKILL)를 Windows 초기화 실패로 표시한 것도 오분류. **수정**: (a) **플랫폼 게이팅** — NTSTATUS는 Windows에서만 유의미(`windows` 인자, 기본 현재 플랫폼, 시험 주입 가능); POSIX 음수 코드는 신호이지 NTSTATUS가 아니다. (b) **loader-stage 전용 allowlist** `{0xC0000142 STATUS_DLL_INIT_FAILED, 0xC0000135 STATUS_DLL_NOT_FOUND}` — entry point 이전 실패만(프로세스 미실행 = 재시도 안전). crash(0xC0000005)·signal(−9)은 제외(실행됨 → 미재시도). (c) `describe_failure`가 init 실패·crash·signal·timeout·docker오류를 각각 다른 문구로 명명(반증 가능). (d) 시험: crash한 변경 명령(`docker volume create` → 0xC0000005)이 **정확히 1회** 호출됨을 검증, 시도별 결과를 순서대로 보존함을 검증, 플랫폼 게이팅·loader-only allowlist 검증.
- **R2-03 (비밀 마스킹 불완전)**: URL `user:password@`만 가려지고 libpq `password=...`는 노출됐다. **수정**: `masked_stderr`가 URL·libpq(`password=` bare)·인용 문자열(single/double) 세 형태를 모두 마스킹, `password=` 마커와 비밀 아닌 키워드(`dbname=` 등)·원본 오류 종류는 보존. 회귀 시험(세 형태 동시)을 추가.
- **finally 결과 보존 (Codex 추가 지적)**: 러너 `finally`의 inspect/rm이 `OSError`를 안 잡아(그리고 이전엔 TimeoutExpired도) proof JSON 기록을 건너뛸 수 있었다 — 러너 63행 TimeoutExpired 전파와 같은 뿌리. **수정**: cleanup 전체를 try/except로 감싸 실패를 마스킹해 `proof['cleanup']`에 남기고, **JSON write는 finally의 마지막 무조건 실행문**으로 둬 cleanup이 실패해도 비밀 없는 증거 JSON이 항상 기록되게 함. (docker_diag.run이 TimeoutExpired를 이미 분류하므로 그 경로는 이중으로 막힘.)

### 검증 (R3 수정)

- 순수 로직 직접 실행 통과: 플랫폼 게이팅(0xC0000142 win=True만 True, off-Windows False), loader-only(0xC0000005/−9 미분류), 변경명령 crash 1회 호출(중복 방지), 시도별 결과 순서 보존, timeout 분류·미재시도, describe 5범주, 마스킹 3형태(URL·libpq·인용)+오류 보존, finally OSError가 비밀 마스킹된 JSON을 기록. 변경 6파일 `py_compile` OK, 잔여 구-시그니처 호출부 0.
- *본 worktree pytest 미설치*로 pytest 스위트는 이 환경 미실행(정직 기록); 위는 표준 라이브러리만으로 직접 실행.

## 사용자 실측 결함 — timeout 반환 타입 불일치와 그 은폐 (2026-09-18)

사용자가 내가 정직하게 남긴 공백(worktree pytest 미설치)을 메워 b809fbe를 clean worktree에서 pytest로 돌렸고 **11 passed / 1 failed**, 실패는 `test_check_kernel_docker_hygiene.py::test_prune_removes_old_exited_residue_but_spares_a_recent_one`, 오류는 `check_kernel_docker.py:91 AttributeError: 'str' object has no attribute 'decode'`. 이건 **VF-CL-R-001의 오류 가림이 다른 층위에서 재발**한 것으로, 근거가 정확했다.

- **근본 원인**: `docker_diag.run`의 반환 stdout/stderr 타입이 경로마다 달랐다. 정상/재시도 경로는 `subprocess.run(capture_output=True)`를 text 없이 불러 **bytes**를, timeout 경로는 `_timeout_result`가 `stdout='' or str`을 넣어 **str**을 돌려줬다. `check_kernel_docker`는 run()을 전부 text 없이(bytes 계약) 부르고 `.decode()` 4곳·build 로그 `write_bytes` 2곳에서 bytes를 요구하므로, **타임아웃이 나는 순간**(= 호스트 압박, 이 모듈의 존재 이유) 전부 터진다 — 가장 필요한 순간의 붕괴.
- **은폐 구조**: 사전 prune의 `try: ... except Exception: pass`(R2-02)가 이 AttributeError(프로그래밍 버그)를 조용히 삼켜, 압박 하에서 prune이 무일하고 R2-01 누수 방지가 무력화된 채 아무도 모른다. 개별로 타당한 R2-01·R2-02가 상호작용으로 하나가 다른 하나의 실패를 가린다.
- **근본 수정(타입 일관성)**: `docker_diag.run`이 **호출 모드와 무관하게 subprocess가 줬을 타입**을 반환하도록 `_timeout_result`를 모드 인지형으로 고침(text/encoding/errors 없으면 bytes, 있으면 str). `text=True` 전면 통일은 `check_kernel_docker`의 build 로그 `write_bytes`가 bytes를 요구해 불가하므로, 각 호출자의 계약(bytes 호출자=decode, text 호출자=strip)을 그대로 지키는 모드 일치가 정답이다. 정상/timeout/재시도 세 경로 × bytes/text 두 모드 타입 일관성 회귀 시험, 그리고 timeout bytes stdout이 실제 `.decode()`되는지(정확한 크래시 지점) 회귀 시험을 추가.
- **best-effort가 프로그래밍 오류를 삼키지 않도록 (판단)**: 사전 prune 래퍼를 `except Exception`→**`except OSError`**로 좁혔다. best-effort는 **운영 실패**(압박 하 docker 불가 = OSError)만 관용하고, 타입/속성 버그는 표면화해야 한다 — 그래야 R2-01 무력화가 다시 은폐되지 않는다(run()이 timeout을 분류하므로 유일한 정당 escape는 OSError). finally의 cleanup 래퍼는 `owned()`/`release_network`의 **의도적 ValueError**(소유권 불일치 시 보존)를 관용해야 하므로 넓은 catch가 정당해 그대로 둔다.
- **실측(이번엔 pytest 실제 실행)**: 사용자의 근본 원인 지적을 받아 내 worktree에 pytest를 설치(`--user`)하고 conftest 의존(sqlalchemy 등) 없는 단위 시험을 `--noconftest`로 **실제 실행 → 17 passed**(test_docker_diag 12 + hygiene 5, 실 docker에서 R2-01 동시성 prune 2종 포함). 타입 일관성·decode 회귀가 결정적으로 통과. 전체 postgres 스위트는 사용자 제공 DSN(:55432)과 무거운 의존이 있어야 하므로 CI/사용자 몫으로 남긴다.

## R5 후속 — docker 부재 환경 동작 실측 (2026-09-19)

착지 후 Codex가 통합 회귀에서 배치 문제를 짚었다: `tests/test_docker_diag.py`·`tests/test_check_kernel_docker_hygiene.py`·`tests/test_vf_docker.py`가 `tests/` 바로 아래라 tests/integration 제외 기본 스위트에 포함되는데, 호스트 압박 조건에서 실 docker 호출(hygiene의 prune 2종)이 느려/타임아웃 나 스위트가 완주하지 못한다(3파일 제외 시 62초). **배치·CI 경계 판단은 Codex 영역**(marker 분리/integration 이동/현행). 사용자가 내게 요청한 것은 하나 — **docker 부재 시 이 3파일이 깔끔히 skip되는지, 오류로 실패하는지 실측**.

- **실측(docker를 PATH에서 제거)**: `PATH` 제한으로 `shutil.which("docker")==None` 확인 후 `pytest --noconftest` 3파일 → **22 passed / 2 skipped / 0 failed (0.16s)**. 2개 skip은 실 docker prune 시험(`docker CLI is required`, `@skipif(not _HAS_DOCKER)`)이며 **깔끔히 skip**. 나머지 22건은 subprocess.run monkeypatch/순수 로직이라 docker 무관하게 통과.
