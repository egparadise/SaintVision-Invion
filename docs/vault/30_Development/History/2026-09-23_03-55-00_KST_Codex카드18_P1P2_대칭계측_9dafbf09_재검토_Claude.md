## 3. (2) P2 — 귀속 근거·경계·lock_timeout 검증

- **55P03 12건 귀속 근거**: `_ObservedConnection.execute`가 오류 시 `statement`(500자 template)·`phase`·`sqlState`·`errorType`·`elapsedMs`를 기록(db.py:60~104) → evidence `timeoutStatement = {limits FOR UPDATE, 55P03, 12, placement-limit-row-wait}`. 코드 경로상 candidate에서 `55P03`이 날 수 있는 잠금 statement는 그 phase 안의 limits 한 개뿐이므로 귀속은 **결정적**. ✔
- **`lock_timeout` 면제 경로 없음**: 저장소 전체에서 `lock_timeout`/`statement_timeout` 설정은 db.py:173~174 `SET LOCAL` 한 곳뿐(grep). legacy·candidate 모두 `Database.transaction`으로 연결을 열고, `BoundDatabase.transaction`(db.py:122~126)은 caller conn을 그대로 yield하므로 상속. ✔ 주장 검증됨.
- **legacy 1454ms 무-55P03 해석**: Codex는 "client wall clock이라 thread scheduling 포함, wait_event timeline 미수집 → 미확정, F-S05-02 경계 유지"로 적었다. 정직하다. 다만 §4의 probe로 **더 단순한 설명이 성립**한다: PostgreSQL `lock_timeout`은 statement 전체가 아니라 **단일 잠금 대기 구간마다** 재시작하므로, 앞선 holder들이 각각 500ms 미만이면 legacy 한 statement가 1.45초 줄을 서도 55P03이 나지 않는다. 즉 legacy 1454ms는 client 지연 가설 없이도 **server lock wait만으로 설명 가능**하다(단, 큐가 얕거나 handoff마다 waiter가 tuple lock을 넘겨받는 조건에서). 이 해석이 문서에 없으므로 추가를 요청한다(관찰 O1). 결론 "미확정"은 유지되지만 "가설 두 개 중 어느 쪽인지"로 좁혀진다.
- 57014 0건 → 새 귀속 없음, 과거 57014를 heavyweight-lock 대기로 부르지 않음 유지 — 정합 ✔.

## 4. 반례 시나리오(서면 + 실측) — PG lock_timeout 큐 의미

카드 19 §4에서 나는 "k번째 waiter의 단일 대기 ≈ 앞선 k개 보유 합"이라 썼고, Codex는 이번에 "client scheduling"을 대안으로 세웠다. 둘 다 검증되지 않은 모델이라 커널과 무관한 probe(disposable DB `inv_probe_claude_lockq`, 표 1행, 연결별 `SET LOCAL lock_timeout='500ms'`, H가 row를 잡고 h ms 뒤 commit, 뒤 waiter들이 80ms 간격 도착·획득 후 h ms 보유)로 실측했다. 실행 뒤 DB drop.

| 시나리오 | 결과 | 의미 |
|---|---|---|
| depth 2: H450 → A450 → B(도착 160ms) | B **acquired 728ms** | 한 statement가 500ms 넘게 기다려도 55P03 없음 — **timer는 대기 구간마다 재시작**(B: tuple lock 290ms → A xid 450ms) |
| depth 3: H400 → A400 → B400 → C(도착 240ms) | **C 55P03 503.5ms**, B acquired 649ms | C는 B가 row를 얻을 때까지 tuple lock 한 구간에서 H잔여+A보유=560ms 대기 → 누적 → timeout. **모든 holder가 500ms 미만이어도 depth≥3에서 55P03** |
| depth 3: H300 ×3, C 도착 240ms | C acquired 674ms | 구간 360+300 각각 <500 → 통과 |
| depth 4: H250 ×4, D 도착 320ms | D acquired 695ms | 구간 430+250 → 통과 |

**규칙(실측)**: depth k waiter의 최장 단일 구간 ≈ holder 잔여 + 앞선 (k−2)개 hold. 따라서 (i) legacy가 1454ms 대기에도 0건이려면 그 순간 큐 깊이가 ~2~3 이하이거나 hold가 매우 짧아야 하고(도착이 분산됐다는 뜻), (ii) candidate 12건이 정확히 ~504ms에 난 것은 speculation을 마친 요청들이 limits row에 **동시에 깊게** 줄을 선 결과다. 카드 19의 내 모델은 depth≥3에서만 맞고 depth 2에서는 틀렸으므로 **정정**한다. 이 반례는 다음 카드의 두 후보 모두의 전제(큐 깊이 × hold가 500ms를 넘는다)를 지지하되, 결정 전에 **도착 timeline(요청별 lock statement 시작 시각)과 `log_lock_waits=on`(+`deadlock_timeout` 단축) 또는 `pg_stat_activity` wait_event 샘플**로 큐 깊이를 실측해야 한다는 조건을 붙인다 — 이것이 F-S05-02 "미확정"을 닫는 최소 계측이다.
