## 1. 방법과 경계

- 착지 SHA는 `git log --diff-filter=A`로 각 산출물 파일이 **처음 들어온 커밋**을 찾아 확정하고, 전부 `git merge-base --is-ancestor`로 `origin/integration/all-agents-unified` 조상임을 확인했다(25/25 YES).
- 실행 근거는 hosted Core junit을 **모듈 단위**로 파싱했다. "workflow가 success였다"는 카드의 시험이 돌았다는 뜻이 아니므로 모듈별 passed/skipped까지 내려갔다.
- **실 PG·Docker·vitest·tsc·전체 suite 없음**(코디네이터 12:25 메모리 규칙). 새 worktree도 만들지 않았다 — 이 문서는 기존 `.worktrees/claude-vfcl-ledger`에서 작성했다. 로컬 실행 수치를 새로 만들지 않았고, 인용하는 수치는 전부 **hosted CI 산출물**이거나 **기존 문서에 이미 기록된 것**이다.
- 자기 작성 산출물을 내가 검토한 것으로 세지 않는다. VF-CL-01~04는 내 카드이므로 **reviewer는 Codex**이고, §4가 그 근거다. VF-CL-05는 반대로 **내가 reviewer인 카드**이므로 §5는 그 산출물 목록이다.

## 6. 남은 공백 — 현재 사실로 갱신

### 6-1. VF-CL-02 `manifest_reader` 운영 결속 — **닫혔다** (owner Codex)

내 카드([[2026-09-22_19-20-00_KST_VF-CL-02_model-kind_URI_shards_설계_Claude]])는 `resolve_model`을 **주입식 reader**로 두고 운영 결속을 (a) `inv_app`에 `inv.model_manifests` SELECT grant / (b) 커널 HTTP / (c) 커널 확장 라우트 중 Codex 결정 대기로 남겼다. 현재 integration 실측:

- 커널 라우트 **둘 다 live**다 — `services/control-plane/src/inv/app.py:454` `GET /v1/projects/{project}/models/{model_id}/versions/{version}/execution-manifest`, `:459` `GET /v1/projects/{project}/models/resolve`.
- 채택된 답은 **(a)가 아니다**: Codex 02(c)/(d)는 `inv_app`에 새 SECURITY DEFINER EXECUTE를 주지 않고 `inv_kernel`에도 `public.data_replicas` 원시 SELECT를 주지 않았다고 기록한다. 결속은 **(c) 커널 라우트 + 그 관측을 `resolve_model`의 주입 reader로 연결**하는 방식이고, 비즈니스 측은 별도 restricted `inv_app` engine에서 RLS·reader scope로 **재확인**한 뒤 `readyNodes`를 **두 관측의 교집합**으로만 낸다. stale·version drift·ready 소실은 빈 배열과 `false`로만 강등한다.
- 내 7개 시험의 반환 의미는 유지됐다고 Codex가 기록하고, hosted에서 `test_model_uri_resolver` **7 passed**로 살아 있다(§3).
- 따라서 이 공백은 **문서 갱신으로 닫힌다**: 설계 §3의 "(a)/(b)/(c) 대기"는 **(c) 채택으로 해소**. 아직 내가 하지 않은 것은 **02(c)/(d)/(e) 세 착지에 대한 내 독립 검토**이며, 카드 2 검토(PR #58, `4473c7f1`)가 02(c)의 실행 Manifest 관측·F1 403·0046 DEFINER를 이미 덮었다 — 남은 것은 **02(d) resolver 결속과 02(e) node-agent wire**다(§9).

현재 hosted에서 `test_recovery_drill`은 **1 passed / 19 skipped**이고, 19건의 사유는 전부 `CX01_CONTAINER is unset; container identity/ownership cannot be verified`다(§3). 즉 VF-CL-04의 합격 증거 중 **"restore drill"은 hosted에서 실질적으로 미실행**이다.

#126(`agent/codex/cx01-hosted-core`)이 CI가 직접 소유한 PostgreSQL 16 컨테이너를 만들어 `CX01_CONTAINER`를 공급하고, recovery 파일을 **별도 fresh pytest session**(`dist/cx01-recovery-tests.xml`)으로 분리한다. focused gate는 **20 cases / 18 passed / 2 skipped / 0 failed**를 정확히 요구하며, standalone cleanup 1건을 빼면 **기존 setup skip 19건이 17 passed + 구체적 body-level 환경 skip 2건**(Docker-only internal-network archiver)으로 바뀐다. backend job은 CX01을 공급하지 않으므로 그쪽 19 skip은 유지된다.

Codex 기록에 따르면 두 번째 run `36351804484`에서 14 failed가 났고 원인은 **운영 데이터 처리 실패가 아니라 owner-only 부정 시험 오염**(앞 시험이 trigger를 끄고 만든 orphan `inv.result_commitments` → 복원 시 FK 거부)이며, 그래서 recovery를 fresh session으로 분리하고 **제품 predicate와 무결성 단언은 바꾸지 않았다**. 이 구분이 중요하다 — drill이 손상 source를 통과시키지 않았다는 것이 오히려 drill의 무게다.

**따라서 VF-CL-04의 drill 공백은 내 lane에서 닫을 수 없다**(CI 워크플로 = Codex 소유, #126 병합 대기). 병합 뒤 17 passed가 관측되면 그때 `ciVerified`를 drill 포함으로 올리는 것이 순서다.

### 6-4. VF-CL-04 정리 절차·운영 게이트 — **열려 있다** (owner 코디네이터/운영)

`tools/pitr_readiness.py`·`tools/pitr_archive_retention.py`는 착지했고 불변식 시험이 hosted에서 **9 + 9 passed**다. 그런데 **어떤 workflow도 이 도구들을 직접 부르지 않는다** — `.github/workflows/`에서 `pitr_readiness`·`pitr_archive_retention`·`recovery_drill`·`replica_repair` 참조는 **0건**이고, 실행되는 것은 그 도구의 pytest 파일뿐이다.

정직한 상태: **"도구와 불변식은 검증됐다"와 "운영 보관 정리가 주기적으로 돌고 있다"는 다른 주장**이고 후자의 증거는 없다. 후자는 실 아카이브 매체와 주기 결정이 필요하므로 [[2026-09-22_CX-09_PITR_Tier-A_활성여부_결정준비_Claude]]의 CX-09 결정에 매달려 있다(보관 주기 7일은 파일럿 값, 코디네이터 확인). **owner는 코디네이터/운영**이고 내 lane에서 닫을 수 없다.
