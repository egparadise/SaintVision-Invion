## 구현과 정직한 경계

하네스는 매 실행마다 표준 fixture로 disposable PostgreSQL database와 난수 login role을 만들고 정리한다. 각 반복은 N개의 합성 measured node, CPU offer/observation, shard-like location과 ready replica를 만든 뒤 한 node의 heartbeat만 중단한다. 생존 node는 실제 `record_heartbeat`와 `record_observations` 경로로 계속 갱신하고, 실제 `mark_lost_nodes`, replica stale 전환, `locations_needing_repair`, 15초 `node_spare`, `replica_health`를 측정한다.

현재 제품 경로는 repair 계획과 상태 전환까지 제공하며 물리 bytes 이동 executor는 제공하지 않는다. 따라서 복구 성공률은 plan 뒤 owner fixture가 verified replacement를 넣었을 때 실제 health가 healthy가 되는 **합성 proxy**이고 JSON은 언제나 `operationalAcceptanceAssessed=false`, `projectLockContentionMeasured=false`를 기록한다. N=5로 실행해도 물리 5-node·node-agent 중단·bytes transfer·execution shard replay 합격 판정이 아니다.

## 실 PG 예비 측정

착지 SHA에서 `--nodes 3 --repetitions 3 --liveness-timeout-seconds 1 --poll-interval-seconds 0.1 --max-detection-seconds 1.5`를 실행했다. pytest/JUnit은 1 passed, exit 0이고 JSON 결과는 다음과 같다.

- 감지 지연 min/p50/p95/max: `1.034432 / 1.103582 / 1.112639 / 1.112639`초.
- 이탈 node replica stale: 3/3, fresh replacement candidate: 3/3.
- 합성 shard proxy: 3 attempted / 3 recovered, 성공률 `1.0`; 운영 합격 판정은 false.

별도 N=3/R=1 실제 60초 경계 실행은 `60.066591`초로 `--max-detection-seconds 60`을 넘겨 JUnit exit 1을 냈다. `mark_lost_nodes`의 판정이 `last_seen < now - timeout`인 탓에 정확히 60.000초에는 여유가 없고 poll·DB 시간이 더해진다. 이를 **F-S07-03**으로 보존했으며 과거 시각 주입이나 timeout 완화로 우회하지 않았다. fresh candidate 0이면 **F-S07-01**을 기록하고 fail-closed하며, 물리 복구 미검증은 **F-S07-02**다.
