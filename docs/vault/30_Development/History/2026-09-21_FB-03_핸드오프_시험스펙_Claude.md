# UI-FB-03 핸드오프 시험 스펙

**목적**: Gemini가 이 문서를 받는 순간 **무엇을 만들지가 아니라 무엇이 통과 기준인지**를 알고 시작하게 한다. FB-01에서 "시험을 추가하라"고만 했을 때 **통과하는(그러나 회귀를 못 잡는) 시험**이 추가됐던 것을 반복하지 않기 위함이다. **경계: apps/web은 Gemini 소유 — Claude는 구현하지 않았다. 아래는 준비/스펙이며, 시험 파일은 Gemini가 작성한다.** 코드 인용은 integration tip `03e0c61`(읽기 전용) 기준.

## 왜 지금 시험이 공허한가 (근거)
`apps/web/tests/developer-studio.test.ts`는 **`.ts`(렌더 아님)** 이고, FB-03 관련 두 시험(L425, L434)은 `isRouteNotFoundError`를 **헬퍼 단독**으로 검증한다 — `DeveloperStudio` 컴포넌트를 mount하지도, `apiClient` 실패→fallback 분기를 거치지도 않는다. 그래서 Codex가 확인했듯 컴포넌트의 `if (isRouteNotFoundError(err))`를 `if (true)`로 바꿔도 **13건이 전부 통과**한다. FB-03의 빈틈은 **컴포넌트를 DOM에서 mount해 `apiClient`가 각 오류로 reject할 때 실제 fetch/fallback/오류 동작을 effect 경로로 검증하는 시험이 없다**는 것이다.

## 검증 대상 (DeveloperStudio.tsx)
아티팩트 effect(L259~330, deps `[activeRunId, liveRun?.state]`):
1. `apiClient<RunResultView>('/v1/projects/{prj}/runs/{runId}/result')` 조회.
2. `.catch(err)`에서 **`if (isRouteNotFoundError(err))`** → `apiClient(.../artifacts)` **fallback**, `setArtifactData({...data, fallbackUsed:true})`.
3. **else**(401/403/5xx/parse/network/**app-404**) → fallback 없음, `setArtifactError(...)`, ERROR 로그.

렌더(전부 `currentStep === 4` 내부, L1733):
- fallback: `data-testid="artifact-fallback-badge"`(L1991, "404 호환 폴백: /artifacts") + 상태배지 "⚠️ … Artifact Fallback / UNVERIFIED"(L2028).
- 오류: `data-testid="artifact-error-banner"`(L2069, "⚠️ 산출물 조회 오류: {msg}").
- verified: "✓ 산출물 검증 완료 (Output Verified)"(L2025, `succeeded && verifiedEvidenceId && !fallbackUsed`).

`isRouteNotFoundError`(client.ts:72) 판별(실전 유효 — client가 `application/(problem+)json`이면 backend ProblemDetails code를 그대로 surface): status 404 + (code 없음 | `detail==='Not Found'` | `code==='NET-404'`) → **route-404(fallback)**; 404인데 code가 `RES-/APP-/SEC-/VAL-` → **app-404(fallback 금지)**; 비-404 → false.

## 시험 모양 — FB-01(resource-explorer-dom.test.tsx) 재사용/변경
선례 파일: `apps/web/tests/resource-explorer-dom.test.tsx`(FB-01 연속조회, f5bb37c 계열, 변형을 실제로 잡음).

**그대로 재사용(복사)**:
- 파일 상단 `// @vitest-environment happy-dom`.
- `import React, { act } from 'react'; import { createRoot, Root } from 'react-dom/client';`
- `deferred<T>()` 헬퍼(제어형 promise).
- `beforeEach`(`IS_REACT_ACT_ENVIRONMENT=true`, container 생성, `createRoot`) / `afterEach`(unmount, remove, `vi.restoreAllMocks()`).
- `await act(async () => root.render(...))` 후 `await act(async () => deferred.resolve/reject(...))`로 effect 완료를 기다리는 구조.
- `container.querySelector('[data-testid=...]')` / `container.textContent` 단언 방식.

**반드시 달라져야 하는 부분**:
1. 대상 import: `ResourceExplorer` → `DeveloperStudio`(`../src/features/studio/DeveloperStudio`).
2. mock 대상: FB-01은 named adapter(`fabricControlApi`)를 `vi.spyOn`. FB-03은 **`apiClient`를 mock하되 `isRouteNotFoundError`는 실물 유지**(소스 분기를 뒤집으면 깨져야 하므로). 방법:
   ```ts
   import * as client from '../src/shared/api/client';
   let artifactsCalls = 0;
   vi.spyOn(client, 'apiClient').mockImplementation((endpoint: string) => {
     if (endpoint.endsWith('/result'))    return Promise.reject(ERR);      // 시나리오별 ERR
     if (endpoint.endsWith('/artifacts')) { artifactsCalls++; return Promise.resolve({}); }
     return Promise.resolve({} as any);
   });
   // isRouteNotFoundError는 mock하지 않는다(실물). client.apiClient만 교체.
   ```
3. 렌더 주입: `<DeveloperStudio initialStep={4} initialRunId="run_fb03" ... />` — `initialRunId`가 `activeRunId`를 세팅(L192)해 아티팩트 effect가 mount 시 발화, `initialStep={4}`로 아티팩트 UI가 렌더된다(ResourceExplorer의 `initialTab`/`initialCandidatesState` 주입과 동형). 다른 필수 prop(있다면)은 컴포넌트 시그니처(L22~31) 참조.
4. `/artifacts` 호출 횟수 카운터(`artifactsCalls`)로 "fallback 호출 0/1"을 단언.

## 시나리오별 통과 기준 (무엇이 통과 기준인가 — 핵심)
각 시나리오: `apiClient(.../result)`가 아래 ERR로 reject. 단언은 effect 완료 후.

| # | 시나리오 | mock ERR (result reject) | `/artifacts` 호출 | error-banner | fallback-badge | "Output Verified" |
|---|---|---|---:|:--:|:--:|:--:|
| 1 | 401 | `{problem:{status:401,code:'NET-401',detail:'Unauthorized'}}` | **0** | 있음 | 없음 | 없음 |
| 2 | 403 | `{problem:{status:403,code:'NET-403',detail:'Forbidden'}}` | **0** | 있음 | 없음 | 없음 |
| 3 | 5xx | `{problem:{status:500,code:'NET-500',detail:'Internal'}}` | **0** | 있음 | 없음 | 없음 |
| 4 | malformed JSON | `{problem:{status:500,code:'NET-PARSE',detail:'Failed to parse...'}}` | **0** | 있음 | 없음 | 없음 |
| 5 | network rejection | `new Error('Network request failed')` (problem/status 없음) | **0** | 있음 | 없음 | 없음 |
| 6 | **app-404**(fallback 금지) | `{problem:{status:404,code:'RES-RUN-404',detail:'run not found'}}` | **0** | 있음 | 없음 | 없음 |
| 7 | **route-only 404**(fallback 허용) | `{problem:{status:404,detail:'Not Found'}}` (code 없음) | **1** | 없음 | **있음**("UNVERIFIED") | 없음 |

단언 표현(예): `[data-testid="artifact-error-banner"]` 존재/부재, `[data-testid="artifact-fallback-badge"]` 존재/부재, `expect(artifactsCalls).toBe(0|1)`, `expect(container.textContent).not.toContain('✓ 산출물 검증 완료 (Output Verified)')`, route-404에서 `expect(container.textContent).toContain('UNVERIFIED')`.
**#6이 가장 중요한 판별자다** — 404이지만 app-code라 fallback 금지. 이것이 route-404와 비-404 사이의 경계를 못 박는다.

## 시나리오별 짝지을 변형 (통과하는 검사 ≠ 잡는 검사)
`DeveloperStudio.tsx` L291 `if (isRouteNotFoundError(err))`를 변형:
- **`if (true)`(항상 route-404 취급)** → 시나리오 **1~6이 전부 깨져야 한다**(잘못 `/artifacts`를 호출하고 fallback-badge를 띄우며 error-banner를 안 냄). 특히 **#6(app-404)**가 깨지는지가 핵심 — 오늘 Codex가 `if(true)`로 13건 전부 통과함을 확인했으니, 고친 뒤엔 최소 1~6이 깨져야 진짜다. (#7은 이미 true라 안 깨짐 → #7만으로는 변형을 못 잡는다.)
- **`if (false)`(fallback 제거)** → 시나리오 **7이 깨져야 한다**(route-404인데 fallback-badge/UNVERIFIED가 안 뜸). #1~6은 안 깨짐.
- 두 방향을 함께 두면 분기가 양쪽에서 고정된다. 최소 요구: #6과 #7을 반드시 포함(한쪽은 `if(true)`, 다른 쪽은 `if(false)`로 각각 깨짐).

## 작성 가능성 확인 (Claude가 확인, 구현은 안 함)
- **happy-dom**: `package.json`에 `happy-dom ^20.14.5` 존재. `// @vitest-environment happy-dom`로 파일별 지정(선례와 동일).
- **주입점**: `DeveloperStudio`에 `initialRunId`(L31,70)·`initialStep`(L28,67) prop 있음, L192 effect가 `initialRunId`→`activeRunId` 반영 → mount 시 아티팩트 effect 발화. ResourceExplorer와 동형이라 같은 방식 성립.
- **mock 경계**: `apiClient`만 `vi.spyOn`으로 교체하고 `isRouteNotFoundError`는 실물 유지 가능(같은 모듈의 다른 export). 소스 분기 변형이 시험에 실제로 반영됨.
- **판별 유효성**: client가 backend ProblemDetails code를 surface하므로(client.ts L123) app-404(RES-)와 route-404(code 없음)가 런타임에 실제로 갈린다 — 죽은 분기가 아니라서 시험이 현실을 반영한다.
- **막는 이유 없음**: 선례(resource-explorer-dom.test.tsx)가 그대로 틀이 된다. 추가로 필요한 mock/harness 없음. (만약 `DeveloperStudio`가 `initialStep={4}`+`initialRunId`만으로 아티팩트 섹션을 렌더하지 않는 추가 가드가 있으면 — L1733 이하를 확인 — 그 prop을 더 채우면 된다. 현재 읽기로는 `activeRunId` 세팅으로 충분.)
