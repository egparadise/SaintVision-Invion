- 직전 검토에서 좁힌 `WorkspaceSummaryResponse.status`, `NodeResponse.status`, `ContributionResponse.status/mode`는 이번 위험 후보 재조사에서 제외했다.
- `schemas.py`의 공개 `Literal` 및 제한 패턴, 관련 생성 TypeScript, DB 모델·마이그레이션의 CHECK, 그 값을 받거나 소비하는 서비스/API 경로를 읽었다. 판정은 소스 검토와 아래의 집중 시험으로 한정한다. DB/노드 실측, 브라우저 인수, 값 확장 변형은 하지 않았다.

Discovery credential의 `reason_code`는 API 응답 계약에서 열거형으로 좁혀져 있지 않다. `ProblemDetails.code`도 문자열 계약이며, `DiscoveryGrantRejected`의 내부 audit 사유는 알려진 안전 목록만 보존하고 알 수 없는 값은 동일한 공개 403으로 정규화한다. 공개 오류 응답이 내부 사유를 새 값으로 노출하지 않게 하는 의도된 보안 경계다. 이 경우 “외부 값이면 모두 unknown을 그대로 내보내라”는 규칙은 맞지 않는다.

## 소비자 영향

- 생성된 workspace 타입은 `projectObservation.ts`에서 읽혀 화면 모델로 전달되고 표시된다. workspace 생성은 응답만 소비한다. 조사한 프런트 경로에서는 이 읽기 상태를 저장하거나 같은 상태값으로 다시 보내지 않는다. 상태 변경 API의 입력은 별도 계약이다.
- 생성된 Contribution 타입은 `fabricControlApi.ts`에서 읽기·등록·활성화·철회 응답에 쓰인다. 화면은 `status === 'active'`로 동작 버튼을 선택하고 mode/status를 표시한다. 응답 값을 DB에 다시 쓰는 프런트 경로는 발견하지 못했다.
- Node wire 타입은 `App.tsx`의 `/v1/nodes` 응답에 사용된 뒤 `observedNode`의 화면 투영으로 변환된다. 이 경로에서 중요한 잔여 불일치가 있다. 현재 `observedNode`는 `online/degraded/offline/draining/enrolling/retired`를 인정하고 `lost`를 별도 처리하지만 백엔드의 정상 `active`는 목록에 없다. 따라서 `active`가 `unknown`으로 매핑되고 `valid=false`가 된다. 이는 좁힌 wire 타입이 만든 타입 오류라기보다 앞서 숨겨졌던 wire↔view 어휘 불일치이며 화면 동작 결함이다. Gemini 화면 레인에서 해결/재검증되어야 한다. 본 리뷰에서는 수정하지 않았다.
- 전반적으로 세 응답 상태는 프런트에서 표시·분기에 쓰이고 요청으로 재전송되지는 않는다. 다만 Node의 projection 매핑은 예외적으로 현재 실제 의미에 영향을 준다.

## 규칙 7에 대한 의견

규칙 7의 기본 방향에는 동의한다. 그러나 “참 도메인”과 “외부/확장 값” 예외는 다음 두 경우를 구분해야 한다.

1. **미지값을 의미 손실 없이 보존·전달해도 안전한 opaque code**: 허용 집합이 자주 외부에서 확장되거나 producer가 독립 배포되는 값이면 계약을 열어 두고 원 값을 보존한다. 화면/소비자는 unknown을 성공 또는 알려진 값으로 둔갑시키지 않는다.
2. **미지값을 실행·권한·단위·경로 선택에 사용할 수 없는 control value**: 출처가 Node나 사용자여도 현재 지원 집합은 닫고 명시적으로 거부한다. 새 값은 producer와 consumer의 의미 구현 및 DB 제약을 함께 추가한 뒤 계약에 넣는다.

따라서 “외부에서 온다”만으로 넓히지 말고, **미지값을 받아 보존해도 안전한가**를 판정 기준으로 넣어야 한다. capability kind, placement strategy, OS type은 지금은 두 번째에 해당한다. 반대로 reason/error metadata는 내부 사유와 공개 오류를 분리하고 알 수 없는 사유를 정규화해야 할 수 있어 첫 번째의 단순한 “보존 후 표출” 규칙을 적용하면 안 된다.

또한 DB CHECK는 현재 저장을 허용하는 실효 제약이지 미래 제품 의미가 자동으로 불변이라는 보증이 아니다. 현재 모델 상수·마이그레이션 CHECK·Pydantic 계약·생성 TypeScript가 각자 값을 반복한다. 조사 범위에서 이 네 표현의 집합을 직접 서로 비교하는 공통 parity 시험은 찾지 못했다. 도메인 변경 때는 의도된 의미를 먼저 정하고, 마이그레이션/데이터 전환/모델/계약/생성 타입과 소비자를 한 변경으로 맞춰야 한다. 기존 값을 폐기할 때도 단계 배포나 데이터 전환이 필요할 수 있다.
