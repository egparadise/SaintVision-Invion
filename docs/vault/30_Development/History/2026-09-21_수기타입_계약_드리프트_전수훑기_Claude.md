# 수기 타입 ↔ 계약 드리프트 전수 훑기

run-logs·run-attempts 둘 다 드리프트가 나와, 개별 결속과 별개로 한 번에 훑었다. **스크립트 출력은 리드이지 사실이 아니다** — 아래는 실제 TS·스키마로 재확인한 결과다(초록≠도달과 같은 층).

## 훑은 범위 (명시 — "없음"이 무엇에 대한 없음인지)
- 고정 SHA `d416fe5`. 대상: `apps/web/src/contracts/types.ts`의 `export interface` **48개** 중 `contracts/v1alpha1/core.schema.json`의 `$def`와 **동명인 11개**를 필드 전수 대조.
- 대조 11개: ApprovalPage, ApprovalView, NodeStopReceipt, ProblemDetails, RunArtifactList, RunAttemptList, RunLogView, RunResultView, ShardObservation, ShardObservedMember, ShardResultMember.
- 분류 4갈래: **(a)** const 무력화(`| string`) · **(b)** required→optional · **(c)** 필드누락 · **(d)** nullability 좁힘(계약 null허용인데 타입 non-null).
- **알려진 사각(blind spot)**: 동명 대조만 함. **이름이 다른 대응**은 놓친다 — 실증 사례: 계약 `RunAttemptObservation` ↔ 프런트 `RunAttemptItem`(run-attempts 문서에서 수동 대조함). 완전 훑기는 이름 매핑 필요.

## 검증된 드리프트 지도 (소비 여부 = 위험도)
| 타입 | 소비 | 결속 | 드리프트(검증됨) |
|---|---|---|---|
| **RunResultView** | O (RunDetail·DeveloperStudio) | 됨(Claude) | (a) source · (b)+(d) commandId·nodeId·stopReceipt·evidence·output(전부 계약 required+nullable, TS는 optional+non-null) 등 — 다수 |
| **ProblemDetails** | O (client.ts 에러경로·ErrorState·NodeList·mlopsEngine) | **안 됨** | (b)+(d) causeRef·evidenceId(계약 required+nullable, TS optional+non-null) |
| **RunArtifactList** | O (DeveloperStudio) | 됨(Claude) | (a) source · (b) absentReason |
| **RunLogView** | O (runLogObservation.ts — Gemini가 이번 세션에 배선) | 됨(Claude) | (a) source · (b) truncated·absentReason |
| **RunAttemptList** | X (0 소비, 잠복) | 됨(Claude) | (a) source · (b) nextCursor · [item] (d) startedAt·nodeId |
| ApprovalPage/ApprovalView/ShardObservation/ShardObservedMember/ShardResultMember | — | — | **드리프트 없음**(동명 필드 전수 대조 기준) |

### 오탐 제외 — 이름 충돌 (드리프트 아님)
- **NodeStopReceipt**: 스크립트가 "11 필드누락"으로 최대 발견처럼 보였으나 **오탐**. TS `NodeStopReceipt`(receiptId·physicallyStopped·resourceReclaimed·verified·supervisorLabel — UI 투영)와 스키마 `$def`(claimId·recoveryEpoch·planDigest·containerId·allocations — 내부 wire)는 **다른 개념·다른 shape로 이름만 같다**. → 드리프트로 세지 않음. 다만 **이름 충돌 자체가 위험**(둘을 같은 것으로 오인 가능) — 별도 관찰로 남김.

## 소비×드리프트 우선순위 (내 이전 직감 정정)
- 소비O·드리프트 = 즉시 위험. 그러나 RunResultView/RunArtifactList/RunLogView는 **이미 계약 결속됨** → 남은 것은 **Gemini의 TS 수기타입 정합**뿐(프런트 owner). 특히 (d)(계약 null인데 타입 non-null)는 실제 null 응답에 프런트가 깨지므로 최우선 정합 대상.
- **ProblemDetails만 미결속+소비O+드리프트.** 단 **백엔드가 ProblemDetails로 self-validate 하지 않는다**(`_checked`/`validate_contract("ProblemDetails")` 부재) → 결속해도 백엔드 앵커가 없어 run-result류(커널이 `_checked`로 자기 응답 검증)보다 결속 가치가 약하다. 결속하려면 **백엔드 에러경로에 계약 검증을 추가**하는 편이 함께 필요(에러/동시성 경로 = Codex 계약 대상 가능성).

## 근본 원인·권고 (핵심)
드리프트는 우연이 아니라 **구조적**이다 — 수기 타입은 계약과 따로 관리되어 시간이 지나면 갈라진다. 개별 정합은 두더지잡기다.
- **권고**: `types.ts`의 커널 응답 인터페이스를 **손으로 쓰지 말고 생성 타입(`packages/contracts-ts`) re-export로 대체**한다. Codex가 ApprovalPage/ControlRunPage에 이미 이 방식을 씀(`apps/web/src/contracts/kernel-observation.ts`). 이러면 (a)(b)(c)(d) 드리프트 클래스가 근원에서 사라진다.
- 그전까지 개별 결속마다 프런트 Ajv 시험 + 공유 fixture로 방어(내가 run-result/logs/attempts에 한 것).

## 인계
- **Gemini(프런트)**: 소비O 타입의 TS 정합 — RunResultView(다수, 특히 (d)), RunLogView, RunArtifactList. 생성 타입 re-export로의 전환 검토. 각 정합은 고치기 전 통과/고친 뒤 실패 실증.
- **다음(Claude/판단 대기)**: ProblemDetails 결속은 백엔드 에러경로 계약 검증 동반 필요 → 그 변경 owner(Codex?) 확인 후 진행. 앵커 없는 fixture-only 결속만이면 가치 낮음.
- 공유 진행판 담당 기록은 Gemini 편집 중(dirty)이라 미기입.
