## 3. (3) sampler가 blocking chain을 정확히 재구성하는가 — 코드 정독 + 교정

- 코드: 표본마다 `pid,state,wait_event_type,wait_event,pg_blocking_pids(pid),statement_class(position 기반, parameter 미보존),query_age_ms`를 `datname=current_database() AND usename=current_user AND state<>'idle'`로 읽고, `_chain_depth`는 blockers 그래프에서 DFS(순환 방지 `seen`)로 1+max. PID는 `backend-N`으로 치환, SQL 원문 미보존, observer 실패는 type만 — 설계대로. 단, 그래프는 **표본에 포함된 pid만** 노드로 갖는다(holder가 'idle in transaction'이면 `state<>'idle'`에 포함되므로 정상; 다른 role/DB의 blocker는 depth 0으로 끊김 — 이 벤치에서는 해당 없음).
- **교정(커널 무관, disposable DB)**: 알려진 chain H(row 보유)→A→B→C(80ms 간격 도착, `lock_timeout` 5s)에 같은 query를 적용: **A `Lock:transactionid` blockers [H] depth 1 · B `Lock:tuple` [A] depth 2 · C `Lock:tuple` [A,B] depth 3** — `FOR NO KEY UPDATE`·`FOR UPDATE` 두 모드 동일. sampler query와 depth 계산은 tuple-lock FIFO chain을 **정확히** 재구성한다. ✔
- 따라서 Codex wave의 "depth 1·Lock waiter 19"는 sampler 한계가 아니라 **실제 signature**다. 내 50동시 실행(구조만 인용)도 같았다: Lock waiter 표본 **3931건 전부 `Lock:transactionid`, blocker 정확히 1, depth 1**, `Lock:tuple` **0건**, max Lock waiter 49. 즉 legacy waiter들은 tuple-lock 큐에 서지 않고 **전원이 holder의 transactionid를 직접** 기다린다.

## 4. 반례·F-S05-02 근원 가설 (probe 증거, 사실 승격 아님)

**질문**: 왜 legacy는 tuple FIFO가 없고(depth 1), candidate는 카드 20 probe처럼 FIFO 누적으로 55P03이 나는가?

**가설(코드 근거)**: legacy `reserve`는 projects 잠금(`FOR NO KEY UPDATE`, placement.py:132) **전에** `approvals._ledger`가 `INSERT INTO inv.idempotency(...)`(approvals.py:86)를 실행하고, `inv.idempotency`는 `FOREIGN KEY (tenant_id, project_id) REFERENCES inv.projects`(0001_core.sql:71)다. RI 검사는 부모 행에 **`FOR KEY SHARE`** 를 건다. 같은 transaction이 이미 그 행의 약한 잠금을 쥔 상태에서 `FOR NO KEY UPDATE`를 요청하면 PostgreSQL `heap_lock_tuple`은 tuple lock(FIFO 순서 확보용)을 **건너뛰고** xmax transaction을 직접 기다린다. 그러면 (a) 모든 waiter가 `transactionid` depth 1, (b) holder가 commit할 때마다 **전원이 깨어 재경쟁**하고 새 대기는 새 구간이라 `lock_timeout` 500ms가 **재시작**, (c) 순서는 FIFO가 아니라 재경쟁 순(불공정·기아 가능)이며 지는 쪽은 `statement_timeout` 2초에 **57014**로 죽는다. candidate의 `project_resource_limits FOR UPDATE`는 그 행을 참조하는 FK가 없고(grep 0) 선행 약한 잠금이 없어 tuple FIFO → 앞선 hold 누적 → ~504ms에 55P03.

**probe(커널 무관, disposable DB `inv_probe_claude_fk`, 부모 `projects`+자식 `child(project_id FK)`, H 400ms 보유·A/B/C 80ms 간격 도착·각 400ms 보유·`lock_timeout` 500ms)**:

| 조건 | 결과 | signature |
|---|---|---|
| 선행 약한 잠금 **없음** → `FOR NO KEY UPDATE` | A acquired 388ms, B 711ms, **C 55P03 504ms** | A transactionid d1, B tuple d2, C tuple d3 (FIFO 누적 = 카드 20 재현) |
| 자식 INSERT(FK KEY SHARE) **후** `FOR NO KEY UPDATE` | **B 239ms, C 613ms, A 1112ms 전원 acquired, 55P03 0** | A·B·C **전부 transactionid, blockers [H], depth 1** (= Codex wave·내 wave signature) |

두 번째 행은 (a)(b)(c)를 모두 보인다: 1112ms를 기다린 A가 500ms에 죽지 않았고(구간 재시작), 도착 순서(A→B→C)와 획득 순서(B→C→A)가 다르며(재경쟁), sampler signature가 실제 legacy wave와 동일하다. 이 가설은 **legacy 55P03 0·57014 2s 와 candidate 55P03 FIFO 누적을 한꺼번에 설명**한다. 카드 13 조건 1의 "57014 statement"도 이 그림에서는 projects 잠금 statement의 재경쟁 패자(내 50동시 실행: 57014 27건 전부 `projects FOR NO KEY UPDATE`, 대기 p50 2009.6ms — 구조 인용)다.

**아직 사실이 아니다** — 제품 커널에서 직접 확인한 것은 (i) FK와 INSERT 순서(정적), (ii) wave signature(동적)뿐이고, "KEY SHARE 때문"이라는 인과는 커널 무관 probe에서만 보였다. **확인 시험**(다음 카드, 별도 승인): ① 20동시 legacy에서 `log_lock_waits=on` + `deadlock_timeout` 단축(예: 50ms) — 각 waiter의 log에 "waiting for ShareLock on transaction X … acquired after N ms"가 **holder마다 다른 X로 반복**되고 "ExclusiveLock on tuple" 줄이 **없으면** 가설 확인; ② 같은 wave에서 `pgrowlocks('inv.projects')` 1회 스냅샷 — 행 lock modes에 `Key Share`(다수)+`No Key Update`(1) 멀티잭트가 보이면 원인 확인; ③ 제품 수준 반증: candidate가 limits 행에 선행 약한 잠금을 쥐는 변형(§5 제안)에서 signature가 depth 1로 바뀌고 55P03이 사라지는지.

## 5. (4) 후속 제안 평가·검토자 제안

- **`log_lock_waits=on` 재실행 카드는 가설 검증에 충분**하다(위 ①): 대기 구간마다 로그가 남으므로 "구간별 재시작"을 직접 보고, tuple lock 대기 유무로 FIFO 우회를 판별한다. 조건: `deadlock_timeout`을 hold(~50~150ms)보다 짧게, log line은 pid·xid만(비밀 없음), 20동시 1회.
- **`pg_locks` 스냅샷은 불충분**: 행 잠금은 xmax에 있어 `pg_locks`에는 대기 중인 `tuple` locktype만 나타난다(legacy는 그것도 없음). 원인(약한 잠금 보유)을 보려면 contrib **`pgrowlocks`**(②)가 맞다. 필요 여부: ①만으로 "재시작" 확인은 되지만 "왜"는 ②가 필요 — 둘 다 같은 wave에서 1회.
- **candidate 대기 정책 제안(Codex 카드 20용, 검토자 의견)**: migration 없이 candidate final commit에서 limits 행에 **선행 약한 잠금**을 쥐어 legacy와 같은 큐 의미(구간별 `lock_timeout` 재시작)를 얻는 변형. 주의 3가지 — (1) 현재 `FOR UPDATE`는 `KEY SHARE`와 **충돌**하므로 그대로 두면 두 transaction이 서로의 KEY SHARE를 기다리는 **교착**이 난다; limits 행의 key 열을 갱신하지 않는다면 `FOR NO KEY UPDATE`로 바꿔야 하며(legacy가 그렇게 안전한 이유), 그 변경의 잠금 순서·`_reserve_prepared_locked` 영향은 Codex 검토 대상; (2) 순서가 FIFO가 아니게 되어 **기아**가 생기고 패자는 2초 57014로 실패한다 — fail-fast 목표(빠른 503)와 상충하므로 목표 함수를 먼저 정해야 함; (3) 20개가 commit마다 전원 깨는 thundering herd. 대안은 큐 깊이 상한(admission)으로, 이는 FIFO를 유지한다. 어느 쪽이든 §4 확인 시험 ①②가 선행.
