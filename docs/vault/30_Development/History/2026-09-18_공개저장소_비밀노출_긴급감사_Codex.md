# 공개 저장소 비밀 노출 긴급 감사

## 감사 범위와 방법

공개 전환 후 현재 worktree와 reachable Git history를 대상으로 확인했다. `git rev-list --all` 기준 779개 commit, tracked path inventory, 알려진 secret shape(private-key/JWT/GitHub token/AWS key/DSN/password/API key), `.env*`·key·credential 경로, `docs/vault/30_Development/Evidence`의 JSON/XML을 검사했다. 비밀값 자체는 출력·복사하지 않고 경로·commit·값 길이·짧은 해시만 사용했다. 임의 고엔트로피 문자열처럼 이름과 형식이 없는 비밀은 정적 패턴 감사로 부재를 증명할 수 없다는 한계가 있다.

## 확인된 노출

### 1. 공개 개발 TLS 개인키

- `deploy/certs/saintvision.key`: 현재 1,679바이트 RSA private key, 공개 raw URL에서 익명 HTTP 200이라는 사용자 실측.
- 사용자가 운영은 별도 인증서이고 이 키는 개발 전용이라고 확인했다. 운영 TLS 키로 분류하지 않고 P2 개발환경 finding으로 재평가했다.
- 상세: [[2026-09-18_커밋된_TLS_개인키_보안_finding_Codex]].

### 2. Git 과거 이력의 기본 DB/MinIO 자격증명 후보

초기 production compose commit `fbe8feb`에서 다음 값 형태가 확인됐다.

- `docker-compose.prod.yml`: `INV_DATABASE_URL`에 비소유자 DB DSN 자격증명, `POSTGRES_PASSWORD` 기본값, `MINIO_ROOT_PASSWORD` 기본값.
- 이후 `510ced4` 계열에서 `${VAR:?}` 외부 주입으로 바뀌었지만 공개 Git history에는 과거 blob이 남아 있다.
- 현재 값의 유효성이나 실제 운영 사용 여부는 확인하지 않았다. 사용 이력이 있으면 회전 대상이다.

### 3. 공개 Evidence proposal 텍스트의 평문 DSN

현재 tracked `docs/vault/30_Development/Evidence/obsidian-proposals-*`는 22개이고, 그중 사용자가 독립 확인한 14개 `proposal-3.txt`에 `inv_app` DSN과 비밀번호가 평문으로 반복된다. 공개 raw URL 익명 요청에서 표본 HTTP 200도 확인됐다. business-workspace, configured-server, db-test-role, retained-backup, approval-review, frontend-fix, live-project, migration-guard, shard-observation, approval-browser, studio-auth, studio-tls proposal에 해당 패턴이 나타난다. 실제 DB가 살아 있는지·폐기됐는지는 사용자 확인 대기다.

이 파일들은 자동 생성되는 제품 Evidence가 아니다. 각 디렉터리의 `manifest.json`이 외부 Obsidian 파일의 proposal snapshot과 SHA를 보존하고, Git history의 `docs: preserve...proposal` 커밋들이 수신 원문을 수동 보존했다. `tools/sync_obsidian.py`는 `docs/vault`의 모든 파일을 내보내므로 이런 snapshot을 계속 추가하면 다시 tracked/public 상태가 될 수 있다. 앞으로는 외부 proposal을 저장하기 전에 비밀값을 마스킹하거나, 민감 원문은 저장소 밖에 두고 manifest와 해시만 보존해야 한다.

## 확인되지 않은 항목

- 현재 tracked `.env` 실파일은 없고 `.env.example`만 있다.
- 현재 Evidence JSON/XML에서 실제 DSN·Bearer JWT·API key 패턴은 발견하지 못했다. 합성 테스트의 `synthetic-*`, `test-only`, 예시 JWT/private-key 문자열은 실행 문맥상 실제 자격증명으로 분류하지 않았다.
- 사용자가 제공한 disposable PG DSN은 증거 문서에 기록하지 않은 것으로 확인된다.
- 운영용 TLS 인증서·키, GitHub token, AWS access key는 알려진 패턴 검사에서 추가 발견하지 못했다. 이는 비밀값 부재의 절대 증명이 아니다.

## 즉시 완화와 사용자 결정

### 항목별 순서

1. **개발 TLS 키**: (a) 개발 신뢰 저장소와 사용처를 확인하고 새 개발 인증서를 발급한다. (b) 외부 주입으로 전환한 뒤 preflight에서 인증서·키가 `Test-Path -PathType Leaf`이고 서로 일치하는지 확인한다. (c) Compose는 short bind 대신 `create_host_path: false`를 사용하는 long syntax로 바꾼다. (d) 생성 실패 시 `generate_tls_cert`가 빈 디렉터리와 부분 파일을 정리하도록 한다. (e) 새 경로를 검증한 뒤 기존 키를 폐기한다. 새 인증서 발급·배포는 되돌릴 수 있지만 폐기한 키의 신뢰 회복은 되돌릴 수 없다. 인증서 없는 상태에서 Compose가 빈 host directory를 만드는 현재 함정은 이 순서로 차단한다.
2. **과거 DB/MinIO 자격증명**: (a) 값이 실제 운영·개발 어디에 사용됐는지 확인한다. (b) 사용 이력이 있으면 DB role/password와 MinIO root credential을 폐기·교체한다. (c) Compose 환경변수와 secret provider를 새 값으로 갱신하고 연결·복구를 확인한다. (d) 공개 이력 재작성 여부를 별도로 결정한다. 회전 전후 배포 전환은 되돌릴 수 있으나 폐기한 자격증명은 복구하지 않는다.
3. **proposal DSN 14개**: (a) 먼저 해당 DB role의 유효성과 접근 로그를 확인하고 유효하면 즉시 회전한다. (b) 사용자가 승인한 뒤 proposal snapshot의 평문을 마스킹한 대체 문서를 만들고 원문은 저장소 밖에 보관한다. (c) 이후 Obsidian 수신·export 전에 secret scan을 통과시키고 manifest에는 경로·해시만 남긴다. 공개 이력 재작성은 선택사항이며, 파일을 현재 tip에서만 지워도 과거 공개 blob은 남는다.

**즉시 준비 가능하지만 구현·삭제는 별도 승인:** `deploy/certs` 외부 주입과 `.gitignore`, preflight의 파일·키 일치 검사, 빈 디렉터리 정리, proposal DSN 마스킹·secret scan 설계를 준비할 수 있다.

**사용자 결정 필요:** 공개 상태 유지/비공개 전환, 개발 키와 과거 DB·MinIO 자격증명 회전, 공개 Git history 재작성, 외부 secret provider 선택. 저장소를 비공개로 되돌려도 이미 공개된 값의 취득 가능성은 소급해 없어지지 않지만, 추가 익명 접근과 검색 노출은 줄인다.

forks가 0이고 공개 시간이 짧다는 점은 추가 복제·검색 노출 가능성을 낮추는 정황이지만, raw URL 200으로 이미 익명 취득이 가능했던 사실을 취소하지 않는다. 위험 감소 효과는 정량화할 수 없으며, 비공개 전환은 완화이지 회전·마스킹을 대신하지 않는다.

키 삭제, 이력 재작성, credential rotation, 저장소 visibility 변경은 이 감사에서 수행하지 않았다.
