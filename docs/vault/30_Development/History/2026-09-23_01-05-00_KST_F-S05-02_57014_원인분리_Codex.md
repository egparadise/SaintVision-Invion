# F-S05-02 57014와 project row lock timeout 원인 분리

## 결론

20동시 legacy 측정의 `57014 QueryCanceled`가 `SELECT project_id FROM inv.projects … FOR NO KEY UPDATE`에서 보고됐다는 사실만으로 project row **Lock 대기**라고 결론 내릴 수 없다. 동일 `Database.transaction`에서 `lock_timeout=500ms`와 `statement_timeout=2s`가 실제 적용됐고, 의도적으로 project row를 보유한 조건에서는 `wait_event_type=Lock`을 거쳐 **557.919ms에 `55P03 LockNotAvailable`**이 먼저 발생했다. 반대로 비-Lock 서버 대기 `pg_sleep(2.5)`는 `wait_event_type=Timeout`에서 **2,092.747ms에 `57014 QueryCanceled`**가 났다.

따라서 과거 20동시의 57014는 단순 project row heavyweight-lock 대기가 아니다. 해당 실행은 `pg_stat_activity.wait_event`를 수집하지 않았으므로 query 실행·CPU 포화·다른 종류의 서버 대기 중 무엇이었는지는 **미확정**으로 남긴다. 수정은 별도 카드이며 이 조사에서는 커널·계약 코드를 바꾸지 않는다.

## 1. transaction 설정·role·session 실측

`services/control-plane/src/inv/db.py`의 실제 순서는 다음과 같다.

1. 매 `Database.transaction`마다 새 `psycopg.connect`를 연다. connection pool 재사용은 없다.
2. `READ COMMITTED` 설정과 runtime role의 non-owner/non-superuser/RLS-bypass 부재를 검사한다.
3. transaction-local `inv.tenant_id`를 설정한다.
4. `SET LOCAL lock_timeout='500ms'`, 이어 `SET LOCAL statement_timeout='2s'`를 실행한다.
5. recovery epoch와 tenant containment gate를 확인한 뒤 service 본문에 connection을 넘긴다.

disposable DB의 난수 `inv_app_*` login에서 같은 connection으로 `SHOW` 상당의 `current_setting`을 읽은 결과는 `500ms`와 `2s`였다. `current_user == session_user`였고 tenant GUC도 해당 시험 tenant와 일치했다. `PlacementStore.reserve`의 early-grant와 mutation은 서로 다른 새 transaction이므로 둘 다 이 설정 순서를 다시 거친다. `BoundDatabase`의 nested transaction은 별도 session을 열지 않지만, 이미 설정된 outer transaction만 공유한다.

## 2. 실 PG 소규모 분리 측정

환경은 PostgreSQL 16 dev container의 **일회용 DB·시험별 난수 login role**이다. 다른 Codex 20동시 레인이 없음을 status에서 확인했고, Gemini 브라우저 레인과의 간섭을 줄이기 위해 holder 1 + waiter 1만 사용했다.

| 조건 | `pg_stat_activity` 관측 | 결과 | 해석 |
|---|---|---|---|
| owner가 project row를 `FOR UPDATE`로 보유, runtime이 같은 row를 `FOR NO KEY UPDATE` | `state=active`, `wait_event_type=Lock`, `wait_event=transactionid` | 557.919ms, `55P03`, `LockNotAvailable` → `RES-0007` / 503 / retryable | 500ms lock timeout이 2초 statement timeout보다 먼저 발동 |
| runtime transaction 안에서 `SELECT pg_sleep(2.5)` | `state=active`, `wait_event_type=Timeout`, `wait_event=PgSleep` | 2,092.747ms, `57014`, `QueryCanceled` → `RES-0007` / 503 / retryable | heavyweight Lock이 아닌 서버 실행/대기는 statement timeout이 발동 |

명령은 `PYTHONPATH=src;services/control-plane/src`, `PYTHONUTF8=1`, `.env`의 `INV_TEST_ADMIN_DSN`을 사용해 임시 진단 단일 파일을 `pytest -q -s`로 실행했다. 결과는 **2 passed / 0 failed / 0 skipped / exit 0 / 18.33s**였고 진단 파일은 측정 뒤 삭제했다. 구조화 결과는 [[f-s05-02-timeout-diagnostic-a1470435.json]]에 비밀·DSN·role password 없이 보존한다.

기존 `tests/integration/test_placement.py::test_project_lock_timeout_is_retryable_res_0007_problem`의 1.2초 보유 → `55P03` 결과와도 일치한다. 차이는 주입 시험은 **알려진 단일 row Lock**을 500ms 넘게 보유하지만, 과거 20동시는 20개 새 session의 연결·early grant·mutation 전체가 경합했고 오류 순간의 wait-event를 수집하지 않았다는 점이다.

## 3. F-S05-02 판정

- **배제:** `SET LOCAL` 미적용, 잘못된 runtime role, session pool에서 timeout 초기화 누락, project row Lock이 2초까지 기다렸다는 설명.
- **확정:** project row heavyweight-lock 대기는 `55P03`; Lock 외 서버 실행/대기는 `57014`; 둘 다 현재 공개 표면 `RES-0007` / HTTP 503 / `retryable=true`로 정규화된다.
- **미확정:** 과거 20동시 3건의 정확한 `wait_event`와 2초를 소비한 executor 단계. 당시 statement label은 cancellation 시 실행 중 statement를 가리킬 뿐 wait 이유를 증명하지 않는다.
- **다음 첫 행동:** legacy와 candidate의 20동시 비교 카드에서 backend PID별 `query_id`·`state`·`wait_event_type/event`를 주기 샘플링하고, 허용 가능한 서버측 계측으로 장기 statement를 특정한다. lock hold p95와 `55P03+57014` 합계 감소를 함께 판정한다.

## 4. 계약 표면 영향

이번 조사로 JSON Schema·generated type·fixture·HTTP route 변경은 없다. `LockNotAvailable(55P03)`와 `QueryCanceled(57014)`는 이미 동일 `ProblemDetails`인 `RES-0007`, status 503, `retryable=true`로 매핑된다. 두 원인을 외부 code로 분리하거나 `Retry-After` 같은 새 wire 의미를 추가하려면 별도 계약 결정과 fixture/anchor 갱신이 필요하다. 옵션 1 구현은 승인 전까지 현재 공개 오류 표면을 유지한다.
