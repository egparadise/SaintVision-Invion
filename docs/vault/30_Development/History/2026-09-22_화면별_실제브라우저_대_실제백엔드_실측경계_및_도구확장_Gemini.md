# 화면별 실제 브라우저(Chrome 153) 대 실제 백엔드(Uvicorn) 실측 경계 및 검속 도구 확장 가이드

## 1. 개요 및 목적

오늘 밤 Gemini 레인에서는 jsdom 가상 환경의 한계(CSS 붕괴 미감지, WebCrypto 생략, 네이티브 I/O 부재 등)를 벗겨내고 **실제 Google Chrome 153 (공식 빌드, Blink 엔진)** 브라우저 실측을 도입했으며, 더 나아가 모의 네트워크 계층을 걷어내고 **실제 Uvicorn 0.52.4 ASGI 서버**와 연결하는 종단간 실측까지 진입했다.

그러나 **"실제 브라우저에서 보았다"는 사실이 "실제 백엔드와 데이터베이스까지 전부 연결되어 검증되었다"는 뜻은 아니다.**
화면마다 대역을 벗겨낸 깊이가 다르며, 대부분의 화면은 실제 Chrome 브라우저에서 렌더링되었으나 네트워크 응답은 정본 스키마 기반의 모의(Mock) 응답으로 채워졌다.

다음 작업자가 "실제 브라우저 검증 완료"라는 단편적 문구만 보고 시스템 전체가 단단하다고 착각하는 병(초록의 착각)을 원천 차단하기 위해, **어디가 단단한 실제이고 어디가 아직 모의에 머물러 있는 무른 층인지** 그 경계를 정직하게 기록한다.

## 3. 정식 검속 도구 (`tools/run_real_browser_acceptance.py`) 확장된 역량

현재 승격된 CLI 검속 도구는 가장 깊은 층(실제 백엔드 wire ↔ 실제 브라우저)까지 검증하도록 확장되어 있다.

### 3.1 현재 검속 범위 (총 6대 시나리오)
- **검증 대상 1: 산출물 다운로드 및 WebCrypto 전송 무결성 (`DeveloperStudio.tsx`)**
  - 구동 환경: `uvicorn 0.52.4` (포트 8080) ↔ `Vite` (포트 3005) ↔ `Google Chrome 153`.
  - 시나리오:
    1. `--scenario verified`: 정상 wire 헤더 일치 ➔ Chrome 다운로드 성공 (50B 저장) ➔ `[전송 확인 완료]` 배너 표출.
    2. `--scenario mismatch`: 바이트 변조 주입 ➔ Chrome 다운로드 0건 차단 ➔ `[전송 불일치 · 저장 차단]` 배너 표출.
    3. `--scenario missing-header`: `X-Content-SHA256` 헤더 제거 ➔ 다운그레이드 방지 차단 ➔ `[전송 헤더 누락 · 저장 차단]` 배너 표출.
- **검증 대상 2: 불변 증거 뷰어 3대 상태 및 실행 상세 왕복 네비게이션 (`RunDetail.tsx` ➔ `EvidenceViewer.tsx`)**
  - 구동 환경: `uvicorn 0.52.4` ↔ `Vite` ↔ `Google Chrome 153`.
  - 시나리오:
    4. `--scenario evidence-verified`: 정상 커밋 실행 ➔ 타임라인 렌더링 ➔ `🔍 불변 증거 열람` 클릭 ➔ `EvidenceViewer` 진입 ➔ `✓ 출력 무결성 검증 통과 (PASS)` 뱃지 및 `[시스템 정책 사양]` 배너 단언 ➔ `← 이전으로 돌아가기` 복귀 실측 (`real_chrome_evidence_verified_pass.png`).
    5. `--scenario evidence-unverified`: 산출물 미커밋 실행(`outputAbsentReason` 부여) ➔ `⚠️ 출력 무결성 미검증 (UNVERIFIED)` 호박색 뱃지 및 명확한 사유/권장조치 배너 단언 실측 (`real_chrome_evidence_unverified_notice.png`).
    6. `--scenario evidence-failed`: 무결성 실패 실행(`verified === false`) ➔ `✗ 출력 무결성 검증 실패 (FAIL)` 적색 뱃지 단언 실측 (`real_chrome_evidence_failed.png`).

## 4. 새 화면을 검속 도구에 편입하기 위한 확장 가이드

다음 작업자가 `NodeList`, `WorkspaceList`, `ApprovalCenter`, `EvidenceViewer` 등을 이 도구에 붙여 **"실제 백엔드 ↔ 실제 브라우저"**로 승격시키고자 할 때 수행해야 하는 구체적 절차:

### 단계 1: Uvicorn 테스트 서버에 라우트 마운트
`tools/run_real_browser_acceptance.py` 내부의 `create_test_app()` 함수에 대상 화면이 호출하는 백엔드 API를 마운트한다:
```python
# 예: 노드 인벤토리 확장의 경우
@app.get("/v1/nodes")
async def get_nodes():
    # 정본 NodeResponse 계약에 맞춘 DB 조회 또는 fixture 반환
    return {
        "items": [
            {"nodeId": "nod_01", "hostname": "worker-01", "status": "active", ...}
        ]
    }
```

### 단계 2: Playwright 브라우저 시나리오 핸들러 추가
도구에 신규 시나리오 플래그(예: `--scenario nodes` 또는 `--scenario evidence`)를 추가하고, 실제 Chrome 페이지에서 해당 탭을 클릭하여 요소를 단언하는 로직을 작성한다:
```python
def verify_node_inventory(page):
    # 1. 탭 네비게이션
    page.click("button:has-text('Nodes 인벤토리')")
    # 2. 필수 계약 요소 단언 (가짜 초록 방지)
    badge = page.wait_for_selector("[data-testid='node-status-badge-nod_01']")
    assert "ACTIVE" in badge.inner_text()
    # 3. 안전한 스크린샷 증거 캡처 (scratch/에 보존)
    page.screenshot(path="scratch/real_chrome_nodes_acceptance.png")
```

### 단계 3: 돌연변이 사살(Mutation Killing) 실증
도구가 초록인데 아무것도 지키지 않는 "거짓 통과"가 되지 않도록, 의도적으로 백엔드 상태를 깨뜨렸을 때 도구가 `exit code 1`로 즉시 사살하는지 실측한다.

## 5. 결론 및 원칙

1. **실제 브라우저(Blink)와 실제 백엔드(Wire)는 별개의 검증 층이다.**
2. 화면 렌더링을 실측했다고 해서 백엔드 계약까지 실제 연결된 것으로 과장하지 않는다.
3. 현재 SaintVision-Invion 프런트엔드에서 두 층이 모두 실제 서버 소켓과 브라우저 네이티브 I/O로 완결된 곳은 **산출물 다운로드(GM-01/VF-GM-01)** 영역이며, 나머지 화면들은 실제 Chrome 렌더링에 모의 계약 응답이 결합된 상태이다.
4. 다음 작업자는 위 매트릭스의 '무른 층'부터 차례대로 실제 Uvicorn 라우트에 결속해 나가야 한다.
