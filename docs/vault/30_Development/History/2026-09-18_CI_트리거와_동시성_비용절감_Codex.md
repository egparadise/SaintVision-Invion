# CI 트리거와 동시성 비용 절감

## 변경

다섯 workflow(`backend.yml`, `core.yml`, `desktop-browser.yml`, `docs.yml`, `frontend.yml`)의 `push`를 `main`과 `integration/all-agents-unified`로 제한했다. `pull_request` 트리거와 frontend의 기존 `paths` 필터는 유지했다.

각 workflow에 다음 동시성 정책을 추가했다.

```yaml
concurrency:
  group: ${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: ${{ github.ref_name != 'main' }}
```

같은 workflow/ref의 이전 실행은 새 push가 오면 취소한다. `main`은 취소하지 않아 최종 검증 결과를 보존한다. PR은 PR ref별로 묶이며 새 커밋이 이전 PR 실행을 대체한다.

## 검증 범위와 트레이드오프

실행 빈도만 줄였고 각 workflow가 실행될 때 검사하는 단계·서비스·artifact 계약은 변경하지 않았다. 개인 브랜치 push의 즉시 CI 피드백은 사라지고 PR 생성·갱신 시점으로 이동한다. 개인 브랜치에서 별도 실행이 필요하면 명시적 PR 또는 수동 workflow 설계를 추가해야 한다.

## 비용 원인에 대한 한정

GitHub 무료 비공개 저장소의 2,000분 한도 소진이 현재 CI 차단의 원인이라는 것은 사용자가 Billing에서 아직 확인하지 못한 **정황 추정**이다. `gh` 인증 부재로 실제 사용량·잔여분·지출 한도는 조회하지 못했다. 지출 한도 0, 저장소/조직 정책, 다른 runner 제한도 가능한 원인이다. 이번 변경은 원인이 무엇이든 중복·불필요 실행을 줄인다.

## 검증 기록

GitHub Actions는 실제 실행하지 않았다. 다섯 YAML의 trigger branch, frontend `paths`, workflow별 concurrency와 main 예외를 정적 구조로 확인한다. CI 실행 복구 후 main과 integration의 push, PR 갱신, 연속 push 취소 동작을 한 번씩 확인해야 한다.

## Agent 작업 흐름 영향

기존 운영 절차의 `push → CI build → report`는 유지하되, 개인 Agent branch push에는 더 이상 자동 CI run이 생기지 않는다. 개인 branch의 CI 증거가 필요한 작업은 PR을 열거나 갱신해 PR workflow의 동일 SHA run ID·상태·artifact를 인계해야 한다. main과 integration push는 계속 자동 실행되며, CI 결과를 기다리는 기존 절차의 의미는 바뀌지 않고 실행 시점만 PR로 이동한다. 개인 push만으로 CI가 성공했다고 기록하는 절차는 문서에서 확인되지 않았다.
