# 서빙 앵커 감사 — "형식만 갖춘 결속" 색출

계약 결속을 많이 했으니, 그중 **fixture·시험은 통과하나 백엔드 서빙 경로가 실제로 계약을 검증하지 않는 것**(앵커 없는 결속=형식만)이 섞이면 잘못된 안전감을 준다. 묶인 응답 전부의 서빙 경로가 실제로 검증을 부르는지 감사한다.

## 범위·방법 (명시)
- 고정 SHA `6c6ad4d`. 대상: `contracts/fixtures/*.json` **28개** 전부(요청형 terminal-ticket-input 제외).
- 두 앵커 기제: **커널** = 서빙 코드가 명시적 `validate_contract("X", result)`/`_checked("X", result)` 호출(수동, **빠뜨릴 수 있음** — ShardObservation이 실제로 빠졌었음). **saintvision** = FastAPI `response_model=schemas.X`(+ 모델 구성/`model_validate`) — 프레임워크가 매 응답 자동 검증(구조적으로 견고, 조용히 사라지기 어려움).
- **1(무게 확인) vs 2(앵커만 존재) 구별**: 앵커 호출이 코드에 있다 ≠ 제거하면 시험이 깨진다. **시험의 import로 판정**(서빙 모듈/함수 import=서빙 행사, `contracts`만 import=fixture↔schema만). 다중행 `_checked(`는 다음 줄 인자까지 확인(단일행 grep 함정 회피).
- **표본 근거**: 커널 앵커는 서빙 모듈 전수 grep(측정). saintvision은 대표 4개(replica-status·discovery-candidates·pools/capacity·storage-locations) 확인, `response_model` 패턴 균일 → 나머지 saintvision 동형 추정. 되돌림(가드 제거) 대조는 ProblemDetails(앞선 검토)로 대표 실행, 나머지는 import·코드 판정.
- 이름 유사 주의(오늘 교훈): `ModelManifest`=검증워커 앵커(서빙 아님), `NodeStopReceipt`=이름충돌 — 서빙 응답 앵커만 셈.

## ① 앵커 있고 무게 진다고 확인됨 (서빙 경로를 시험이 행사)
- **ShardObservation** — `shards.py:332 validate_contract(result)`; 시험 `test_shard_runtime_status_is_anchored_before_serving`가 `ShardRuntime._status`를 불러 `validations==["ShardObservation"]` 단언(Codex가 내 앵커-갭 지적 후 추가). [측정]
- **ProblemDetails** — `app.py:41 validate_contract(body)`; 커버리지 시험이 create_app+실 503/429 요청으로 앵커 도달 단언, **내가 가드 제거 되살림까지 확인**. [측정]
- **ControlRunPage·ApprovalPage** — `control.py:109/134 validate_contract(result)`; `test_run_approval_observation_contract`가 `inv.control.Control` provider(list_runs/list_approvals=서빙)를 불러 `result==fixture` 단언 → 서빙 앵커 행사. [측정]

## ② 앵커는 서빙 코드에 있으나 무게 진다고 확인 안 됨 (제거해도 시험 안 깨짐) — **내 결속들**
서빙 코드에 `_checked`/`validate_contract(result)`가 **있음(코드로 확인)**. 그러나 시험이 `from inv.contracts import validate_contract`만 import해 **`validate_contract(fixture)`만** 대조 — 서빙 함수(result_view/model_view/storage_view/WorkspaceEditor)를 부르지 않는다. ⇒ 서빙 코드에서 앵커를 지워도 이 시험들은 초록. [측정: 앵커 위치 + 시험 import]
| 응답 | 서빙 앵커(코드) | 시험 |
|---|---|---|
| RunResultView | result_view.py:115 `_checked` | fixture↔schema만 |
| RunArtifactList | result_view.py:183 `_checked` | fixture↔schema만 |
| RunLogView | result_view.py:232 `_checked` | fixture↔schema만 |
| RunAttemptList | result_view.py:266 `_checked` | fixture↔schema만 |
| ModelCommitObservation | model_view.py:56 `validate_contract` | fixture↔schema만 |
| WorkspaceEditView | workspace_editor.py:156 `validate_contract` | fixture↔schema만 |
| StorageObservationView | storage_view.py:101 `validate_contract` | fixture↔schema만 |
- (추가) ApprovalReviewView·ApprovalChallenge — `approvals.py`에 앵커 존재, 서빙-행사 시험 미확인 → 버킷2 후보(미표본). 
- **saintvision**(replica·storage-locations·pool-capacity/created/member/removal·placement-preview·distributed-plan·storage-contributions·project-list·project-workspaces·discovery-candidates·legacy-catalog·workspace-execution-readiness): FastAPI `response_model`로 **프레임워크가 서빙 응답을 자동 검증**(구조적 앵커) — 커널 수동보다 견고. 계약 시험은 fixture↔schema(pydantic)라 엔드포인트를 직접 행사하진 않으나, response_model이 서빙 앵커를 보장. ⇒ 버킷2이되 위험 낮음(프레임워크 강제).

## ③ 앵커가 아예 없음
- **없음.** 묶인 28개 응답 전부 서빙 앵커 보유(커널 수동 or saintvision response_model). 마지막 갭이던 ShardObservation을 Codex가 닫았다(내가 flag). terminal-ticket-result는 terminal=Codex 도메인이라 이 감사 범위 밖(별도).

## 위험·소관 (다음 할 일)
- **버킷2 커널 7개(전부 내 결속)가 유일한 실질 위험**: 수동 앵커라 지워질 수 있는데 시험이 안 잡는다("형식만 갖춘 결속"의 정의에 가장 가까움). 소비처 있고 판단에 쓰이는 순: WorkspaceEditView·StorageObservationView(무결성 표시)·RunResultView/RunArtifactList(verify_content 결과)·ModelCommitObservation(재검증)·RunLogView·RunAttemptList. **소관=커널=내 레인. 다음 할 일: 각 응답에 Codex의 `test_shard_runtime_status_is_anchored_before_serving`형 서빙-앵커 시험 추가**(서빙 함수 호출+앵커 제거 시 실패). 그러면 버킷2→버킷1.
- ApprovalReviewView/Challenge: 커널, 표본 미실시 — 서빙-행사 시험 유무 확인 후 필요 시 추가(내 레인/공유).
- saintvision response_model 앵커는 견고하나, 원하면 엔드포인트 행사 시험으로 버킷1화(그 레이어=Codex).
- 버킷3 없음 → 새 앵커 신설 불요.

## 이 감사가 내 작업에 준 것 (자기적용)
"앵커 호출이 코드에 있다 ≠ 제거하면 시험이 깨진다"는 오늘의 축을 **내 결속 7개에 적용하니 전부 버킷2**였다. 계약이 있다는 사실이 증거처럼 읽히는 바로 그 함정이다. 서빙-앵커 시험이 다음 작업.
