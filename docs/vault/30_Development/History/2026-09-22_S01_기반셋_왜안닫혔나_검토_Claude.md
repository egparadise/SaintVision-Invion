# S01 기반 셋 — 왜 아직 안 닫혔나 (reviewer 검토)

세 과제 S01-BE/DB/ST는 owner Codex·reviewer Claude·**모두 in_progress**이고 12 스프린트의 맨 앞이다. 위 S02~S12가 전부 planned인 이유는 이 기반이 안 닫혀서다. 요구 증거는 셋 다 **계약 검증·설계 검토·인벤토리 보고**. 나는 검토자로서 왜 안 닫혔나를 과제별·증거별로 (①없음 ②있으나 미기록 ③범위 미덮음)로 갈랐다. **닫지 않았다** — closing은 증거가 서면 owner(Codex)가 절차대로.

## 한 줄 결론 (사용자 "숫자가 안 움직인다"의 답)
S01의 **소프트웨어 증거는 대부분 이미 있다**(상당수 오늘 밤). 그런데 (a) **기록이 stale해서 undercount**(합격증거 문서엔 "migrations 0001~0006"인데 **실제 head는 0045** — 39개 앞), (b) **peer review가 수행됐으나 S01 증거로 consolidate 안 됨**, 그리고 결정적으로 (c) **닫는 것을 막는 하드 블로커 = Codex의 DoD가 요구하는 실장비·IdP/CA/DNS·Storage 제품 값(사용자 대기, 물리/운영)**. 그래서 **소프트웨어를 아무리 해도 % 안 움직인다** — 기반의 done 조건이 사용자 입력에 걸려 있고, 이미 한 소프트웨어 몫조차 기록이 낡아 안 세어진다.

## 과제별 (증거별 ①없음/②있으나 미기록/③범위 미덮음)

### S01-BE (저장소·계약·개발환경·권한경계)
- **계약 검증 → ② 있으나(대폭 확장) 미기록**: 정본 schema·계약 시험이 있고 **오늘 밤 크게 늘었다**(export_schemas --check 56·check_contract_bindings 46/12·contracts:check 16·CI-스코프 백엔드 1622 passed, 다수 write/read 응답 결속). 기록의 "0001~0006"은 **stale**(실제 0045). → **기록 갱신하면 이 축은 선다.**
- **설계 검토 → ② 수행됐으나 미consolidate**: 오늘 밤 Codex 기반물 독립검토 다수(쓰기응답 재판정+PG, contribution lifecycle, artifact-content, discovery tenant/자격증명, 마이그레이션 head, retry 부재). 개별 review 문서로 있으나 "S01 peer review 완료"로 묶이지 않음. → **내(reviewer)가 consolidate 가능**(소프트웨어 범위).
- **개발환경 → ② 있음**: [[2026-09-11_DEV-ENV_Codex_로컬개발환경구성과검증]] 등. 실제 5대/원격은 ③.
- **권한 경계 → ② 소프트웨어분 있음(내가 검토)**: 운영자 자격증명 발급·RLS·NOLOGIN·tenant 격리. 단 **실제 IdP/CA 연결은 ③**(사용자 값 대기).
- **닫으려면**: (내 몫) peer-review consolidate + 계약 증거 기록 갱신. (사용자 몫) 실제 IdP/CA — 소프트웨어 권한경계는 이미 검토됨이나 DoD가 실연결을 요구하면 대기.

### S01-DB (ERD·ID·상태·마이그레이션 순서)
- **계약 검증 → ② 있음**: DB-backed 계약 시험, RLS 강제.
- **설계 검토 → ② 오늘 확인**: **마이그레이션 단일 head 0045**(migration_graph, reversible-tail 포함) 오늘 확인 · 상태기계(run/node/workspace/contribution의 DB CHECK 도메인)를 오늘 전수 열거(retry 검토에서 failed=종단 구조 확인) = 사실상 **상태 인벤토리**. ID 스킴(new_id). ERD는 전용 문서 없이 "DB 최종 개발 계획"에 있음.
- **인벤토리 보고 → ② 있음**: schema/ID/state 인벤토리.
- **③ 없음**: DB 자체는 물리 장비 의존이 **없다.** → **S01-DB는 사용자 대기 없이 증거만 기록·consolidate하면 닫힘에 가장 가깝다.** (내 몫 + Codex 절차.)

### S01-ST (URI·보존·제품검증·장비 인벤토리)
- **계약 검증 → ② 있음(오늘 좁힘)**: 저장소 계약(Contribution/DataLocation/StorageObservation) 결속·시험, ContributionResponse 오늘 좁힘, artifact-content 다운로드(X-Content-SHA256) 검증.
- **URI → ② 있음**: `inv://` 리졸버(db/models/storage.py 등), 오늘도 접촉.
- **보존 → ② 부분**: retention_pinned_until·GC eligibility(합격증거 표의 CR-07). 정책 완성도는 확인 필요.
- **제품 검증·Storage 제품 선택 → ③ 사용자/결정 대기**: Storage 제품/라이선스 미확정(브리프 #5 다운로드 정본과도 인접).
- **장비 인벤토리 → ③ 사용자 대기(물리)**: **실장비 5대·허용 폴더/자원·IdP/CA/DNS.** 개발 PC를 제품 Node로 임의 등록 금지. → **S01-ST가 진짜 하드 블로커를 안고 있다**(장비+Storage 제품). S05~S08이 기다리는 "장비 Evidence"가 바로 이것.

## 무엇을 하면 되나 (닫지 않음, reviewer 권고)
1. **기록 갱신(undercount 해소, 지금 가능)**: S01 합격증거를 실제 상태로 — migrations 0001~0006 → **0045**, 오늘 밤 계약 스위트 결과(0b7d51ed GREEN)·독립검토들을 S01 증거로 첨부. done 처리가 아니라 **한 일이 숫자에 잡히게**.
2. **peer review consolidate(내 몫)**: 세션의 Codex 기반물 독립검토를 "S01 소프트웨어 peer review"로 묶어 sign-off(운영/장비 범위는 별도로 명시). 이건 검토자 산출물이라 내가 할 수 있다.
3. **하드 블로커는 사용자 입력**: 실장비 5대·허용 폴더·IdP/CA/DNS·Storage 제품 값이 와야 S01-ST(및 S05~S08의 장비 Evidence)가 닫힌다. **이것이 % 정체의 실제 원인.** 브리프에 "기반 셋을 닫으려면 필요한 사용자 입력"으로 올린다(브리프 #4 DSN·#5 다운로드정본·기존 노드/IdP 대기와 묶임).
4. **닫기 순서 권고**: S01-DB는 장비 의존이 없어 **증거 기록+consolidate만으로 절차상 닫기 후보**(Codex 확인). S01-BE는 소프트웨어분 대부분 서나 실 IdP 연결 요구 시 부분 대기. S01-ST는 장비/제품 값 대기 = 사용자 없이는 못 닫음.
5. **닫는 것은 Codex(owner)가 증거 서면 절차대로.** 나는 검토·기록·consolidate·블로커 표면화까지.
