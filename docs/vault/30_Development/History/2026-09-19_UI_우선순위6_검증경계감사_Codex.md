# UI 우선순위 6 fake fallback 및 backend 경계 감사

## 범위와 검증 경계

`apps/web/src`의 route adapter·화면·관련 시험을 정적 추적했다. backend가 실행되지 않은 상태에서 실제 HTTP 실패 주입은 수행하지 않았고, 소스에서 확인한 동작과 시험의 fixture 범위를 분리한다. Gemini CLI 인증 부재로 구현·독립 UI 검토는 보류한다.

## 확정된 소스 finding

### UI-FB-01 / P1 후보 — ResourceExplorer가 backend 오류 뒤 합성 자원을 표시

`features/desktop/ResourceExplorer.tsx`:

- discovery `candidates` 상태가 처음부터 Node-06-EdgeWorker 합성 후보 하나를 갖는다(약 87~105행).
- `getDiscoveryCandidates()` 실패 시 catch가 이 후보를 유지한다(약 258~263행). 화면에는 승인 대기 후보와 승인/거부 버튼이 그대로 렌더된다. `verified: false` 문구는 있지만 backend가 죽은 상태라는 오류/미검증 배너가 없다.
- `getPoolCapacity()` 실패 시 48C/192GiB/3GPU 등 합성 capacity를 `poolCapacity`에 넣는다(약 203~216행). 풀 카드에는 실제 backend 응답인지 fallback인지 표시되지 않는다.
- `getNodeDetail()` 실패 시 부모 `nodes`의 정보와 고정 capability 값을 노드 상세 API 결과처럼 채운다(약 220~257행).

이는 단순 빈 상태가 아니라 backend 장애 뒤에도 후보·용량·상세 데이터와 운영 버튼을 제공하는 구조다. 실제 HTTP 401/403/5xx/JSON 오류/무응답에서 화면이 그렇게 되는 것은 아직 런타임 주입으로 재현하지 않았으므로, 현재는 소스 확정 finding으로 분류한다.

### UI-FB-02 / P2 경계 — PlacementSimulator가 backend 실패 뒤 로컬 배치 결과를 계속 표시

`features/placement/PlacementSimulator.tsx`는 pool/candidate/placement-preview fetch 실패를 console warning만 남기고 로컬 `evaluatePlacement(nodes, ...)` 결과를 계속 렌더한다. pool 부재 배너에는 “로컬 결정론적 평가 활성”이라고 명시되어 있어 UI-FB-01과 달리 범위를 일부 고지한다. 다만 서버 적격성·lease·실제 pool 상태가 필요한 사용자가 로컬 결과를 실행 가능 판정으로 오해할 여지는 남는다. 이 항목은 소스 경계 finding이며 제품 결함 확정이나 런타임 오표시 실측으로 승격하지 않는다.

### UI-FB-03 / P2 후보 — DeveloperStudio result 오류의 artifacts fallback

`features/studio/DeveloperStudio.tsx`의 canonical ResultView 조회가 어떤 예외든 catch하면 artifacts endpoint를 재조회하고, 그 결과를 `artifactData`로 표시한다(약 285~298행). 404 route 부재와 401/403/5xx/깨진 JSON/네트워크 오류를 구분하지 않는다. artifacts가 성공하면 ResultView 실패 사실이 화면에 남지 않아 부분 결과가 정상 결과처럼 보일 수 있다. 기존 route 정합 fallback과 구분해 실제 상태코드별 정책을 확인해야 한다. 현재 소스 finding 후보이며 runtime 주입은 하지 않았다.

## 시험 범위와 공백

- `apps/web/tests/fabric-control-plane.test.tsx`: API client는 mock이고 ResourceExplorer는 `renderToStaticMarkup`으로 렌더한다. React `useEffect`가 실행되지 않아 discovery/pool/node fetch 실패 후 fallback이 실제로 렌더되는지 시험하지 않는다. 22 tests 통과는 endpoint 호출 shape·정적 화면 문구의 증거이지 backend 장애 UI 인수 증거가 아니다.
- `apps/web/tests/placement-explain.test.ts`: 순수 `evaluatePlacement` 계산 8 tests다. pool/placement-preview fetch의 401/403/5xx/JSON 오류와 화면 상태를 시험하지 않는다.
- `apps/web/tests/evidence-viewer.test.ts`는 EvidenceViewer 실패·UNVERIFIED를 다루며, ResourceExplorer/PlacementSimulator/DeveloperStudio fallback을 덮지 않는다.
- 실제 실행 명령: `npm exec vitest run tests/fabric-control-plane.test.tsx tests/placement-explain.test.ts` (working directory `apps/web`) → **30 passed**. 이 결과는 mock/순수 계산 범위다.

## 판정과 다음 owner

UI-FB-01은 Gemini 구현 owner에게 backend 실패 시 합성 후보·capacity·detail을 제거하거나 명시적 UNVERIFIED/오류 상태로 분리하는 설계 검토를 넘긴다. UI-FB-02는 local simulation과 server admission의 표시·행동 경계를 명시해야 한다. UI-FB-03은 404 route fallback만 허용하고 401/403/5xx/parse/network 오류는 오류 상태로 표면화하는지 계약 검토가 필요하다. Codex는 경계 reviewer로 남고 Gemini 인증 회복 전 구현하지 않는다.

실제 확인되지 않은 사항은 명확히 유지한다: backend가 없는 상태에서 위 세 화면을 브라우저로 실행한 증거, 상태코드별 주입 결과, 실제 사용자 클릭으로 합성 데이터를 승인하는지 여부, CI/운영 UI 인수.

## Gemini 구현 계약

다음 변경은 Gemini가 owner로 구현하고 Codex가 경계를 재검토한다.

### UI-FB-01 ResourceExplorer

1. 합성 Node-06 후보와 합성 capacity/detail 초기값을 제거하고 초기 상태는 빈 데이터와 명시적 로딩 상태로 둔다.
2. `loading`, `success-empty`, `success-with-data`, `error`를 별도 상태로 유지한다. 정상 응답의 `items: []`도 반드시 state에 반영한다. `length > 0` 조건으로 기존 합성값을 보존해서는 안 된다.
3. `error`에서는 후보·capacity·detail을 성공 데이터처럼 표시하거나 admission/decline 운영 버튼을 렌더하지 않는다. 오류 상태와 재시도 경로를 보여준다.
4. 회귀시험은 (a) 정상 빈 응답이 빈 상태를 렌더하는지, (b) 401/403/5xx·깨진 JSON·무응답이 오류 상태를 렌더하는지, (c) 오류에서 운영 버튼이 없는지, (d) 합성 초기값을 되살리면 시험이 실패하는지를 각각 단언한다.

### UI-FB-02 PlacementSimulator

1. backend pool/candidate/preview 실패와 로컬 결정론적 설명을 별도 상태로 유지한다.
2. 로컬 평가 결과는 서버 admission 또는 실행 가능 판정으로 표시하지 않고 `local/unverified` 범위를 항상 노출한다.
3. 401/403/5xx·깨진 JSON·무응답에서는 성공 badge나 실행 버튼을 만들지 않는다. 시험은 정상 빈 상태, 오류 상태, 로컬 설명 상태를 각각 분리한다.

### UI-FB-03 DeveloperStudio

1. ResultView의 404 route fallback만 명시적으로 허용하고, 401/403/5xx·깨진 JSON·네트워크 오류는 artifacts 성공으로 대체하지 않는다.
2. fallback이 수행되면 화면과 evidence에 `result-unavailable`과 fallback 범위를 기록한다. artifacts 데이터는 canonical ResultView 성공으로 집계하지 않는다.
3. 상태코드별 회귀시험을 넣고, 오류를 성공으로 바꾸는 fallback을 되돌리면 시험이 실패해야 한다.

모든 회귀시험은 실제 backend/브라우저 인수와 구분해 fixture 또는 주입 범위를 기록해야 하며, 합성 fixture 통과를 운영 UI 인수로 승격하지 않는다.
