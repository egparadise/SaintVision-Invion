# UI 우선순위 6 fake fallback 및 backend 경계 감사

## 범위와 검증 경계

`apps/web/src`의 route adapter·화면·관련 시험을 정적 추적했다. backend가 실행되지 않은 상태에서 실제 HTTP 실패 주입은 수행하지 않았고, 소스에서 확인한 동작과 시험의 fixture 범위를 분리한다. Gemini CLI 인증 부재로 구현·독립 UI 검토는 보류한다.

## 확정된 소스 finding

### UI-FB-01 / P1 후보 — ResourceExplorer가 backend 오류 뒤 합성 자원을 표시

`features/desktop/ResourceExplorer.tsx`:

- discovery `candidates` 상태가 처음부터 Node-06-EdgeWorker 합성 후보 하나를 갖는다(약 87~105행).
- `getDiscoveryCandidates()` 실패 시 catch가 이 후보를 유지한다(약 258~263행). 화면에는 승인 대기 후보와 승인/거부 버튼이 그대로 렌더된다. `verified: false` 문구는 있지만 backend가 죽은 상태라는 오류/미검증 배너가 없다.
- `getPoolCapacity()` 실패 시 48C/192GiB/3GPU 등 합성 capacity를 `poolCapacity`에 넣는다(약 203~216행). 풀 카드에는 실제 backend 응답인지 fallback인지 표시되지 않는다.
- `getNodeDetail()` 실패 시 부모 `nodes`의 정보와 고정 capability 값을 노드 상세 API 결과처럼 채운다(약 220~257행).

이는 단순 빈 상태가 아니라 backend 장애 뒤에도 후보·용량·상세 데이터와 운영 버튼을 제공하는 구조다. 실제 HTTP 401/403/5xx/JSON 오류/무응답에서 화면이 그렇게 되는 것은 아직 런타임 주입으로 재현하지 않았으므로, 현재는 소스 확정 finding으로 분류한다.

### UI-FB-02 / P2 경계 — PlacementSimulator가 backend 실패 뒤 로컬 배치 결과를 계속 표시

`features/placement/PlacementSimulator.tsx`는 pool/candidate/placement-preview fetch 실패를 console warning만 남기고 로컬 `evaluatePlacement(nodes, ...)` 결과를 계속 렌더한다. pool 부재 배너에는 “로컬 결정론적 평가 활성”이라고 명시되어 있어 UI-FB-01과 달리 범위를 일부 고지한다. 다만 서버 적격성·lease·실제 pool 상태가 필요한 사용자가 로컬 결과를 실행 가능 판정으로 오해할 여지는 남는다. 이 항목은 소스 경계 finding이며 제품 결함 확정이나 런타임 오표시 실측으로 승격하지 않는다.

### UI-FB-03 / P2 후보 — DeveloperStudio result 오류의 artifacts fallback

`features/studio/DeveloperStudio.tsx`의 canonical ResultView 조회가 어떤 예외든 catch하면 artifacts endpoint를 재조회하고, 그 결과를 `artifactData`로 표시한다(약 285~298행). 404 route 부재와 401/403/5xx/깨진 JSON/네트워크 오류를 구분하지 않는다. artifacts가 성공하면 ResultView 실패 사실이 화면에 남지 않아 부분 결과가 정상 결과처럼 보일 수 있다. 기존 route 정합 fallback과 구분해 실제 상태코드별 정책을 확인해야 한다. 현재 소스 finding 후보이며 runtime 주입은 하지 않았다.

## 시험 범위와 공백

- `apps/web/tests/fabric-control-plane.test.tsx`: API client는 mock이고 ResourceExplorer는 `renderToStaticMarkup`으로 렌더한다. React `useEffect`가 실행되지 않아 discovery/pool/node fetch 실패 후 fallback이 실제로 렌더되는지 시험하지 않는다. 22 tests 통과는 endpoint 호출 shape·정적 화면 문구의 증거이지 backend 장애 UI 인수 증거가 아니다.
- `apps/web/tests/placement-explain.test.ts`: 순수 `evaluatePlacement` 계산 8 tests다. pool/placement-preview fetch의 401/403/5xx/JSON 오류와 화면 상태를 시험하지 않는다.
- `apps/web/tests/evidence-viewer.test.ts`는 EvidenceViewer 실패·UNVERIFIED를 다루며, ResourceExplorer/PlacementSimulator/DeveloperStudio fallback을 덮지 않는다.
- 실제 실행 명령: `npm exec vitest run tests/fabric-control-plane.test.tsx tests/placement-explain.test.ts` (working directory `apps/web`) → **30 passed**. 이 결과는 mock/순수 계산 범위다.

## 판정과 다음 owner

UI-FB-01은 Gemini 구현 owner에게 backend 실패 시 합성 후보·capacity·detail을 제거하거나 명시적 UNVERIFIED/오류 상태로 분리하는 설계 검토를 넘긴다. UI-FB-02는 local simulation과 server admission의 표시·행동 경계를 명시해야 한다. UI-FB-03은 404 route fallback만 허용하고 401/403/5xx/parse/network 오류는 오류 상태로 표면화하는지 계약 검토가 필요하다. Codex는 경계 reviewer로 남고 Gemini 인증 회복 전 구현하지 않는다.

실제 확인되지 않은 사항은 명확히 유지한다: backend가 없는 상태에서 위 세 화면을 브라우저로 실행한 증거, 상태코드별 주입 결과, 실제 사용자 클릭으로 합성 데이터를 승인하는지 여부, CI/운영 UI 인수.

## Gemini 구현 계약

다음 변경은 Gemini가 owner로 구현하고 Codex가 경계를 재검토한다.

### UI-FB-01 ResourceExplorer

1. 합성 Node-06 후보와 합성 capacity/detail 초기값을 제거하고 초기 상태는 빈 데이터와 명시적 로딩 상태로 둔다.
2. `loading`, `success-empty`, `success-with-data`, `error`를 별도 상태로 유지한다. 정상 응답의 `items: []`도 반드시 state에 반영한다. `length > 0` 조건으로 기존 합성값을 보존해서는 안 된다.
3. `error`에서는 후보·capacity·detail을 성공 데이터처럼 표시하거나 admission/decline 운영 버튼을 렌더하지 않는다. 오류 상태와 재시도 경로를 보여준다.
4. 회귀시험은 (a) 정상 빈 응답이 빈 상태를 렌더하는지, (b) 401/403/5xx·깨진 JSON·무응답이 오류 상태를 렌더하는지, (c) 오류에서 운영 버튼이 없는지, (d) 합성 초기값을 되살리면 시험이 실패하는지를 각각 단언한다.

### UI-FB-02 PlacementSimulator

1. backend pool/candidate/preview 실패와 로컬 결정론적 설명을 별도 상태로 유지한다.
2. 로컬 평가 결과는 서버 admission 또는 실행 가능 판정으로 표시하지 않고 `local/unverified` 범위를 항상 노출한다.
3. 401/403/5xx·깨진 JSON·무응답에서는 성공 badge나 실행 버튼을 만들지 않는다. 시험은 정상 빈 상태, 오류 상태, 로컬 설명 상태를 각각 분리한다.

### UI-FB-03 DeveloperStudio

1. ResultView의 404 route fallback만 명시적으로 허용하고, 401/403/5xx·깨진 JSON·네트워크 오류는 artifacts 성공으로 대체하지 않는다.
2. fallback이 수행되면 화면과 evidence에 `result-unavailable`과 fallback 범위를 기록한다. artifacts 데이터는 canonical ResultView 성공으로 집계하지 않는다.
3. 상태코드별 회귀시험을 넣고, 오류를 성공으로 바꾸는 fallback을 되돌리면 시험이 실패해야 한다.

모든 회귀시험은 실제 backend/브라우저 인수와 구분해 fixture 또는 주입 범위를 기록해야 하며, 합성 fixture 통과를 운영 UI 인수로 승격하지 않는다.

## 2026-09-21 계약 완결성 검토 — 구현 승인 기준

기존 세 계약은 방향은 맞지만 구현자가 합격 여부를 추측할 여지가 있어 아래 판정 조건으로 구체화한다. 이 부록이 앞의 요약 요구와 충돌하면 부록의 명시적 pass/fail 조건을 우선한다. 이는 Gemini 구현을 대신하거나 현재 화면 변경을 승인하는 내용이 아니다.

### 세 화면 공통 판정 규칙

- 원격 조회 상태는 `loading`, `success-empty`, `success-with-data`, `error`가 서로 구별되어야 한다. `idle`/요청 미완료를 `success-empty`로 렌더하면 안 된다. 빈 상태 문구는 성공한 응답의 유효한 빈 결과에서만 허용한다.
- HTTP 401/403/5xx, 성공 상태의 잘못된 JSON/응답 shape, fetch rejection·timeout은 오류 상태다. 해당 오류를 빈 데이터, 성공 배지, 실행/승인 판단으로 바꾸면 실패다. 화면 문구는 모두 같을 필요는 없지만 접근 가능한 오류(`role="alert"` 또는 동등한 assertive live region), 문제의 데이터 영역, 그리고 읽기 재시도 가능 여부를 분명히 한다.
- 요청 실패 뒤 직전 데이터가 남아 있다면 그것을 최신 조회 성공 또는 실행 가능 근거처럼 보여주거나 그 데이터로 mutation을 시작할 수 없어야 한다. 캐시를 계속 보여주는 선택을 한다면 stale/unverified임을 명시하고 해당 mutation을 막는다.
- local/deterministic 계산은 `local-unverified` 범주다. server response, admission, reservation, 실행 가능 여부를 뜻하는 `PASS`, `eligible`, `ready`, `server-confirmed` 표시와 섞이지 않는다.
- 회귀시험은 최소한 요청 대기(pending), 성공 빈 응답, 오류 응답을 각각 실제 컴포넌트의 상태 전이에 통과시킨다. `renderToStaticMarkup`은 `useEffect`를 실행하지 않으므로 초기 정적 markup만 검사해서 fetch 결과 단언으로 인정하지 않는다. 테스트는 효과를 구동하는 DOM harness를 쓰거나, 동등한 경로를 가진 추출 상태 전이 함수를 검증하고 실제 컴포넌트와 연결된 사실을 함께 단언해야 한다. 이 저장소의 `fabric-control-plane.test.tsx`는 현재 API client mock과 SSR 렌더만 사용한다.

### UI-FB-01 ResourceExplorer — pass/fail 조건

확인 대상은 discovery candidate, pool capacity, node detail, 그리고 storage contribution/location 조회다. 이 finding에서 확인한 storage `.catch(() => empty)`도 빠뜨리지 않는다.

1. 기본 discovery 상태에는 후보가 0개이며 sentinel `ann_node06_unverified` / `Node-06-EdgeWorker`가 없다. 용량·상세 데이터도 해당 GET 성공 전에 합성값으로 초기화되지 않는다.
2. 응답 `200 {items: []}`는 `success-empty`가 된다. 반면 pending 요청 중에는 loading이고 빈 상태 문구가 나오지 않는다. storage도 각 조회의 `200 {items: []}`에서만 “없음” 문구를 보인다. 정상적인 `0` 용량은 서버가 실제 반환한 값이면 데이터로 취급한다.
3. discovery의 401/403/5xx·JSON parse 실패·네트워크 거부 및 capacity/detail/storage GET 실패는 visible error다. 실패한 영역을 빈 성공으로 표시하지 않는다. 특히 storage 오류는 단지 `storageError` state에 저장하는 것으로 불충분하며 실제 화면에서 오류가 보여야 한다.
4. discovery 오류 시 후보 카드, bootstrap token 성공 표시, 승인/거부 버튼은 모두 0개다. 대조군으로 정상 pending 후보 응답에서는 그 후보만 정확히 한 번 렌더되고 버튼이 보일 수 있다. 후보 request가 실패하면 이전 후보도 mutation 대상으로 남기지 않는다.
5. 합성 초기값 회귀 대조는 API가 pending인 시점과 `200 {items: []}` 완료 시점 모두에서 수행한다. markup/DOM에 sentinel hostname·announcement가 없고, 승인/거부 버튼도 없어야 한다. 이전 합성 초기 배열을 복원하면 pending 단계의 no-sentinel 단언이 깨져야 한다. 응답이 비어도 합성값을 유지하도록 되돌리면 success-empty 단언이 깨져야 한다. 이는 기존 정적 SSR의 `initialCandidatesState="error"` 렌더 단언만으로 대체되지 않는다.

예시의 핵심 단언(렌더 helper 이름은 기존 테스트 도구에 맞춰 구현):

```tsx
const pending = deferred<{ items: DiscoveryCandidate[] }>();
mockApi.mockReturnValueOnce(pending.promise);
const view = renderWithEffects(<ResourceExplorer nodes={sampleNodes} initialTab="discovery" />);
expect(view.getByTestId('discovery-loading')).toBeVisible();
expect(view.queryByText('Node-06-EdgeWorker')).toBeNull();
expect(view.queryByRole('button', { name: /승인|거부/ })).toBeNull();
await act(async () => pending.resolve({ items: [] }));
expect(view.getByTestId('discovery-empty-state')).toBeVisible();
expect(view.queryByText('ann_node06_unverified')).toBeNull();
```

추가로 injected `error` state에서 `role="alert"`와 no-operation-buttons를, injected `success` + empty list에서 success-empty 문구를 SSR/컴포넌트 렌더 시험으로 고정할 수 있다. 이 정적 상태 시험은 위 async transition 대조를 대신하지 않는다. 위 예시에서 기존 합성 초기 배열을 되살리면 pending 검사에서 바로 실패하고, 빈 응답을 무시하도록 되돌리면 완료 후 empty-state 검사가 실패해야 한다.

### UI-FB-02 PlacementSimulator — pass/fail 조건

1. `/v1/pools`, `/v1/discovery/candidates`, placement-preview가 각각 pending/loading·성공 빈 결과·오류를 구분한다. 현재 `idle`에서 `length === 0`이라는 이유만으로 pool/candidate “정보 없음” 배너를 성공 empty로 출력하면 안 된다.
2. 화면의 결정론적 결과는 항상 로컬 결과임을 표시한다. preview 성공 전 로컬 적격/점수는 서버 적격·예약·배치 완료가 아니다. 서버 설명과 server-shard 표시는 preview 성공 응답에서만 채운다.
3. 각 GET의 401/403/5xx/JSON parse/network 실패에서 error가 화면에 보이고 서버 shard/explanation의 성공 내용이 없다. 로컬 설명을 남기는 경우에도 `local-unverified` 표지를 결과와 함께 유지한다. 어떠한 run/admit/commit mutation도 로컬 점수만으로 활성화하지 않는다.
4. 시험은 pool/candidate 빈 응답과 preview 빈 응답을 오류와 따로 확인하고, preview 오류 때 local label은 남지만 server success 문구/행은 없음을 단언한다. 합성 pool이나 server shard를 재도입하면 성공 데이터처럼 렌더되는 테스트가 실패해야 한다.

### UI-FB-03 DeveloperStudio — pass/fail 조건

1. canonical `/result` 응답의 명시적 route-not-found만 artifacts route fallback을 허용한다. 구현은 문자열 포함 검사 대신 `shared/api/client`의 `isRouteNotFoundError(err)`를 사용한다. application/resource 404(예: `RES-*`), 401/403, 5xx, network error, JSON parse error는 fallback하면 안 된다.
2. `/result`가 2xx여도 envelope/output이 누락되거나 유효하지 않으면 route 부재가 아니다. 이를 artifacts 결과로 조용히 대체하지 말고 `result-unavailable`/unverified 오류로 표현한다.
3. 허용된 404 fallback은 artifacts-only 부분 결과임을 화면에서 식별하고 원본 ResultView 부재와 범위를 남긴다. 이 경로를 canonical ResultView 성공, integrity PASS 또는 서버 완료 증거로 세지 않는다. artifacts GET도 실패하면 visible error 상태다.
4. parameterized test에서 route-not-found 404만 artifacts 호출 1회와 fallback label을 기대한다. 401/403/5xx/resource 404/invalid JSON/network error는 artifacts 호출 0회, error 표시, canonical PASS 0건이어야 한다. 성공 2xx지만 output 누락도 fallback 0회를 확인한다. 넓은 catch→fallback을 되살리면 이 대조군이 실패해야 한다.

### 현재 소스 대조와 Codex 재검토 범위
