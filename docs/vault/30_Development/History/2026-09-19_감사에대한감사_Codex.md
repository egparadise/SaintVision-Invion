## 발견된 정정

### AOA-01 — `provision_credentials.py`의 수정 위치를 잘못 짚음

- **당초 기록/설명:** 첫 수정 `91a8dc1`을 `provision()`의 broad catch-all 해결로 설명했다.
- **실제:** 그 커밋은 파일 내 다른 오류 처리 helper를 바꿨고, `provision()` 본문의 catch-all은 남아 있었다. `git show 91a8dc1:tools/provision_credentials.py`와 이후 통합 소스를 대조하면 구분된다.
- **실측 근거 정정:** 사용자의 첫 주입은 빈 manifest가 DB 연결 전에 정상 거부되어 catch-all에 도달하지 않았다. 그 실행은 붕괴 증거가 아니었다. 이후 `validate_manifest`를 우회해 예외가 본문 handler에 도달하도록 한 재현에서 DB `OperationalError`, `TypeError`, `RuntimeError`가 모두 `ProvisioningDenied`로 뭉개지는 것이 확인됐다.
- **수정/현재 근거:** `25051e3`에서 실제 `provision()` 경로가 고쳐졌다. DB 오류는 `ProvisioningDatabaseError`, 예기치 않은 오류는 비밀 없는 `ProvisioningInternalError`, 의도된 거부는 `ProvisioningDenied`로 구분한다. `.venv\Scripts\python.exe -m pytest -q tests/core/test_credential_provision_cli.py tests/core/test_lan_migration_plan.py` 재검증은 **24 passed, 1 skipped, exit 0**이었다. skip은 DSN 부재의 DB 시험이다. 사용자 독립 주입은 비밀 비노출과 범주 분리를 확인했다. 첫 잘못된 재현은 성공 근거에서 제외한다.

### AOA-02 — Python 인터프리터 오기로 실행 가능 시험을 미실행으로 기록

- **당초 기록:** Codex가 `tests/test_independent_restore.py`와 `tests/core/test_lan_restore_upgrade.py`를 `cryptography` 부재로 collection 불가라 적었다. Claude도 같은 날 별도 DB/credential 파일을 bare `python`으로 실행해 collection 불가라고 먼저 기록했다.
- **실제:** bare `python`은 시스템 `C:\Python314\python.exe`를 가리켰고 프로젝트 `.venv`에는 의존성이 있었다. Claude의 정정 기록은 해당 두 파일의 **69 collected / 69 skipped**(DSN 부재)와 올바른 `.venv`를 구분한다. Codex의 기존 24-pass 정정도 별도 기록에 있다.
- **Codex 재검증:** `.venv\Scripts\python.exe -m pytest -q tests/test_independent_restore.py tests/core/test_lan_restore_upgrade.py` → **30 passed, exit 0**. 테스트 추가 전의 “24 passed”와 현재 30은 시점이 다른 실행이며 합산하지 않는다.
- **추가 명령 문서 결함:** Launcher와 Priority-4 기록의 일부 초기 명령은 bare `python -m pytest`라 당시 실행 파일을 확정할 수 없다. 원 실행의 interpreter는 미상으로 유지한다. 감사자는 launcher 두 파일을 `.venv\Scripts\python.exe -m pytest -q tests/core/test_launcher_failure_boundaries.py tests/test_deploy_intranet_preflight.py`로 재실행해 **18 passed, exit 0**을 확인했다. Priority-4 readiness/storage도 올바른 venv로 재실행해 **5 passed / 30 skipped, exit 0**이었다. 모든 skip은 `INV_TEST_ADMIN_DSN` 부재로 PG 본문에 도달하지 않은 것이다.

### AOA-03 — LiveConsole Docker shim 주입을 실장비 필요로 오분류

- **당초 기록:** Docker start 실패를 실장비/Docker daemon이 있어야 시험할 수 있는 미검증 항목으로 분류했다.
- **실제:** C#으로 만든 `docker.exe` shim을 PATH 앞에 두고 원본 PowerShell launcher를 실행하는 daemon-free 주입이 가능하다. 시험은 `inspect`와 `start` shim 호출을 먼저 확인하고, 도달하지 못하면 `ASSERT-FAIL` 또는 선행조건이 없는 경우 이유 있는 `SKIPPED`를 낸다.
- **근거:** 사용자는 start exit 7 주입과 guard 제거 되돌림 실패, Vite 선행파일 부재 시 명시 skip을 독립 재현했다. Codex는 위 venv 명령에서 현재 **18 passed**를 재확인했다. **shim 주입은 검증됨; 실제 Docker daemon·WSL·GUI child-tool 및 운영 인수는 미검증**으로 분리한다. 작성자 시험, Codex 재실행, 사용자 독립 재현은 각각 별도 근거다.

### AOA-04 — MJS 소스의 status 기대를 live API 응답처럼 읽을 여지

초기 MJS 문서의 “actual API rejection”은 소스가 요청을 보내고 특정 status/code를 요구한다는 뜻으로 한정했다. 당시 고정 backend를 실행하지 않았고 live 400/404는 관측되지 않았다. 이번 감사자는 Node v24.17.0에서 세 도구 `node --check`를 실행해 exit 0을 확인했다. `reproduce_handoff_review.mjs`도 절대 repo 경로와 TypeScript 모듈을 지정해 normal exit 0, 의도 mismatch `--self-test` exit 1을 확인했다. 이것은 helper 계산과 자체 판정 실패 경로다. API/화면/장비 rejection은 계속 UNVERIFIED다.

### AOA-05 — Disposable PostgreSQL 집계는 단일 실행 근거로 재현되지 않음

- `.work/codex-dbtest-recovery.xml`: 같은 18건이 기대 owner label 부재로 setup 단계에서 실패했다.

### AOA-06 — Claude TLS 독립검토의 stale-branch finding 철회

Claude TLS review의 “preflight는 Test-Path만 쓰고 leaf/key pair 검증이 없다” 및 폴백 모순 판정은 현재 통합본에는 맞지 않는다. 현행 `tools/deploy_intranet.ps1`에는 `PathType Leaf`, 0-byte 검사, `verify_tls_cert_pair.py` 검증이 있고 `02ed2ee`는 선택된 `certDir`를 Compose 환경에 전달한다. 이 잘못된 항목은 open finding에서 철회하고 문서에 원 주장과 정정 근거를 남겼다. 현재 source 확인은 배포 실행 증거가 아니다.

해당 Claude 문서의 frontmatter `updated=2026-09-20...`는 Git commit `6bfcca7` 시간 `2026-09-19T01:17:33+09:00`보다 뒤다. ### AOA-07 — Readiness/restore rollback 비교 강도 과장 위험

## 문서별 실행자와 검토자
