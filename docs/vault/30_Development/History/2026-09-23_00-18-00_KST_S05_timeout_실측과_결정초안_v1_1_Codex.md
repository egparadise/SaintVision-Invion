# S05 F-S05-01 timeout 실측과 결정 초안 v1.1

## 결론

현 코드의 실측 경합 실패 모드는 15초 snapshot freshness 초과가 아니라 500ms lock timeout 또는 2초 statement timeout이 기존 `RES-0007` / HTTP 503 / `retryable=true`로 매핑되는 경로다. 20동시 한 라운드에서 17/20만 성공했고 성공 P95도 2,417.912ms여서 개발 PC 예비 조건부터 AC-05 2초 경계를 넘었다. 50동시와 물리 5노드는 미측정이며 S05-DB를 `done`으로 올리지 않는다.

## 1. 단일 lock timeout 주입

시험: `tests/integration/test_placement.py::test_project_lock_timeout_is_retryable_res_0007_problem`

- disposable PostgreSQL에서 owner connection이 project row를 `FOR UPDATE`로 잡고 `pg_sleep(1.2)`를 실행하는 동안 placement reserve 한 건을 호출했다.
- 첫 시도는 Linux Docker 전용 fixture를 사용해 1 skipped였고 실측에서 제외했다. benchmark disposable-PG fixture로 교정한 selector는 **1 passed / exit 0 / 10.05s**였다.
- 실제 표면: `DomainError RES-0007`, HTTP 503, `retryable=true`, cause `LockNotAvailable`, SQLSTATE `55P03`.
- 실패 뒤 해당 Run의 Lease와 `placement.reserve` idempotency row는 각각 0건이었다.

이 결과로 Codex v1.0의 “freshness → `RES-0003`” 인과와 Claude PR #74의 “`LockNotAvailable` 미매핑·계약 변경 필요” 전제를 함께 정정했다. `inv/db.py`의 기존 매핑을 그대로 사용하므로 이 경로만으로 새 ProblemDetails 계약은 필요하지 않다.

## 2. 3·10·20동시 비교

조건: 개발 PC 1대, PostgreSQL 16 disposable DB, 한 개 합성 measured-node, 실 PG. 3·10동시는 두 라운드, 20동시는 코디네이터 승인 아래 한 라운드만 실행했다. 이는 물리 5노드 AC-05 판정이 아니다.

| 동시 | 성공/실패 | 성공 P95 | 실패 원인 | 불변식 |
|---:|---:|---:|---|---|
| 3 | 3/3 × 2, 실패 0 | 861.651ms | 없음 | 결정성·replay·fencing·no-overbooking true |
| 10 | 10/10 × 2, 실패 0 | 1,738.762ms | 없음 | 결정성·replay·fencing·no-overbooking true |
| 20 | 17/20, 실패 3 | **2,417.912ms** | 모두 `RES-0007`, `QueryCanceled`, SQLSTATE `57014`, `statement_timeout` | 단일 라운드라 결정성/replay 미측정, fencing·no-overbooking true, active 합계 일치 |
| 50 | 미실행 | 미측정 | 미측정 | 별도 승인 전 실행 금지 |

20동시 명령:

`python tools/placement_benchmark.py --requests 20 --concurrency 20 --rounds 1 --report .work/card13/placement-20.json --junit .work/card13/placement-20.xml --timeout 240`

JUnit은 finding을 실패로 노출해 **1 test / 1 failure / exit 1 / 15.140s**였다. 실패 request index 5·7·16의 완료 순번은 17·19·18, lock-wait 포함 지연은 2,372.379ms·2,372.816ms·2,372.381ms다. fixture teardown 뒤 admin catalogue의 `inv_backend_test_%` 잔존 DB는 0개였다.

분리 프로세스가 감시기 연결 전에 종료되어 peak working set은 **미측정**이다. 수치를 만들기 위해 재실행하지 않았다. JSON의 `codeSHA=a4bf2cee`는 실행 시작 HEAD이고 하네스 변경은 working tree였으므로, 재현 정본은 이 History와 도구 변경을 포함하는 R1 착지다.

## 3. 하네스 v1.1

- 요청별 lock-wait 포함 latency, completion order, error code/status/retryable, cause class, SQLSTATE, timeout kind를 JSON에 남긴다.
- `--rounds 1|2`를 지원한다. 한 라운드에서는 결정성·replay를 false가 아니라 `null`/미측정으로 남기고 JUnit 실패로 오판하지 않는다.
- 실패가 `RES-0003` 또는 `RES-0007`이면 `F-S05-01`을 기록한다.
- `requestLatencyIncludesLockWait=true`, `serverSideLockWaitSeparatelyMeasured=false`를 명시한다. server-side row별 wait/hold 시간은 아직 측정하지 않았다.

## 4. 결정 C와 v1.1 설계 응답

코디네이터는 2026-09-22 23:53 KST에 A/B를 승인하지 않고 C(조건부 보류)를 결정했다. [[2026-09-22_S05_배치잠금_입도_결정제안_Codex]] v1.1은 다음을 반영한다.

- 옵션 1의 핵심 성공 지표를 project row 제거가 아니라 transaction별 project/limit/node/resource 잠금 보유 시간 p50/p95/max로 정의했다.
- retry는 기존 `RES-0007 && retryable=true`, exact key/body, 새 transaction, bounded attempts/time을 따른다.
- final commit 아래 `active_total`, ceiling, offered fit을 재계산하고 바뀌면 stale winner를 쓰지 않고 후보 계산부터 재시도한다.
- 단일 Node pool의 Node/Resource row 병목을 별도 위험으로 남긴다.
- `leases.py:176` 중복 project lock과 placement/direct lease의 네 `require_*` 순서를 canonical commit primitive 하나로 통일한다.
- freshness 확대는 현 2초 timeout을 고치지 못하고 stale 결정을 허용하므로 기각한다.

## 5. 독립 재검토 인계

reviewer Claude는 다음을 확인한다.

1. 두 인과 정정이 `db.py`, `placement.py`, `leases.py`의 실제 순서와 일치하는가.
2. `RES-0007` bounded retry가 idempotency·fencing·RLS·네 admission guard를 약화하지 않는가.
3. active fit 재계산과 stale winner 폐기가 결정성·원자성을 보존하는가.
4. 단일/다중 Node에서 lock hold 계측이 옵션 1의 이득과 병목을 구분하는가.

Claude 재검토와 코디네이터 후속 결정 전 커널 구현과 50동시 재실행은 시작하지 않는다.
