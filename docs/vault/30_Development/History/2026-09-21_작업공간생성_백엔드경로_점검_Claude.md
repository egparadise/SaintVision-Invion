# 작업공간 생성 백엔드 경로 점검

Gemini가 찾은 6건 중 하나: **작업공간 생성 화면이 가짜 ID를 합성하고 백엔드에 배선돼 있지 않다.** 백엔드는 내 레인이라 병행 확인. 먼저 "있는데 안 부르는가 / 엔드포인트 자체가 없는가"를 가른다. **지금 만들지 않고 무엇이 필요한지만** 적는다(알람 도구처럼 규격·소비처 먼저).

## 결론 (먼저 가른 구별)
- **기능은 있다. 생성만 "응답 계약 밖"에 있다.** 아예 기능이 없는 것이 **아니다.**
- **있는데 화면이 안 부른다** → Gemini가 배선. 백엔드는 응답을 계약에 묶으면 된다(작음, 내 레인, 지금 안 만들고 명세만).
- **생성 ≠ 단순 ready 삽입.** 생성은 `provisioning` 레코드를 만들 뿐이고, 실제 자원 할당/체크아웃은 **별도 커널 prepare 단계**다. → 화면은 진짜 생성(provisioning)은 부를 수 있으나 **"ready"를 흉내 낼 수 없다.**

## ① 백엔드 생성 경로 — 있다
- `POST /v1/projects/{project_id}/workspaces` (projects.py:129, **status 201**) → `project_service.create_workspace` → 감사 `workspace.created` → `Location: /v1/workspaces/{id}`.
- 서비스: 이름 검증(2–128) + **역할 권한 검사**(`canRequest`; 이 프로젝트 역할이 생성 가능한지) 후 레코드 생성. 도크스트링: *"It starts `provisioning`, never `ready`. Nothing has prepared storage for it yet."*

## ② 계약 결속 — 요청은 묶임, 응답은 안 묶임
- **요청 O**: `WorkspaceCreateRequest`(Strict, `extra=forbid`) = `name`(2–128)뿐.
- **응답 X**: POST 라우트에 **`response_model` 없음**(같은 파일의 GET `list_workspaces`는 `response_model=ProjectWorkspacesResponse`로 묶임과 대비). 반환은 서비스 dict를 그대로.
- **그러나 반환 dict가 기존 스키마와 정확히 일치**: `create_workspace`의 `workspace_body`는 `workspaceId·projectId·name·status·nodeId·toolName·createdAt·allowedNext` — **기존 `WorkspaceSummaryResponse`(GET 목록이 쓰는)와 필드·alias 동일**. → **새 스키마 불필요.** 응답 결속 = POST에 `response_model=schemas.WorkspaceSummaryResponse` 한 줄 + 공유 fixture + provider/Ajv 시험. (지금 안 만듦 — 명세만.)

## ③ 생성이 흉내 낼 수 있는 것과 없는 것의 경계
- **생성 자체 = 레코드 삽입(provisioning)**: 화면이 POST를 부르면 **진짜 workspaceId·진짜 createdAt·status=provisioning**을 받는다. 이건 흉내가 아니라 실물이다.
- **자원 할당/체크아웃 = 별도 커널 prepare 단계**(이미 계약 결속됨): `POST /v1/projects/{project}/runs/{run_id}/start/prepare`→`WorkspacePrepareResult`(core.schema.json 결속), `resume/prepare`, 그리고 checkouts(git/files)→`WorkspaceEditView`. 즉 provisioning→ready로 가는 실제 준비는 커널이 한다.
- **경계**: 화면은 **생성(provisioning)은 실물로 부를 수 있으나 "ready"를 만들 수 없다.** ready는 prepare 흐름의 결과다. 지금처럼 가짜 ready workspace를 합성하면, **백엔드에 레코드가 없어** 이후 execution-readiness·prepare·checkout이 전부 대상 없음으로 깨진다.

## ④ 현재 화면 동작 (Gemini 소관 — 확인만)
- `App.tsx:404-411`의 `onCreate`: `id: `wsp_${Date.now().toString(36)}``(클라이언트 합성), `createdAt: new Date().toISOString()`(가짜), `setWorkspaces((prev)=>[created,...prev])`(로컬만). **`apiClient` POST 호출 없음.** → 백엔드에 레코드 0. 새로고침하면 사라지고, 그 ID로 어떤 후속 작업도 실패.

## 무엇이 필요한가 (지금 만들지 않음)
1. **[Gemini] 화면 배선**: `WorkspaceCreateModal.onCreate` → `apiClient(POST /v1/projects/{projectId}/workspaces, {name})`. 반환 실물(workspaceId·status=`provisioning`·createdAt)을 목록에 넣고 **합성 id/가짜 createdAt 제거**. UI는 **provisioning 상태를 그대로 표기**(ready로 표시 금지). node/tool 선택은 생성 요청 스키마에 없으므로(요청은 `name`만) 생성 후 `PUT /workspaces/{id}/tool` 등 별도 단계.
2. **[Claude/백엔드, 작음] 생성 응답 계약 결속**: POST에 `response_model=schemas.WorkspaceSummaryResponse` + 공유 fixture + provider/Ajv 양방향 시험. 새 스키마 불필요(기존 재사용). — **명세만, 사용자 지시 시 착수.**
3. **결정 불요 항목**: 생성 기능·요청 스키마·권한 검사·provisioning 시작·prepare 커널 계약은 이미 존재. 갭은 (1) 배선과 (2) 응답 결속 둘뿐.
