# S05 legacy 20동시 도착 timeline·큐 깊이 실측

## 결론

개발 PC·합성 measured Node 1개의 legacy/`placementShortCommit=false`에서 20개 요청을 0.793ms 안에 동시 진입시켰다. 20/20 성공, timeout 0, 요청 P95 2142.809ms, project+limits acquire client elapsed P95 1588.193ms, post-acquire hold P95 151.225ms였다. 이 값은 5노드 AC-05 판정이 아니며 S05-DB는 `review`, candidate flag는 off를 유지한다.

5ms 간격 `pg_stat_activity`/`pg_blocking_pids` 98개 표본에서 active backend 최대 20, Lock waiter 최대 19, project-lock waiter 최대 19, blocking chain depth 최대 1을 관측했다. Lock 표본 801개는 모두 parameter-free `project-lock` class였고 첫/마지막 표본 offset은 515.384/2136.576ms였다. 즉 한 시점에 19개 waiter가 현재 holder를 직접 기다리는 depth-1 fan-in이었으며 카드 20의 인공 depth≥3 holder chain과 같은 모양은 아니었다.

그럼에도 `lock_timeout=500ms`에서 `55P03`은 0건이었다. 이 wave의 server log를 읽지 않았고 `log_lock_waits=off`, `deadlock_timeout=1s`였으므로 원인을 확정하지 않는다. 현재 좁혀진 가설은 holder가 교체될 때 waiter의 실제 lock-wait 구간도 바뀌어 `lock_timeout`이 구간마다 다시 시작되고, 누적 client elapsed는 500ms를 넘더라도 어느 한 구간은 500ms를 넘지 않았다는 것이다. 검증은 `log_lock_waits=on`과 server log 상관을 갖춘 별도 승인 카드로 제안하며 이번 카드에서 재실행하지 않았다.

## 하네스 변경

- `run_round` barrier release를 공통 clock origin으로 삼아 요청별 arrival/completion offset을 보존한다.
- opt-in `--queue-diagnostic`은 runtime role의 같은 disposable DB만 5ms 표본화한다. raw PID는 `backend-N`으로 치환하고 SQL 원문·parameter를 저장하지 않으며 statement class, state, wait event, blocker alias, chain depth만 남긴다.
- report schema 1.6에 `requestTimeline`, `queueObservation`, `measurementLimitations`를 additive로 추가했다. 공개 API·ProblemDetails·계약·migration은 변경하지 않았다.
- observer는 `log_lock_waits`/`deadlock_timeout` 설정만 기록하며 server log를 읽었다고 주장하지 않는다.

## O1/O2/O3 경계

- O1: 카드 20 probe는 lock timeout이 lock 대기 구간마다 적용될 수 있음을 보였고, Card19은 실제 legacy wave가 max waiter 19·graph depth 1임을 보였다. 정확한 55P03 부재 원인은 `log_lock_waits=on` 상관 전까지 미확정이다.
- O2: caller-owned outer transaction의 `BoundDatabase` stale attempt 1은 savepoint rollback 뒤 phase가 overwrite돼 finalizer metric에 post-acquire hold가 남지 않는다. 이번 benchmark는 attempt별 독립 transaction이라 이 경로를 측정하지 않았다.
- O3: 운영 `app.py`는 `placement_metric_sink`를 주입하지 않고 logger fallback은 candidate flag on에서만 활성화된다. 따라서 기본 legacy 운영 metric sink는 없으며 이번 수치는 benchmark 주입 sink의 evidence다.
