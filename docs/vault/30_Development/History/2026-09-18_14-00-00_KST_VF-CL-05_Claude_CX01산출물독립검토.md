## #4 95c605f image-tests.json 분류 — FINDING (심각도 Medium/P2)

**finding VF-CL-R-001**: image 시험 실패 분류가 진단을 은폐한 눈먼 근사치이며, 자기유발 test-harness 자원 누수를 "환경 문제"로 오분류하고, 보안 관련 image 단언을 사실상 미실행 상태로 남긴다.

실측 대조:
- image-tests.json: exitCode 1, 7 failed, 전부 `test_candidate_nonroot_configuration_and_workspace[*]` — `docker-daemon-io-timeout`(3) 또는 `docker-resource-cleanup-or-operation-failure`(4).
- 사용자 실측: daemon 건강(version 0.377s), 컨테이너 187개 중 활성 4·exited 176(170개 2026-09 시험 잔재), 회수 가능 ~9.7GB, MemTotal 8.23GB.

분석:
1. **서버 이미지 제품 결함은 아니다(제외 타당)** — 실패는 docker create/start/inspect 연산 수준에서 나고, 제품에 도달한 곳에서는 실제 단언(nonroot uid 65532·auth 401/403·workspace)이 수행된다. 7 실패는 이미지 결함의 증거가 아니다.
2. **그러나 "daemon-io-timeout"은 눈먼 라벨이다** — `docker()` 헬퍼가 `timeout=90` + `assert returncode==0`이며 실패 시 **"diagnostics suppressed"로 docker 오류를 버린다**. 분류기는 timeout이 daemon/자원/제품 중 무엇인지 볼 수 없어 추측했다. 사용자의 out-of-band 실측(daemon 건강, 170 누수, 9.7GB/8.23GB)이 은폐된 진단을 대신 제공하며 원인이 **스위트 자신의 누적 잔재로 인한 호스트 자원 고갈**임을 가리킨다. daemon은 느린 게 아니라, 스위트가 자원을 소진시켰다.
3. **누수는 자기강화·무한이다** — 시험의 `finally`가 정리를 시도하나 **같은 raising 헬퍼**(`assert docker("inspect"...)==name` 후 `rm -f`)를 쓴다. 실패를 부른 바로 그 압박 하에서 inspect/rm이 timeout·assert로 raise → `rm`이 실행되기 전에 finally가 중단 → 그 run의 컨테이너/볼륨도 누수. `ai.saintvision.test` 라벨 잔재의 **사전 prune이 없어** 이전/크래시 run의 잔재가 무한 누적(수주간 170개).
4. **결과: 보안 관련 단언이 미실행** — 이 시험은 nonroot(uid 65532)·auth 경계·workspace 지속을 검증한다. 8케이스 중 7이 완료 실패 → 이 속성들은 **실제로 검증되지 않았다**. 이를 "unverified"가 아니라 "environment"로 기록하는 것이 안티패턴이다("돌지 못함"을 결함 없음으로 읽음).

**심각도 Medium/P2**: 출하 제품 회귀를 덮지는 않으나, (a) 보안 관련 image 시험이 사실상 미실행이며 환경으로 오라벨, (b) 누수가 호스트를 능동적으로 degrade하고 무한(이미 9.7GB/8.23GB 압박), (c) 진단을 설계상 은폐해 artifact만으로는 분류가 반증 불가. P1 아님(제품 결함·데이터 손실 없음), P3 아님(보안 검사 미실행·능동적 degrade).

**권고(test_server_container owner=Codex/dev-environment)**:
- 스위트 전 `label=ai.saintvision.test` 잔재(컨테이너+볼륨) 사전 prune.
- 정리를 best-effort로: finally는 raising 헬퍼의 assert-then-rm 대신 오류 무시 강제 제거(한 정리 실패가 나머지를 건너뛰지 않게).
- docker 실패 시 **진단 은폐 중단** — stderr 보존해 timeout을 daemon/자원/제품으로 구분 가능하게(그래야 이 분류가 반증 가능).
