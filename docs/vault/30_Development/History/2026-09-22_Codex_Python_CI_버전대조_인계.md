## 확인 결과

| 워크플로 | Python 설정 | 판정 |
|---|---|---|
| `backend.yml` | `['3.12', '3.14']` 매트릭스 | 두 버전에서 backend를 실행하도록 의도됨 |
| `core.yml` | `3.12` | 3.12 호환성 레인 |
| `desktop-browser.yml` | `3.12` | 브라우저 HTTP 레인의 Python |
| `docs.yml` | `3.12` | 문서·계약·온톨로지 검사 레인 |
| `frontend.yml` | Python 없음, Node 22 | Python 버전 대조 대상 아님 |

따라서 “다섯 워크플로가 모두 같은 Python을 쓴다”는 상태가 아니다. Python을 쓰는 네 워크플로 중 backend는 3.12와 3.14를 모두 실행하고, core/desktop-browser/docs는 3.12만 실행한다.

저장소의 `pyproject.toml`은 `requires-python = ">=3.11"`로 선언되어 있다. 현재 코드와 의존성 선언에서 3.14 전용 문법을 사용한다는 근거는 확인하지 못했다. 새 PC 절차서는 개발 환경을 Python 3.14.6으로 고정하고 있다.

## 왜 다른가

`backend.yml` 주석은 3.12에서만 실패하고 3.14 개발 환경에서는 통과한 과거 사례를 근거로 두 버전을 함께 돌린다고 설명한다. 이 주석이 현재 의도를 가장 직접적으로 보여준다. 다만 이 세션에서 hosted CI 실행 결과 자체를 읽지는 못했으므로, 주석의 과거 실행을 독립 실측으로 승격하지 않는다.

현재 증거만으로는 3.12가 우연히 남은 값이라고 볼 수 없다. 프로젝트가 `>=3.11`을 지원 범위로 선언하고, CI가 3.12를 호환성 하한 레인으로 유지하며, backend만 3.14까지 함께 확인하는 구조다. 반대로 이 PC에서 만든 PostgreSQL·통합 증거가 3.14.6에서 실행됐다는 사실은 3.12에서 같은 증거가 성립한다는 보장이 아니다.

## 판단 및 권고

1. **첫 hosted CI 실행 전에는 워크플로를 바꾸지 않는다.** backend의 3.12/3.14 매트릭스를 유지하고, core/desktop-browser/docs의 3.12 실행을 그대로 둔다.
2. **새 PC의 주 개발 Python은 절차서대로 3.14.6을 사용한다.** 이 PC의 실행 증거와 개발 도구 체계가 3.14.6에 맞춰져 있으므로 개발 환경을 임의로 3.12로 내리지 않는다.
3. **첫 CI의 3.12 결과를 별도 호환성 증거로 취급한다.** 3.12가 실패하고 3.14가 통과하면 의존성·코드 호환성 문제를 먼저 고치거나, 지원 범위를 바꾸는 별도 결정을 해야 한다. 그 전에는 CI를 3.14로 올리거나 3.12를 제거하지 않는다.
4. **절차서에는 두 층을 구분해 기록해야 한다.** 새 PC의 기본 개발 버전은 3.14.6이고, CI는 3.12 호환성 및 3.14 backend 매트릭스를 검증한다. 로컬 3.14.6 통과를 CI 3.12 통과로 표시하지 않는다.

이 판단은 CI 버전 변경이나 새 PC 절차서 수정이 아니다. 절차서 소유자인 Claude가 위 결과를 반영할 수 있도록 전달하는 인계 기록이다.

## 확인 범위와 한계

- **소스 읽기로 확인:** 다섯 워크플로의 Python 설정, `requires-python`, 절차서의 3.14.6 고정.
- **로컬 실행으로 확인:** 이 PC의 절대 경로 인터프리터가 Python 3.14.6임.
- **아직 확인하지 못함:** hosted CI에서 실제 3.12/3.14 job이 완료되는지, 3.12에서 PostgreSQL·브라우저·문서 전체 증거가 통과하는지.
- 따라서 이번 기록은 “버전을 맞췄다”는 완료 보고가 아니라, 첫 CI 실행 전에 유지할 기준과 확인할 호환성 경계를 기록한다.
