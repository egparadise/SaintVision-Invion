# MJS 우선순위 1 음성 경로 및 증거 범위 감사

## 범위

대상은 `tools/verify_two_pc_distributed_execution.mjs`, `tools/reconcile_receipts_evidence.mjs`, `tools/reproduce_handoff_review.mjs`다. 목적은 음성 대조가 실제 rejection/helper 경로를 호출하는지, 다른 run/node/digest 입력이 원본 검사 경로를 통과하는지, manifest canonical serialization과 HTTP/API·UI·실장비 범위가 분리되는지를 확인하는 것이다. Gemini CLI 인증 부재로 Gemini 독립 실행은 수행하지 않았다.

## 판정

### 1. verify_two_pc_distributed_execution.mjs

일부 음성 경로는 실제 API rejection을 호출한다. observation-only node dispatch는 실제 `POST /v1/projects/{project}/runs`를 보내고 HTTP 400과 `VAL-NODE-OBSERVATION-ONLY`를 확인한다. 최대 시도 초과 resume도 실제 `/resume/prepare` 호출에서 HTTP 400과 `VAL-MAX-ATTEMPTS-EXCEEDED`를 확인한다. 이 두 건은 원본 서버 경로에 도달한 대조다.

반면 receipt identity/digest 음성 대조는 서버 rejection을 호출하지 않는다. `syntheticMismatchedReceipt`를 메모리에서 만들고 `runId !== runId`, `nodeId !== nodeId`, `isValidSha256Digest(...)`를 로컬로 평가할 뿐이다. 따라서 다른 run/node/digest가 실제 receipt 조회·dispatch·admission 경로에서 거부됐다는 증거가 아니다. 입력을 바꿔도 이 로컬 비교식은 거의 항상 통과한다. 이를 실제 장비 또는 API rejection 인수로 표시하지 않는다.

### 2. reconcile_receipts_evidence.mjs

`sha256:not-a-digest` 음성 대조와 modified working copy 대조는 모두 로컬 정규식·해시 계산이다. malformed inputHash를 API에 보내거나 frozen manifest를 서버가 거부하는 경로를 호출하지 않는다. receipt contrast도 서버가 반환한 고정 record의 `verified:false`를 읽는 것이며, 변조된 receipt를 제출해 거부받는 시험이 아니다.

canonical manifest 계산은 `frozenFiles`를 Python `json.dumps(..., sort_keys=True)` 모양의 문자열로 재구성해 inputHash와 비교한다. 실제 응답의 목록 순서·공백·escape·Unicode·중복 키 edge를 생성해 서버/클라이언트 양쪽 계약을 대조한 것은 아니다. 현재는 HTTP API 응답 필드와 클라이언트 재계산의 일치만 증명한다.

### 3. reproduce_handoff_review.mjs

TypeScript 모듈을 메모리에서 transpile해 Release/Recovery/Deployment helper를 호출한다. browser, HTTP, TLS, dispatch identity, artifact bytes, physical node traffic은 호출하지 않는다. `futureEpochAccepted`, `futureSequenceAccepted`, rollback과 signoff 결과를 JSON 필드로 기록하지만, 각 결과를 rejection gate의 음성 대조로 assert하거나 nonzero로 실패시키지 않는다. 따라서 이 도구는 helper snapshot/계산 결과이며 운영 인수나 실제 rejection 증거가 아니다.

## 범위 구분

- 소스에서 확인됨: 관찰 전용 dispatch와 max-attempt resume가 API 요청을 보내고 특정 400/code를 기대하도록 작성된 점, 로컬 digest/manifest 계산 경로, Node 문법. 이 감사에서 해당 두 HTTP 응답을 live backend로 받아 확인한 것은 아니다.
- 미확인: 변조 run/node/digest를 실제 API·receipt admission·dispatch identity 경로에 주입한 거부, canonical serialization edge의 양방향 서버 대조, browser/UI 관측, 실제 장비·트래픽·TLS.
- 환경 미실행: 고정 backend의 HTTP suite는 이 감사에서 재실행하지 않았다. 실행 환경이 없을 때 이를 PASS로 세지 않는다.

## 다음 조건

실제 음성 대조를 완료하려면 소유한 격리 backend fixture 또는 disposable PostgreSQL/API가 필요하다. 각 case는 (1) 요청/fixture가 원본 route에 도달했음을 marker 또는 HTTP trace로 확인하고, (2) 기대 status/code를 확인하며, (3) 미도달이면 PASS가 아니라 명시적 inconclusive/skip으로 남겨야 한다. runId, nodeId, digest, manifest 순서·escape·Unicode·중복 edge를 각각 분리하고, HTTP API 증거·UI 표시·물리 장비 인수를 별도 결과로 기록한다.

Node syntax check:
`node --check tools/verify_two_pc_distributed_execution.mjs`,
`node --check tools/reconcile_receipts_evidence.mjs`,
`node --check tools/reproduce_handoff_review.mjs` → exit 0.

## 감사 재검증 — live API와 helper 실행 분리

이 문서의 초기 “actual API rejection 경로” 표현은 소스가 요청과 예상 상태를 구현한다는 뜻으로 한정한다. 당시 고정 backend를 재실행하지 않았고, 확인 가능한 backend가 없었으므로 live 400/404 응답은 관측되지 않았다. 서버 rejection은 여전히 UNVERIFIED다.

2026-09-19 Codex 감사자는 Node v24.17.0으로 세 파일의 `node --check`를 다시 실행해 모두 exit 0을 받았다. 또한 `node tools/reproduce_handoff_review.mjs <absolute-repo-root> <absolute-repo-root>/apps/web/node_modules/typescript/lib/typescript.js --output <.work-json>` 실행은 exit 0, `--self-test` 실행은 의도적 불일치를 기록하고 exit 1이었다. 이는 helper 계산과 자체 실패 경로의 실행 증거일 뿐 browser/API/장비 검증이 아니다. 실행자는 Codex(이번 재검증)이며, 이전 normal/self-test 독립 재현은 사용자 보고로 별도 취급한다.

## 후속 수정

`verify_two_pc_distributed_execution.mjs`의 상수 비교형 `strictly rejected` 세 단언을 제거했다. 존재하지 않는 run의 receipt 조회를 동일 backend의 `/v1/runs/{id}/receipts`에 실제 요청하고 HTTP 404일 때만 PASS로 세며, fetch가 backend에 도달하지 못하면 `[UNVERIFIED]`로 남긴다. nodeId 불일치와 malformed digest는 제출 endpoint를 호출하지 않으므로 PASS에서 제외하고 `[UNVERIFIED]`로 표시한다. 미검증 수는 최종 PASS 분모에 포함하지 않지만 요약에 명시한다.

## reproduce_handoff_review 판정 경계 보강

`tools/reproduce_handoff_review.mjs`는 이제 helper 계산 결과를 기대값과 비교한다. 미래 epoch/sequence token은 거부(`false`), 인증 없는 sign-off는 거부, manifest digest 형식과 SPA index fallback은 참, in-memory rollback 선택은 성공이어야 하며 어긋나면 exit 1이다. SLO·접근성·rollback 운영 인수·node traffic·training·색상 대비는 helper/로컬 계산만으로는 인수할 수 없어 `UNVERIFIED`로 기록하고 PASS 분모에 넣지 않는다. 출력과 `frontend.json`의 `scope`는 browser/API/TLS/배포/장비 인수가 아님을 명시한다.

자기 검증: 정상 실행은 `NORMAL_RC=0`, `--self-test`로 의도적 기대값 불일치를 주입하면 `FAIL SELF-TEST intentional mismatch`와 `SELF_TEST_RC=1`이 발생했다. 따라서 판정 경로가 실제로 nonzero를 낼 수 있음을 확인했다.

## reproduce_handoff_review 호출 계약

호출 형식은 다음과 같다.

`node tools/reproduce_handoff_review.mjs <folder> <typescript-module> [--output <path>] [--self-test]`

`<folder>`와 `<typescript-module>`가 빠지거나 알 수 없는 옵션이면 사용법 오류를 사람이 읽을 수 있게 출력하고 exit 2를 반환한다. 기본 결과 파일은 루트의 추적되지 않은 파일이 아니라 `<folder>/.work/reproduce-handoff/frontend.json`이며 `--output`으로 별도 경로를 지정할 수 있다. 판정 실패는 exit 1, 정상 helper 판정은 exit 0이다. `--self-test`는 의도적 불일치를 주입하므로 exit 1이어야 한다.

`reconcile_receipts_evidence.mjs`도 malformed hash·modified working copy·manifest 순서/공백/escape·Unicode·중복-key 로컬 대조를 실제 API 거부로 세지 않는다. 존재하지 않는 run receipt 조회만 backend에 도달해 HTTP 404일 때 rejection PASS가 되며, 연결 실패는 `UNVERIFIED`다. 나머지는 이유와 함께 PASS 분모에서 제외한다.
