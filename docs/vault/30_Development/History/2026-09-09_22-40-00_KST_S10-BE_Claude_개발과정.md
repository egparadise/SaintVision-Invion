## 실제 Provider SDK 코드를 쓰지 않은 이유

`skills/claude-api`를 지침대로 먼저 읽었고, 그 결과 **지금 특정 Provider SDK를 넣지 않는 것이 맞다**고 판단했다.

1. **의존성 lock은 S01-BE 소유다.** [[Backend 최종 개발 계획]]은 "버전은 S01 호환성 검증 후 lock한다"고 정한다. 한쪽 벤더 SDK를 지금 넣으면 그 결정을 앞질러 가고, 계약이 먼저 들어온 쪽으로 기운다.
2. **자격증명 주입 방식이 미결이다.** [[Storage 최종 개발 계획]]은 "비밀은 credential provider 참조를 통해 주입한다"고 정했는데 그 provider가 S01 결정이다. 환경변수에서 API 키를 읽는 adapter는 명세와 **다른 보안 모델**이다.
3. AC-10은 "Codex/Claude **계약 동일**"이다. 계약이 실제 객체이고 그 뒤에 conformance 스위트가 있어야 검사 가능한 명제가 된다. 계약층은 본질적으로 provider 중립이다.

어떤 두 Provider인지, transport가 무엇인지는 `unknown`으로 남겼다.

## 설계에서 실질적으로 얻은 것 — 취소 의미론

`cancel()`은 **boolean이 아니라 3-상태**를 반환한다: `stopped` / `already_finished` / `not_supported` / `unknown`.

스트리밍 HTTP 연결을 클라이언트가 닫아도 서버는 생성을 계속하고 과금도 계속할 수 있으며, 서버측 취소를 아예 제공하지 않는 provider도 있다. 취소했다고 보고했는데 provider가 계속 돌았다면 **Run 기록이 틀리고 청구서가 놀랍게 된다.**

`unknown`은 진짜 결과이고, 이것이 orchestrator의 자동 재시도를 막는다. [[Backend 최종 개발 계획]]의 "외부 부수 효과 확인 불가 시 자동 재시도하지 않는다"가 여기서 강제된다.

## conformance 스위트가 판별력을 갖게 만든 방법

**모두를 통과시키는 스위트는 아무것도 증명하지 못한다.** 그래서 `tests/test_adapters.py`의 절반은 adapter가 아니라 **스위트를 시험한다.** 일부러 한 군데씩 고장 낸 adapter 12개가 각각 자기 결함에 해당하는 검사에서만 실패해야 한다:

- redaction을 건너뛰는 adapter → `redact_removes_known_secrets`, `collect_returns_redacted_content` 실패
- boolean을 반환하는 cancel → `cancel_returns_a_tri_state` 실패
- 이미 끝난 요청을 "멈췄다"고 하는 cancel → `cancel_after_completion_is_not_stopped` 실패
- 아무것도 검증하지 않고 `VERIFIED`라고 하는 attest → `attest_does_not_overclaim` 실패
- 자격증명 참조를 그대로 돌려주는 authenticate → `authenticate_takes_a_reference` 실패
- 선언만 하고 구현하지 않은 capability → 해당 capability 검사 실패
- 예외를 던지는 adapter → **실패로 기록되고 나머지 검사는 계속 실행된다**

반대로 `UNVERIFIABLE`을 정직하게 반환하는 adapter는 **통과한다.** 검증할 수 없다고 말하는 것은 진짜 답이고, 거짓으로 `VERIFIED`라고 하는 것만 실패다. **실패할 수 없는 attestation은 attestation이 아니다.**

스위트가 보상하지 않는 것 둘:

- **과대 선언**: 선언한 capability는 전부 실행해 본다.
- **조용한 협소함**: `skipped`를 `passed`와 별도로 센다. 좁은 adapter가 넓은 adapter처럼 보이지 않는다.

`compare_reports`는 한 걸음 더 간다. 두 adapter가 각자 통과해도 **서로 다른 검사를 돌렸을 수 있고**, 그 차이가 바로 상호운용이 깨지는 지점이다. 평균 내지 않고 그대로 보고한다.
