# S05-DB placement benchmark 교정 — 3·10동시 실측과 50동시 미측정 경계

> [!danger] 2026-09-22 23:04 KST 교정
> 이 문서 v1.0.0의 “50동시에서 `RES-0003`·78.15초/61.69초를 실측했다”는 표현은 철회한다. exact landing `3f0fab3d`를 검토한 Claude가 F-R1/F-R2를 발견했고, 해당 수치는 착지본으로 재현되지 않으며 출처 SHA도 고정되지 않았다. 아래의 3·10동시 결과만 유효한 실측이다. **50동시는 실행하지 않았고 결과를 추정하지 않는다.**

## 1. 독립 검토에서 발견된 하네스 결함

Claude 독립 검토 [PR #71](https://github.com/egparadise/SaintVision-Invion/pull/71)은 다음을 확인했다.

- **F-R1:** 합성 snapshot이 `NodeResourceSnapshot` required 13필드 중 capacity 4필드만 담아 `additionalProperties=false` 계약 검증에서 `VAL-0002`가 났다. exact `3f0fab3d`의 3동시 실행은 reserve의 placement 잠금 경로에 도달하지 못했다.
- **F-R2:** 첫 라운드 뒤 `summarize()` 호출에 필수 keyword `active_after_first`가 없어 TypeError가 발생했다. 이 파일은 hosted Backend가 수집하므로 integration을 red로 만들 수 있었다.
- **F-R3:** 하나의 고정 snapshot은 운영 Node의 주기 heartbeat/resource observation 갱신과 다르다. 이 adapter의 결과는 고정 관측을 쓰는 stress 조건이지 운영 heartbeat 모델의 직접 측정이 아니다.
- **F-R4:** v1.0.0의 78.15초/61.69초 `RES-0003` 값은 exact landing으로 재현할 수 없고 실행 source SHA가 없다. 따라서 증거에서 제외한다.

코드상 위험 경로는 남는다. `placement.py`는 project row를 `FOR NO KEY UPDATE`로 잠근 뒤 현재 시각을 읽고, scheduler는 snapshot freshness 15초를 검사해 유효 후보가 없으면 `RES-0003`을 낸다. 다만 이 인과가 **50동시에서 실제 발생했다는 측정은 아직 없다.**

## 2. F-R1/F-R2 교정과 착지

R1 commit `7569c4189586f8e91c369f5ecdc9827c901c07b9`는 최신 integration `63d2e7c6` 위에 다음 1파일만 fast-forward로 착지했다(force 없음).

- snapshot에 `nonce`, tenant/node/epoch, profile/observedAt/sample, capacity, OS/agent 13필드를 모두 넣고 fixture 생성 시 `validate_contract("NodeResourceSnapshot", snapshot)`로 검증한다.
- `summarize(..., active_after_first=active_after_rounds[0])`를 전달해 report/JUnit 단계까지 도달시킨다.

착지 전 `tests/test_placement_benchmark_tool.py` 3 passed, Python compile, `git diff --check`가 모두 exit 0이었고, 3동시 교정 실측이 report 생성까지 통과했다.

## 3. 유효한 실 PG 소규모 측정

조건은 PostgreSQL 16.15, 매 실행 자체 생성·migration·정리되는 disposable DB, **개발 PC 1대의 1개 합성 measured-node**, 고정 resource snapshot이다. 각 실행은 같은 초기 용량의 두 라운드를 수행하고, 성공 뒤 idempotent replay와 release/활성량 0 복귀를 확인한다. 물리 Node 5대가 아니며 `acceptanceClaim=false`, `fiveNodeAC05=not_evaluated`다.

| 동시 요청 | source | 라운드 결과 | worst successful P95 | 불변식 | 판정 |
|---|---|---|---:|---|---|
| 3 | F-R1/F-R2 수정 working tree, 이후 동일 diff가 `7569c418`로 착지 | 3/3 성공 × 2, 오류 0 | **861.651ms** | Explain/snapshot 결정성, replay 안정성, fencing 유일성, no-overbooking 모두 true | 유효한 개발 PC 예비 측정. 당시 report의 HEAD-only `codeSHA=3f0fab3d`는 dirty source를 표현하지 못하므로 source는 landed correction SHA로 보정 기록 |
| 10 | **`7569c418`**를 report `codeSHA`로 고정 | 10/10 성공 × 2, 오류 0 | **1,738.762ms** | 동일 4종 모두 true | 유효한 개발 PC 예비 측정, pytest 1 passed / exit 0 / 20.13초 |
| 50 | 실행하지 않음 | 미측정 | 미산출 | 미측정 | 코디네이터 지시대로 설계 결정 전 재실행 금지 |

두 유효 실행 뒤 admin catalogue에서 `inv_backend_test_%`/`inv_test_%` disposable database 잔존 **0개**를 확인했다. `.work` JSON/JUnit에는 자격증명을 기록하지 않았다.

## 4. F-S05-01의 정직한 현재 상태

F-S05-01은 **측정된 50동시 실패가 아니라 코드상 위험 가설**이다.

- 측정됨: 개발 PC 1대·합성 Node에서 3동시 P95 861.651ms, 10동시 P95 1,738.762ms, 각 2라운드 전부 성공, 불변식 4종 true.
- 해석: 10동시에서 AC-05의 2초 한도에 이미 근접했다. 50동시 직렬화 지연 위험의 근거는 강해졌지만 성공·실패·P95를 예측값으로 쓰지 않는다.
- 미측정: 11~50 동시 지연 분포, 최초 freshness 초과 순번, 50동시 성공/실패/P95, 물리 5노드 결정성.
- 코드상 가능성: project 단위 직렬 구간이 15초를 넘으면 후순위 요청은 commit 전 freshness 재검사에서 `RES-0003`이 될 수 있다.
- 운영 차이: 실제 Node heartbeat/resource snapshot 갱신은 고정 snapshot stress adapter와 다르므로 5노드 adapter에서 현재 관측 흐름을 사용해야 한다.

따라서 S05-DB는 `review`를 유지하고 AC-05 통과·실패를 모두 주장하지 않는다. 설계 제안은 이 위험을 예방적으로 다루며 실측 결론을 전제하지 않는다.

## 5. 재실행과 다음 행동

개발 PC adapter 명령은 다음과 같지만, 코디네이터 결정 전 50동시는 실행하지 않는다.

`python tools/placement_benchmark.py --requests <N> --concurrency <N> --junit .work/s05-placement-benchmark.xml --report .work/s05-placement-benchmark.json`

이 명령은 여전히 1개 합성 measured-node를 만든다. DSN만 5노드 랩으로 바꿔도 물리 5노드 증거가 되지 않는다. 결정 뒤 실제 lab project/Node observation adapter를 연결하고 같은 JSON/JUnit schema로 50독립 요청을 측정해야 한다.
