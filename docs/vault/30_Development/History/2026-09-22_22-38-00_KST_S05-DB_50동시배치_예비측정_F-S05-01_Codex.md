# S05-DB 50동시 배치 예비 측정 — F-S05-01

## 범위와 판정 경계

`tools/placement_benchmark.py`와 `tests/integration/test_placement_benchmark.py`를 추가했다. disposable PostgreSQL에서 50개 planned Run을 먼저 준비하고, 하나의 고정된 measured snapshot을 취득한 뒤 50개 `PlacementStore.reserve`를 barrier로 동시에 시작한다. 요청별 잠금 대기를 포함한 지연, 성공/실패, 오류 코드, request index와 completion order, snapshot ID, node ID, fencing token, 실제 활성 예약량을 JSON과 JUnit으로 남긴다. 완전 성공한 경우에만 같은 초기 용량의 두 번째 라운드와 **snapshot ID를 포함한 전체 Explain**을 비교한다. snapshot ID를 제거하거나 freshness를 연장해 결과를 정상화하지 않는다.

이번 개발 PC 조건은 물리 Node가 아니라 **실 PostgreSQL + 1개 합성 measured-node 행**이다. 따라서 아래 값은 5노드 랩 전 예비 측정이며 AC-05 합격 판정이 아니다. 계약·migration·제품 API는 변경하지 않았다.

## 실제 실행과 실패 이력

| 시도 | 조건 | 실제 결과 | 메모리 | 보존 판단 |
|---|---|---|---|---|
| 1 | snapshot을 fixture 준비 초기에 생성, 50동시 첫 라운드 | `RES-0003 No eligible node`, `1 failed`, 전체 pytest 78.15초, P95 미산출 | 관측 process tree peak 34.8MB | 준비 시간이 15초 freshness를 소진한 하네스 오류. credential-bearing pytest 실패 로그/JUnit은 폐기 |
| 2 | 100개 Run 준비를 끝낸 뒤 snapshot/heartbeat를 바로 생성, 50동시 첫 라운드 | 다시 `RES-0003`, `1 failed`, 전체 pytest 61.69초, P95 미산출 | process tree peak 218MB | 동시 wave의 project-lock 대기 중 후순위가 15초 freshness를 넘긴 제품 성질. 같은 PG 서버에 별도 disposable DB의 경량 RLS 레인 1개가 동시에 존재 |

두 실행 모두 `Start-Process` 분리·폴링으로 수행했고 1.0GB 중단선 아래였다. 두 번째 실행 뒤 공유 PG 서버의 `inv_test_%` database가 0개임을 확인했다. 당시 runner는 `pool.map`이 첫 예외에서 중단되어 성공/실패 전체 분포와 최초 실패 순번을 남기지 못했다. 따라서 **N번째 이후 실패라고 추정하거나 P95 값을 만들지 않는다.** 이 결함을 고쳐 future run은 모든 Future를 끝까지 수집하고 JSON을 먼저 쓴 뒤 pytest를 실패시킨다. fixture 표현도 자격증명을 노출하지 않도록 redacted repr로 바꿨다.

## Finding F-S05-01

50개의 독립 placement 요청은 각자 `projects` row의 `FOR NO KEY UPDATE`를 거쳐 직렬화된다. 단일 고정 snapshot의 유효기간은 15초이므로, 동시 부하의 후순위 요청이 그 창을 넘으면 충분한 총 제공량이 있어도 `RES-0003`으로 탈락한다. 이는 AC-05의 50동시·P95 2초 요구와 직접 충돌할 가능성이 있으며, 이번 카드에서 성공이나 결정성을 주장할 수 없다.

결정 선택지는 다음과 같다.

1. **project-lock 입도 완화(우선 검토 제안):** ceiling과 membership 불변식을 보존하면서 프로젝트 전체 mutex를 자원/용량 단위로 좁힌다. 기존 N개 독립 요청 의미를 유지하지만 교착·초과 예약 변이 시험이 필요하다.
2. **배치 예약 API:** 50개를 한 트랜잭션/한 lock acquisition으로 예약한다. 처리량은 개선될 수 있으나 N개의 독립 placement 요청이라는 AC 의미와 공개 계약 변경 여부를 먼저 결정해야 한다.
3. **freshness 창 정책 변경:** 15초를 늘리거나 lock 대기 시작 시점의 snapshot을 동결한다. stale 자원 수용 위험과 Node 관측 계약을 바꾸므로 단순 성능 수정으로 처리할 수 없다.

Codex 제안은 1번의 잠금 입도 완화를 먼저 설계하고, 2번은 별도 batch semantics가 실제 요구일 때만 계약 변경으로 검토하며, 3번은 안전 기본값을 약화시키므로 마지막 선택지로 두는 것이다. 결정 전에는 실 PG 부하를 다시 실행하지 않는다. reviewer는 Claude, 결정자는 코디네이터다.

## 재실행과 5노드 경계

현재 개발 PC 재현 명령은 다음 한 줄이다.

`python tools/placement_benchmark.py --requests 50 --concurrency 50 --junit .work/s05-placement-benchmark.xml --report .work/s05-placement-benchmark.json`

명령은 `INV_TEST_ADMIN_DSN`의 PostgreSQL 16+ 서버에 자체 disposable DB를 만들고 정리한다. 현재 adapter는 그 DB에 1개 합성 measured-node 행을 만들므로, 이 명령의 DSN만 5노드 랩으로 바꿔도 물리 5노드 증거가 되지 않는다. 결정 뒤 실제 lab project/Node observation을 주입하는 adapter를 연결하고 **같은 CLI·JSON/JUnit schema**로 실행해야 한다. 물리 5노드용 명령을 완성했다고 기록하지 않는다.
