# 계약이 못 잡는 부류 — 모양은 맞지만 실체 없는 가짜 값

계약 결속으로 오늘 합성 여럿을 잡았다(무결성·복구·샤드건강·모델재검증·lineage). 그러나 **계약은 모양을 검사하지 실체를 검사하지 않는다** — 정본 계약에 정확히 맞는 가짜 값은 계약 시험을 그대로 통과한다. 대표: PTY 티켓 `commandId`가 하드코딩 자리표시자 UUID.

## 훑은 범위 (명시)
- 고정 SHA `b08b227`. 대상: `apps/web/src`(프런트 프로덕션, 테스트 제외) + `tools/` + `src/saintvision/`·`services/`(비-test 프로덕션). **테스트 fixture의 가짜 id는 정상이라 제외**(테스트는 가짜를 쓰는 게 맞다) — 관심은 **프로덕션/도구가 실 요청·실 동작에 가짜를 넣는 자리**.
- 3 기준: ① 하드코딩 식별자(UUID/ID/해시, 반복 1·0, example/dummy/placeholder/test/DEMO), ② 기본값으로 대체되는 필수값(없으면 못 하는데 기본값으로 조용히 진행), ③ 형식만 맞춘 값(스키마 문자열/UUID면 아무거나 통과, 실존 대조 없음).
- 각 값을 **어디로 가는지 추적**해 위험 분류: 표시로만=낮음, 서버 요청=높음, 인가/승인/테넌시 판단=최고.
- 실측/추정 구분: 값의 존재·전달 경로는 [측정], 백엔드가 그 가짜를 잡는지는 잡는 코드를 본 경우만 [측정], 아니면 [추정].

## 최고 등급 (인가/승인/테넌시 요청에 진입)
1. **PTY `commandId`** — `WebTerminal.tsx:16` 기본값 `11111111-1111-4111-8111-111111111111`, `TerminalSessionView.tsx:389` 동일 값 하드코딩, `App.tsx:504`는 안 넘겨 기본값 사용(+`workspaceId="wsp-saint-pilot"`·`sessionId="sid_terminal_01"`도 하드코딩). [측정] `body:{commandId}`로 `POST /v1/workspaces/{id}/terminal-tickets` 전송(기준 ①②③ 모두).
   - **무엇이 잡나**: [측정] 백엔드 `terminal.py _current`가 command_id를 `inv.commands⋈execution_deliveries⋈approval_dispatches`와 SQL 대조 → 자리표시자는 실 command와 안 맞아 **티켓 발급 실패(fail-closed)**. **계약은 못 잡음**(UUID 형식 유효). ⇒ 보안 구멍 아님, 그러나 **PTY가 항상 가짜를 보내 실제로 동작 안 함**을 계약 통과가 가림. **다음 할 일**: 프런트가 실 commandId(활성 attempt의 command)를 배선.
2. **discovery 안내 `tenantId`** — `ResourceExplorer.tsx:420`이 `'00000000-0000-0000-0000-000000000001'`을 `broadcastAnnouncement(data, tenantId)`에 전달 → [측정] `X-Inv-Tenant` **헤더**로 `POST /v1/discovery/announcements`(노드를 테넌트로 발견 등록, "안내 방송 승인됨" 표시). **테넌시=격리 경계라 최고 등급.**
   - **무엇이 잡나**: [추정] 엔드포인트가 saintvision 레이어(inv/app.py에 없음=discovery는 Codex 도메인)라 헤더 테넌트를 인증 principal과 **대조하는지 미확인**. 대조하면 fail-closed, 안 하면 테넌시 혼동 위험. **다음 할 일(Codex 도메인)**: saintvision discovery 핸들러의 `X-Inv-Tenant` vs principal 대조 확인; 프런트는 세션 테넌트를 넘기게.

## 결론 — 무엇이 이 부류를 잡나 (다음 할 일 규정)
- **계약 시험: 절대 못 잡음**(모양 유효). 이 부류의 정의.
- **백엔드 런타임 상태 검증**(DB 조회·테넌시·인가): PTY commandId(fail-closed 확인)·projected fallback(추정 fail-closed)를 잡음 — **안전하나 기능이 조용히 깨짐**(가짜라 항상 거부). tenantId는 saintvision enforcement 미확인(Codex).
- **아무것도 안 잡는 자리 = 다음 우선 작업**: (가) 프런트가 실 식별자를 배선해야 하는 곳(PTY commandId·tenantId·projectId — 기능이 실제 동작하도록), (나) 클라이언트 합성 엔진(mlops/deployment/security)이 실 데이터처럼 표시하는 것(백엔드 관측 없으면 "데이터 없음"으로). (나)가 사용자 오인 위험 최고(합성).
