# S05 P1/P2 대칭 hold 계측과 SQL timeout statement 특정

## 결론

Claude 카드 19의 F-C1을 수용했다. 기존 legacy `lockHoldMs`는 project/limits 잠금 대기를 포함했지만 candidate는 limits 획득 뒤부터 측정해 1526.365→116.848ms 비교가 비대칭이었다. legacy phase mark를 limits 획득 뒤로 옮기고 그 전 project+limits 구간을 별도 `placement-legacy-lock-wait` metric으로 분리했다. 카드 16의 “hold 감소 통과”는 철회한다.

코디네이터는 결정 문서 v1.3의 **(b) legacy 유지·5노드 후 재판단**을 확정했다. `placementShortCommit` 기본값은 false, S05-DB는 `review`, 20동시 초과·50동시와 물리 5노드 승격은 없다.

## P1 코드와 report schema v1.5

- legacy: `projects ... FOR NO KEY UPDATE`와 `project_resource_limits ... FOR UPDATE` 앞에서 hold 없는 diagnostic phase를 시작한다. 두 statement가 끝나면 `placement-legacy-lock-wait` client elapsed를 기록하고 그 뒤 `placement-legacy-lock-scope` hold clock을 시작한다.
- candidate: limits `FOR UPDATE` 전에 hold 없는 `placement-limit-row-wait` diagnostic phase를 표시하고, 성공 뒤 기존 `placement-short-commit` hold clock을 시작한다.
- report schema 1.5는 `legacyLockWait`, `limitRowWait`, mode별 `lockAcquireWait`, post-acquire `lockHold`를 분리한다. acquire 값은 server wait_event 전용 시간이 아니라 **SQL 호출 전후 client wall clock**임을 `measurementMethod`와 `serverSideLockWaitSeparatelyMeasured=false`로 기록한다.
- SQL observer는 parameter 값을 버린 최대 500자 statement template, phase, success/error, SQLSTATE/error type, elapsed를 기록한다. benchmark는 오류 전부와 50ms 이상 성공 statement만 보존한다. 기존 role에 `ALTER ROLE log_min_duration_statement`를 남기는 부수 효과는 제거했다.

공개 HTTP/ProblemDetails/route, JSON Schema/generated type, migration, Lease·fencing·idempotency 계약은 바꾸지 않았다. report evidence schema만 additive 1.5로 올렸다.

## P2 실 PostgreSQL 20동시 × 각 1회

각 mode는 별도 disposable DB process에서 순차 실행했고, 시작·종료를 coordinator/status에 알렸다. 개발 PC·합성 measured Node 1개의 예비 측정이며 AC-05 판정이 아니다.

| 모드 | process exit | 성공/실패 | 요청 전체 P95 | post-acquire hold P95 | acquire client elapsed P95 | 오류 statement |
|---|---:|---:|---:|---:|---:|---|
| legacy / flag off | 0 | 20/0 | 1885.489ms | **289.365ms** | **1453.658ms** | 없음 |
| candidate / fail-fast | 1(evidence red) | 8/12 | 1054.907ms | **170.766ms**(성공 8개) | **528.705ms** | limits `FOR UPDATE`, `55P03` 12 |

candidate의 12개 실패는 모두 기존 `RES-0007`/503/retryable이며 SQL observer가 `SELECT * FROM inv.project_resource_limits WHERE project_id=%s FOR UPDATE`, phase `placement-limit-row-wait`, SQLSTATE `55P03`으로 특정했다. 두 mode의 fencing token은 유일했고 no-overbooking은 true였다. candidate exit 1은 이 실패를 숨기지 않는 benchmark 판정이다.

대칭 hold는 289.365→170.766ms 방향으로 줄었지만 candidate는 성공 survivor가 8개뿐이고 한 번만 실행했다. 따라서 hold 감소를 acceptance gate 통과로 승격하지 않는다. timeout 비증가 조건은 0→12로 명백히 실패한다.

## legacy 1454ms인데 55P03 0인 이유

코드상 mode별 `lock_timeout` 면제나 다른 설정 경로는 없다. 둘 다 같은 `Database.transaction`에서 `SET LOCAL lock_timeout='500ms'`와 `statement_timeout='2s'`를 적용한다. observer에서 legacy의 가장 느린 성공 event는 `projects ... FOR NO KEY UPDATE` 1492.238ms였고 candidate timeout은 limits `FOR UPDATE`였다.

다만 observer elapsed와 `placement-legacy-lock-wait`은 client wall clock이다. server가 lock을 획득한 뒤 Python thread가 다시 실행될 때까지의 scheduling/return delay도 포함하며 backend PID별 `pg_stat_activity.wait_event` timeline은 수집하지 않았다. 따라서 legacy가 같은 heavyweight lock을 1.45초 기다리면서 500ms 설정을 면제받았다고 결론 내릴 수 없다. 실제 server lock wait이 500ms 미만이었는지, client/CPU scheduling이 나머지를 만들었는지는 **미확정**이며 F-S05-02 경계를 유지한다.

이번 두 wave에는 `57014`가 0건이라 새 statement 귀속을 만들지 않는다. 과거 `57014`를 단순 project heavyweight-lock 대기로 부르지 않는다는 [[2026-09-23_01-05-00_KST_F-S05-02_57014_원인분리_Codex]] 결론도 유지한다.
