# MJS 빈집합 단언 수정과 상수 PASS finding

base03f1f7b, task VB-MJS-01, owner Codex(검증경계), reviewer Gemini(미검토), branch agent/codex/model-registry-binding. agent-delivery1.1.0/core-reliability1.0.0 적용. 사용자 빈배열 재현 수신 후 tools의 .mjs4파일 every 패턴 검색 및 해당5호출 의미 검토. 전체939행/다른 스크립트 전체 의미 검토는 아니다.

## VB-MJS-01 / P2 — 빈 shard 목록의 PASS / 수정 완료·독립검토 대기

tools/run_browser_smoke.mjs:489~490은 items=[]에서 두 every가 참이었다. 이번에 Array.isArray + length===2를 각 단언 자체에 결합했다. 바로 앞 children listing도 이 고정 run fixture의2개를 기대하므로 실제 배열 크기에서 기대값을 계산하지 않았다. null row는 false로 처리한다. 다른 필드의 유효성/암호학적 영수증 검증 범위를 새로 주장하지 않는다. outputHash string 검사는 기존 의미를 유지하며 이 변경이 실제 commitment 진위를 증명하지 않는다.

나머지 every3곳은 같은 파일의 node capacity/headroom 각 length===5와 GPU length===3 가드가 있다. 다른 .mjs3파일에는 every 호출0. 빈집합 every에 한정해 추가 무가드 후보는 없었다. 다른 loop/reduce·상수·fixture/fallback까지 안전하다는 뜻은 아니다.

## 실제 검증

Node v24.17.0, `node --test tests/browser_smoke_assertions.test.mjs` exit0,12passed/0failed/0skipped. 도구를 import하면 실제 네트워크 요청을 시작하므로 소스의 실제 두 assert 문장만 추출해 node:vm에서 실행했다. 복제한 수정 함수를 시험하지 않는다. 누락/null/빈배열/object/array-like/1개/3개/null row는 두 판정 false, 정상2개는 true, stop 거부와 hash 누락은 각각 해당 단언만 false. 수정 전 빈 every 표현의 true와 수정 후 false도 대조했다. `node --check tools/run_browser_smoke.mjs` exit0. standalone Node 시험이며 Python 기본 suite나 CI에 자동 포함됐다고 하지 않는다.

Evidence/verification-boundary-audit/mjs-shards.json에 범위/명령/소스hash/결과를 보존했다. 실제 backend/browser/full smoke를 실행하지 않았으므로 과거 특정200여 checks 실행에서 빈목록이 나왔다는 결론은 없다. 해당 두 단언이 PASS였다는 숫자만으로 shard 관측 존재를 보장할 수 없다는 한계를 기록한다. 과거 수치를 임의로 재계산하지 않는다.

## VB-MJS-02 / P2 — UI 상수 true 단언 / 미수정

같은 파일 :912~921의 windowManagerValid, keyboardA11ySupported, layoutPersistenceValid는 모두 const true이며 곧바로 assert에 전달된다. 각각 창관리, 키보드 조작, layout 저장을 검증했다고 출력하지만 실제 UI 관측값이 아니다. 실제 여섯 소스 문장만 node:vm에서 실행했고 DOM/browser/backend 없이 PASS3개를 관측했다. 이는 단언 경로가 실행되면 언제나 통과하는 코드 구조의 실증이다. 전체 live smoke에서 해당 문장에 도달했는지는 이번에 재실행하지 않았다.

수정 owner Gemini(UI 인수), reviewer Codex. 실제 브라우저 상호작용·DOM 상태·재로드 후 persistence 등을 관측해 실패 대조군을 갖추거나, 이 runner에서 미검증으로 표시하고 PASS 분자에서 제외해야 한다. 상수 false로 바꾸는 것도 실제 제품 결함 판정은 아니므로 부적절하다. 이번 빈 shard 수정에서 UI 검증을 만들어낸 것으로 처리하지 않고 별도 finding으로 남긴다. 기존200여 checks만으로 전체 UI 합격을 주장할 수 없다. 다른 browser 시험의 유효한 증거는 해당 범위대로 유지한다.
