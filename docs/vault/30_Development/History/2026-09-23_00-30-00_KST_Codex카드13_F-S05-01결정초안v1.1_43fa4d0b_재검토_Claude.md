## 0. 내 오류 정정 (먼저)

카드 15 §0에서 "`LockNotAvailable`/`55P03`를 DomainError로 매핑하는 코드가 없다(grep 0건) → 계약 변경 필요"라고 적었다. **틀렸다.** `inv/db.py:74~82`는 `psycopg.errors.LockNotAvailable`, `QueryCanceled`, `DeadlockDetected`를 **`RES-0007` / 503 / `retryable=True`** 로 매핑한다. 내 grep이 `db.py` 결과를 제외하도록 필터링했고(`grep -v db.py`), 그 파일의 15~70행만 읽어 74행 이후를 보지 않았다. 규칙 2(빈 결과는 사실 아님)·규칙 "답을 아는 자리에 대보라"를 내가 어겼다. Codex v1.1의 정정(§0 2항)은 정확하며 실 PG 주입 시험이 그것을 실측으로 고정했다. 카드 15의 나머지(500ms 상한이 15초보다 먼저·RES-0003 도달 불가·병목 위치 미계측·반례 7건)는 유지된다.

## 2. (3) 옵션 1이 statement_timeout 2s 아래에서 잠금 보유 시간을 실제로 줄이는가 — 코드 논리

현 `PlacementStore.reserve`가 **project lock(`placement.py:103`)을 잡은 뒤 commit까지** 수행하는 일:
- (a) `project_resource_limits FOR UPDATE`(`:107`) → (b) `project_nodes` pool 조회(`≤33`) → (c) pool 전체 `resources` 목록(`≤129`) → (d) `lock_resources`(pool 전체 node/resource FOR UPDATE) → (e) grant 재검사 → (f) **`project_capacity`** — pool 전체 자원에 대해 `coalesce((SELECT sum(l.amount) FROM inv.resource_leases …))` 상관 부질의 + 15초 창 조인(`capacity.py:10~22`) → (g) pool 전체 snapshot 행 조회 → (h) `now` → (i) `place()` 점수 계산(순수 Python) → (j) 선택 node의 allocation 계산(`active_total` × 자원 수) → (k) `_reserve_locked`(project·limits·resources 재잠금, ceiling sum, node 유효성, allocation당 `active_total` + INSERT) → (l) model bind(선택) → (m) `event` outbox → (n) ledger `_save`.

옵션 1은 (b)(c)(d의 pool 전체)(f)(g)(i)를 **speculative read(잠금 없음, 별도 트랜잭션)** 로 옮기고, final commit에는 (a)+선택 node/resource만의 잠금+(e)(j)(k)(l)(m)(n)과 "재검증(선택 자원 `active_total`·ceiling·node 유효성·receivedAt·grant)"만 남긴다. 잠금 보유 구간이 **O(pool)에서 O(selected)로** 줄며, 특히 (f)의 pool 전체 상관 sum과 (d)의 pool 전체 row lock이 빠진다. 5노드·자원 10개 pool에서는 명확한 감소, **단일 node pool에서는 (d)(f)가 원래 O(1) 규모라 감소폭이 작다**(v1.1 §3.2가 스스로 인정). 논리 성립. ✔

단, **57014의 원인 statement는 아직 미특정**이다: lock 대기는 500ms에서 `55P03`으로 잘리므로 2초를 넘긴 것은 **잠금 대기가 아니라 어떤 statement의 실행 자체**다(후보: (f) 상관 sum·(k) ceiling sum·outbox INSERT, 또는 20 스레드가 한 PG를 CPU 포화시킨 상태). 이 statement가 잠금 보유 구간 안에 있으면 옵션 1이 줄이고, 밖(예: 첫 grant 트랜잭션·연결 수립)에 있으면 옵션 1은 P95를 못 고친다. 하네스 v1.1은 `serverSideLockWaitSeparatelyMeasured=false`로 이를 정직히 표기했다. → §4 조건 1.

## 4. 의견: **A — 조건부 승인(옵션 1 상세 설계 + 구현 카드), 구현 카드에 조건 2 부착**

- **A인 이유**: 카드 15의 조건 (1)(2)가 실측·설계로 충족됐고, 계약 변경 전제는 내 오류로 소멸했으며, 성공 지표가 "project row 제거"가 아니라 **잠금 보유 시간**으로 바로잡혀 이득/병목을 가를 수 있게 됐다. 옵션 2 후순위·옵션 3 기각 근거(2초 timeout은 freshness와 무관)도 실측과 일치한다.
- **조건 1(구현 카드 첫 단계, 개발 PC 20동시 1회)**: `log_min_duration_statement`(예: 500ms) 또는 `pg_stat_statements`로 **57014를 낸 statement를 특정**하고 잠금 보유 구간 안/밖을 기록한다. 밖이면 옵션 1과 별개의 조치(쿼리 계획·연결 풀·grant 트랜잭션 통합)를 같은 카드에 추가한다.
- **조건 2(acceptance)**: 개발 PC 20동시에서 candidate가 legacy 대비 **잠금 보유 p95를 낮추고 57014·55P03 합계가 감소**해야 5노드 랩으로 간다. 성공 수만으로 판정하지 않는다.
- 유지: 50동시·5노드는 별도 승인, S05-DB `review`.

## 5. 검토자 관찰(비차단)
- O1 하네스 `requestLatencyIncludesLockWait=true`는 클라이언트 관점 지연이라 서버 hold 시간과 다르다 — 조건 1로 보완.
- O2 20동시 실패 index 5·7·16의 완료 순번 17~19(마지막 3)와 지연 ~2,372ms 일치는 "뒤에 선 요청이 2초 statement에 걸림"과 정합 — 직렬화 자체가 원인이라는 v1.1 §0 서술과 일관.
- O3 v1.1이 내 오류를 지목한 방식(실측으로 반박)이 옳았고, 이 문서에 기록해 둔다.
