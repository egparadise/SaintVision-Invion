# 화면 정직성 스캐너 6대 한계 명시 및 5대 규칙 양방향 실측 사살 완료 보고서

## 1. 개요 및 배경

사용자의 피드백에 따라 `tools/check_frontend_integrity.py` 및 거버넌스 문서 `docs/vault/40_Governance/화면_개발_정직성_지침_및_사례집.md`의 최상단에 **스캐너가 구조적으로 잡지 못하는 6대 한계(What this scanner does NOT check)**를 명문화했다. 자동화 검사의 초록(0 violations)이 완벽한 안전을 보장하지 않으며, 정적 스캐너의 탐지 범위를 벗어난 영역은 인간 검토자와 런타임 E2E 시험이 감당해야 함을 명확히 정의했다.

아울러 "통과만 보면 아무것도 안 잡는 검사도 통과한다"는 원칙에 따라, 실제 프로덕션 소스 코드에 대해 5대 규칙 각각에 대한 인위적 돌연변이(Mutations)를 주입하고, 스캐너가 즉시 exit code 1과 해당 규칙 위반을 정확히 포착하는지 실측한 뒤 원복하는 **양방향 검증(Bidirectional Negative Verification)**을 전수 완결했다.

---

## 2. 스캐너의 6대 구조적 한계 명시 (스캐너가 못 잡는 것)

도구 소스 상단 독스트링 및 거버넌스 문서 섹션 3.2에 다음 6가지 한계를 등재했다:

1. **변수 조립 및 계산식으로 합성한 가짜 식별자 (Dynamic / Computed Values)**:
   - 스캐너는 정적 문자열 리터럴/정규식 패턴을 스캔한다.
   - 문자열 연결(`'00000000-' + '0000-...'`), 템플릿 리터럴(`` `run_${computedId}` ``), 또는 난수/해시 함수로 런타임에 동적 조립된 가짜 식별자는 정규식 스캐너를 우회할 수 있다.
2. **오늘 목록에 없는 신규 형태의 합성 식별자 (Unregistered Novel Patterns)**:
   - 본 도구는 오늘 발견된 위반의 지문(`00000000-0000-...`, `run_01J...`, `apr_01J...`, `prj_01J...` 등)을 등록해 방어한다.
   - 향후 새로운 명명 체계(예: `mock_node_9999`, `test_tenant_xyz`)로 주입된 가짜 데이터는 `FORBIDDEN_PLACEHOLDERS`에 등록되기 전까지 자동으로 탐지되지 않는다.
3. **특정 컴포넌트를 이름으로 지정한 규칙의 미추적 (Targeted Component Scope vs New Files)**:
   - 규칙 4(엄격한 3상태)는 `InvFileExplorer.tsx`를 지목하고, 규칙 5(0-call 가드)는 `ResourceExplorer.tsx`를 지목한다.
   - 새 뷰(예: `DatasetExplorer.tsx`, `ModelRegistryView.tsx`)가 신설되어 유사한 해시 검증이나 안내 방송을 수행하더라도 파일명이 하드코딩된 규칙은 자동으로 새 파일에 적용되지 않는다.
4. **소스 어휘의 존재 vs 런타임 데이터 흐름 (Lexical Syntax vs Runtime Data Flow)**:
   - 소스 코드에 `!tenantId` 조건문이 어휘적으로 존재하는지만 보며, 그 변수가 실제 HTTP 요청의 `X-Inv-Tenant` 헤더로 바인딩되는지(Data Flow)는 추적하지 못한다.
   - `activeRunId || ""`의 빈 문자열 fallback이 백엔드 스키마 유효성 검사를 통과하는지 실패하는지는 런타임 통합 시험으로만 확인할 수 있다.
5. **모양만 유효한 임의 식별자의 실존성 (Syntactic Shape Validity vs Semantic Existence)**:
   - 금지 목록에 없는 정상 형식의 UUID(예: `d4e5f6a7-b8c9-...`)는 스캐너를 그대로 통과한다.
   - 그 식별자가 백엔드 DB에 실재하는지, 세션 테넌트의 소유인지는 백엔드 fail-closed 인가 계층과 DB 대조 시험만이 증명할 수 있다.
6. **비-텍스트적/시각적 조기 성공 표출 (Visual / Non-Textual Premature Success)**:
   - 스캐너는 `'Connected via secure WebSocket'` 등 텍스트 키워드를 검출한다.
   - 텍스트 대신 녹색 점(Green Dot), 체크마크 SVG 아이콘, CSS 클래스(`is-connected`)로 소켓 연결 전에 조기 성공을 암시하는 시각적 표출은 텍스트 정규식으로 잡을 수 없다.

## 3. 5대 규칙 양방향 돌연변이 실측 사살 (Mutation Proofs)

실제 프로덕션 파일에 고의 결함을 주입하고 `python tools/check_frontend_integrity.py`를 실행하여 exit code 1과 에러 메시지를 포착한 뒤 원복했다.

| 번호 | 검사 규칙 | 주입 대상 파일 및 위치 | 주입된 돌연변이 내용 (Mutation) | 스캐너 감지 결과 (Exit Code & Message) | 사살 판정 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **M1** | [RULE-1] 표준 금지 자리표시자 | `apps/web/src/features/desktop/ResourceExplorer.tsx:2` | `export const FORBIDDEN_TENANT_TEST = '00000000-0000-0000-0000-000000000001';` | **Exit 1**: `[RULE-1 Placeholders] ResourceExplorer.tsx:2 contains forbidden placeholder '00000000-...'` | **KILLED** |
| **M2** | [RULE-1] 미인가 컴포넌트 commandId 자리표시자 | `apps/web/src/features/desktop/TerminalSessionView.tsx:2` | `const BAD_CMD = '11111111-1111-4111-8111-111111111111';` | **Exit 1**: `[RULE-1 Placeholders] TerminalSessionView.tsx:2 contains command placeholder '11111111-...'` | **KILLED** |
| **M3** | [RULE-2] 안내 방송 세션 테넌트 0-Call 가드 | `apps/web/src/features/desktop/ResourceExplorer.tsx:449` | `handleBroadcastAnnouncement` 내부 `if (!tenantId)` 가드를 `if (false)`로 무력화 | **Exit 1**: `[RULE-2 Zero-Call Guard] ResourceExplorer.tsx handleBroadcastAnnouncement must guard against missing tenantId (!tenantId) before invoking broadcastAnnouncement` | **KILLED** |
| **M4** | [RULE-3] 소켓 연결 전 조기 Connected 출력 | `apps/web/src/features/terminal/WebTerminal.tsx:30` | 초기 버퍼에 `'Connected via secure WebSocket with 30s one-time ticket.'` 주입 | **Exit 1**: `[RULE-3 Premature Display] WebTerminal.tsx declares premature 'Connected' message in initial state before socket onopen` | **KILLED** |
| **M5** | [RULE-3] 일회용 권한 증표 티켓 콘솔 로깅 | `apps/web/src/features/terminal/WebTerminal.tsx:78` | `console.warn('Leaking ticket data:', ticketData.ticket);` 주입 | **Exit 1**: `[RULE-3 Credential Logging] WebTerminal.tsx:78 logs credential/ticket directly: 'console.warn(...)'` | **KILLED** |
| **M6** | [RULE-4] 해시 불일치 시 verified 전이 거부 | `apps/web/src/features/desktop/InvFileExplorer.tsx:258` | `if (isMatch)`의 `else` 블록에서 `status: 'mismatch'` 대신 `status: 'verified'` 설정 | **Exit 1**: `[RULE-4 Tri-State] InvFileExplorer.tsx sets status to 'verified' in else branch of isMatch check` | **KILLED** |

> [!NOTE]
> **실측을 통해 검사 도구를 강화한 핵심 발견**:
> - **M3 실측 과정**: 기존 검사기가 파일 전체에서 `!tenantId` 존재 여부만 보아 JSX의 `disabled={!tenantId}` 때문에 함수 내 가드가 빠져도 놓치는 결함 발견 -> 함수 본문 내에서 `broadcastAnnouncement` 호출 전에 `!tenantId` 검사가 선행하는지 정밀 검사하도록 정규식 대폭 강화.
> - **M6 실측 과정**: 기존 검사기가 파일 전체의 `'mismatch'` 토큰 존재 여부만 보아 else 블록에서 `status: 'verified'`로 조작해도 놓치는 결함 발견 -> `if (isMatch)`의 `else` 블록 내부에서 `status: 'verified'`를 지정하거나 삼항 연산자로 조작하는 패턴을 정확히 검출하도록 규칙 대폭 강화.
