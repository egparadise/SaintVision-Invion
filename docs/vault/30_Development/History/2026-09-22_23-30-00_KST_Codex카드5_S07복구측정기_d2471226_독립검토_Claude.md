## 2. (a) 하네스가 제품 경로를 실제 PG에서 측정하는가 — 정독

- **liveness**: 생존 노드는 매 폴마다 `nodes.record_heartbeat(...)`·`nodes.record_observations(...)`(제품 함수, `.applied`·`==1` 단언)로 살아 있고, 이탈 노드만 heartbeat 중단 → `nodes.mark_lost_nodes(session, tenant_id, now, timeout_seconds)`(제품, `nodes.py:305`)가 `status='lost'` 전이. 하네스는 `SELECT status FROM nodes`로 **DB 상태를 읽어** detected 판정(case 191~206행). ✔
- **replica stale 전이**: 하네스가 직접 UPDATE하지 않는다. `mark_lost_nodes` 내부가 `replica_repair.mark_node_replicas_unavailable(...)`를 호출(`nodes.py:320~326`, 주석 "Without this call the replica repair service … count a lost node's copy as ready") → 하네스는 `SELECT count(*) … state='stale'`로 **결과만 읽음**(case 254~257행). ✔ 제품 배선 의존.
- **repair plan**: `replica_repair.locations_needing_repair(...)`(제품)로 계획을 받고 `len(planned)==len(locations)` 조건에서만 proxy 진행(case 212~217행). ✔
- **합성 proxy**: owner 픽스처가 `data_replicas`에 **verified/ready 대체 복제본을 INSERT**(230~234행)한 뒤 `replica_repair.replica_health(...)=='healthy'`(제품)를 센다. `summarize()`는 `operationalAcceptanceAssessed: False`를 **상수**로 쓰고 `syntheticRecoveryMode="verified-owner-fixture-after-product-repair-plan"`·주석 "Current replica repair code plans and marks state; the harness fixture …"를 JSON에 남긴다(tool 70·105·108행). `recoveryTargetMet`는 이 proxy 성공률에 대한 것이며 운영 인수와 **분리**됨. ✔ 정직.
