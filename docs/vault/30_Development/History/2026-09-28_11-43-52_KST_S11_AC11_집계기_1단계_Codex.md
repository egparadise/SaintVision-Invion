# S11 AC-11 증거 집계기 1단계 구현

## 기준과 범위

- owner/reviewer: Codex / Claude.
- branch/base: `agent/codex/s11-ac11-aggregator` / `1e8baf045c5a554209aaef601ae4883b64da50a7`.
- 승인 설계: [PR #157](https://github.com/egparadise/SaintVision-Invion/pull/157) v1.1.1, head `a793f258`.
- 이번 단계는 `tools/aggregate_ac11_evidence.py`, security allowlist v0와 PG-free 부정 시험만 구현한다. migration forward/rollback/forward hosted lane과 실 PostgreSQL 실행은 2단계이며 이번 변경에 없다.

## 구현

집계기는 producer의 `verdict`를 합격 근거로 쓰지 않는다. 닫힌 7개 verdict enum을 먼저 검증하고, 현재 schema 봉투의 Git tree·target ancestor·같은 path blob, clean checkout, 성공 run, artifact 가용·만료, UTC 구간, 관측 분모·실패 분류·목표 비교와 cleanup residue를 다시 판정한다. schema 이전 증거는 `referenceOnly=true`와 `NOT_OBSERVED`로만 남고 PASS 분자에 들어가지 않는다.

필수 8축은 다음 exact ID로 고정했다.

1. `migration-reversible-segment`
2. `irreversible-restore-forward`
3. `actual-pitr-rpo-rto-retention`
4. `physical-five-node-ac05-placement-load`
5. `physical-five-node-failure-recovery`
6. `long-soak`
7. `security-critical-high-zero`
8. `accessibility-e2e`

누락·중복·unknown axis는 `INVALID_RUN`이다. 원칙적으로 `done=true`는 여덟 축 모두 집계기가 재계산한 `MEASURED_PASS`일 때만 가능하다. 유일한 구조 예외로 `sourceHeadSha`의 migration graph를 Git 내용에서 직접 읽어 reversible tail 0을 증명하고, 짝인 `irreversible-restore-forward`가 `MEASURED_PASS`일 때만 reversible 축의 `NOT_APPLICABLE`을 분모에서 제외한다. 자기 선언 count만으로는 예외를 열지 않는다.

security 축은 승인 설계의 allowlist를 `docs/vault/30_Development/Evidence/s11-security-allowlist-v0.json`의 reviewed blob으로 고정했다. `SEC-DEF-001`은 실제 출력 키 `functions`와 12개 policy signature 전부, `status`, `unsafe`, process exit 0/1/2를 함께 확인하므로 exit 0 + 빈 목록은 `INVALID_RUN`이다. `SEC-RLS-001`은 실제 evidence의 `roles`, `ground_truth`, `violations`, `accepted`, `unmeasured`, `verdict`와 process exit 0/1/2/3을 읽고, role/table inventory가 비면 `INVALID_RUN`이다. `tools/rls-boundary-baseline.json`의 `(role, table, rules)` 집합은 allowlist disposition과 exact match해야 한다. `SEC-VF-001`은 실제 proof의 `subprocessExitCode`, `evidenceStatus`, `caseIdentitiesSha256`, `tests`를 읽고 고정된 6개 case identity, passed 6, skipped/failure/error 0을 요구한다. exit 125는 실행되지 않은 증거이므로 `NOT_OBSERVED`다.

목표 임계치는 evidence 봉투가 정하지 않는다. `docs/vault/30_Development/Evidence/s11-ac11-target-registry-v0.json`을 targetRef의 commit/path/blob으로 고정하고 Git 내용의 `targetId`에서 criteria를 읽는다. 봉투 criteria는 registry와 exact match해야 하며, registry가 인용하는 원 목표 문서도 source의 조상·동일 blob이어야 한다. 현재 registry는 S05 물리 5노드 AC-05, 실제 PITR RPO/RTO/35일 보존, S11 critical/high 0만 등록한다. 다른 축은 목표가 먼저 merge되기 전 `NOT_REGISTERED`다.

CLI exit contract는 `0=done`, `1=유효하지만 미완료`, `2=INVALID_RUN`이다. 제품 계약, migration, registry 상태는 변경하지 않았다.

## Claude r2 검토 반영 (12:58 KST)

- target registry는 조상 commit에서 느슨하게 바꿀 수 없도록 reviewed Git blob `34c975cba77fada5abfd5afd025f411fa85bddfa`를 집계기 상수로 고정했다. 각 target의 원 문서 blob도 현재 tree와 같아야 한다.
- release manifest에 단일 `releaseSha`를 필수화했고 여덟 축의 `sourceHeadSha`가 모두 이 SHA와 같아야 한다. reversible N/A와 짝 restore도 서로 다른 source tree를 섞을 수 없다.
- registry target마다 `requiredEnvironment`를 사전 등록했다. AC-05는 `physical-five-node`와 ADR-100의 eligible 4/excluded 1을, 실제 PITR은 물리 topology·분리 장애영역·운영 archive·same-host 금지를 요구한다. hosted 합성 5노드 또는 same-host logical rehearsal은 해당 축의 합격 증거가 될 수 없다.
- 실제 PITR 목표에 `consecutiveWeeklyRestoreSmokeWeeks >= 2`와 `maxRestoreSmokeGapDays <= 7`을 추가했다. 반복 기준을 충족하지 않은 단발 복원은 RPO/RTO/retention 수치가 좋아도 통과하지 않는다.
- security target은 자주 바뀌는 S11 sprint 문서 대신 reviewed security allowlist blob `ff2f9966...`에 결속했다. #157과 #170의 add/add 충돌을 없애기 위해 #157 쪽 allowlist도 같은 blob으로 맞추는 후속 commit이 필요하다.

PG-free focused 시험은 위 변이(느슨한 ancestor registry, release SHA 혼합, hosted→physical 대체, same-host PITR 대체, registry target의 HEAD blob 불일치)를 포함해 **54 passed**다. 이는 여전히 판정기 검증이며 실제 물리 5노드·운영 PITR·weekly restore evidence가 아니다.

### 병합 방식 제약(C1)

security target의 원 문서 commit `c62cb671692479b0ee2bc2cc8a12d3c10587174b`은 이 PR branch의 조상이다. 따라서 #170은 #157 뒤에 반드시 GitHub **merge commit 방식(`--merge`)**으로 병합해야 하며 squash 또는 rebase 병합을 금지한다. squash/rebase는 `sourceDocument.commit`을 integration history에서 도달 불가하게 만들어 security 축을 영구 `INVALID_RUN`으로 만든다. 병합 뒤 integration commit으로 sourceDocument를 옮기는 후속은 가능하지만, 그 전에는 이 제약이 release gate의 일부다.

PITR 반복 기준은 최소 2개 연속 주를 요구해야 한 번 이상의 실제 주간 간격을 관측할 수 있다는 이유로 `consecutiveWeeklyRestoreSmokeWeeks >= 2`를 택했고, “주간”을 늘여 해석하지 못하도록 `maxRestoreSmokeGapDays <= 7`을 함께 고정했다. 환경 필드는 1단계에서 producer 자기 신고와 registry exact value를 대조하며, 2단계 importer는 ADR-100 inventory/JUnit과 독립 대조해야 한다.
