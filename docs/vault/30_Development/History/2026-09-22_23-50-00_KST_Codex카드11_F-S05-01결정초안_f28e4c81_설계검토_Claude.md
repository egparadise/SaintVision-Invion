# Codex 카드 11 F-S05-01 결정 초안 `f28e4c81` 설계 검토 (2026-09-22, 23:50 KST)

대상: [[2026-09-22_S05_배치잠금_입도_결정제안_Codex]] · [[2026-09-22_23-30-00_KST_S05_배치잠금_결정초안_Codex]] · [[ERR-DESIGN-008 프로젝트 배치 잠금과 관측 freshness 충돌]]. 방법: 커널 코드 정독(`inv/placement.py`·`leases.py`·`capacity.py`·`scheduler.py`·`approvals.py`·`db.py`, tip `f28e4c81`), 실 PG 실행 없음(지시), 반례 시나리오 서면.

## 0. 초안이 놓친 코드 사실 (검토의 출발점)

`inv/db.py:52~54`: 모든 커널 트랜잭션은 `set_config('inv.tenant_id')` 직후 **`SET LOCAL lock_timeout = '500ms'`**, **`SET LOCAL statement_timeout = '2s'`** 를 건다. 그리고 `inv/*.py`에 `LockNotAvailable`/`55P03`/`QueryCanceled`를 DomainError로 매핑하는 코드가 **없다**(grep 0건).

결과:
- `placement.py:103` `inv.projects FOR NO KEY UPDATE`에서 **500ms 넘게 기다리는 요청은 `RES-0003`이 아니라 psycopg `LockNotAvailable`(미매핑 → 내부 오류 500, retryable 표시 없음)** 로 끝난다. 따라서 "project 직렬 구간이 15초를 넘어 후순위가 RES-0003"(ERR-DESIGN-008 §문제)은 **현 코드에서 도달할 수 없는 시나리오**다 — 15초 창에 닿기 30배 전에 lock_timeout이 자른다.
- 실제 50동시 실패 모드는 **lock timeout 대량 발생(미분류 오류, 재시도 계약 없음)**이며, 이것은 옵션 1·2·3 어느 것으로도 다뤄지지 않았다. 초안 §3 "잠금 순서"·§4 "livelock" 방어는 이 상한을 전제하지 않는다.
- Codex 10동시 측정(P95 1,738ms·오류 0)은 이 상한과 **양립하려면** 개별 요청의 project-lock 대기가 500ms 미만이어야 한다 — 즉 지연의 대부분이 lock 보유 구간 밖(연결 수립·role 조회·grant 트랜잭션 #1·Python 스레드)에 있다는 뜻. 이 경우 project lock 입도 완화(옵션 1)의 이득은 **가정만큼 크지 않을 수 있다**. 어느 쪽인지는 lock 대기 분포 계측 없이는 알 수 없다(§4 의견의 근거).

## 1. (a) 옵션 1이 불변식을 보존하는가 — 반례 시나리오

현 코드의 lock 순서(사실): `_ledger`(idempotency FOR UPDATE, `approvals.py:91`) → `lock_run`(runs FOR UPDATE, `leases.py:24`) → `projects FOR NO KEY UPDATE`(`placement.py:103`) → `project_resource_limits FOR UPDATE`(`:107`) → `lock_resources`(nodes FOR UPDATE 정렬 → resources FOR UPDATE 정렬, `leases.py:32~55`) → `project_capacity`(15초 SQL 창, `capacity.py:16~17`) → `now`(`placement.py:156`) → `place`(`scheduler.py:126` freshness, `:183` RES-0003) → 할당(`active_total` 재조회 후 `RES-0001`) → `_reserve_locked`(Run 상태·미해제 lease·ceiling·node 15초/skew/epoch·`active_total+amount>offered`, `leases.py:155~256`) → lease INSERT(epoch 스탬프·fencing) → `event` → `_save`.

## 2. (b) 기각 사유(옵션 3)의 타당성

타당. 창 확대·진입 시각 동결은 격리/epoch 변경 노드의 stale capacity를 수락한다(`scheduler.py:126`·`leases.py:215` 두 층이 같은 15초를 쓰므로 한쪽만 늘리면 불일치까지 생긴다). 다만 §0 때문에 **기각 근거 문장 "RES-0003만 늦추거나 숨긴다"는 부정확** — 현 코드에서 15초에 닿기 전에 lock_timeout이 먼저다. 기각 결론은 유지하되 근거를 "stale 수락"으로만 두어야 한다.

## 3. (c) 5노드 검증·롤백의 실행 가능성

- 실행 가능: feature flag(`project_serial` 기본)·migration 없음·정상 Lease 보존은 현 스키마와 맞다(lease 테이블에 epoch·fencing 이미 있음).
- **누락 계측**: 요청별 **lock 대기 시간(pg_stat/`lock_timeout` 발생 수)**, `LockNotAvailable` 건수, retry 횟수 분포, 어느 row(project/limits/node/resource)에서 기다렸는가. 이것 없이는 "옵션 1이 병목을 옮겼는지"를 판정할 수 없다(CE-2).
- acceptance "50/50 성공"은 lock_timeout 매핑 전에는 단일 노드에서 성립 불가 — 5노드 랩 전 **개발 PC 20동시 계측**으로 병목 위치를 먼저 확인하는 것이 싸다.
- 롤백: 설정 되돌리기로 충분. 단 candidate가 만든 lease는 `project_serial`과 같은 테이블이라 혼합 시 ceiling 계산이 같은 SQL(`leases.py:191~206`)이므로 안전.

## 4. (d) 변경 범위 누락

| 누락 | 왜 |
|---|---|
| **lock_timeout/statement_timeout 처리** | 옵션 1의 "bounded retry"는 DomainError 기준이라 `LockNotAvailable`을 못 잡는다. 매핑(예: `RES-0007`류 retryable 409/503)이 필요하고 이는 **ProblemDetails 계약 표면**(오류 코드 목록·`retryable`)에 닿는다 → 초안 "계약 변경 없음"과 충돌 가능. 구현 전 계약 보고 필요 |
| direct `LeaseStore.reserve`와의 공통 primitive | 초안이 언급(§4)했으나 `_reserve_locked`가 이미 공통이며 project lock을 **또** 잡는다(`leases.py:176`) — 옵션 1은 여기도 손대야 하며, 그러면 shard/workspace/business handoff 경로(`require_*` 4종, `leases.py:163~171`)의 lock 순서 가정을 재검토해야 한다 |
| 관측 지표 | retry·conflict 원인·lock 대기 히스토그램의 노출 경로(로그/메트릭 계약) 미정 |
| 시험 | 초안 목록에 **lock_timeout 주입 시험**(pg_sleep으로 project/limits row를 잡은 채 reserve 호출 → 어떤 오류로 끝나는가)이 없다. 현 코드의 실제 실패 모드를 먼저 고정해야 한다 |
| 문서 | ERR-DESIGN-008 §문제의 인과 문장을 §0 사실로 정정 |

## 5. 의견: **C — 조건부 보류(계측 1회 후 A), B는 반대**

- **B(batch 계약 우선) 반대**: AC-05 의미("50개의 독립 요청")를 바꾸고 blast radius를 키우며, §0의 실제 병목(row lock + 500ms 상한)은 batch로도 그대로다.
- **A를 지금 승인하지 않는 이유**: 초안의 위험 모델(15초 freshness)이 현 코드와 다르고(§0), 옵션 1의 이득이 병목 위치(project row vs node/resource row)에 달려 있는데 그 위치를 아무도 재지 않았다(CE-2). lock_timeout 매핑은 계약 표면에 닿아 "계약 변경 없음" 전제가 흔들린다.
- **C의 조건(작고 구체적)**: (1) 개발 PC에서 **20동시 1회**(코디네이터 메모리 slot) — 하네스에 요청별 lock 대기·오류 클래스(`LockNotAvailable` 포함) 기록 추가; (2) `pg_sleep`로 project row를 잡은 채 reserve 1건 호출하는 **lock_timeout 주입 시험** 1개로 현 실패 모드 고정; (3) 그 결과로 §0·CE-2를 반영해 초안 v1.1 → **그때 A**(옵션 1 상세 설계 승인). 50동시 재실행은 여전히 별도 승인.

## 판정 요약
초안은 불변식 목록·잠금 순서·롤백 계획이 잘 잡혀 있고 옵션 3 기각과 옵션 2 후순위는 타당하다. 그러나 커널의 500ms lock_timeout/2s statement_timeout을 빠뜨려 위험 모델이 틀렸고(RES-0003 도달 불가), 옵션 1의 핵심 이득이 미계측 가정에 기대며, lock timeout 매핑이 계약 표면에 닿는다. **의견 C(조건부)**, 조건 충족 시 A.
