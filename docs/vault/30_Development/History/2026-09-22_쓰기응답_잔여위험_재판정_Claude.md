# 남은 쓰기 응답 위험 재판정

Codex가 고위험 상위 4건(create_project·admit·set_member_role·set_resource_offer)을 결속(`6b82a2d`, 그중 admit는 실 PG 확인 진행 중 `9cc8d2e4`). 위험도 판정은 Codex가 했고 목록은 내가 만들었으니 **다시 본다.** 렌즈: 사용자 지정 — **반환값이 후속 동작의 입력이 되는 것.** 응답이 틀리면 다음 요청이 틀린 대상에 간다.

## 재판정의 축 (새로 명확해진 것)
위험은 "response_model 유무"만이 아니다. **본문이 스키마 생성자를 통해 만들어지는가**가 갈린다:
- **자체 검증형**: 라우트에 response_model이 없어도 본문을 `schemas.X(...).model_dump()`로 만들면 **생성 시 타입/필드가 검증**된다. id·경로가 타입-체크됨 → 위험이 내가 목록에서 매긴 것보다 **낮다**.
- **날 dict형**: 손으로 쌓은 `{...}` — 아무것도 강제 안 됨. **여기가 진짜 노출.**

## 남은 쓰기 라우트 재판정 (Codex 4건 제외)

### ★ 저평가 발견 — `PUT /workspaces/{id}/status` set_workspace_status (MED-HIGH → **HIGH**)
- **반환**: **날 dict** `{workspaceId, status, allowedNext: sorted(WORKSPACE_TRANSITIONS.get(status))}` — 스키마 생성 없음.
- **응답이 후속 입력**: `allowedNext`는 클라이언트가 **다음 상태 전이 요청**을 만드는 근거다(provisioning→ready→suspended…). 응답 shape가 드리프트하면(allowedNext 개명/누락/여분 필드) 클라이언트의 다음-전이 로직이 조용히 깨지고 **틀린/무효 전이 요청**을 보낸다. 상태기계를 구동하는 필드가 미검증 날 dict인 것.
- **왜 저평가됐나**: 내 목록은 "상태 setter"를 MED-HIGH 뭉치로 봤는데, 이건 (a) 날 dict이고 (b) allowedNext가 후속 요청을 만든다 — 두 축 다 상위. create류가 id를 주듯 이건 **다음 전이 집합을 준다.** → **HIGH, 다음 결속 1순위.**
- **결속 비용**: 정확 일치 스키마 없음(3필드 부분집합, WorkspaceSummaryResponse보다 좁음). 작은 `WorkspaceStatusResponse{workspaceId, status, allowedNext}` 신설 필요(내 레인, 명세만 — 지금 안 만듦).

## 판정·권고
- **결속 1순위 = `set_workspace_status`**(저평가 정정): 날 dict + allowedNext가 다음 전이를 구동 → 응답 드리프트가 틀린 다음-요청을 낳는다. 작은 `WorkspaceStatusResponse` 신설 후 response_model. (Codex 상위 4건과 같은 급으로 올림.)
- **완화 명시(위험 하향은 아님, 정확도)**: enroll_node·register_contribution·activate/revoke는 본문을 **스키마 생성자로** 만들어 id·경로가 이미 타입-검증된다 — "날 dict"보다 낮다. 결속은 여전히 값짐(래퍼/라우트/replay 미강제 닫기, 스키마 이미 존재)이나 set_workspace_status보다 후순위.
- **후속-입력 렌즈의 일반 규칙**: 응답이 id·handle·**전이집합**·경로처럼 **다음 요청의 대상/입력을 정하는 값**을 담으면, 미결속·날 dict는 상위 위험. 단순 상태-표시 수령증은 하위.
- **소관**: 결속은 saintvision 백엔드=내 레인(명세만, 지시 시 착수). Codex의 상위 4건 판정은 타당했고, 이 재판정은 그 아래에서 set_workspace_status 하나를 끌어올린다.

## 직접 확인 vs 보고 수용
- **직접(소스)**: 세 라우트 반환 본문·`_node_body`/`_contribution_body`의 스키마 생성·set_workspace_status의 allowedNext 계산 (전부 tip `c4b62108` 소스).
- **보고 수용**: Codex 4건 결속의 실 PG 확인(admit `9cc8d2e4`)은 Codex 실행 결과 수용. 클라이언트가 실제로 allowedNext로 다음 전이를 만든다는 것은 프런트 소관(Gemini)이라 백엔드 계약 관점에서만 판정.
