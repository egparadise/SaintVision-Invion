## Blocking finding

**B5-M1 (Medium) PRE_IO 안전 의무의 수명주기가 닫히지 않았다.**

- register(RUN/VER)와 OP 전용 protected settle만 있다.
  - 정상 성공 IO 뒤에 처리할 경로가 없다(MA2b).
  - 그래서 성공한 GPU 교환이나 build dispatch도 operator settle 전까지 영구 부적격이 된다. 그렇지 않다면 미정의 암묵 성공 경로가 있어야 한다.
- 의무가 선행해야 할 실제 IO 지점이 이름 붙어 있지 않다.
  - 해당 지점은 `node_transport.py:289`와 `build_execution.py:787`이다.
  - permit, dispatch, receipt 어디에도 의무가 결속돼 있지 않다.
- 실제 source는 quarantine fence 실패를 삼킨다(`build_execution.py:414/429`).
- plain 적격성 reader 13곳이 의무를 확인하도록 매핑돼 있지 않다.
  - placement 239/538, dispatch 79, leases 253, capacity 23, scheduler 106, build_adapter 138, gpu 97, model_commit 57, model_locality 27, tooling 203, terminal 78, node_channels 137이다.
  - 따라서 EXECUTE를 잃으면 Node가 plain 배정으로 돌아간다.
- model `cp_eligible`에도 문제가 있다.
  - 전역이며 B 전용이다. 다른 Node의 의무가 이 Node를 막는다(MA1).
  - settle 전이와 그 negative가 없다.
- **필요 수정:** 다음을 정의한다. 자세한 항목은 review.json에 있다.
  - (tenant, node, epoch, operation) key와 PENDING_IO → VERIFIED_CLEAN | UNCERTAIN → SETTLED_PROTECTED 상태기계
  - 정확한 receipt와 같은 transaction에서만 이뤄지는 성공 settle
  - UNCERTAIN은 OP+물리 증거로만 내린다
  - IO 전 등록 지점과 permit 결속
  - 모든 plain·B reader를 단일 fixed read로 교체
  - 거부 격자
  - scoped 모델과 시간 진행 fixture

**B5-M2 (Medium) UNKNOWN/BLOCK이 이름 충돌로 만든 사실상 전역 BLOCK이다.**

- BLOCK 5426건은 구성이 이렇다.
  - 1459건: 이미 기록된 DB record와 같은 호출 지점이다.
  - 3283건: `.get` 호출이다.
  - 나머지 684건 상위: `subprocess.run` 199, `self.db.transaction` 76, `conn.transaction` 15 등이다.
- concrete plan이 있는 critical 진입점 20개가 모두 자기 closure에 BLOCK edge를 가진다. 예외는 `lock_current` 하나다.
  - 산출물끼리 서로 모순된다.
  - Root가 금지한 전역 boilerplate block이다.
- `getattr(leases,'lock_run')`는 edge, unknown, record 어디에도 잡히지 않는다(L5).
- **필요 수정:**
  - DB record와 같은 호출 지점, builtin `.get`, stdlib 호출을 제외한다.
  - transaction owner receiver를 해석한다.
  - 남은 unknown을 plan별로 붙이고 disposition을 정한다.

  - critical plan에 정당화되지 않은 BLOCK이 0임을 fixture로 확인한다.

## 확인되어 유지되는 설계

다음은 실제 실행이나 공격으로 확인했고, 유지된다.

- **M2 변형 해석:** L1 dotted alias, L2 self instance, L3 import constant, L4 class 상수(명시 BLOCK), L7 inversion 재정렬.
- **L1:** 6개 commit gate가 철회 뒤 거부하고, ancestor 만료는 철회와 분리된다.
- **L2:** retired history가 terminal이고, duplicate에는 원래 ACK만 돌려준다.
  - stale·missing ACK는 HOLD다.
  - closed readback이 refusal/extra/missing을 거부한다(MA7).
- **L3:** 다른 caller는 APPROVAL을 받지 못한다(MA5). controller scope는 정확하다.
- **증거와 동의:** evidence append로 성공을 만들 수 없다. 소유자 동의는 B 승인에 더해 따로 필요하다.
- **기존 결정:** 24h 갱신, strict JSON, VM과 4 worker, role identity/C+1/P+1/P+2 결정이 보존된다.
