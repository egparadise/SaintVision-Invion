## 2. (a) 하네스가 freshness/RES-0003를 우회하지 않는가 — 정독 결과

- `run_round`(tool 77~130행): `Barrier(request_count)`로 동시 시작, `attempt`는 `except Exception`으로 **모든 예외를 `error_code`(DomainError.code) + type으로 기록**하고 계속 진행(우회·재시도·삼킴 없음). `summarize`: `benchmark_complete = second and all(failure_count==0)`, `deterministic`는 실패 0일 때만 True → 시험 말미 `assert report["benchmarkComplete"]` 등 5개 단언이 **실패 1건이라도 있으면 red**. 즉 RES-0003를 통과로 위장할 경로 없음.
- `_start_observation_window`(126~139행): wave 직전 `heartbeat_at=clock_timestamp()` + snapshot UPSERT **1회**만. wave 중 재갱신 없음(고정 snapshot 의도). ttl·시각 주입·monkeypatch 없음. → **우회 없음(설계 의도대로)**. 단 F-R1 때문에 그 고정 snapshot이 계약 위반이라 freshness 검사 이전 단계에서 탈락한다.

## 3. (b) F-S05-01 인과 서술이 커널 코드에서 성립하는가 — 인용

1. **project 직렬화**: `inv/placement.py:103` `SELECT project_id FROM inv.projects WHERE project_id=%s FOR NO KEY UPDATE`(reserve 트랜잭션 초반; `leases.py:176` LeaseStore.reserve도 동일 lock). 같은 project의 N개 reserve는 이 행 lock에서 **직렬**된다. ✔
2. **`now`는 lock 획득 후**: `placement.py:156` `now = conn.execute("SELECT clock_timestamp() AS now")` — lock 대기 시간이 `now`에 포함된다. ✔
3. **후보 관측 시각 = 저장된 snapshot**: `placement.py:152~154` `SELECT n.node_id,n.clock_skew_seconds,s.received_at,s.snapshot FROM inv.nodes n JOIN inv.node_resource_snapshots s`; Candidate.observed_at = `received_at`. ✔
4. **freshness 15초 두 곳**: (i) `capacity.py:16~17` SQL `s.received_at BETWEEN clock_timestamp()-interval '15 seconds' AND clock_timestamp()` 및 heartbeat 동일 → 아니면 `measured=False`로 후보 제외; (ii) `scheduler.py:126` `not 0 <= (now - c.observed_at).total_seconds() <= ttl_seconds(15)` → `snapshot_stale_or_future`. ✔
5. **RES-0003**: `scheduler.py:183` `if not values: raise DomainError("RES-0003", "No eligible node", retryable=True)`. ✔

결론: "고정 snapshot 1개 + 같은 project의 50 동시 요청 + 요청당 처리 시간 합이 15초 초과 → 후순위 RES-0003"는 **코드상 성립**한다(retryable=True로 표기되는 점도 일치). 다만 F-R3: 운영에서는 snapshot이 갱신되므로 이 실패 모드는 "관측이 멈춘 노드"에 한정되고, 일반 병목은 직렬화 지연이다.
