# 최신 기술 출처와 설계 근거

> [!summary]
> 이 문서는 2026-09-09 기준으로 SaintVision 설계에 반영한 공식·1차 출처와 그 적용 범위를 기록한다. 출처가 말하는 사실, SaintVision의 설계 결정, 설계팀의 추론을 구분한다.

## 2. 핵심 결론

### 여섯 엔지니어링 단계

- **사실:** Prompt Engineering, Context Engineering, Harness Engineering, Agent Engineering은 현재 주요 AI 플랫폼·연구 조직이 사용하는 개념이다.
- **사실:** Graph 기반 실행은 LangGraph, Microsoft GraphRAG 등에서 워크플로 상태와 지식 구조를 다루는 핵심 방식으로 사용된다.
- **추론:** “Graph Engineering”은 하나의 표준화된 직무·학문명이라기보다 실행 그래프, 자원 그래프, 지식 그래프를 설계하는 SaintVision 통합 범주로 쓰는 것이 정확하다.
- **추론/설계 결정:** “Roof Engineering”은 조사한 주요 1차 출처에서 독립된 표준 AI 엔지니어링 용어로 확인되지 않았다. 사용자 용어를 존중하되 SaintVision에서는 `Risk controls + Observability + Ownership & approvals + Failure containment & fallback`의 공통 상부 통제 계층인 **ROOF Engineering**으로 공식 정의한다.
- **설계 결정:** “Loop Engineering”을 의도한 경우의 개념은 ROOF의 Failure containment 아래 bounded `plan → act → observe → evaluate → repair → verify` 루프로 포함한다.

## 3. Prompt Engineering

### OpenAI Prompt Engineering

- 출처: [Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering)
- 확인일: 2026-09-09
- 사실: 역할·지시 계층, 관련 컨텍스트 제공, 예시, 구조화, 평가에 대한 공식 지침을 제공한다.
- SaintVision 적용: Prompt를 실행 코드로 취급하여 버전, 입력 계약, 출력 스키마, 평가셋을 함께 관리한다.

### OpenAI 모델 선택 지침

- 출처: [Using GPT-6 Astra](https://developers.openai.com/api/docs/guides/latest-model)
- 확인일: 2026-09-09
- 사실: 최신 모델별 사용 방식과 추론·도구 사용 지침은 변경될 수 있다.
- SaintVision 적용: Agent가 특정 모델명에 고정되지 않도록 Model Profile과 capability 기반 라우팅을 둔다.

## 4. Context Engineering

### Anthropic Context Engineering

- 출처: [Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- 게시일: 2025-09-29
- 사실: 장기 Agent에서 컨텍스트는 유한 자원이며, 적절한 정보를 선별·압축·구조화하는 것이 핵심이라는 설명을 제공한다.
- SaintVision 적용: Context Registry, 출처·시각·신뢰도 메타데이터, 토큰 예산, 압축, 단기/장기 메모리 분리를 채택한다.

### OpenAI Compaction

- 출처: [Compaction](https://developers.openai.com/api/docs/guides/compaction)
- 확인일: 2026-09-09
- 사실: 장기 실행에서 컨텍스트 압축을 통해 유효한 상태를 유지하는 공식 패턴을 제공한다.
- SaintVision 적용: 실행 체크포인트에 요약 상태와 원본 Evidence 참조를 함께 보존한다.

## 5. Harness Engineering

### OpenAI Harness Engineering

- 출처: [Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)
- 게시일: 2026-02-11
- 사실: Agent가 효과적으로 일하도록 저장소 구조, 도구, 문서, 평가, 피드백 루프를 설계하는 접근을 설명한다.
- SaintVision 적용: Prompt 바깥의 실행 환경, 도구 계약, 저장소 문맥, 샌드박스, 로그, 검증기를 독립 제품 계층으로 둔다.

### Anthropic 장기 실행 Harness

- 출처: [Effective harnesses for long-running agents](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)
- 게시일: 2025-11-26
- 사실: 세션 경계를 넘는 진행 상태, 명확한 다음 작업, 테스트, 커밋·아티팩트가 장기 Agent 성능에 중요하다는 경험을 제시한다.
- SaintVision 적용: Run 체크포인트, 진행 파일 대신 구조화 상태, 작은 검증 단위, 실패 후 재개를 설계한다.

- 출처: [Harness design for long-running application development](https://www.anthropic.com/engineering/harness-design-long-running-apps)
- 게시일: 2026-03-24
- 사실: 장기간 응용 프로그램 개발에서 Harness가 계획·실행·검증의 지속성을 지원해야 함을 설명한다.
- SaintVision 적용: Planner와 Executor보다 독립적인 Verifier, regression eval, Evidence 저장을 둔다.

## 13. 설계 결정과 출처의 경계

다음은 출처가 직접 요구하는 것이 아니라 SaintVision이 선택한 결정이다.

- 6단계를 `Prompt → Context → Harness → Graph → ROOF → Agent` 순서로 성숙시킨다.
- Workspace와 Node를 분리한다.
- 결정론적 Scheduler V1을 먼저 만들고 학습 기반 최적화는 후순위로 둔다.
- Agent가 직접 인프라 API를 호출하지 않고 Tool Gateway를 거친다.
- RunGraph, ResourceGraph, KnowledgeGraph를 별도 모델로 유지한다.
- L0~L3 위험 등급과 명시적 승인 상태를 사용한다.
- 5노드 랩과 24주 파일럿을 기준으로 MVP를 계획한다.

## 14. 재검토가 필요한 변동 영역

다음 항목은 변화가 빠르므로 각 릴리스 전에 공식 문서를 다시 확인한다.

- OpenAI 모델명, API, Agents SDK, eval 기능
- MCP 명세와 Authorization draft
- LangGraph API와 persistence 의미
- OpenTelemetry GenAI semantic conventions
- Ray와 vLLM 분산 실행 구성
- Web IDE·extension marketplace 라이선스
- NIST·OWASP의 AI/Agent 보안 지침

## 15. 출처 사용 원칙

- 블로그 요약보다 공식 문서·명세·원저자 글을 우선한다.
- 제품 기능의 존재와 SaintVision에 적합하다는 판단을 구분한다.
- 빠르게 바뀌는 문서는 버전과 확인일을 기록한다.
- 실험 상태 명세를 영구 내부 계약으로 직접 노출하지 않는다.
- 출처가 없는 프로젝트 고유 용어는 추론 또는 설계 결정으로 명시한다.
