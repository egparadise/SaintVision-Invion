# Saint Vision INV 개발 플랜

## 계획의 결론

5대 PC 파일럿은 24주, 12개 2주 Sprint로 개발한다. 첫 수직 기능은 **한 Node 등록 → 자원 표시 → 격리된 명령 실행 → 결과와 감사 기록 확인**이다. 이후 다중 Node Scheduler, Dev Workspace, Docker와 Git, GPU 실행, MLOps와 AI CLI를 단계적으로 연결한다.

상세 Sprint 백로그는 [[24주 구현 로드맵과 백로그]], 엔지니어링 성숙도는 [[단계별 개발 계획]], 계약 기준은 [[공통 계약 요구사항과 완료 기준]]을 따른다.

## 1. 전제

- 초기 규모는 같은 LAN에 있는 이기종 Windows와 Linux PC 5대다.
- 기존 OS, 사용자 데이터와 일상 업무를 유지한다.
- 중앙 Control Plane은 1개로 시작하되 데이터와 상태는 백업 가능하게 설계한다.
- Node 간 GPU 병렬 실행은 네트워크와 Framework 지원 여부를 사전 검증한다.
- MVP의 기본 실행 단위는 Container이며, Host Process 실행은 제한된 관리 기능으로 둔다.
- 개발 팀이 작을 경우 Control Plane, Node Runtime, Portal 순으로 책임을 나누고 보안과 검증은 모든 Sprint의 공통 작업으로 운영한다.

## 2. MVP 범위

### 포함

- 사용자, Project, Workspace와 역할 기반 권한
- Node 등록, Heartbeat, Capability와 Resource Snapshot
- CPU, GPU, RAM, Storage와 Network의 논리적 자원 모델
- 자원 Lease와 Placement Plan을 만드는 결정론적 Scheduler V1
- Web Terminal, PowerShell과 Bash
- 프로젝트별 Container Workspace와 Template
- Git clone, branch, diff, commit, pull과 push
- Docker build, run과 compose의 정책 통제 실행
- 단일 GPU 실행과 Ray 또는 PyTorch 기반 분산 Job PoC
- AI CLI Provider Adapter와 사용자별 Credential 연결
- MLflow 기반 Experiment, Artifact와 Model Registry
- L0-L3 명령 위험 등급, Approval, Secret Vault와 Audit
- OpenTelemetry 기반 Trace, Metrics와 Logs

### 제외

- 여러 Node의 일반 RAM을 하나의 투명 메모리로 제공
- 모든 LLM의 자동 Tensor Parallel
- 멀티테넌트 공용 클라우드 수준의 과금과 법적 격리
- 완전한 Kubernetes, Kubeflow와 Service Mesh
- 학습 기반 Scheduler가 결정론적 Scheduler를 대체
- AI Agent의 무감독 인프라 관리자 권한

## 5. Scheduler V1 구현 순서

1. **Hard Filter**  
   Online 상태, OS, Architecture, GPU 종류, 최소 VRAM, CPU, RAM, Storage 접근, Runtime 지원과 정책을 검사한다.

2. **Reservation**  
   낙관적 조회만 하지 않고 TTL이 있는 Resource Lease를 원자적으로 생성한다.

3. **Scoring**  
   데이터 지역성, 예상 전송 시간, 가용 자원, 네트워크, 에너지 또는 비용, Host 사용자 부하와 신뢰도를 점수화한다.

4. **Placement Plan**  
   선택 Node, Resource Slice, 데이터 Mount, 실행 Mode와 대안을 기록한다.

5. **Explain**  
   선택 이유, 제외된 후보와 필요한 Trade-off를 사람이 읽을 수 있게 제공한다.

6. **Reconciliation**  
   Agent의 실제 상태와 원하는 상태를 비교해 재시도, 취소, 격리 또는 복구한다.

## 6. 개발 순서의 수직 기능

~~~mermaid
flowchart LR
    A[Node 등록] --> B[자원 관찰]
    B --> C[Workload 제출]
    C --> D[정책 검사]
    D --> E[자원 Lease]
    E --> F[실행]
    F --> G[로그와 Artifact]
    G --> H[검증]
    H --> I[감사와 Explain]
~~~

각 단계는 독립 서비스의 완성보다 위 흐름을 종단간 연결하는 방향으로 개발한다.

## 8. 시험 전략

- Unit: 점수 함수, 정책 규칙, 상태 전이와 Adapter
- Contract: Control Plane, Node Agent, Tool Gateway와 Provider Adapter
- Integration: PostgreSQL, Object Storage, Container Runtime와 GPU
- End-to-end: Workspace 생성부터 Build, Test, Train과 Deploy
- Failure Injection: Node 단절, Disk 부족, Network 지연, Credential 만료
- Security: Prompt Injection, Path Escape, Secret Exfiltration, 승인 우회
- Performance: 5 Node 동시 Run, 대형 Artifact, GPU Queue와 Dataset Locality

## 9. 주요 위험과 대응

| 위험 | 대응 |
|---|---|
| 이기종 GPU와 Driver 충돌 | Capability Matrix와 호환 Runtime Image |
| 느린 Network에서 분산 GPU 성능 저하 | 사전 Benchmark, 실행 Mode 분리, 데이터 지역성 |
| Host 사용자의 체감 성능 저하 | 제공 한도, Idle 정책, 즉시 선점과 Thermal Guard |
| Container 안의 Docker 권한 상승 | Rootless 또는 격리 Build Service, Socket 직접 노출 금지 |
| AI CLI Credential 노출 | Vault, 단기 Token, 로그 Redaction |
| Scheduler 이중 할당 | Transactional Lease, Fencing Token, Reconciliation |
| 기능 범위 팽창 | 수직 기능과 Gate 중심 Scope 관리 |

## 10. 최종 파일럿 시나리오

1. Medical Vision AI Template으로 Workspace를 만든다.
2. Repository를 clone하고 AI CLI와 함께 DICOM 처리 코드를 수정한다.
3. Unit Test와 Docker Build를 실행한다.
4. Dataset 위치를 고려해 GPU Node에 Evaluation을 배치한다.
5. Metrics와 Artifact를 MLflow Run과 연결한다.
6. 승인된 Model Version을 Container Image로 배포한다.
7. Node 한 대를 중단하고 Run 복구와 Evidence 완전성을 확인한다.
