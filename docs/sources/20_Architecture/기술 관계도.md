# Saint Vision INV 기술 관계도

## 목적

이 문서는 제품 요구사항, 자체 핵심 기술, 외부 기술과 운영 통제의 관계를 보여준다. 외부 Framework는 교체 가능한 Adapter로 사용하고, Saint Vision의 차별 영역인 ResourceGraph, Policy-aware Scheduler, Workspace와 Node 분리, 데이터 지역성과 실행 설명은 자체 계약으로 유지한다.

## 2. 계층 의존성

~~~mermaid
flowchart TB
    EXPERIENCE[Experience Layer]
    WORKSPACE[Workspace and AI Tool Layer]
    CONTROL[INV Control Plane]
    TRUST[Trust Plane]
    ADAPTER[Runtime and Infrastructure Adapters]
    NODE[Node Agent and Data Plane]
    HARDWARE[Existing Hardware]

    EXPERIENCE --> WORKSPACE
    WORKSPACE --> CONTROL
    CONTROL --> ADAPTER
    ADAPTER --> NODE
    NODE --> HARDWARE

    TRUST -. governs .-> EXPERIENCE
    TRUST -. governs .-> WORKSPACE
    TRUST -. governs .-> CONTROL
    TRUST -. governs .-> ADAPTER
    TRUST -. governs .-> NODE
~~~

상위 계층은 하위 계층의 Provider 세부사항을 직접 참조하지 않는다. Workspace가 Docker Socket이나 Node OS API를 직접 호출하지 않고 Tool Gateway와 Runtime Adapter를 거치는 이유가 이 규칙이다.

## 3. 그래프 간 관계

~~~mermaid
graph LR
    KG[KnowledgeGraph]
    RG[ResourceGraph]
    RUN[RunGraph]
    POL[PolicyGraph]
    EVID[EvidenceGraph]

    KG -->|project context| RUN
    RG -->|placement candidates| RUN
    POL -->|allowed transitions| RUN
    RUN -->|resource observations| RG
    RUN -->|produces| EVID
    POL -->|records decisions| EVID
    KG -->|links source and artifact| EVID
    EVID -->|evaluation feedback| KG
~~~

| 그래프 | 질문 | 대표 Node |
|---|---|---|
| ResourceGraph | 어떤 자원을 어디서 쓸 수 있는가 | Cluster, Node, Resource, DataLocation, NetworkLink |
| RunGraph | 어떤 순서와 상태로 실행하는가 | Workload, Run, Task, Approval, Retry |
| KnowledgeGraph | 어떤 Project 지식과 Artifact가 관련되는가 | Requirement, Repository, Commit, Dataset, Model |
| PolicyGraph | 누가 어떤 조건에서 무엇을 할 수 있는가 | Subject, Role, Action, Resource, Rule |
| EvidenceGraph | 무엇을 근거로 결과와 결정을 재현하는가 | Event, Trace, Metric, Log, Artifact, Decision |

## 4. 실행 기술의 관계와 경계

~~~mermaid
graph TD
    INV[INV Scheduler] --> MODE{Execution Mode}
    MODE --> SINGLE[Single Node]
    MODE --> TASK[Task Parallel]
    MODE --> ROUTE[Request Routing]
    MODE --> DP[Data Parallel]
    MODE --> TP[Tensor Parallel]
    MODE --> PP[Pipeline Parallel]

    SINGLE --> DOCKER[Docker containerd]
    TASK --> RAY[Ray]
    ROUTE --> VLLM[vLLM replicas]
    DP --> PT[PyTorch Distributed]
    TP --> NCCL[NCCL or supported collective]
    PP --> VLLM
    PP --> PT

    INV --> POLICY[INV Policy]
    INV --> DATA[Data Locality]
    INV --> LEASE[INV Resource Lease]
    INV --> EXPLAIN[INV Explain]
~~~

Ray, vLLM, PyTorch와 NCCL은 실행 기능을 제공한다. 어느 Framework를 어떤 Node와 정책으로 실행할지는 INV가 결정한다.

## 6. 소유권 Matrix

| 기능 | Saint Vision 자체 | Adapter 또는 외부 기술 | 비고 |
|---|---|---|---|
| Node Offer와 Host 보호 | 소유 | OS별 측정 API | 제품 핵심 |
| ResourceGraph | 소유 | PostgreSQL, Telemetry | Provider 중립 |
| Placement와 Explain | 소유 | Ray, K8s, Slurm Adapter | 제품 핵심 |
| Container 실행 | 정책과 계약 소유 | Docker 또는 containerd | Runtime 교체 가능 |
| 분산 AI 실행 | Mode와 배치 소유 | Ray, PyTorch, vLLM | Framework 기능 활용 |
| Web Terminal | Session과 권한 소유 | xterm.js와 PTY | Node 직접 노출 금지 |
| AI CLI | 공통 Adapter 소유 | Provider CLI | 계정과 License는 사용자 |
| MLOps 계보 | 공통 Metadata 소유 | MLflow 후보 | 후속 교체 가능 |
| Policy와 Audit | 계약과 판정 흐름 소유 | OPA, Vault, OTEL 후보 | 우회 불가 |
| Ontology | Namespace와 의미 소유 | RDF, OWL, JSON-LD | 상호운용 표준 |

## 7. Requirement Traceability

| Requirement | 설계 요소 | 검증 Evidence |
|---|---|---|
| 기존 PC를 계속 사용 | Node Offer Policy, Host Load Guard | 사용자 부하 시험, 선점 기록 |
| 자원을 하나처럼 표시 | ResourceGraph와 Portal Projection | 5 Node Inventory Snapshot |
| GPU 작업 자동 배치 | WorkloadSpec, Scheduler, Lease | PlacementPlan과 Explain |
| 데이터 이동 최소화 | DataLocation과 Transfer Cost | 전송량, 실행 시간 비교 |
| 프로그램 개발 가능 | Dev Workspace, Git, Docker, Terminal | Commit, Build, Test Run |
| 상용 AI CLI 사용 | AI CLI Hub, CredentialRef | Provider 연결과 감사 기록 |
| 안전한 Agent | Tool Gateway, L0-L3, Approval | PolicyDecision과 차단 시험 |
| 학습부터 배포 추적 | Experiment, Artifact, ModelVersion, Deployment | Lineage Query와 Registry |
