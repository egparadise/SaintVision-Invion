# DB 보완 설계

## 이 문서가 메우는 공백

기존 설계는 "PostgreSQL을 source of truth로 쓴다"까지만 정했다. 물리 스키마가 없고, 엔티티 필드 표가 있는 것은 `Node` 하나뿐이다. 가장 위험한 공백은 **Lease 원자성**이다 — "원자적으로 생성", "낙관적 조회만 하지 않고"라는 요구만 있고 구현이 없는데, "중복 부수 효과 0건"이 파일럿 합격 지표다.

## 1. 공통 규약

### ID

기존 설계의 접두사 규약을 따르되, 형식을 확정한다. **ULID + 접두사**를 `text` PK로 쓴다.

```
usr_01JQXW8ZKF3M9NPRT5VYBCDEFG
```

- ULID는 **시간 정렬 가능**하다. UUIDv4와 달리 B-tree 인덱스 삽입이 뒤쪽에 몰려 페이지 분할이 적다
- 접두사가 있으면 로그와 오류 메시지에서 타입을 즉시 알 수 있다
- 접두사: `usr, prj, wsp, nod, wld, run, tsk, lse, plc, dat, art, mdl, dep, pol, apr, evt, ctx, stp, grf, agt, prm, tool`
- **`job_`은 폐기한다** ([[00_보완 설계 종합 요약]] §4 정본표 #4)

### 공통 컬럼

기존 설계의 "공통 ID와 Metadata" 표를 DDL로 고정한다.

```sql
CREATE DOMAIN inv_id AS text
  CHECK (VALUE ~ '^[a-z]{3,4}_[0-9A-HJKMNP-TV-Z]{26}$');

-- 모든 주요 테이블이 갖는 컬럼
--   id             inv_id      PRIMARY KEY
--   tenant_id      uuid        NOT NULL
--   version        integer     NOT NULL DEFAULT 1     -- 낙관적 동시성
--   created_at     timestamptz NOT NULL DEFAULT now()
--   updated_at     timestamptz NOT NULL DEFAULT now()
--   labels         jsonb       NOT NULL DEFAULT '{}'  -- 검색·배치용
--   annotations    jsonb       NOT NULL DEFAULT '{}'  -- 비식별 설명
--   correlation_id uuid
```

`version` 컬럼은 기존 설계의 "optimistic concurrency 또는 version column" 요구에 대응한다. `UPDATE ... WHERE id = ? AND version = ?`로 갱신하고 0행이면 409 `GRAPH-*`를 반환한다.

### 열거형

기존 설계의 자유 문자열 상태를 **PostgreSQL enum**으로 고정한다. 온톨로지 `sv:status`가 `xsd:string`이라 통제 어휘가 없던 문제를 DB 층에서 막는다.

```sql
CREATE TYPE run_state AS ENUM (
  'draft', 'validated', 'planned', 'awaiting_approval', 'scheduled',
  'running', 'verifying', 'recovering', 'succeeded', 'failed', 'cancelled'
);

CREATE TYPE node_status AS ENUM (
  'registering', 'online', 'draining', 'offline', 'quarantined'
);

CREATE TYPE risk_level AS ENUM ('L0', 'L1', 'L2', 'L3');

CREATE TYPE trust_level AS ENUM ('attested', 'managed', 'untrusted');
```

`run_state`는 [[00_보완 설계 종합 요약]] §4 정본표 #1의 11개 상태 그대로다. "임의 문자열을 추가하지 않는다"는 원칙이 enum으로 강제된다.

## 2. 핵심 테이블

`Ontology 설계` §12의 테이블↔클래스 매핑 15행을 출발점으로 하고, 누락분을 채운다.

### 자원 계층

```sql
CREATE TABLE clusters (
  id            inv_id PRIMARY KEY,
  tenant_id     uuid NOT NULL,
  display_name  text NOT NULL,
  version       integer NOT NULL DEFAULT 1,
  created_at    timestamptz NOT NULL DEFAULT now(),
  updated_at    timestamptz NOT NULL DEFAULT now(),
  labels        jsonb NOT NULL DEFAULT '{}',
  annotations   jsonb NOT NULL DEFAULT '{}'
);

CREATE TABLE nodes (
  id                 inv_id PRIMARY KEY,
  tenant_id          uuid NOT NULL,
  cluster_id         inv_id NOT NULL REFERENCES clusters(id),
  hostname           text NOT NULL,          -- 표시용. ID로 사용하지 않는다
  os_family          text NOT NULL,          -- windows | linux
  os_version         text NOT NULL,
  architecture       text NOT NULL,          -- amd64 | arm64
  agent_version      text NOT NULL,
  status             node_status NOT NULL DEFAULT 'registering',
  trust_level        trust_level NOT NULL DEFAULT 'managed',
  provider_policy_id inv_id,
  hardware_fingerprint text NOT NULL,        -- 인증서 복사 탐지용
  cert_serial        text,
  cert_expires_at    timestamptz,
  last_heartbeat_at  timestamptz,
  version            integer NOT NULL DEFAULT 1,
  created_at         timestamptz NOT NULL DEFAULT now(),
  updated_at         timestamptz NOT NULL DEFAULT now(),
  labels             jsonb NOT NULL DEFAULT '{}',
  annotations        jsonb NOT NULL DEFAULT '{}'
);

-- Node 이탈 감지 60초 SLO를 만족하는 조회
CREATE INDEX idx_nodes_heartbeat
  ON nodes (last_heartbeat_at)
  WHERE status IN ('online', 'draining');

CREATE INDEX idx_nodes_schedulable
  ON nodes (cluster_id, status)
  WHERE status = 'online';
```

`Capability`는 "현재 남은 양이 아니라 가능 여부와 호환성"이라는 기존 정의를 따라 별도 테이블로 둔다.

```sql
CREATE TABLE node_capabilities (
  id          inv_id PRIMARY KEY,
  node_id     inv_id NOT NULL REFERENCES nodes(id) ON DELETE CASCADE,
  kind        text NOT NULL,     -- gpu.vendor | container.runtime | shell | cuda | filesystem
  key         text NOT NULL,     -- nvidia | docker | pwsh | 12.4
  attributes  jsonb NOT NULL DEFAULT '{}',
  created_at  timestamptz NOT NULL DEFAULT now(),
  UNIQUE (node_id, kind, key)
);

CREATE TABLE resources (
  id            inv_id PRIMARY KEY,
  node_id       inv_id NOT NULL REFERENCES nodes(id) ON DELETE CASCADE,
  kind          text NOT NULL,   -- cpu | gpu | memory | storage | network
  device_index  integer,         -- GPU Device ID. Placement는 Device 단위
  vendor        text,
  model         text,
  capacity      bigint NOT NULL, -- cores(밀리코어) | bytes | bps
  attributes    jsonb NOT NULL DEFAULT '{}',  -- compute_capability, driver, mig_support, topology
  created_at    timestamptz NOT NULL DEFAULT now(),
  UNIQUE (node_id, kind, device_index)
);

-- Host 소유자가 제공하기로 한 한도
CREATE TABLE resource_offers (
  id            inv_id PRIMARY KEY,
  resource_id   inv_id NOT NULL REFERENCES resources(id) ON DELETE CASCADE,
  offered       bigint NOT NULL,
  policy_id     inv_id,
  effective_from timestamptz NOT NULL DEFAULT now(),
  effective_to   timestamptz,
  status        text NOT NULL DEFAULT 'available',
  created_at    timestamptz NOT NULL DEFAULT now()
);
```

`ResourceSnapshot`은 기존 설계가 "불변 Event로 저장하고 최신 Projection을 별도 유지"하라고 명시했다. 그대로 구현한다.

```sql
-- 불변 이벤트. 월 단위 파티션
CREATE TABLE resource_snapshots (
  id            inv_id NOT NULL,
  node_id       inv_id NOT NULL,
  observed_at   timestamptz NOT NULL,
  measurements  jsonb NOT NULL,   -- {cpu:{used,total}, gpu:[{idx,vram_used,util,temp}], ...}
  host_load     numeric(4,3),     -- 0.000 ~ 1.000
  thermal_c     numeric(5,2),
  power_w       numeric(7,2),
  PRIMARY KEY (id, observed_at)
) PARTITION BY RANGE (observed_at);

CREATE INDEX idx_snapshots_node_time
  ON resource_snapshots (node_id, observed_at DESC);

-- 최신 Projection. Scheduler가 읽는 곳
CREATE TABLE resource_current (
  node_id       inv_id PRIMARY KEY REFERENCES nodes(id) ON DELETE CASCADE,
  observed_at   timestamptz NOT NULL,
  measurements  jsonb NOT NULL,
  host_load     numeric(4,3),
  snapshot_id   inv_id NOT NULL,
  updated_at    timestamptz NOT NULL DEFAULT now()
);
```

Scheduler가 파티션 테이블을 매번 스캔하지 않고 `resource_current` 한 행만 읽게 하는 것이 `스케줄 결정 P95 2초` 달성의 전제다.

### 상태 전이 강제

기존 설계의 "모든 상태 전이가 허용 목록으로 검증됨"(G4)을 DB 층에서도 막는다. 애플리케이션 버그가 있어도 불법 전이가 저장되지 않는다.

```sql
CREATE TABLE run_state_transitions (
  from_state run_state NOT NULL,
  to_state   run_state NOT NULL,
  PRIMARY KEY (from_state, to_state)
);

INSERT INTO run_state_transitions VALUES
  ('draft','validated'), ('validated','planned'),
  ('planned','awaiting_approval'), ('planned','scheduled'),
  ('awaiting_approval','scheduled'), ('awaiting_approval','cancelled'),
  ('scheduled','running'), ('scheduled','cancelled'),
  ('running','verifying'), ('running','recovering'), ('running','failed'), ('running','cancelled'),
  ('recovering','scheduled'), ('recovering','failed'),
  ('verifying','succeeded'), ('verifying','recovering');
-- 어느 상태에서든 timed_out/lost는 failed로 정규화한다

CREATE FUNCTION check_run_transition() RETURNS trigger AS $$
BEGIN
  IF OLD.state IS DISTINCT FROM NEW.state THEN
    IF NOT EXISTS (
      SELECT 1 FROM run_state_transitions
      WHERE from_state = OLD.state AND to_state = NEW.state
    ) THEN
      RAISE EXCEPTION 'GRAPH-0001: 허용되지 않은 전이 % -> %', OLD.state, NEW.state;
    END IF;
  END IF;
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_run_transition
  BEFORE UPDATE ON runs
  FOR EACH ROW EXECUTE FUNCTION check_run_transition();
```

## 3. Lease 원자성 — 최우선 공백

기존 설계는 요구만 있고 구현이 없다. "낙관적 조회만 하지 않고 TTL 있는 Resource Lease를 원자적으로 생성", "하나의 활성 Resource Slice에는 하나의 유효한 Fencing Token만 존재한다", "중복 부수 효과 0건".

### 스키마

```sql
CREATE TABLE resource_leases (
  id             inv_id PRIMARY KEY,
  tenant_id      uuid NOT NULL,
  run_id         inv_id NOT NULL REFERENCES runs(id),
  node_id        inv_id NOT NULL REFERENCES nodes(id),
  resource_id    inv_id NOT NULL REFERENCES resources(id),
  amount         bigint NOT NULL CHECK (amount > 0),
  fencing_token  bigint NOT NULL DEFAULT nextval('lease_fencing_seq'),
  granted_at     timestamptz NOT NULL DEFAULT now(),
  expires_at     timestamptz NOT NULL,
  released_at    timestamptz,
  release_reason text,
  CHECK (expires_at > granted_at)
);

CREATE SEQUENCE lease_fencing_seq;

-- 활성 Lease만 유일성 검사 대상
CREATE UNIQUE INDEX uq_lease_active_run_resource
  ON resource_leases (run_id, resource_id)
  WHERE released_at IS NULL;

CREATE INDEX idx_lease_active_by_resource
  ON resource_leases (resource_id)
  WHERE released_at IS NULL;

CREATE INDEX idx_lease_expiring
  ON resource_leases (expires_at)
  WHERE released_at IS NULL;
```

**`fencing_token`이 전역 단조 증가 시퀀스**인 것이 핵심이다. Node Agent는 자신이 아는 토큰보다 작은 토큰을 가진 명령을 거부한다. 이것이 "이전 실행의 늦은 명령 차단"의 구현이다.

### 원자적 예약

경합 상황에서 초과 예약을 막는 방법이다. 조건부 INSERT 한 문장으로 처리한다 — 읽고 나서 쓰는 사이의 틈을 없앤다.

```sql
INSERT INTO resource_leases (id, tenant_id, run_id, node_id, resource_id, amount, expires_at)
SELECT
    $1, $2, $3, r.node_id, r.id, $4::bigint, now() + $5::interval
FROM resources r
JOIN resource_offers o ON o.resource_id = r.id
                      AND o.status = 'available'
                      AND o.effective_from <= now()
                      AND (o.effective_to IS NULL OR o.effective_to > now())
JOIN nodes n ON n.id = r.node_id AND n.status = 'online'
WHERE r.id = $6
  AND o.offered - COALESCE((
        SELECT SUM(l.amount)
        FROM resource_leases l
        WHERE l.resource_id = r.id
          AND l.released_at IS NULL
          AND l.expires_at > now()
      ), 0) >= $4::bigint
RETURNING id, fencing_token, expires_at;
```

0행이 반환되면 예약 실패다 — `RES-*` 오류로 다음 후보 Node를 시도한다.

이 문장은 기존 설계의 예약 가능량 공식 **"Offer에서 활성 Lease를 뺀 값"** 을 그대로 SQL로 옮긴 것이다. `n.status = 'online'` 조인이 불변 조건 "Node가 offline 또는 quarantined면 새 Lease를 발급하지 않는다"를 강제한다.

### 동시성 수준

| 작업 | 격리 수준 | 이유 |
|---|---|---|
| 일반 조회 | `READ COMMITTED` | 기본값 |
| Lease 예약 | `READ COMMITTED` + 위 조건부 INSERT | 단일 문장이라 원자적. `SERIALIZABLE`은 불필요한 재시도를 유발 |
| Gang Scheduling (다중 자원 동시 확보) | 트랜잭션 + `SELECT ... FOR UPDATE`를 **`resource_id` 오름차순**으로 | 데드락 방지 — 락 획득 순서를 고정한다 |

Gang Scheduling에서 일부만 확보되면 트랜잭션 전체를 롤백한다. 부분 확보 상태로 대기하면 기아(starvation)가 발생한다.

### 만료 회수와 Orphan Reconciliation

```sql
-- 만료 Lease 회수 (워커가 10초마다)
UPDATE resource_leases
SET released_at = now(), release_reason = 'expired'
WHERE released_at IS NULL AND expires_at <= now()
RETURNING id, run_id, node_id, fencing_token;

-- Heartbeat 유실 Node의 Lease 회수 (60초 SLO)
UPDATE resource_leases l
SET released_at = now(), release_reason = 'node_lost'
FROM nodes n
WHERE l.node_id = n.id
  AND l.released_at IS NULL
  AND n.last_heartbeat_at < now() - interval '60 seconds';
```

회수 시 해당 Run은 `recovering`으로 전이하고, 재스케줄 시 **새 fencing token**을 발급받는다. 이전 토큰을 든 늦은 명령은 Node Agent가 거부한다.

## 4. RunRecord — 신규 정의

기존 설계에서 `RunRecord`는 2·4단계의 핵심 저장소로 반복 참조되지만 공통 계약 8종 목록에 없다. 여기서 정의한다.

역할: **한 Run에서 사용된 모든 구성 요소의 불변 버전 조합을 보존**한다. "실행 기록은 사용된 모든 버전의 조합을 보존한다", "`latest` 같은 움직이는 값만 저장하지 않는다"는 기존 원칙의 구현체다.

```sql
CREATE TABLE run_records (
  run_id              inv_id PRIMARY KEY REFERENCES runs(id),
  tenant_id           uuid NOT NULL,
  -- 6단계 각 계층의 불변 버전
  prompt_id           inv_id,
  prompt_version      text,
  context_bundle_id   inv_id,
  context_bundle_hash text,          -- ContextBundle은 생성 후 불변
  tool_manifest_hash  text,
  graph_id            inv_id,
  graph_version       text,
  policy_bundle_version text NOT NULL,
  agent_profile_id    inv_id,
  -- 모델 호출
  model_name          text,
  model_version       text,
  reasoning_config    jsonb,
  -- Scheduler 재현
  snapshot_id         inv_id,
  scheduler_weights_version text,
  -- 집계
  token_input         bigint,
  token_output        bigint,
  cost_amount         numeric(12,2),
  cost_currency       text DEFAULT 'KRW',
  created_at          timestamptz NOT NULL DEFAULT now()
);
```

이 테이블이 있으면 "모델·공급자 변경 시 같은 평가 세트로 비교 가능"(G6)과 "실패 실행을 trace와 로그만으로 재현 가능"(G3)이 성립한다. 없으면 어떤 프롬프트·컨텍스트·정책 조합에서 실패했는지 사후에 알 수 없다.

## 5. Evidence Store

`Evidence 기록 성공률 99.99%`와 "Run을 재구성할 Evidence 누락"이 릴리스 차단 조건이다. 물리 설계를 정한다.

```sql
CREATE TABLE evidence_envelopes (
  id            inv_id NOT NULL,
  tenant_id     uuid NOT NULL,
  trace_id      uuid NOT NULL,
  run_id        inv_id NOT NULL,
  step_id       inv_id,
  tool_call_id  inv_id,
  timestamp     timestamptz NOT NULL,
  actor_type    text NOT NULL,        -- user | agent | service | node
  actor_id      inv_id NOT NULL,
  action        text NOT NULL,        -- test.run 등
  policy_id     inv_id,
  policy_effect text,                 -- allow | deny
  approval_id   inv_id,
  input_schema  text,
  input_sha256  char(64),
  output_schema text,
  output_artifact_ref inv_id,
  result        text NOT NULL,        -- succeeded | failed | denied
  telemetry     jsonb NOT NULL DEFAULT '{}',
  PRIMARY KEY (id, timestamp)
) PARTITION BY RANGE (timestamp);

CREATE INDEX idx_evidence_run ON evidence_envelopes (run_id, timestamp);
CREATE INDEX idx_evidence_trace ON evidence_envelopes (trace_id);
CREATE INDEX idx_evidence_actor ON evidence_envelopes (actor_id, timestamp DESC);
```

### 불변성 (WORM 근사)

PostgreSQL에는 진짜 WORM이 없다. 다층으로 근사한다.

```sql
-- 1. 애플리케이션 롤에서 UPDATE/DELETE 권한 제거
REVOKE UPDATE, DELETE ON evidence_envelopes FROM inv_app;
GRANT INSERT, SELECT ON evidence_envelopes TO inv_app;

-- 2. 트리거로 이중 차단 (슈퍼유저 실수 방지)
CREATE FUNCTION deny_evidence_mutation() RETURNS trigger AS $$
BEGIN
  RAISE EXCEPTION 'SEC-0010: Evidence는 변경·삭제할 수 없습니다';
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_evidence_immutable
  BEFORE UPDATE OR DELETE ON evidence_envelopes
  FOR EACH ROW EXECUTE FUNCTION deny_evidence_mutation();
```

파티션 삭제(보존 기간 만료)는 별도 관리 롤로만 수행한다.

### 쓰기 경로 — 99.99% 달성

기존 설계의 실패 매트릭스가 "Evidence 저장 실패 → **완료 상태 보류**"를 명시한다. 구현:

1. Evidence INSERT와 Run 상태 전이를 **같은 트랜잭션**에 둔다
2. `synchronous_commit = on` (이 트랜잭션 한정). Evidence는 유실을 허용하지 않는다
3. INSERT 실패 시 Run은 `verifying`에 머무르고 `succeeded`로 가지 않는다 — 불변 조건 "succeeded Run은 최소 하나의 Evidence Envelope을 가진다"가 지켜진다
4. 재시도는 outbox와 별개로 즉시 3회, 실패 시 심각 알람

### 보존 기간

기존 설계에 수치가 없다. 제안값:

| 데이터 | 보존 | 근거 |
|---|---|---|
| `evidence_envelopes` | **1년** | 감사·사고 조사. 릴리스 게이트가 "Run 재구성"을 요구 |
| `audit_events` | **1년** | 동상 |
| `resource_snapshots` | **90일** | 용량 계획과 사후 분석. 그 이상은 집계본으로 |
| Run 로그 본문 (Object Storage) | **90일** | |
| `run_records` | **영구** | 크기가 작고 모델 비교의 기준선 |

파티션 관리는 `pg_partman` 또는 Alembic에 포함한 월간 잡으로 자동화한다.

> 의료 데이터가 관여하는 경우 보존 기간이 법정 요건에 종속될 수 있다. [[00_보완 설계 종합 요약]] §8에 따라 이 문서는 규제 판단을 하지 않는다.

## 6. 정책·승인

```sql
CREATE TABLE policy_decisions (
  id             inv_id PRIMARY KEY,
  tenant_id      uuid NOT NULL,
  run_id         inv_id REFERENCES runs(id),
  tool_call_id   inv_id,
  policy_id      inv_id NOT NULL,
  policy_version text NOT NULL,
  effect         text NOT NULL CHECK (effect IN ('allow','deny','require_approval')),
  risk_level     risk_level NOT NULL,     -- 정책 엔진이 재계산한 값
  proposed_risk_level risk_level,         -- 모델이 제안한 값. 신뢰하지 않음
  reason         text NOT NULL,
  expires_at     timestamptz,
  decided_at     timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE approvals (
  id              inv_id PRIMARY KEY,
  tenant_id       uuid NOT NULL,
  policy_decision_id inv_id NOT NULL REFERENCES policy_decisions(id),
  run_id          inv_id NOT NULL REFERENCES runs(id),
  required_count  smallint NOT NULL DEFAULT 1,   -- two-person rule이면 2
  status          text NOT NULL DEFAULT 'pending',
  nonce           uuid NOT NULL DEFAULT gen_random_uuid(),
  expires_at      timestamptz NOT NULL,
  created_at      timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE approval_decisions (
  id           inv_id PRIMARY KEY,
  approval_id  inv_id NOT NULL REFERENCES approvals(id),
  approver_id  inv_id NOT NULL REFERENCES users(id),
  effect       text NOT NULL CHECK (effect IN ('approve','reject')),
  reason       text,
  decided_at   timestamptz NOT NULL DEFAULT now(),
  -- two-person rule: 같은 사람이 두 번 승인할 수 없다
  UNIQUE (approval_id, approver_id)
);
```

`UNIQUE (approval_id, approver_id)` 한 줄이 two-person rule의 핵심 방어선이다. UI 검증은 우회될 수 있다.

부분 인덱스가 중요하다. 발행 완료된 행이 쌓여도 폴링 쿼리는 미발행분만 스캔한다.

발행 워커는 `SELECT ... FOR UPDATE SKIP LOCKED`로 여러 인스턴스가 동시에 돌아도 중복 발행하지 않게 한다.

## 8. 컨텍스트와 벡터 검색

기존 설계에서 임베딩 검색은 `단계별 개발 계획` §C4의 **한 줄**이 전부다 — "MVP는 lexical search와 metadata filter를 먼저 사용한다. 문서가 늘어나면 embedding 검색과 reranker를 추가한다." 의도만 있고 **제품·스키마·인덱스가 없다.** AI Operator와 ContextBundle이 제품의 축인데 검색 저장소가 설계되지 않았다.

### 결정: pgvector

별도 벡터 DB(Qdrant, Milvus 등)를 도입하지 않는다.

- 사내 `SaintviewPACSai`가 이미 `pgvector`를 쓰고 있다 — 운영 경험과 배포 절차가 있다
- 5노드 랩에 인프라를 하나 더 얹지 않는다. 기존 설계의 "초기에는 불필요한 중복 도입 금지" 원칙에 맞다
- ContextBundle 검색은 **권한 필터가 필수**다(`authorize → retrieve → filter → …`). 별도 벡터 DB를 쓰면 권한 정보를 두 곳에 복제해야 하고, 그것이 곧 유출 경로가 된다. 같은 DB 안에 있으면 SQL 조인 한 번으로 끝난다

```sql
CREATE EXTENSION IF NOT EXISTS vector;

CREATE TABLE context_items (
  id             inv_id PRIMARY KEY,
  tenant_id      uuid NOT NULL,
  project_id     inv_id REFERENCES projects(id),
  source_id      text NOT NULL,          -- Context Source Registry의 source ID
  authority      text NOT NULL,          -- 권위 수준
  data_class     text NOT NULL,          -- public | internal | confidential | restricted
  provenance_uri text NOT NULL,
  content        text NOT NULL,
  content_tsv    tsvector GENERATED ALWAYS AS (to_tsvector('simple', content)) STORED,
  embedding      vector(1024),           -- 2단계에서 채움. 초기엔 NULL 허용
  token_cost     integer NOT NULL,
  trust_level    text NOT NULL,          -- 외부 문서는 낮은 신뢰
  valid_until    timestamptz,            -- TTL. 만료 자원 정보로 결정 금지
  created_at     timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX idx_ctx_fts ON context_items USING GIN (content_tsv);
CREATE INDEX idx_ctx_scope ON context_items (tenant_id, project_id, data_class);
CREATE INDEX idx_ctx_ttl ON context_items (valid_until) WHERE valid_until IS NOT NULL;

-- 2단계에서 생성
-- CREATE INDEX idx_ctx_vec ON context_items
--   USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
```

### 단계적 도입

기존 설계의 "MVP는 lexical search + metadata filter 우선, 문서가 늘어나면 embedding 검색과 reranker를 추가한다"를 그대로 따른다.

- **1단계 (MVP)**: `content_tsv` 전문 검색 + `data_class`·`project_id`·`valid_until` 필터만. `embedding` 컬럼은 NULL로 둔다
- **2단계**: 임베딩 채우고 HNSW 인덱스 생성. 하이브리드 검색(RRF로 BM25와 벡터 순위 융합)
- **3단계**: reranker

컬럼을 처음부터 만들어 두는 이유는 나중에 대형 테이블에 컬럼을 추가하는 비용을 피하기 위해서다. 인덱스는 데이터가 쌓인 뒤 생성한다.

### ContextBundle 불변성

기존 설계가 "ContextBundle은 생성 시점 이후 불변이며 hash와 구성 목록을 RunRecord에 남긴다"고 요구한다.

```sql
CREATE TABLE context_bundles (
  id            inv_id PRIMARY KEY,
  tenant_id     uuid NOT NULL,
  run_id        inv_id REFERENCES runs(id),
  content_hash  char(64) NOT NULL,       -- 재현 검증용
  item_ids      inv_id[] NOT NULL,
  total_tokens  integer NOT NULL,
  assembled_at  timestamptz NOT NULL DEFAULT now(),
  redaction_applied boolean NOT NULL DEFAULT false
);
```

## 9. 멀티테넌시

`tenant_id`는 "배포 단위가 단일 조직이어도 예약"이라고만 되어 있다. **Row Level Security를 처음부터 켠다.**

```sql
ALTER TABLE runs ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON runs
  USING (tenant_id = current_setting('inv.tenant_id')::uuid);
```

애플리케이션은 커넥션 획득 시 `SET LOCAL inv.tenant_id = ...`를 실행한다. MVP가 단일 테넌트여도 RLS를 켜는 이유는, 나중에 켜려면 모든 쿼리를 재검증해야 하기 때문이다. 처음부터 켜면 테넌트 누락 버그가 즉시 드러난다.

## 10. 마이그레이션

**Alembic**을 쓴다. 사내 `SaintviewPACSai/backend/migrations`와 동일한 도구다.

### 규약

- 파일명: `{revision}_{동사}_{대상}.py` (예: `a1b2c3_add_lease_fencing_token.py`)
- **`downgrade()`를 비워두지 않는다.** 롤백 불가 마이그레이션은 리뷰에서 거부한다
- 데이터 마이그레이션과 스키마 마이그레이션을 분리한다
- 대형 테이블 인덱스는 `CREATE INDEX CONCURRENTLY` (별도 리비전, 트랜잭션 밖)
- 컬럼 삭제는 2단계: (1) 애플리케이션이 안 쓰게 배포 → (2) 다음 릴리스에서 DROP

### 스키마 변경 PR 체크리스트

기존 설계가 "스키마 변경 PR에는 마이그레이션, 호환성 테스트, 롤백 계획 포함"을 요구한다.

- [ ] `upgrade()`와 `downgrade()` 모두 작성, 로컬에서 왕복 검증
- [ ] 계약 JSON Schema 변경 시 하위 호환 검사 통과 (필드 삭제·타입 변경 없음)
- [ ] 새 컬럼은 `NOT NULL DEFAULT` 또는 nullable — 기존 행이 있는 테이블에 `NOT NULL` 무기본값 금지
- [ ] 인덱스 추가 시 예상 크기와 쓰기 영향 기록
- [ ] Ontology 클래스 매핑 영향 확인 (`Ontology 설계` §12)
- [ ] Release Manifest에 DB 스키마 버전 + 계약 버전 + Ontology 버전을 함께 기록

## 11. 성능과 운영

### 연결 풀

`P95 읽기 API 300ms` 목표. 5노드 랩 기준:

- PostgreSQL `max_connections = 200`
- 애플리케이션 풀 크기 = `(코어 수 × 2) + 유효 스핀들` → 8코어 서버 기준 **20**
- SSE 연결은 DB 커넥션을 붙잡지 않는다 — 이벤트는 NATS에서 오고, DB는 초기 상태 조회에만 쓴다. 이 분리가 없으면 동시 접속자 수만큼 커넥션이 고갈된다

### 백업과 복구

기존 설계는 "백업 가능하게 설계한다" 한 줄이다. 수치를 제안한다.

| 항목 | 목표 |
|---|---|
| RPO | **15분** (WAL 아카이빙) |
| RTO | **1시간** |
| 전체 백업 | 일 1회 (`pg_basebackup`) |
| WAL 아카이브 | 지속 (MinIO 별도 버킷) |
| 복원 훈련 | **분기 1회** — 기존 설계의 "분기 복구 훈련"에 대응 |
| 백업 검증 | 매주 자동 복원 후 스모크 쿼리 |

### 가용성 — 명시적 간극

기존 설계는 "중앙 Control Plane 1개로 시작"과 "**Control Plane 월 가용성 99.5%**"를 동시에 적고 있다. 이 둘은 그대로는 양립하지 않는다.

99.5%/월 = **월 3.6시간** 다운타임 허용. 단일 인스턴스에서 이 예산에 들어가는 것:

- 계획 재시작(배포, OS 패치): 월 4회 × 5분 = 20분
- PostgreSQL 마이너 업그레이드: 분기 1회 × 15분 = 월 5분
- **예산 잔여: 약 3시간 15분** — 계획되지 않은 장애 전부가 여기에 들어가야 한다

즉 **1시간짜리 장애 3번이면 SLO 위반**이다. 판단:

- 파일럿(5노드, 단일 팀)에서는 단일 인스턴스로 시작하되, **RTO 1시간을 실제로 달성할 수 있는지 복원 훈련으로 검증**한다. 검증 없이 99.5%를 주장하지 않는다
- 20노드 이상 또는 다중 팀으로 확장하면 그때 HA(Patroni + 동기 복제)를 도입한다. 기존 설계의 "확장 시 재검토할 결정"에 이미 "event bus와 control plane 고가용성"이 들어 있다
- 파일럿 보고 시 목표값과 실제값을 함께 보고한다
